# Capability × surface matrix

**Purpose: to stop a lag being read as a defect.**

This repo builds one capability across four surfaces, and they are deliberately not in lockstep. A
reviewer who does not know that correctly reports every gap between them as a fault. This file is
the declaration of which gaps are the plan.

Generated by hand on 2026-08-19 from the tree, not from a doc. **Re-derive it, do not trust it** —
the commands under each surface are how.

## The four surfaces

| Surface | What it is | How it runs | Why it exists |
| :-- | :-- | :-- | :-- |
| **Contract** | `contracts/CarbonEscrow.sol`, `ReputationStake.sol` | deployed to Base Sepolia | the only one-way door; everything else is rewritable |
| **Scripts** | `scripts/admin/`, `scripts/audit/`, `scripts/deploy/` | `tsx` / `hardhat` from a laptop or CI, keys from `.env.local` or KMS | proves the bytecode against a real chain before any product exists |
| **App** | `src/app/api/*`, `src/app/dashboard`, `src/lib/*` | Next.js on Vercel | what a human uses |
| **MCP** | `src/lib/mcp/server.ts` via `/api/basedhuman.mcp` | HTTP, agent-driven | what an agent uses |

**MCP is not a privileged layer.** It is a third client of the same contract functions the scripts
already call. Once a capability exists in the app's service layer, the MCP tool exposing it is a
thin wrapper. Nothing in the money path depends on MCP existing.

## Stage vocabulary

| Marker | Meaning |
| :-- | :-- |
| `live` | exists and has been exercised against the deployed contract |
| `built` | exists, not yet exercised end to end |
| `broken: CC-###` | exists and cannot succeed — a real defect, ticketed |
| `next: CC-###` | intended, ticketed, and the next rung of the ladder |
| `deferred: CC-###` | intended, ticketed, deliberately later |
| `v2` | designed, not scheduled |
| `—` | not applicable to this surface by design |

**The Contract column means the source tree, not the chain.** They are usually the same and are not
right now: the arbitration clock is `built` in `CarbonEscrow.sol` and absent from the live Sepolia
deployment until `CC-034` redeploys. Where the two differ the row says so. `chain-constants.json` is
the record of what is actually deployed.

## The build ladder, and where we are

Standard sequencing for an on-chain product. Each rung is cheaper to get wrong than the one below it
is to fix.

1. **Contract, unit-tested locally** — `npm run test:contracts`. Instant, free, no chain. ✅
2. **Scripts against the deployed testnet contract** — `verify-escrow-lifecycle.ts`. Proves the
   bytecode does what the ADR says against a real chain. ✅ (submit, verdict, claim all PASS;
   dispute phase outstanding)
3. **App write paths** — the server and UI learn to do what the scripts do. ← **we are here**
   (`CC-084` → `CC-083` → `CC-092`)
4. **Client surfaces** — dashboard for humans, MCP for agents (`CC-044` rewritten against v2)
5. **End to end through the product, no scripts in the path** — `CC-077`/`078`/`079`
6. **Mainnet with the operator's own funds** — `CC-034`/`CC-039`

**Rung 2 passing is not rung 5 passing, and that distinction is the whole point of this file.**
`Lessons-Learned.md` §23 is the same lesson from the other direction: a passing test suite that
exercises the wrong layer buys nothing.

## How to review this repo without generating false findings

Three buckets. Anything that does not land in one of them is an opinion, not a finding.

1. **Published and wrong** — a public claim contradicts reality *today*. Real defect. File it.
2. **One-way door** — contract bytecode, mainnet cutover, key custody, licence, legal
   classification. Expensive or impossible to reverse. Worth raising even when the work is distant.
3. **Not built yet** — a `next`/`deferred`/`v2` cell above. This is the plan. Not a finding.
