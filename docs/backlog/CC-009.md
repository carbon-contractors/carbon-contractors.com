# CC-009 — Waitlist emails written to Vercel logs in cleartext

## Problem
`src/app/api/waitlist/route.ts:29` logs the signup event including the email address.
`maskMeta` in `src/lib/logging.ts:22-33` only masks `0x…` wallet addresses, so emails pass
straight through into the Vercel log stream.

Every waitlist signup therefore exists as plaintext PII in logs, with a different retention
and access model to the database — and it contradicts the "Zero PII" claim in the README.

## Fix
Add an email branch to `maskMeta` (e.g. `a***n@domain.com`) or log a SHA-256 hash. Sweep the
other routes for the same pattern while you are in there.

## Update 2026-08-11 — backlog triage pass

Reviewed in the triage pass — **stays P1** — but re-verification found the defect has
**doubled** since filing, and how it doubled is the interesting part.

There are now **two** cleartext-email log sites, not one:

- `src/app/api/waitlist/route.ts:27` — `log("info", "waitlist_signup", { email })` (the original)
- `src/app/api/waitlist/route.ts:66` — `log("info", "waitlist_unsubscribed", { email })` (new)

The second was introduced by **`CC-067`** (self-serve waitlist unsubscribe), which is closed. So
closing one issue re-introduced the exact defect a different open issue already described, in the
same file, roughly forty lines apart.

`maskMeta` (`src/lib/logging.ts`) confirmed unchanged: it masks only values matching
`/^0x[0-9a-fA-F]{40}$/`, recurses into nested objects, and passes everything else through
verbatim. Emails are untouched.

Fix both sites, then sweep the other routes as this issue already says.

**This has earned a `docs/Lessons-Learned.md` entry** — the transferable point being that an open
issue describing a defect class is not a defence against re-introducing it, because nobody re-reads
open issues against new code. Written up as part of the triage pass.

## Update 2026-08-13 — scope extends to task payload, per `ADR-0002` D9

This issue's own fix already says to *"sweep the other routes for the same pattern"*. `ADR-0002` D9
makes that sweep load-bearing rather than tidy, and names it as **the most commonly missed trap** in
a deletion claim:

> If task descriptions, evidence URLs or spec contents reach log lines, deleting the row achieves
> nothing.

So the sweep must specifically confirm that **no task description, acceptance spec content, or
evidence URL reaches a log line**, and redact at source where it would. Without that, `CC-087`'s
retention job and the `ADR-0002` D2 published claim are both false regardless of what the database
holds.

The waitlist half of this issue becomes moot when `CC-089` drops the table — but the two log sites
should still be fixed now rather than waiting, since `maskMeta` needs the email branch either way
for `notification_channels`.

Priority stays **P1**.

Related: `ADR-0002` D9, `CC-087`, `CC-089`, `CC-067`.
