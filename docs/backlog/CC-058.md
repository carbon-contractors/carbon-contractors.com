# CC-058 — Supabase tier decision — a paused database during promotion kills the launch

## Problem
The project is on the Supabase free tier, which pauses after a period of inactivity. Aaron
confirmed it **did** pause during the hiatus, and that the keepalive cron did not prevent it —
GitHub Actions ran on schedule, the project slept anyway. The cron is being removed in CC-006 and
migration 013 rather than debugged, because it was solving the wrong problem.

This is a launch blocker, not housekeeping. The failure mode is specific and bad:

- A promotion push sends first-time visitors to the site.
- If the project is asleep, `/api/waitlist` and `/api/register` return 500s. The site does not
  degrade, it breaks.
- Those visitors do not come back. First impressions from a promotion push are the whole return on
  the promotion.
- The audience is non-crypto workers being asked to trust an escrow platform with their labour.
  "It was broken when I tried it" is unrecoverable for exactly that audience.

Pre-launch traffic is by definition sporadic, which is precisely the pattern that triggers pausing.

## Second argument: backups
The free tier has no automated backups. The database holds real waitlist email addresses and, after
launch, worker registrations. `humans` is the registry the entire marketplace depends on. There is
currently no recovery path from an accidental `DROP` or a bad migration — and note that migrations
are applied by hand through the SQL editor (CC-057), which is exactly the workflow where that
happens.

Paid tiers include automated daily backups and point-in-time recovery.

## Options
**(a) Pay for Pro — recommended.** Removes pausing entirely, adds daily backups and PITR. At
roughly US$25/month it is the cheapest insurance available against a broken launch, and it is
trivially justified the moment there are real signups to lose. Verify current pricing and included
features before committing.

**(b) Stay free until there is traffic.** Viable only if launch is deliberately soft — no promotion
push, a handful of hand-held signups, close monitoring. Do not combine free tier with any coordinated
promotion.

**(c) Self-host Postgres.** Removes the constraint and adds an operations burden that is squarely
not the point of this project right now. Note CC-048 already contemplates a Z220 for a Sepolia node;
do not conflate the two.

## Do
1. Confirm current Supabase pricing and what pausing/backup behaviour each tier actually has.
2. Decide before the coming-soon gate comes off, not after.
3. If staying free, add external uptime monitoring against `/api/health` (CC-040) so a pause is
   noticed within minutes rather than by a user.
4. Either way, make sure `/api/waitlist` and `/api/register` fail with something human-readable
   rather than a raw 500 — a paused database should not look like a broken product.

## Acceptance
A recorded decision, and if staying free, monitoring that catches a pause before a visitor does.
