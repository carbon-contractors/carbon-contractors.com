# CC-003 — CSP blocks Coinbase wallet RPC and passkey endpoints in production

## Problem
`next.config.ts:37` restricts `connect-src` to `'self' *.supabase.co sepolia.base.org mainnet.base.org`.

OnchainKit's default wagmi transport talks to
`https://api.developer.coinbase.com/rpc/v1/base-sepolia/<apiKey>`, and the `Name`/`Avatar`
identity components resolve through the same host. The passkey flow runs in an iframe from
`https://keys.coinbase.com`, and `frame-src` is not declared so it falls back to
`default-src 'self'`.

All of that is blocked in production. Wallet connect will fail on the live site even though
it works locally, because local dev has a different CSP path.

## Fix
Add to `connect-src`: `https://api.developer.coinbase.com https://keys.coinbase.com https://*.coinbase.com`.
Add an explicit `frame-src https://keys.coinbase.com`.
Then verify with the browser console open on the deployed site, not just locally.

## Acceptance
Zero CSP violations in the console during a full connect → sign → register cycle on production.

## Update 2026-07-25 — confirmed, and worse than described

Read the actual header. `next.config.ts` emits:

```
default-src 'self'
connect-src 'self' https://*.supabase.co https://sepolia.base.org https://mainnet.base.org wss://*.supabase.co
frame-ancestors 'none'
```

There is **no `frame-src` directive at all**, so the `keys.coinbase.com` passkey iframe falls back
to `default-src 'self'` and is blocked outright. And `connect-src` has no
`api.developer.coinbase.com`, which is where OnchainKit's default transport and the `Name`/`Avatar`
identity components send their requests.

### Why this was never noticed
All testing used the Coinbase Wallet **browser extension** (see CC-055). The extension handles
signing in its own popup and proxies RPC through its own background context, so neither the
blocked iframe nor the blocked RPC host is ever touched. The defect is invisible to the person
testing and total for everyone else.

### Also check — Permissions-Policy
`next.config.ts` sets `Permissions-Policy: camera=(), microphone=(), geolocation=()`. WebAuthn in a
**cross-origin iframe** additionally requires `publickey-credentials-get` to be delegated to that
origin. OnchainKit should set the `allow` attribute on the iframe itself, but page-level policy can
still interfere. If the passkey dialog opens and then fails silently after the CSP fix, this is the
next thing to look at.

### Verification
Not "it works locally." Test on the deployed site, in a profile with **no Coinbase extension
installed**, console open, zero CSP violations through a full connect → sign → register cycle.

## Update 2026-08-01 — CC-043 landed, the fix is narrower than originally scoped

`src/lib/wallet/providers.tsx` now uses an explicit `createConfig` with `http()` transport and no
argument — that resolves to the chain's default RPC (`https://sepolia.base.org` /
`https://mainnet.base.org`), both **already** in `connect-src`. OnchainKit and its
`api.developer.coinbase.com` identity/RPC host are gone (`NavBar.tsx` no longer renders
`Name`/`Avatar`, just a truncated address), so that host is no longer needed at all — do not add it.

Still needed, unchanged: the `baseAccount` connector (kept explicitly, see CC-055 update) still runs
its passkey flow through the same `@base-org/account` SDK, which is hardcoded to
`https://keys.coinbase.com` for the signing iframe. A read of the SDK bundle also turned up
`rpc.wallet.coinbase.com`, `cca-lite.coinbase.com` and `as.coinbase.com` as hosts it can call during
account creation/sign-in — **unconfirmed which of these actually fire**, only that they exist in the
bundle. So the fix is now:

- Add `frame-src https://keys.coinbase.com`.
- Leave `connect-src` as-is (`sepolia.base.org`/`mainnet.base.org` already present) and add
  Coinbase hosts only as the console proves they're hit — start the deployed-site verification
  pass with nothing added beyond `frame-src`, and widen `connect-src` from actual violations, not
  from reading the SDK.

This replaces the original `Fix` section's `https://api.developer.coinbase.com https://*.coinbase.com`
addition to `connect-src` — that was written against the OnchainKit transport, which no longer runs.

## Update 2026-08-08 — fixed and verified end-to-end on a real Vercel preview

Added `frame-src https://keys.coinbase.com` and, once the console actually proved it, `font-src
'self' data:` and `https://cca-lite.coinbase.com` on `connect-src` — done via exactly the
evidence-based process this issue asked for, not by reading the SDK bundle further:

1. **Local, clean-profile pass first** (no wallet extension — the actual test condition this issue
   and `CC-055` require). Loading `/connect` and clicking through to the `Base Account` connector
   produced two concrete violations: `cca-lite.coinbase.com` (`/amp` and `/metrics`, the SDK's own
   telemetry beacon, firing on page load *and* on connect) blocked on `connect-src`, and a `data:`
   URI font blocked on `default-src` because `font-src` had never been declared at all — a gap
   this issue hadn't previously identified. Fixed both; a fresh tab afterward showed zero
   violations through page load and connector selection. Local testing stopped there: the SDK
   opens a real browser popup for the actual passkey step, and the sandboxed browser tool used for
   local verification blocks popups — a permission wall, not a CSP violation.

2. **Real Vercel preview, by Aaron, on a real browser** — the step local tooling couldn't reach.
   Preview deployments sit behind Vercel's own SSO, and `/connect` was unreachable through it
   because `middleware.ts` redirects every non-API route to `/` whenever `NEXT_PUBLIC_COMING_SOON`
   isn't `"false"`, which every preview inherits from the Preview environment same as production.
   With Aaron's explicit go-ahead, set `NEXT_PUBLIC_COMING_SOON=false` scoped to the **Preview**
   environment only (Production untouched) — previews are already access-controlled by Vercel
   login, so this doesn't expose anything new, and it's a standing change so future preview reviews
   don't hit the same wall. Documented here rather than left as a silent env change.

3. **Aaron ran the actual flow** on the redeployed preview: `/connect` → `Connect Wallet` →
   `Base Account` → received a real Coinbase "login code for Base" email — a genuine passkey/Smart
   Wallet authentication round-trip, further than this session's own sandboxed browser could reach.
   Two more real violations surfaced along the way, both Vercel's own preview-only review-feedback
   toolbar (`vercel.live`), unrelated to the wallet flow: blocked on `script-src`, then (after that
   fix) blocked on `frame-src` too. Both fixed, scoped to `VERCEL_ENV !== "production"` so
   production's CSP is never widened for a script that never loads there. Confirmed clean on
   Aaron's own follow-up check: **zero console errors** through the full connect → passkey
   login-code flow.

**Not fully proven**: this was a desktop browser test, and the login-code step was not carried
through to a completed registration. `CC-055`'s own acceptance criterion (a wallet created by
passkey *on a phone*, landing in `humans`, rendering on `/dashboard`) is still open — this issue's
fix removed the CSP blocker that was `CC-055`'s step-1 prerequisite, but does not itself satisfy
`CC-055`. See that issue for what's still outstanding.

`npm test` (111/111), `npm run typecheck`, `npm run lint`, `npm run build` all clean throughout.
PR: `claude/cc-003-csp-wallet-hosts` (three commits: `frame-src`/`font-src`/`cca-lite.coinbase.com`,
then two `vercel.live` follow-ups found live on the preview itself).

**Closed.**
