# CC-061 — Dependency advisories, and the CI audit gate now fails

## Problem

`npm audit` on 2026-07-30, after a clean `npm ci`:

```
56 vulnerabilities (3 low, 34 moderate, 17 high, 2 critical)
npm audit --audit-level=high   ->   exit 1
```

`.github/workflows/ci.yml:29` runs `npm audit --audit-level=high`, so **CI fails at the audit step
on the next push to `master`.** Everything else is clean: `lint` exit 0 (31 warnings, 0 errors),
`typecheck` exit 0, `build` exit 0, tests 74 passing (see `CC-060` for their flakiness).

CI is not red today — it is *idle*. The last run on `master` was 2026-05-09 (success); nothing has
pushed to `master` in 82 days. GitHub's Dependabot view shows 76 open alerts (1 critical, 28 high,
42 medium, 5 low); it counts per-alert where `npm audit` counts per-package.

Accepted deliberately: the 12 commits of 2026-07-25/30 are being pushed before this is fixed, so
the first public CI run will be red. Publishing a red build is a more honest signal than holding
the work on one machine. Fix follows immediately after.

## The two criticals

Both are `vitest` — GHSA-5xrq-8626-4rwp, arbitrary file read and execution when the Vitest UI
server is listening. Dev-only, and the UI server is not used here. Fix is non-major:
`vitest >=3.2.6` plus `@vitest/coverage-v8`.

## The high-severity ones that matter

**`next` 16.2.6 carries 9 advisories, fixed in 16.2.12 — a non-major bump.** Two are directly
relevant to this application:

- **GHSA-6gpp-xcg3-4w24** — middleware/proxy bypass in App Router. `middleware.ts` is the entire
  coming-soon gate. Worth confirming whether the Turbopack + single-locale precondition applies
  here before assuming exposure, but this is the one to read first.
- **GHSA-q8wf-6r8g-63ch** — denial of service in the Image Optimization API via SVG. **This answers
  `CC-042`: the Next.js DoS advisory is not closed.**

Also: GHSA-955p-x3mx-jcvp (unauthenticated disclosure of internal Server Function endpoints),
GHSA-89xv-2m56-2m9x (SSRF in Server Actions), GHSA-68g3-v927-f742 and GHSA-4633-3j49-mh5q (cache
confusion). `postcss` and `sharp` resolve via the same bump.

Transitive leaves, all with fixes available: `@grpc/grpc-js`, `axios` (10 advisories), `hono` (12),
`protobufjs` (11), `brace-expansion`, `fast-uri`, `form-data`, `js-yaml`, `undici`, `vite`.

## The two awkward ones

- **`ws` → wants `wagmi` 3.x, a semver major.** `CC-043` already plans to drop OnchainKit for
  explicit wagmi + viem. **Do these together** — bumping wagmi twice would mean re-testing the
  wallet path twice, and the wallet path is the one thing that has never been properly tested
  (`CC-055`).
- **`hardhat` / `hardhat-deploy` / `adm-zip`** — `npm audit` proposes `hardhat@0.0.7`, which is
  nonsense; its resolver is confused. Dev-only, used for contract compilation, never shipped.
  Likely needs manual version selection or an override.

## The `overrides` block is stale

`package.json:55-63` pins `protobufjs >=7.5.5` while the tree resolves 8.x, and `vite >=6.4.2 <7`
while the advisory covers `<=6.4.2`. These overrides were added to silence earlier audits and now
silence nothing. Re-derive them rather than nudging the numbers.

## Fix

1. Non-major first, and measure the effect: `next@16.2.12`, `vitest`/`@vitest/coverage-v8`, then
   refresh the `overrides` block for the transitive leaves.
2. Re-run `npm audit --audit-level=high` and see what is left.
3. Fold the `wagmi`/`ws` chain into `CC-043` rather than doing it standalone.
4. Handle `hardhat` separately; it is dev-only and should not gate a launch.
5. Close `CC-042` once the Next bump lands and the advisory is confirmed absent.

## Acceptance

`npm audit --audit-level=high` exits 0, and CI is green on `master`.

Related: `CC-042`, `CC-043`, `CC-060`.

PR #44 does steps 1, 2 and 4 above. `next` → 16.2.12, `@modelcontextprotocol/sdk` re-resolved to
1.30.0 (closes the whole `hono`/`@hono/node-server` cluster — the SDK's own 1.30.0 `package.json`

forcing an unsupported pairing), `vitest`/`@vitest/coverage-v8` re-resolved to 3.2.7 (clears both
criticals), and the `overrides` block re-derived against what's actually resolved now — `protobufjs`,
`axios`, `hono`, `@hono/node-server`, `sharp`, `esbuild`, `vite`, `postcss` all moved from stale
no-op floors to versions that actually constrain the tree.

One real regression surfaced and was caught before merging: letting `@coinbase/cdp-sdk` float past
its vulnerable `1.0.0–1.45.0` range naturally resolves to `1.54.0`, which added an x402-actions code
path statically importing an unpublished `@x402/core/client` and broke the Next production build
outright (8 Turbopack "Module not found" errors under the wallet-connect import chain). Pinned to
`1.46.0` instead — past the vulnerable range, predates that code path, verified with a full build
afterward. Worth remembering: "npm audit fix picked a version" is not the same as "the version
works" — always rebuild after.

**Result: 55 → 29** (0 critical, 1 high — `ws`, 28 moderate). Every remaining entry is the `wagmi` /
`@coinbase/onchainkit` / MetaMask / WalletConnect / Reown cluster (step 3 — folded into `CC-043` as

pass (its earlier confused `hardhat@0.0.7` suggestion never actually applied; the real fix landed

CI's audit gate (step 2/acceptance) is **not yet green** — expected, since the remaining 29 include

## GitHub's Dependabot count dropped further than npm audit's — reconciled

After both PRs merged, GitHub's Dependabot alert count on `master` fell to **3** (1 high, 2 medium) —
far below the 29 `npm audit` reports locally. Cross-checked directly rather than trusted at face
value: a fresh `git reset --hard origin/master` + `npm ci` + `npm audit` against the actual merged
tree reproduces **29**, matching what was tested before merge. So the local number is the accurate
one; GitHub's Dependabot view is undercounting relative to a straight `npm audit` read of the same
lockfile — likely a scope/dedup difference in how it groups transitive alerts under a shared parent,
not a discrepancy in the underlying dependency tree. Treat `npm audit`'s 29 as authoritative for this
issue's acceptance criterion, not the Dependabot UI count.

`CC-043` (OnchainKit removal) landed after this note and, as a side effect of dropping OnchainKit's
own pinned transitive tree, took 29 down to 23 (0 critical, 1 high, 22 moderate) without touching
`wagmi` at all — confirmed by diffing a clean `npm ci` on `master` before vs. after that merge.

## Resolution 2026-08-01 — the last high (and the two Dependabot mediums) closed without a wagmi bump

Traced the remaining `ws`/`uuid` findings with `npm ls ws` / `npm ls uuid` before reaching for the
planned `wagmi@3.x` bump (step 3 above). Every single path back to both packages runs through
`wagmi@2.19.5 → @wagmi/connectors@6.2.0 → {@metamask/sdk, @walletconnect/ethereum-provider}` — the
MetaMask SDK and WalletConnect/Reown connector implementations `@wagmi/connectors` bundles as
siblings to the two connectors this app actually constructs (`baseAccount`, `injected`, per
`CC-043`). None of that code ever runs — we never call `walletConnect()` or `metaMask()` — so this
is dead weight in `node_modules`, not a live risk, and forcing newer leaf versions of two small,
low-surface utility packages (a WebSocket client, a UUID generator) carries far less risk than a
wagmi major bump that would mean re-verifying the wallet-connect path a second time right after
`CC-043`/`CC-001` just finished verifying it once.

Added to `package.json`'s `overrides`: `"ws": ">=8.21.0"` (clears GHSA-58qx-3vcg-4xpx high +
GHSA-96hv-2xvq-fx4p moderate — `8.21.0`/`8.21.1` were already resolved elsewhere in the tree via
`viem`/`@supabase/realtime-js`/`hardhat`, so this just closes the one straggling `8.18.0` copy under
the nested `@reown/appkit-controllers` subtree) and `"uuid": ">=11.1.1"` (clears
GHSA-w5hq-g745-h8pq moderate, the `@metamask/utils`/`@metamask/rpc-errors` cluster stuck on
`8.3.2`/`9.0.1`).

**Result: 23 → 0.** `npm audit --audit-level=high` exits 0. Verified `npm run typecheck`,
`npx vitest run` (96/96), and `npm run build` all still pass with the overrides in place, plus a
manual check in the dev server that the wallet-connect dropdown still lists `Base Account` and
`Injected` correctly — the concern being that forcing versions on packages this deep in a bundled
SDK could break something at module-load time even if the vulnerable code path itself is never
invoked (see `Lessons-Learned.md` §14, found during `CC-043`, for exactly that failure mode).

`hardhat`/`hardhat-deploy` (step 4) needed no separate action — the progress note above already
recorded that `npm audit fix`'s automatic pass cleared it incidentally.

Acceptance met: `npm audit --audit-level=high` exits 0. "CI is green on `master`" the audit step
specifically will now pass; `CC-060` (flaky Sepolia-broadcasting tests) is a separate, still-open
risk to overall CI going green and is not this issue's job to fix.
