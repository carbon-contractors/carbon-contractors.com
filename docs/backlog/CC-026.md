# CC-026 — Dashboard hides a single failing endpoint

`src/app/dashboard/page.tsx:183-185` only surfaces an error when **both** `/api/tasks` and
`/api/reputation` fail (`if (!tasksData.ok && !repData.ok)`). If tasks alone breaks, the
worker sees a silently empty dashboard and assumes there is no work.

Fix: report each failure independently, with a retry.

## Done 2026-08-21 — commit `ad1c930`

Replaced the single `error` string with per-endpoint state: `errors.tasks` and
`errors.reputation` are set independently from each response's `error` field (falling back to
a generic message), so one failing endpoint renders its own banner line while the other still
populates. A Retry button in the banner re-runs `fetchData` (disabled while loading). The
"no tasks assigned yet" empty state is now also suppressed when `errors.tasks` is set, so a
broken `/api/tasks` can no longer masquerade as an empty task list. The `/api/profile` fetch
was left as best-effort silent-fail — it was never part of the either/or condition and its
absence degrades gracefully. Not verified against a live failing endpoint (the hermetic test
suite blocks network by design, `CC-060`); worth exercising during `CC-032`/`CC-077`
lifecycle testing.
