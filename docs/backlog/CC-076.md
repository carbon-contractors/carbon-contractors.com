# CC-076 — Sepolia validation gate: everything provable before attempting mainnet (hub)

## Why this exists

`CC-039` ("Mainnet go-live gate checklist") had been doing double duty as the checklist for two
different milestones: everything that can be built and proven on Sepolia, and the mainnet
migration itself. That made it hard to tell which items were actually blocking the *next* thing
versus a later one — `CC-034` (mainnet deploy) already says "do not start until CC-032 and CC-035
are green," which is exactly the split this issue makes explicit.

**The actual launch sequence (confirmed by Aaron, 2026-08-10):** build and test everything possible
on Sepolia (this hub) → switch to Base mainnet and re-test the full lifecycle with real personal
funds (`CC-039`) → only once that mainnet re-test is clean does the coming-soon gate lift for the
public. **This hub finishing does not mean the site goes public** — it means Sepolia is proven
enough to justify attempting the one-way mainnet migration. The actual gate flip (`CC-014`) lives
at the end of `CC-039`, after mainnet, not here.

As with `CC-039`, do not trust inherited tick-boxes — re-derive each gate's status from the code
and the backlog before treating anything here as authoritative, this list included.

## Gates

Rewritten 2026-08-11 after the full backlog triage pass. Each entry's priority reflects that pass.

**Blockers — fix before anything else here can be tested**
- `CC-082` (P0) — **CarbonEscrow v2 and the Sepolia redeploy.** `ADR-0001` D1/D4 plus Amendment 1:
  `submitWork`, worker-claimed pull-payment, EIP-712 signed verdicts, commitment fields. Now the
  **first** item in the whole gate — everything in the money path sequences behind the final ABI, and
  the escrow is empty today so the redeploy is free.
- `CC-080` (P0) — `confirm_task_completion` calls `completeTask` as the platform signer and reverts
  unconditionally. **The core hire→pay loop has never worked.** Do it against `CC-082`'s ABI.
- `CC-081` (P0) — the four trust-boundary defects. Defect 2 is resolved by `ADR-0001` D2; Defects 1,
  3 and 4 follow `CC-082`.

**New from the 2026-08-13 ADRs**
- `CC-083` (P0) — deterministic checker, canary fixture, agent-bucket evidence path. Re-runnability
  is the property the whole dispute design rests on.
- `CC-084` (P0) — machine-checkable acceptance spec, committed before the worker accepts.
- `CC-085` (P0) — **invariant monitors, sequenced before the lifecycle tests.** The ADRs introduced
  silent failure modes; these are how you know the lifecycle actually worked. Split out of `CC-040`.
- `CC-086` (P1) — task-creation kill switch, without which the runbooks have no first step.
- `CC-087` (P1) — task content retention, verifiably. Gates the published privacy claim.
- `CC-088` (P1) — data notices both directions, plus PII-prohibited categories.
- `CC-089` (P1) — drop the waitlist. **Prerequisite for `CC-027`'s copy**, not tidying.

**Security**
- `CC-037` (P0) — re-verify the escrow trust boundary against current code (fund-safety
  invariants). **This is the next piece of work**, and it is also the evidence base for `CC-051`.
- `CC-041` (P2) — YubiKey-only 2FA on the GCP project holding the KMS/HSM key. Lowered from P1;
  the key remains non-exportable regardless, but note `CC-059` made this project's console access
  equivalent to control over dispute outcomes.
- **Day-of security sweep** — OWASP Top 10 + Web3 attack-vector sweep, resolve every CRITICAL and
  HIGH, document accepted MEDIUMs, re-run `npm audit`. Run *last*, immediately before the gate
  lifts; a sweep run earlier goes stale. Previously tracked as `CC-035`, closed `wontfix` because
  it is a procedure rather than a defect. Fold in the non-npm items from `CC-045` (the
  `child_process`/`exec`/`spawn`/`eval` audit, Zod coverage on every MCP tool input).

**Correctness / fund safety**
- `CC-070` (P0) — every `eth_getLogs` query in `escrow.ts` exceeds the public RPC's 2000-block
  limit. Raised from P1: `getTaskResolvedOutcome` is `CC-065`'s dispute-recovery path, so this is a
  correctness bug on a money path. **Fix before running any lifecycle stage** — results read back
  through these helpers are otherwise unreliable.
- `CC-032` (P1) — lifecycle **Discovery** stage: register → MCP discovery → correct worker data.
- `CC-077` (P1) — lifecycle **Funding** stage: `request_human_work` → x402 → `escrow.createTask` →
  worker notified.
- `CC-078` (P1, `blocked`) — lifecycle **Settlement** stage. Blocked behind `CC-080`.
- `CC-079` (P1) — lifecycle **Dispute** stage. Partly proven already by `CC-059`/`CC-065`; the
  refund outcome and the product path since `CC-065` are the real gaps.
- `CC-072` (P1) — the on-chain staking flow has never been executed once, end to end. Note the
  7-day cooldown means this has a long tail.
- `CC-060` (P2) — `npm test` broadcasts real Sepolia transactions and is non-deterministic.
  Lowered from P1, but **sequence it before the lifecycle stages**: until it is fixed, "the tests
  pass" is not evidence of anything during launch validation.

**Agent-facing / MCP**
- `CC-046` (P1) — MCP idempotency/retry semantics for the already-live `/api/basedhuman.mcp`
  endpoint. "The agent retried and we paid twice" is the failure that matters.

  The in-app MCP server is real and live (10 tools at `/api/basedhuman.mcp`, reachable by agents
  over HTTP today, since `/api/*` bypasses the coming-soon gate), so the standalone npm package is
  distribution ergonomics rather than a prerequisite. See `CC-044`'s note for the evidence, and for
  the flagged question of whether both should move back to `epic: mcp-package`.

**Smoke test**
Full register → discover (MCP) → x402 fund → notify → deliverable → settlement → payout cycle, plus
the dispute → `resolve_dispute` path in both directions, run against the live Production Sepolia
deployment. Now decomposed into `CC-032`/`CC-077`/`CC-078`/`CC-079` so progress is visible.

This proves Sepolia is ready for the mainnet attempt in `CC-039` — it is **not** the smoke test that
precedes opening to the public; that one happens on mainnet, at the end of `CC-039`.
