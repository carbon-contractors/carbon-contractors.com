# CC-027 — README claims Zero PII while the app stores email addresses

`README.md` design constraints state "**Zero PII** — no personal data stored, ever. Wallets
and skills only." The `waitlist` table stores email addresses, `notification_channels` is
explicitly a PII table in the architecture doc, and CC-005 proposes collecting contact
details at signup.

This is a public repo and the claim is quotable. Fix: restate honestly — minimal PII, only
what is needed to notify you, never exposed to agents — and align it with the privacy policy
from CC-008.

## Update 2026-08-13 — replacement copy specified by `ADR-0002`, and it has a hard dependency

`ADR-0002` supersedes the `README.md` "Zero PII" constraint and specifies what replaces it. This
issue is no longer "write something more honest" — the wording is decided.

**Two separate statements, never merged into one:**

1. **Registration.** The platform holds a wallet address, service categories, a rate, and derived
   reputation. It does not hold, request or verify names, documents or location. There is no account
   in the conventional sense.
2. **Task payload.** Task content is authored by the hiring agent and evidence is produced by the
   worker. It is arbitrary and may contain personal information about third parties. The platform
   stores no task evidence and retains no task content after settlement.

**Say "pseudonymous", not "anonymous", and not "zero PII".** A wallet address plus a service history
plus a payout pattern is pseudonymous data, and under both Australian and EU law it can constitute
personal information where an individual is reasonably identifiable. `ADR-0002` D1 is explicit that
overclaiming here is the kind of statement that gets quoted back from a public repo — which is the
same defect class as `CC-029`.

**Do not publish statement 2 before `CC-087` ships.** `ADR-0002` D2 says so directly. Retention is
what makes it true, and it does not exist yet.

**Do not publish statement 1 before `CC-089` ships.** The `waitlist` table is the only place the
platform holds email addresses, so until it is dropped the claim is false on day one.

**And check the wording against `notification_channels`.** That table stores an optional contact
email per worker, collected at `/connect`, and it is deliberate — a worker cannot be told they have
been hired otherwise. Statement 1 must be worded so it stays true with that table in place: no email
is required, none is verified, and any channel exists solely to notify the worker. Getting this
wrong is how the claim becomes false a second time.

Also in scope per `ADR-0001`'s handover step 8: the `README.md` staking claim ("workers put skin in
the game" — see `CC-081` Defect 5) and the dispute description, both of which change once
`ADR-0001` lands.

Priority stays **P1**.

Related: `ADR-0002` D1/D2/D6, `CC-087`, `CC-089`, `CC-081`, `CC-029`, `/learn` Module 7.

## Update 2026-08-21 — done

Shipped on `feat/cc-027-088-adr0002-notices-and-readme-pii` (commit references this id).

**The "Zero PII" bullet is gone.** The Design constraints list now reads "Pseudonymous by design —
no identity verification, ever", pointing at a new *Privacy posture* subsection that carries the
`ADR-0002` D2 two-part statement verbatim in substance:

1. **Registration** — wallet, categories, rate, derived reputation; nothing else held, requested or
   verified; no conventional account. Worded to stay true with `notification_channels` in place:
   the optional channel is named, "none is required, none is verified, and none is used for
   anything but notification" (the failure mode this issue warned about).
2. **Task payload** — authored by the agent, produced by the worker, may contain third-party PII;
   platform stores no evidence and retains no task content after settlement; hashes on-chain,
   bytes in agent-controlled storage.

Plus the D6 counterweight: on-chain data is permanent and world-readable and is not described as
deletable. "Pseudonymous, not anonymous" stated explicitly; "zero PII" and "anonymous" appear
nowhere.

**Staking and dispute copy aligned to v2 / `ADR-0001`.** The "skin in the game" line is replaced
with staked capital + verifiable event-log track record, and slashing only for *established fault*
(a published re-runnable check failure or jury ruling, never a bare assertion) — closing the
`CC-081` Defect 5 gap. The x402 flow step 5 and the intro paragraph now describe pull-payment
claims by the worker, not automatic release. The dispute tool table matches the v2 contract:
`dispute_task` requires a signed failing verdict from either party; `resolve_dispute` resolves
on-chain to one of the two fixed wallets with no agent self-adjudication.

The D2 statements describe the target state ahead of `CC-087`/`CC-089` — published deliberately
under `ADR-0004` D1, and gated by `CC-014`'s pre-flip checklist, which already carries the
retention, waitlist-drop and staking/dispute-copy boxes.

Verified: `npm test` (244/244), `npm run typecheck`, `npm run lint`, `npm run build` all clean.
