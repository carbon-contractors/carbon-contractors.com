# CC-062 — RLS is the only layer protecting the waitlist emails

## Problem

`CURRENT-STATE.md` §2 and `AUDIT-2026-03-25.md` record `waitlist` as anon-**denied**. Measured with
the public anon key on 2026-07-30, it is not denied — it is *filtered*:

| object | HTTP | `content-range` |
| :-- | :-- | :-- |
| `humans` | 206 | `*/5` |
| `tasks_public` | 206 | `*/1` |
| `waitlist` | **200** | `*/0` |
| `tasks` | **200** | `*/0` |
| `notification_channels` | **200** | `*/0` |
| `used_nonces` | **200** | `*/0` |
| `mcp_challenges` | **200** | `*/0` |

A PostgREST `200` requires the executor to have run, which requires passing the relation ACL check.
A missing `SELECT` grant returns `401`/`403` with SQLSTATE `42501` instead. So **anon holds the
table-level `SELECT` grant on `waitlist`, and row-level security alone is returning zero rows.**

This is Supabase's default posture — `GRANT ALL ON ALL TABLES IN SCHEMA public TO anon,
authenticated` is applied by the platform — so it is not a misconfiguration, and the AUD-001 fix
genuinely holds. Nothing is leaking today.

The point is that it is **single-layered**, on the one table holding real third-party personal data.
Any of the following exposes every email address immediately, with no second barrier:

- `ALTER TABLE waitlist DISABLE ROW LEVEL SECURITY` — one statement, and migrations here are applied
  by hand in a SQL editor with no review (`CC-057`)
- adding a permissive `SELECT` policy while intending to scope it to `service_role`
- a future `waitlist_public` convenience view created without `security_invoker`, which is exactly
  the pattern `tasks_public` already uses deliberately

## Fix

**Update 2026-07-30:** `scripts/audit/inspect-live-schema.sql`, run against production, shows the
grant is wider than first measured. Every table returns `anon_ins=true anon_upd=true anon_del=true`
as well as `anon_sel=true` — Supabase's default `GRANT ALL … TO anon, authenticated` covers every
DML verb, not only `SELECT`. So the fix is `REVOKE ALL`, not `REVOKE SELECT`:

```sql
REVOKE ALL ON public.waitlist FROM anon, authenticated;
REVOKE ALL ON public.notification_channels FROM anon, authenticated;
REVOKE ALL ON public.used_nonces, public.mcp_challenges FROM anon, authenticated;
```

**Currently exploitable: none of it.** `waitlist`, `used_nonces` and `mcp_challenges` have zero
policies with RLS on, which denies every command to every role by default regardless of the grant.
`notification_channels`'s three policies are all scoped to `authenticated`, never `anon`. So no anon
write succeeds anywhere today — but that is RLS and policy scoping doing the work alone, on top of a
grant that has no business being there. The revoke removes a layer that currently does nothing
except sit ready to matter the moment RLS is touched.

Server-side writes use the service role key and bypass both grants and RLS, so nothing in the
application breaks. `tasks` needs care: anon must keep reading `tasks_public`, and that view runs as
its owner, so revoking anon's grant on the underlying `tasks` table is safe — but verify it, because
the public task feed depends on it (see the `tasks_public` landmine in `CLAUDE.md`).

Do **not** revoke anything on `humans`; anon `SELECT` there is the public whitepages (`CC-030`), and
its two real policies (`humans_read_all` SELECT-anon, `humans_update_self` UPDATE-authenticated) are
enough that revoking the raw INSERT/UPDATE/DELETE grants there is optional hardening, not a fix for
an active gap — no policy permits anon to write regardless.

## Acceptance

Block 4 of `scripts/audit/inspect-live-schema.sql` shows every `anon_*` privilege `false` for
`waitlist`, `notification_channels`, `used_nonces` and `mcp_challenges`, `anon_sel=true` (others
`false`) for `humans` and `tasks_public`, and the public task feed still returns rows to the anon
key.

Related: `CC-016`, `CC-030`, `CC-057`, `AUD-001`.

## Closed 2026-08-11 — applied and verified against production

`supabase/migrations/015_revoke_anon_grants.sql` written during the backlog triage pass and applied
by Aaron in the SQL editor. Verified from two directions.

**1. Grants, via `has_table_privilege` in the migration's own verification query:**

| object | anon_sel | anon_ins | anon_upd | anon_del | auth_* |
| :-- | :-- | :-- | :-- | :-- | :-- |
| `humans` | **true** | false | false | false | all true |
| `tasks_public` | **true** | false | false | false | all false |
| `waitlist` | false | false | false | false | all false |
| `tasks` | false | false | false | false | all false |
| `notification_channels` | false | false | false | false | all false |
| `used_nonces` | false | false | false | false | all false |
| `mcp_challenges` | false | false | false | false | all false |

Matches the acceptance criteria exactly. `authenticated` is intentionally untouched on `humans` so
migration 005's dormant `humans_update_self` policy is not silently broken if wallet-based Supabase
Auth is ever wired up (`CC-021` option (b)).

**2. Live behaviour, probed with the real anon key over PostgREST:**

```
tasks_public           HTTP 200  content-range=0-0/1   1 row
humans                 HTTP 206  content-range=0-4/8   5 rows
waitlist               HTTP 401  {"code":"42501","message":"permission denied for table waitlist"}
tasks                  HTTP 401  {"code":"42501","message":"permission denied for table tasks"}
notification_channels  HTTP 401  {"code":"42501","message":"permission denied for table notification_channels"}
```

**This is the result the issue was filed for.** Before the migration those three returned
`200` with zero rows — RLS filtering, with the table-level `SELECT` grant present underneath. They
now fail with SQLSTATE `42501` at the relation ACL check, *before* RLS is consulted. The waitlist
emails have a genuine second barrier for the first time, so a single `DISABLE ROW LEVEL SECURITY` or
one over-broad policy no longer exposes them.

Both required anon reads survived: the public task feed and the whitepages. The `tasks_public` view
behaved exactly as predicted — it has no `security_invoker`, so it executes as its owner and is
unaffected by revoking anon's privileges on the underlying `tasks` table. That prediction was the
one real risk in this change and it held.

**Consequence for `CLAUDE.md`.** Its landmine "'Anon is denied' and 'anon reads zero rows' are
different things" was correct when written and is now out of date for these five tables — they are
genuinely denied. Updated in the same commit. `humans` and `tasks_public` remain granted, by design
(`CC-030`).

Verification tooling note: the ad-hoc check script initially reported a false failure because it
asserted `HTTP === 200` for every required read, and PostgREST correctly answers `206 Partial
Content` for a ranged query — which this issue's own 2026-07-30 measurement table already recorded
(`humans | 206 | */5`). The migration was fine; the check was wrong. Recorded because it is the same
class of mistake this issue is about: reading a status code as a verdict without knowing what the
codes mean.

Applied via migration `015`. Commit: see `git log --grep=CC-062`.
