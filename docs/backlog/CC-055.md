# CC-055 — The Smart Wallet passkey onboarding path has never been executed

## Problem
All testing to date used the **Coinbase Wallet browser extension** — a seed-phrase EOA that
injects `window.ethereum`. That is not the path real users take.

`src/lib/wallet/providers.tsx` configures **no wagmi config and no connectors array at all**
(25 lines, just `OnchainKitProvider` with an apiKey and chain). It relies entirely on
OnchainKit's auto-created default, which uses the `baseAccount` connector — the passkey-based
Smart Wallet. With the extension installed, the extension wins and the passkey flow is never
reached.

So the onboarding path the entire product pitch rests on — "tap FaceID or a fingerprint and
you have a wallet, no seed phrases, no extensions" — has not been exercised once. It is not
known to be broken. It is unknown, which for a launch is worse.

## Why this compounds
On a phone there is no browser extension, so mobile users have **no alternative** to the
passkey path. Three defects stack on that single untested route:

- **CC-001** — no connect button exists on mobile at all
- **CC-003** — CSP blocks both the RPC host and the passkey iframe (see below)
- **This issue** — nobody has ever completed it successfully

Every phone visitor from a promotion push hits all three at once. This is the launch.

## Do
1. Fix CC-001 and CC-003 first — the path cannot work until they are done.
2. Then complete a registration in a browser profile with **no Coinbase extension installed**,
   on a real phone, with the console open. Create a fresh Smart Wallet via passkey, sign the
   registration message, and confirm the row lands in `humans` (CC-002 must be fixed or the
   dashboard will 404 afterwards).
3. Record the working configuration, because CC-043 will replace this stack and the passkey
   connector has to be reconfigured explicitly rather than inherited from a default.

## Acceptance
A wallet that did not exist before, created by passkey on a phone, appears in the database and
renders on the dashboard.

Related: CC-001, CC-002, CC-003, CC-043.

## Update 2026-08-01 — CC-043 landed; item 3 of "Do" is now done, the rest is not

`src/lib/wallet/providers.tsx` now has an explicit `createConfig` with `connectors: [baseAccount({
appName: "Carbon Contractors" }), injected()]` — the working configuration this issue asked to
record. `baseAccount` is listed first and deliberately, so it doesn't disappear on a future patch
bump the way OnchainKit's default could.

That only satisfies step 3. Steps 1 (CC-001, CC-003) and 2 (an actual phone run) are still open —
nothing here has executed a passkey registration end to end. `NavBar.tsx` now presents both
connectors in a dropdown (`Connect Wallet` → pick one), so testing this requires deliberately
choosing `baseAccount`, not just clicking through — on a machine with the Coinbase extension
installed, `injected` is still a visible option and still wins if picked.

## Update 2026-08-08 — CC-003 done; first real signal that the path works, still not this issue's acceptance

`CC-003` is closed — `frame-src`, `font-src` and `cca-lite.coinbase.com` all fixed and verified.
While verifying it, Aaron ran `/connect` → `Connect Wallet` → `Base Account` on a **desktop**

**Still open, unchanged in substance:** that test was on a desktop browser, not a phone, and

registration, and confirming a row in `humans` that renders on `/dashboard`. This issue's
acceptance criterion is specifically a passkey wallet created *on a phone*. Step 2 of the original
"Do" list is the only remaining work: repeat this same flow on a real phone, through to
completion, with the console open.

## Update 2026-08-08 — the real phone test happened, and found the actual bug this issue predicted

Aaron ran it: real phone, real Base Account passkey, real Coinbase login-code email, tapped
**Sign** on the registration message at `keys.coinbase.com`. Registration failed with "Signature
verification failed." Root cause and fix filed as `CC-069`: the registration and MCP-auth
signature checks only supported EOA signatures (raw `ecrecover`), and Base Account is a smart
contract account (ERC-4337) — its signatures are ERC-6492/ERC-1271, structurally different.

This is exactly the risk this issue's "unknown, which for a launch is worse" framing was about.
The onboarding path wasn't just untested — the moment it was tried for real, it was provably
broken for its own target account type. `CC-069` fixes the verification logic; the outstanding
step is the same real-phone retry, to confirm registration now actually completes and a row lands
in `humans`, rendering on `/dashboard` — this issue's original acceptance criterion, still open.
