# CC-108 — Webhook SSRF hardening — block private/reserved targets at registration and delivery

Found by the CC-045 MCP/STDIO hardening audit, spun out rather than scope-crept.

## Problem

Notification delivery is live (CC-095): `src/lib/notifications/channels/webhook.ts` POSTs to
`channel.address` server-side via `postJson` (`src/lib/notifications/http.ts`). Neither the
registration surfaces nor the delivery path restrict *where* a webhook may point:

- `isValidChannelAddress` (`src/lib/validation.ts`) accepts any HTTPS URL with a dotted
  hostname — `https://10.0.0.5/`, `https://169.254.169.254/latest/meta-data` (if it were https),
  `https://host.internal:8443/` all pass.
- `postJson` does no DNS/IP resolution check before fetching.

Before CC-045's fix this was an **unauthenticated** SSRF: the MCP tool
`register_notification_channel` took a caller-supplied `contractor_id` with no auth check, so
anyone could point any worker's webhook at an internal address and wait for the next hire to
trigger the fetch. CC-045 closed that half (tool now binds to the authenticated caller and
validates per type, HTTPS-only). What remains is the **authenticated** vector: any registered
contractor can self-register a webhook pointing at internal infrastructure, and the platform
will fetch it on their next hire.

## Scope

1. Extend `isValidChannelAddress` (or add a delivery-time guard in `channels/webhook.ts`) to
   reject loopback, RFC1918, link-local (169.254.0.0/16), unique-local (fc00::/7), and
   metadata-service targets, by resolved IP — not just literal IP literals (DNS rebinding
   means hostname checks alone are insufficient; resolve-then-fetch or re-validate after
   redirect is the shape that actually holds).
2. Decide the port policy (443-only, or an allowlist) and enforce it in the same place.
3. Apply at both registration surfaces — `/api/channels` (dashboard, CC-073) and the MCP
   `register_notification_channel` tool (CC-045) — plus the delivery path as defence in depth,
   since rows written before the fix may persist.
4. Redirects: `postJson` follows fetch defaults (redirect: follow). A public URL that 302s to
   an internal address bypasses registration-time checks unless delivery re-validates.

## Acceptance

- [x] A webhook registration pointing at a private/reserved/loopback target is rejected with a
  clear message on both surfaces. (`channels-route.test.ts`, `mcp-register-channel.test.ts`)
- [x] Delivery refuses (and logs a sanitised classification, per CC-009 — never the URL) to fetch
  a target that resolves private, even for a row written before the checks existed.
  (`blocked_target`; `webhook-target.test.ts` "refuses a stored private-literal URL", guarded lookup)
- [x] Tests cover IP-literal, hostname-resolving-private, non-standard port, and redirect-to-
  private cases at both registration and delivery. Redirect is registration-irrelevant (a URL
  cannot redirect before it is fetched); at delivery it is never followed.

Related: CC-045 (audit + auth fix), CC-073 (dashboard channels), CC-095 (delivery), CC-009
(no secrets/PII in logs).

## Resolution 2026-10-19

Implemented in `src/lib/notifications/webhook-target.ts`, on branch `claude/peaceful-ride-7jls08`
(PR #258).

- **Address rule:** public unicast only, judged by every resolved address. The blocked ranges are:
  - IPv4: RFC1918, loopback, link-local/metadata, CGNAT, TEST-NETs, multicast and reserved.
  - IPv6: loopback, unique-local, link-local, multicast and documentation.
  - IPv4-mapped and NAT64 addresses are unwrapped and judged as IPv4.
  - Names that never resolve to a public receiver (`localhost`, `.local`, `.internal`,
    `.home.arpa`) are rejected outright.
- **Port policy (scope item 2): 443 only.** Every hosted webhook receiver is on 443. A non-standard
  port is the usual shape of a probe for an internal service.
- **Registration:** `/api/channels` and MCP `register_notification_channel` both run
  `resolveWebhookTarget`. A rejection is a 400 or `INVALID_ARGUMENT` with a `reason` and a clear
  message. A host that does not resolve is rejected too.
- **Delivery:** `channels/webhook.ts` now sends through `postJsonToWebhook` (`node:https`, not
  `fetch`).
  - The URL rules run again, so rows written before this fix are covered.
  - The connection uses a guarded `lookup` that refuses blocked addresses at connect time. That
    closes DNS rebinding, which a check-then-`fetch` would leave open.
  - `https.request` never follows redirects, so a 302 to an internal host is a failed delivery
    (scope item 4).
  - A refusal is classified `blocked_target`: permanent, sanitised, and never logs the URL (CC-009).
- **No new dependency.** `undici` would have allowed pinning under `fetch`, but it is only a
  transitive dev dependency here, and adding it needs PO approval.
- **Tests:**
  - `webhook-target.test.ts` covers IP literals, obfuscated loopback, a hostname resolving private,
    a mixed public and private answer, non-standard ports, redirect-not-followed, rebinding via the
    guarded lookup, timeout, and pre-existing rows.
  - Registration rejections are tested on both surfaces.
  - `npm test` 1116 passed, lint and typecheck clean.
