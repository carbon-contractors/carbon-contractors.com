# CC-054 — Audit the exec_sql RPC on Supabase

## Problem
`.claude/settings.local.json` records approved calls to
`https://<project>.supabase.co/rest/v1/rpc/exec_sql`. So a Postgres function named `exec_sql`
exists on the project — almost certainly added to apply migrations conveniently.

A function that executes arbitrary SQL is the single most dangerous object that can exist in
a Supabase project. If it is `SECURITY DEFINER` and callable by the `anon` role, then the
public anon key — which ships to every browser — grants full read/write over every table,
bypassing every RLS policy in migrations 003, 005, 010 and 011 and every hard-won AUD fix.

This is not in any migration file, so it was created out of band and is not tracked anywhere.

## Do
1. Inspect it: owner, `SECURITY DEFINER` or `INVOKER`, and the exact grants
   (`\df+ exec_sql`, then check `information_schema.role_routine_grants`).
2. If `anon` or `authenticated` can execute it, **revoke immediately** — treat as a live
   critical exposure, then rotate the anon and service role keys.
3. Preferably drop it entirely and apply migrations through the Supabase CLI or the SQL
   editor instead. If it must stay, restrict execution to `service_role` and record it in a
   migration so it stops being invisible.

## Note
This was inferred from local tool-approval history, not from reading the database. It may
already be locked down. Verify before assuming either way — the downside is total.

Related: CC-030, CC-016.

## Progress 2026-07-30 — tooling and fix prepared, needs one run on Aaron's machine

### Confirmed by static inspection
`exec_sql` appears in **no migration and no tracked code** — grep across `src/`, `scripts/` and
`supabase/` returns nothing. The only trace is an approved request URL in the gitignored
`.claude/settings.local.json`. So it was created out of band and its access level has never been
recorded anywhere. That much is certain.

What is **not** yet known: whether it still exists, whether it is `SECURITY DEFINER`, and — the
only question that really matters — whether the `anon` role can execute it.

### Why it could not be determined from here
The Supabase host does not resolve from the analysis sandbox (`EAI_AGAIN`, not on the network
allowlist). Which is the right outcome anyway: an unverified security change should not be applied
unilaterally to a production database.

### Prepared

**`scripts/audit/probe-exec-sql.mjs`** — read-only. Executes no DDL and no writes, and holds no
credentials; it reads them from the environment. It:
1. probes `exec_sql` under six candidate parameter names with the service role, since the signature
   is unknown
2. introspects the function using itself — owner, `prosecdef`, ACL
3. lists explicit `EXECUTE` grants per role
4. **the decisive test:** attempts the call with the public `anon` key
5. enumerates *every* public-schema routine and its grants, to catch out-of-band siblings — the
   generalised version of this issue, and the more valuable output

```bash
node --env-file=.env.local scripts/audit/probe-exec-sql.mjs
```

**`supabase/migrations/012_restrict_exec_sql.sql`** — revokes `EXECUTE` on every `exec_sql`
overload from `PUBLIC`, `anon` and `authenticated`, leaving `service_role` only. Idempotent, and a
no-op with a `RAISE NOTICE` if the function is absent, so it is safe to apply either way. Contains
a commented `DROP` block for the stronger fix.

Restricting to `service_role` adds no new risk: `service_role` already bypasses RLS by design, and
the key never leaves the server. The threat is specifically the anon key, which ships to every
browser.

### Decision rule once the probe output is in
- **anon CAN execute** → treat as a live critical exposure. Apply 012, then **rotate the anon and
  service role keys** (assume both compromised), then check the `waitlist` row count and
  `created_at` distribution for signs of exfiltration or tampering.
- **anon CANNOT execute** → not a live exposure. Still apply 012 so the access level is recorded in
  version control instead of remaining invisible. Close as found-not-exploitable.
- **function absent** → confirm in the SQL editor before closing; absence via PostgREST is not proof
  of absence. Apply 012 anyway as a standing guard.

### Then
Either way, add the `docs/Lessons-Learned.md` entry (the transferable lesson is about out-of-band
schema changes escaping version control, regardless of which way the grant check lands) and push.
This is the only item gating the first push per CC-056.

## Update 2026-07-30 (2) — SQL-editor path added, and the root cause identified

Aaron asked whether these run in the Supabase SQL editor. Yes for the `.sql` files — and checking
why turned up the underlying problem.

**There is no Supabase CLI on this project** (no `supabase/config.toml`, no CLI dependency, no
runner script). Migrations 001-011 were applied by hand. That is almost certainly *why* `exec_sql`
exists: a shim to apply migrations over HTTP because there was no proper channel. Raised as
**CC-057**, which is the actual root cause. Revoking the grant without fixing that invites the next
convenience helper.

### Trap found: the SQL editor does not reliably show RAISE NOTICE
`012` originally reported its work through `RAISE NOTICE`, which the dashboard SQL editor does not
dependably surface. Running it would have shown "Success. No rows returned" and taught nothing —
including in the case where the function was never there.

Fixed by appending a verification `SELECT` that **returns rows**, so the outcome is visible
regardless. Read that output, not the notices.

### Added: `scripts/audit/inspect-exec-sql.sql`
Pure read-only SQL for the editor. Given Aaron is in the dashboard anyway this is easier than the
Node probe and answers most of the question:

1. does `exec_sql` exist, and how is it declared (`prosecdef`, owner, raw ACL)
2. **who can EXECUTE it** — per-role via `has_function_privilege`; any `anon` or `PUBLIC` row is a
   live critical finding
3. generalised — every public-schema function `anon` or `authenticated` can run, to catch siblings
4. bonus: whether the AUD-001/009 RLS fixes held, i.e. what `anon` can still reach at table level.
   `waitlist` and `notification_channels` must not be anon-readable; `humans` intentionally is
   (CC-030)
5. the RLS policies that actually exist, for the record

### Recommended order
1. `scripts/audit/inspect-exec-sql.sql` in the SQL editor — 30 seconds, answers almost everything
2. `supabase/migrations/012_restrict_exec_sql.sql` in the SQL editor — applies the fix, returns
   its own verification
3. `node --env-file=.env.local scripts/audit/probe-exec-sql.mjs` — the empirical end-to-end check
   that a browser-side key genuinely cannot reach it. Grants are the authority, but this also
   proves PostgREST is not exposing the function by some other route.

Step 3 is not redundant: a 200 there when the grants look correct would mean something stranger is
going on than a misgrant.

## Update 2026-07-30 (3) — **the decisive test is done: `anon` cannot execute it. Push unblocked.**

Run from Aaron's machine against production with the real anon key:

```
anon POST /rest/v1/rpc/exec_sql   ->  404 PGRST202   (all six candidate parameter names)
```

`PGRST202` is "no matching function in the schema cache", and PostgREST reports it having also
checked the single-unnamed-json-parameter form for each name. Ten sibling names were tried as well —
`execute_sql`, `run_sql`, `exec`, `execute`, `sql`, `query`, `eval_sql`, `raw_sql`, `admin_sql`,
`apply_migration` — all `404 PGRST202`.

**So no arbitrary-SQL RPC is reachable with the browser-side key.** The `waitlist` email addresses
are not reachable by that route. Per the decision rule above this is the *anon CANNOT execute*
branch: not a live exposure, and it clears the `CC-056` carve-out that was gating the first push.

### What is still not known, and why — this matters

`SUPABASE_SERVICE_ROLE_KEY` in `.env.local` is the literal placeholder string `placeholder…`
(33 characters, not a JWT; the anon key beside it is a valid JWT with `role: anon`, issued
2026-03-16, expiring 2036-03-15). So the service-role half of the probe could not run:

- `probe-exec-sql.mjs` step 1 returned six `401 Invalid API key` responses and then printed
  *"No exec_sql reachable via PostgREST under any tried parameter name."* **That line is an artefact
  of the bad key, not a finding.** Anyone reading the raw output should ignore it. Steps 2, 3 and 5
  did not execute at all.
- The OpenAPI spec endpoint — which would enumerate every exposed table and function in one request,
  and is the generalised answer `CC-057` needs — is service-role only:
  `"Only the service_role API key can be used for this endpoint."`
- Therefore: **proven that `anon` cannot reach `exec_sql`. Not proven that `exec_sql` is absent.**
  Grants and existence remain unmeasured.

That distinction is the whole lesson of `Lessons-Learned.md` §9, so it is stated rather than rounded
off. This issue stays `in-progress` until the catalog query lands.

### Added: `scripts/audit/inspect-live-schema.sql`

The existing `inspect-exec-sql.sql` is six separate statements, and the dashboard SQL Editor shows
only the last result set — so in practice it gets run once and misread. The new file is the same
information as **one statement returning one result set**, so it can be pasted, run once, and copied
back whole. It also covers the two things no external probe can answer: whether `exec_sql` still
exists, and the anon `INSERT`/`UPDATE`/`DELETE` posture (probing that from outside would mean
attempting a real write against production).

2. If section `1_exec_sql` returns rows, apply `012` — now with the `DROP` block activated per
   Aaron's decision to remove the function rather than merely restrict it. If it returns zero rows,

3. Either way, fold section `2_anon_exec_fn` into `CC-057` as the drift baseline.
4. Lessons entry: written as `Lessons-Learned.md` §11, on the placeholder key producing a false

is anon-*filtered* — the `SELECT` grant is present and RLS alone returns zero rows.

## Closed 2026-07-30 (2) — done. `exec_sql` does not exist. Full stop.

Aaron ran `scripts/audit/inspect-live-schema.sql` in the dashboard SQL editor and returned the
result set. Section `1_exec_sql` — `SELECT … FROM pg_proc WHERE proname = 'exec_sql'` — came back
with **zero rows**.

This is the authoritative answer the anon-key probe couldn't give. `pg_proc` is not filtered by role
grants the way PostgREST is — querying it from the SQL editor runs as a privileged role, so a
zero-row result means the function is not in the catalog, not merely unreachable by one credential.
**`exec_sql` does not currently exist on this project, under any schema.**

So the finding upgrades from "not a live exposure" to "there is nothing to be exposed to." Whether it
was quietly dropped at some point after the settings-file reference was recorded, or the original
inference was simply wrong from the start, is now unknowable and not worth chasing — the live state
is what matters, per `Lessons-Learned.md` §9.

**Consequence for `012_restrict_exec_sql.sql`:** there is nothing to revoke or drop. Its `DO $$`
block already handles this (`found_any := false` → `RAISE NOTICE 'no exec_sql function found'`), so
running it is harmless and idempotent, but it is not a live-system action any more — it would be a
no-op recording an already-true fact. Not applying it changes nothing. Left as-is in
`supabase/migrations/` as a standing guard against recurrence; not worth spending a production DDL
statement to run a function that isn't there.

### Section `2_anon_exec_fn` — the generalised CC-057 answer, and it is good news

Exactly **one** public-schema function is executable by `anon`/`authenticated`:
`prevent_task_mutation` (`secdef=false`, `owner=postgres`). Checked against migrations — it is
`supabase/migrations/009_task_immutability_trigger.sql`, the `AUD-002` trigger that blocks mutation
of `to_human_wallet`, `from_agent_wallet`, `amount_usdc`, `deadline_unix` and `payment_request_id`
once a task leaves `pending`, enforced even against `service_role`. Trigger functions are executable
by whichever role's write fires them — that is normal, not a grant anyone made deliberately, and not
a footgun. **Tracked, intentional, no drift.** `exec_sql` and `keepalive` were the only two
out-of-band objects, and both are now gone.

### Section `4_object_acl` — sharper than the earlier read, feeds into `CC-062`

Every table shows `anon_ins=true anon_upd=true anon_del=true`, not just `anon_sel=true` — the
Supabase-default `GRANT ALL … TO anon, authenticated` covers every DML verb, not only `SELECT`. On
`waitlist`, `tasks`, `used_nonces`, `mcp_challenges` (0 policies each), RLS denies every command to
every role by default, so none of those grants currently do anything. On `humans` and
`notification_channels`, the only policies that exist are scoped to `SELECT`-anon or
`authenticated`-only — none permit `anon` to write — so anon is blocked there too, just via policy
rather than via the default-deny path. Net effect unchanged: no anon writes succeed anywhere today.
But it means `CC-062`'s revoke should be `REVOKE ALL`, not `REVOKE SELECT` — updated there.

### Section `8_counts` — no sign of tampering

`waitlist`: 4 rows, `2026-03-21` to `2026-04-18`, 3 distinct days. Small, old, and consistent with
early manual testing before the coming-soon gate went up — not the shape of scraping or injection.
`humans`: 5, `tasks`: 1, `notification_channels`: 0. Nothing here changes any other verdict.

CC-054 is done. CC-057's drift count is now zero known objects.
