# CC-068 — safeErrorResponse prints "[object Object]" for non-Error thrown values

## Problem

Found while manually verifying `CC-067`'s new unsubscribe endpoint against the real (locally
placeholder) Supabase credentials: `safeErrorResponse` (`src/lib/errors.ts`) computed its message
as `err instanceof Error ? err.message : String(err)`. Supabase's client does not always throw a
real `Error`/`PostgrestError` instance — a gateway-level rejection (e.g. an invalid API key, which
is exactly what the local placeholder `SUPABASE_SERVICE_ROLE_KEY` produces) comes back as a plain
object: `{ message: "Invalid API key", hint: "..." }`. Confirmed directly:

```
typeof error: object
instanceof Error: false
constructor.name: Object
String(error): [object Object]
error.message: Invalid API key
```

`String()` on a plain object without a custom `toString` always yields `"[object Object]"`. This
hit both halves of the function: the dev-mode client-facing message (`json.error`) and, more
importantly, the **server-side log line** (`log("error", context, { error: message })`) — meaning
any route depending on this helper loses the actual error detail from its own logs the moment
Supabase (or anything else) throws a non-`Error` value. Six routes depend on it: `waitlist`,
`dispute`, `tasks`, `reputation`, `fund-task`, plus the new `CC-067` unsubscribe endpoint.

This is not a new defect from `CC-067` — it was already live in five existing routes. It surfaced
now because `CC-067`'s local verification happened to hit exactly the failure mode (an auth
rejection returning a plain object) that exposes it.

## Fix

`extractMessage()` now checks, in order: a real `Error` (`.message`), then any object carrying a
string `.message` property (covers `PostgrestError`-shaped plain objects regardless of whether
they're an actual class instance), then falls back to `String(err)` only when neither applies.

## Acceptance

- A thrown plain object with a `.message` string produces that message in both the client
  response (dev mode) and the server log — not `[object Object]`.
- Existing behaviour for real `Error` instances and message-less values is unchanged.
- Reproduced live: ran the `CC-067` unsubscribe form against the real (broken-locally) Supabase
  credentials before and after the fix — before: `"error":"[object Object]"` in both the UI and
  the server log; after: `"error":"Invalid API key"` in both.

## Update 2026-08-08 — fixed

`src/lib/errors.ts` updated as described above. Added `src/lib/__tests__/errors.test.ts` (3 cases:
real `Error`, plain-object-with-message, and message-less fallback). `npm test` (111/111), `npm
run typecheck`, `npm run lint`, `npm run build` all clean.

**Closed.**
