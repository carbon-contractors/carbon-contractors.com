# CC-087 — Task content retention and verifiable deletion

Specified by `ADR-0002` D4 and D9. Step 1 of that ADR's handover, and a **prerequisite for the
public privacy claim** in `CC-027` and `/learn` Module 7.

## The retention rule is not calendar-based

"Thirty days" is a round number chosen for convenience, which is exactly what a regulator asks
about. Retention is tied to the last moment the data can still be needed.

| Field | Retained until | Then |
| :-- | :-- | :-- |
| Task description, acceptance spec | terminal state + dispute window closed | deleted |
| Evidence URL / any scratch copy | verdict posted | deleted immediately |
| Verdict breakdown | terminal state + dispute window closed | deleted |
| `specHash`, `evidenceHash`, `verdictHash` | — | retained (not personal data) |
| Wallet, amount, timestamps, outcome | — | already on-chain |

**Terminal state is not "complete".** Deleting on `Completed` alone destroys the record while a
dispute window is still open. The trigger is terminal state (`Completed`, `Expired`, `Resolved`)
**and** every window that could reopen it has closed. A task settling cleanly in three days has its
content gone on day four, not day thirty.

## Why aggressive deletion is safe

`ADR-0002` D5: the chain is the durable record, the DB is a working set. Reputation, strike counts
and the `CC-075` AWOL signal are all derivable from events, so dropping the task row costs nothing.
**Treat any feature that would need durable task content as a design smell** to resolve against the
event log first.

## Three traps that would make the claim false

Per `ADR-0002` D9 — `DELETE` is not deletion:

- **Backups and PITR.** Supabase retains automated backups; rows deleted from the live table persist
  there for the full window. Cleanest fix is to **never write task content to a backed-up table.**
- **Postgres MVCC.** `DELETE` marks tuples dead; data stays in the heap until vacuumed and in the
  WAL until it ages out. Overwrite before deleting, or keep it out of Postgres.
- **Logs.** The most commonly missed one. If task descriptions, specs or evidence URLs reach a log
  line, deleting the row achieves nothing. Tracked on `CC-009`.

**Preferred mechanism:** partition task content by settlement week and drop whole partitions. No
MVCC residue, no vacuum dependency, one DDL statement. Row `DELETE` is the fallback, `DROP TABLE`
is not the intent.

## Deletion must be verifiable

An unverifiable deletion claim has the same shape as an unfalsifiable verdict, which `ADR-0001` D9
rejected. Publish the retention rule, emit a deletion record (task id, timestamp, retention rule
version), make it auditable. `verify-retention` in `CC-085` is the monitor.

## Acceptance

`verify-retention` passes: no task content persists past terminal state plus window. Deletion
records are emitted and auditable. Task content is provably absent from backups.

## Open

From `ADR-0002`: dispute-window duration (sets the retention period); storage target for task
content — unbacked table, separate store, or none; whether any minimal settlement record is needed
independent of the chain.
