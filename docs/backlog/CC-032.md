# CC-032 — Sepolia end-to-end lifecycle test

Section 1 of the MVP definition of done (`docs/Linear-Document-Archive.md`) and the last
functional blocker before mainnet. Nothing here has been proven with a real agent.

## Happy path
Register → discover via MCP → x402 fund → notification fires → deliverable submitted →
`confirm_task_completion` → `completeTask()` on-chain → USDC lands in the worker wallet →
DB flips to completed **only after** the tx succeeds. Measure funded → USDC received;
target under 30 seconds for the on-chain portion.

## Unhappy paths
Task expiry and refund; dispute resolution to both outcomes; double completion reverts;
invalid task ID reverts cleanly; over-release reverts; unauthorised caller rejected.

## Edge cases
Worker changes wallet after funding (payout must follow the on-chain address, not the DB);
on-chain failure mid-flight leaves the DB untouched; concurrent completions do not collide
on signer nonces.

Blocked by CC-002 — discovery and profile lookup are broken until wallet casing is fixed.

## Update 2026-08-11 — backlog triage pass

**Split by lifecycle stage in the 2026-08-11 triage pass.** This issue was too large to
show progress against, and its happy path turned out to be unrunnable anyway (see `CC-080`).

This issue now covers the **Discovery stage only**: register → discover via MCP
(`search_whitepages`, `get_contractor`) → the worker is findable with correct categories, rate
and availability. Registration itself is largely proven already by `CC-069`'s live testing.

The rest moved out, keeping this issue's structure:

- **`CC-077` — Funding stage.** `request_human_work` → x402 payment → `escrow.createTask` →
  notification fires to the worker.
- **`CC-078` — Settlement stage.** Deliverable → `confirm_task_completion` → `completeTask()`
  on-chain → USDC lands in the worker wallet → DB flips to completed only after the tx succeeds.
  Filed `blocked` behind `CC-080`.
- **`CC-079` — Dispute stage.** `dispute_task` → `resolve_dispute` → on-chain resolution to
  both outcomes. Partly proven already by `CC-059`/`CC-065`.

The unhappy paths and edge cases listed above are distributed to whichever stage owns them rather
than kept here.

**On the overlap with `CC-037`:** deliberately keeping both. `CC-037` establishes the fund-safety
invariants by *reading* the current code; these stage issues prove them by *execution*. That is
belt-and-braces on purpose for money paths, not duplicated effort.

Also relevant before running any of it: `CC-070` (P0) breaks the reputation and dispute-recovery
event queries, so results observed through them are unreliable until it lands, and `CC-060` means
`npm test` is not yet trustworthy as corroborating evidence.
