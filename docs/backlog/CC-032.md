# CC-032 — Sepolia end-to-end lifecycle test

## Acceptance

After the 2026-08-11 split, this issue owns the **Discovery stage**: a wallet registers through the
public API, and is then findable through every discovery surface with correct categories, rate and
availability. Concretely:

- [x] A fresh wallet completes a signed registration against the live deployment.
- [x] `search_whitepages` returns it under each registered category, with identical profile data.
- [x] `get_contractor` resolves it by wallet (casing-tolerant) and by UUID, profiles identical.
- [x] The plain HTTP read (`/api/profile`) agrees with MCP on every field.
- [x] Reads answer from the registry, not a cache — an unregistered wallet is refused
      (`CONTRACTOR_NOT_FOUND` / 404).
- [x] Re-registration upserts in place; profile updates propagate to every surface.

Funding, settlement and dispute stages were split to `CC-077`/`CC-078`/`CC-079` and are out of
scope here.

Section 1 of the MVP definition of done (`docs/Linear-Document-Archive.md`) and the last
functional blocker before mainnet. Nothing here has been proven with a real agent.

## Happy path
Register → discover via MCP → x402 fund → notification fires → deliverable submitted →
`confirm_task_completion` → `completeTask()` on-chain → USDC lands in the worker wallet →
DB flips to completed **only after** the tx succeeds. Measure funded → USDC received;
target under 30 seconds for the on-chain portion.

## Unhappy paths
Task expiry and refund; dispute resolution to both outcomes; double completion reverts;
invalid task ID reverts cleanly; over-release reverts; unauthorised caller rejected.

## Edge cases
Worker changes wallet after funding (payout must follow the on-chain address, not the DB);
on-chain failure mid-flight leaves the DB untouched; concurrent completions do not collide
on signer nonces.

Blocked by CC-002 — discovery and profile lookup are broken until wallet casing is fixed.

## Update 2026-09-16 — Discovery stage proven live; systematic harness shipped

Scope confirmed as the Discovery stage only (per the 2026-08-11 split): register → discover via
MCP → worker findable with correct categories, rate and availability. All former blockers closed
(`CC-002` done, `CC-070` done, `CC-060` done).

### Harness

`scripts/lifecycle/discovery-stage.mjs` (+ `discovery-config/cases/args.mjs`, all pure and
unit-tested — 16 new hermetic tests, house style of the CC-077 funding harness). Off-chain by
design: registration is a signed message (server-side verification), MCP read tools need no auth,
no RPC URL and no funded wallet required. `--generate-wallet` mints an ephemeral throwaway EOA per
run; the key never touches disk or logs. Documented in `scripts/lifecycle/README.md`.

### Live results — production deployment (www.carbon-contractors.com)

All three cases PASS on first execution. Target: `/api/health` green, escrow `0xc6aa…E4d3`
(Base Sepolia 84532, the Production deployment — see CC-034's bytecode finding), 2 USDC
totalLocked untouched.

harness was hardened (see below): identical verdicts, confirming runs 1–3's results reproduce.

### Harness hardening (found during independent re-verification)

The first re-verification run FAILed 21/23: late-run MCP reads came back as transport-level
errors (dropped/expired session) with no `.code`, and the failure messages printed
`code (none) error ""` — no diagnostic detail. A manual probe confirmed the server behaved
correctly on both counts (ghost → `CONTRACTOR_NOT_FOUND`; row `offline`), i.e. the harness was
at fault, not the deployment. Fixed: `McpSession.callTool` now re-initialises the session and
retries once on transport-level failures (a dropped session is not a tool verdict), and both
failure messages now dump the actual `__error` payload. Post-fix, all three cases PASS clean.

Proven, per the acceptance scope:

- **Register**: fresh wallet signs `{categories, rate_usdc, nonce, timestamp}` → `200 {ok:true}`,
  wallet echoed normalised lowercase. Re-registration upserts in place (`onConflict wallet`) —
  exactly one row, new values, dropped category stops matching immediately (no cache).
- **search_whitepages**: the new worker appears in BOTH registered categories (`pet-services`,
  `cleaning`), identically in each, with wallet/categories/`rate_usdc` 42.5/availability/
  `reputation_score` 50 (the default).
- **get_contractor by wallet**: mixed-case input resolves (CC-002's normalisation holds); returns
  UUID, full profile, `accepts_auto_booking`.
- **get_contractor by UUID**: identical profile to the wallet lookup.
- **GET /api/profile**: the plain HTTP surface agrees with MCP on every field.
- **PATCH /api/profile** (signed `profile-update`): availability/rate/categories propagate to
  every read surface without re-registration.
- **Negative control**: an unregistered wallet → MCP `CONTRACTOR_NOT_FOUND` + HTTP 404. The reads
  answer from the registry, not a cache.
- **Hygiene**: every run leaves its row `offline` (visible, unbookable). The six throwaway rows
  from the six live passes (all `offline`, categories `pet-services`+`cleaning` / `event-setup` /
  `moving-hauling`) stay in the production whitepages as evidence rows; delete via Supabase if
  the PO prefers them gone.

The `register → discover` loop this ticket was created to prove has now been proven with a real
signed registration and real MCP reads, systematically — three times by the implementing run and
three times by an independent verification run (six total). Funding (`CC-077`),
settlement (`CC-078`) and dispute (`CC-079`) stages follow with their own harnesses/runs.
