# CC-079 — Sepolia lifecycle: Dispute stage

> **Rescoped 2026-08-28 — read the final Update first.** Every section between here and it was
> written against the pre-`CC-082` architecture and describes a flow that no longer exists. It is
> kept for the reasoning, not as instructions. **Do not execute the steps above the rescope.**

Split out of `CC-032` in the 2026-08-11 triage pass. `CC-032` covers Discovery, `CC-077` Funding,
`CC-078` Settlement, this covers Dispute.

## Scope

`dispute_task` → funds stay locked → `resolve_dispute` → `resolveDispute()` on-chain → funds go to
the worker or back to the funding agent.

## What is already proven, and what is not

More of this stage has been exercised than any other, so scope the work to the gaps rather than
starting from scratch.

**Proven, by `CC-059`'s live test on 2026-07-30:**

- `resolveDisputeOnChain` works end to end via the KMS signer against a real disputed task.
- Transaction `0x08cd2e3…` succeeded; the worker's USDC balance moved `0 → 1 USDC`, exactly the
  escrowed amount.
- An independent Basescan read confirmed the sender was the HSM address
  `0xa8931097540e69B474013D294d0bA6A2cC853e4b`, proving the KMS key itself signed, and showed a
  `TaskResolved`-shaped event with `releasedToWorker=1`.
- Contract ownership sits with that HSM address, so `onlyOwner` on `resolveDispute` is satisfied in
  production. (`CLAUDE.md`'s landmine claiming `transferOwnership()` was never called was stale and
  has been corrected.)

**Fixed since, by `CC-065`:** the `resolve_dispute` MCP tool now actually calls
`resolveDisputeOnChain`. Before that it only updated Supabase and told the caller to call the
contract themselves — so the *product* path has only existed since that fix and has not had the
same live exercise the *mechanism* has.

**Not proven:**

- The dispute path through the product, end to end, since `CC-065` landed.
- `dispute_task` itself — raising a dispute, and that funds correctly stay locked.
- Resolution to the **refund** outcome. `CC-059` only tested release-to-worker.
- The partial-failure recovery path in `getTaskResolvedOutcome`, which is broken by `CC-070`.

## Happy paths

1. Either party raises a dispute via `dispute_task`; the on-chain state becomes `Disputed` and funds
   stay locked.
2. `resolve_dispute` releasing to the worker — USDC reaches the worker, DB reflects it.
3. `resolve_dispute` refunding the funding agent — USDC returns to the agent, DB reflects it.

## Unhappy paths

- A non-owner calling `resolveDispute` is rejected. **This is `CC-037` item 4 and matters more than
  its position suggests:** confirm the owner can only direct funds to `task.worker` or back to the
  funding agent, and to no other destination. An owner-directed arbitrary payout would be both a
  security finding and the collapse of the non-custodial argument in `CC-051`.
- Disputing a task that is not in `Funded` state reverts with `InvalidState`.
- Resolving a dispute twice.
- Disputing after expiry.

## Edge cases

- **Partial failure: on-chain resolution succeeds, the DB write fails.**
  `getTaskResolvedOutcome` exists to recover the true outcome from event logs — and it currently
  **throws**, because of `CC-070`. So this edge case cannot be tested until that lands, and it is
  the reason `CC-070` was raised to P0.
- `CC-059` logged a stale read: `getTask()` immediately after the transfer returned `Disputed` once
  more before flipping to `Resolved` on a second read. Confirm whether anything in the product reads
  state in a way that could act on the stale value.

## Acceptance

Both resolution outcomes have been driven through the product's own `resolve_dispute` tool (not a
script) against real disputed tasks on Base Sepolia, `dispute_task` has been exercised, a non-owner
caller is demonstrably rejected, and the partial-failure recovery path has been shown to recover a
real past `TaskResolved` event rather than throwing or silently returning null.

## Before running this

- `CC-070` (P0) — required for the recovery-path edge case, and for reading events back at all.
- `CC-060` — `npm test` not yet trustworthy.

Related: `CC-059` (what is already proven), `CC-065` (why the product path is newer than the
mechanism), `CC-070` (blocks the recovery edge case), `CC-037` item 4, `CC-051`, `CC-032`,
`CC-077`, `CC-078`.

## Blocked 2026-08-11 — behind `CC-081` Defect 2

`CC-037`'s verification found the dispute authorisation is inverted at the app layer, and that the
worker has no dispute right at all:

- `resolve_dispute` (`src/lib/mcp/server.ts:873`) authorises the **originating agent**, not the platform
  owner. So one party to the dispute chooses its outcome, and the platform's `onlyOwner` key executes
  that choice.
- `dispute_task` (`:731`) is **also** agent-only, even though `CarbonEscrow.disputeTask` permits either
  party. The worker cannot raise a dispute through the product.

The contract itself is sound — `resolveDispute` can only pay `task.worker` or `task.agent`, both fixed
on-chain at funding, so no arbitrary destination is reachable.

Two reasons this stage is blocked rather than merely deferred. The dispute **design** is now under
review (`CC-081` Defect 2 holds the options, deliberately undecided), so testing the current behaviour
would validate something expected to change. And it is blocked in practice anyway by `CC-081` Defect 1
— the x402 funding path creates no on-chain task, so there is nothing in `Funded` state to dispute.

Two items in the "Happy paths" list above need rewriting once the design is settled: step 1 assumes
"either party raises a dispute", which the product does not currently allow, and steps 2-3 assume the
resolver is the platform.

The "Unhappy paths" item about a non-owner caller being rejected has effectively been answered already
by `CC-037` item 4 — at the contract level, by reading. It still needs proving by execution.

## Update 2026-08-13 — now also behind `CC-082`, and the test shape changes

`ADR-0001` lists this stage under `blocks:`. It was already `blocked` behind `CC-081`; the contract
rewrite in `CC-082` now sits in front of it too, and changes what this stage tests.

**What changes.** `ADR-0001` D1 adds `submitWork` and a second clock, and Amendment 1 makes
settlement a **worker-initiated pull-payment claim** rather than anything the platform does. So the
paths below need rewriting around: worker submits → review window → agent accepts early *or* the
worker claims after the window. Verdicts are EIP-712 signatures presented at claim time, not
transactions anyone posts.

Do not rewrite the steps yet — wait for the final ABI from `CC-082`, or they get rewritten twice.

**One dependency cleared:** `CC-070` closed on 2026-08-11, so `getTaskResolvedOutcome` and the event
queries now work. `ADR-0001`'s open item flagging that is resolved.

Also relevant: `CC-085`'s invariant monitors are deliberately sequenced **before** this stage, so
that the lifecycle run has instruments capable of telling you it went wrong.

## Rescoped 2026-08-28 — unblocked, and half of this stage deliberately has no product path

Both blockers are closed: `CC-081` Defect 1 (done 2026-08-21) and `CC-082` (done 2026-08-15). But
what this stage tests changed more than the others, twice.

`status: blocked` → `todo`.

### `resolve_dispute` no longer exists

`CC-065` made the MCP tool actually call the chain; **PR #146 removed the tool outright** under
`ADR-0001` D2. It authorised `task.from_agent_wallet` — the hiring agent — and executed that ruling
with the platform's owner key, so `onlyOwner` was notarising one interested party's decision while
the worker had no adjudicator.

**So this ticket's old Acceptance is now unmeetable by design.** It asked for both outcomes *"driven
through the product's own `resolve_dispute` tool (not a script)"*. There is no such tool and there
must not be one until `ADR-0007`'s adjudication tier exists.

The stage splits in two:

| Half | Surface |
| :-- | :-- |
| **Raising** a dispute | the product — either party, `dispute_task` / `POST /api/dispute` |
| **Resolving** one | **owner-only**, `scripts/admin/verify-escrow-lifecycle.ts` with the KMS key |

### Raising requires a signed failing verdict

There is **no bare-assertion dispute**. `disputeTask` accepts nothing else, because a bare call would
let an agent block the worker's claim and thereby hold both outcomes again. So:

1. Either party obtains a signed failing verdict — `POST /api/verdict` or `get_signed_verdict`,
   against the evidence bundle.
2. That party presents it from **their own wallet**: `escrow.disputeTask(taskId, verdict, signature)`.
3. It must land **before the review window closes**. `disputeTask` and `releaseAfterReview` are exact
   complements — precisely one is available at any timestamp.

### Happy paths

1. **The worker** raises a dispute. Newly possible: the contract always permitted either party and
   the product now does too.
2. The agent raises one, with a failing verdict over the worker's committed evidence.
3. Owner resolves **to the worker** via the admin script — USDC reaches the worker.
4. Owner resolves **as a refund** — USDC returns to the agent. `CC-059` only ever tested
   release-to-worker; the refund outcome is still unproven.

### Unhappy paths

- A non-owner calling `resolveDispute` is rejected (`CC-037` item 4). **Confirm the owner can direct
  funds only to `task.worker` or `task.agent`, both fixed at funding, and to no other destination.**
  An arbitrary payout would be a security finding *and* the collapse of the `CC-051` non-custodial
  argument.
- Disputing with a **passing** verdict reverts `VerdictResultMismatch`.
- Disputing **after** the review window closes reverts `ReviewWindowClosed`.
- Disputing from a wallet that is neither party reverts `NotParty`.
- Resolving twice reverts.
- A replayed verdict nonce reverts `VerdictNonceAlreadyUsed`.

### ~~What cannot be tested on Sepolia~~ — superseded 2026-09-01

*This section said the arbitration timeout was not in the deployed bytecode and belonged to
`CC-034`. That was true of `0xe80d…B1b1`. It is no longer true of anything.*

**The clock is live on Sepolia.** The 2026-09-01 redeploy to
`0xc6aa99a8226b679C71945dd9545685896a91E4d3` is the first deployment anywhere carrying it —
`ARBITRATION_WINDOW` reads `604800s` on chain and the `releaseAfterArbitration` selector is present
in the bytecode, both confirmed by `verify-escrow-deployment.mjs`.

So the timeout **is** in scope here now, and it is the most valuable thing this stage can prove:
that an owner who never rules cannot hold the escrow. That property was the entire reason `ADR-0006`
was written.

**The one real constraint is wall-clock.** Seven days, and a live chain cannot be fast-forwarded. So
the run is a split pair, the same shape as `submit`/`claim`:

| | |
| :-- | :-- |
| `arbitration-hold` | raise the dispute, write state, **and then nobody does anything** |
| `arbitration-claim` | seven days later, the worker calls `releaseAfterArbitration` |

The contract tests already cover the boundary in both directions and are mutation-tested — including
the case Amendment 1 exists for, *a dispute where `beginArbitration` is never called still times
out*. What the live pair adds is the same property against real bytecode, real gas, and a real week.

### Edge cases

- Partial failure: on-chain resolution succeeds, the DB write fails. `getTaskResolvedOutcome`
  recovers the true outcome from `TaskResolved` — now working, since `CC-070` closed.
- `CC-059` logged a stale read: `getTask()` immediately after the transfer returned `Disputed` once
  before flipping to `Resolved`. Confirm nothing acts on the stale value.

### Running it

`scripts/admin/verify-escrow-lifecycle.ts` gained four phases on 2026-09-01 covering exactly the
gaps below. Each is one run except the arbitration pair:

```
dispute             agent raises, owner releases to worker   (CC-059 proof, unchanged)
dispute-by-worker   the WORKER raises it
dispute-refund      owner REFUNDS the agent
arbitration-hold    raise, then stop — nobody rules
arbitration-claim   7 days later, the worker claims by default
```

`dispute-refund` asserts the agent's USDC balance actually increased, and throws if it did not —
a resolve that "succeeds" while moving nothing is the failure worth catching.

### Acceptance

- [ ] **The worker** raises a dispute through the product, with a signed failing verdict.
      *(The admin script's `dispute-by-worker` proves the contract path; the product path through
      `POST /api/dispute` is the separate half.)*
- [ ] The agent raises one.
- [ ] Owner resolves to the worker, via the admin script.
- [ ] Owner resolves as a **refund** — the outcome `CC-059` never covered.
- [ ] **An unruled dispute times out to the worker** — `arbitration-hold`, seven days, then
      `arbitration-claim`. Newly possible; no deployment had the clock before 2026-09-01.
- [ ] A non-owner `resolveDispute` is demonstrably rejected, and no destination other than the two
      fixed at funding is reachable.
- [ ] `getTaskResolvedOutcome` recovers a real past `TaskResolved` event rather than throwing.
- [ ] `verify-escrow-solvency.mjs` reconciles after both outcomes.

**Not in scope, deliberately:** any MCP or app surface for resolution. If one appears, it authorises
an arbitrator — never a party to the task.

ARBITRATION_WINDOW  604800s

### What is already proven by the hold alone

**The clock started at `disputeTask`, and `beginArbitration` was never called.** The state is
`Disputed` (4), not `Arbitrating` (5), and `arbitrationDeadline` is nonetheless seven days out.

That is `ADR-0006` **A1.1** demonstrated on a live chain. D3 as originally accepted started the clock
at `beginArbitration`, which is `onlyOwner` and optional — so an owner who simply never called it
never started a clock, and the task sat `Disputed` with the escrow held indefinitely. The contract
tests cover this; what this adds is that the deployed bytecode does it too.

Also confirmed: `disputedAt + ARBITRATION_WINDOW == arbitrationDeadline` exactly, so the window is
the contract constant and not something the deadline was set to independently (`A1.2`).

### What the wait proves, and what must not happen during it

The remaining claim is that **an owner who never rules cannot hold the escrow**. Three things would
void it:

- **Anyone resolving the dispute.** The point is that nobody does.
- **Losing `.escrow-lifecycle-state.json`.** It holds the only key that can call
  `releaseAfterArbitration` on this task. Lose it and the 1 USDC is unclaimable — harmless on
  testnet, but the run is void.
- **Reading a red monitor as a defect.** `verify-unclaimed` now watches this exact case. From
  2026-09-08 it will report one arbitration timed out and claimable; from **2026-09-11** that becomes
  a breach, because the threshold is three days past claimable. That is the monitor working — and it
  is the first time that check has had anything real to detect.
