# CC-010 — Brand-new worker sees a reputation score of 0 and is told to go register

## Problem
Two bad first impressions immediately after signup:

1. `src/lib/reputation/compute.ts:44-64` returns 0 across every component for a worker with
   zero tasks and zero stake, so the dashboard renders a large "**0** Reputation"
   (`src/app/dashboard/page.tsx:299-341`). Meanwhile `src/app/api/register/route.ts:139`
   wrote `reputation_score: 50` to the DB, so the number shown contradicts the number stored
   — and MCP search ranks on the stored column (`src/lib/db/whitepages.ts:31`).

2. The zero-task empty state (`src/app/dashboard/page.tsx:445-454`) says "Make sure you've
   registered your services" and links back to `/connect` — which the user completed two
   seconds earlier (`src/app/connect/page.tsx:25`).

## Fix
- Render a "New — no history yet" state instead of a bare 0.
- Reconcile the seeded 50 against the computed score; pick one source of truth and document it.
- Branch the empty state on whether a profile exists: if it does, say "You're listed —
  agents can now find you. No tasks yet."

## Acceptance
A freshly registered worker sees a dashboard that reads as success, not failure.

## Update 2026-08-11 — backlog triage pass

Reviewed in the triage pass — **stays P1** — with one correction to how this issue frames
itself. It reads as a first-impressions/UX problem. Verified, the more serious half is a
data-integrity problem:

- `src/app/api/register/route.ts:182` writes `reputation_score: 50` on registration.
- `src/lib/reputation/compute.ts` returns 0 across every component for a worker with no tasks and
  no stake, and that computed 0 is what the dashboard renders.
- `src/lib/db/whitepages.ts:31` (and `:112`) **order MCP search results by the stored
  `reputation_score` column** — the 50, not the computed 0.

So two different reputation numbers exist simultaneously, and agents rank workers on the one the
worker cannot see. That is the part to settle first: pick one source of truth and document it. The
empty-state copy fixes are worth doing but are genuinely cosmetic by comparison.

Note the current effect is benign — every registered worker holds the same seeded 50, so nothing is
mis-ordered relative to anything else yet. It starts mattering the moment computed scores diverge,
which is the moment the first task completes.

## Done 2026-08-21 — fixed on `feat/cc-010-011-017-dashboard-onboarding-and-seed`

`src/app/dashboard/page.tsx` + `src/lib/reputation/compute.ts`:

- **"New" state instead of a bare 0.** New helper `isNewWorker({ totalTasks, stakeAmountUsdc })` in
  `compute.ts` — a worker is new until they have a task *or* a stake (a staked no-task worker earns
  the floor score, so they are not "new"). The dashboard renders a "New Reputation" state with
  "No history yet — your score builds as you complete tasks." instead of the big zero, and hides the
  all-zero breakdown grid and "0 completed / 0 USDC earned" stats for that case. A worker with
  history that genuinely scores 0 (all tasks expired/disputed) still sees the number — that is a
  score, not an empty state, and the tests pin the distinction.
- **Empty task state branches on profile.** A registered worker with no tasks now sees "You're
  listed — agents can now find and hire you. No tasks yet." The register-again prompt with the
  `/connect` link only shows when no profile exists.
- **Source of truth — settled and documented.** The computed score (`/api/reputation`) is the only
  reputation number the worker is ever shown; documented on `isNewWorker`. The `reputation_score: 50`
  the register route writes is an MCP *search-ranking seed*, not a display value. That column is
  write-once at registration today (nothing recomputes it after task completion), so ranking vs
  computed score *will* diverge once the first task completes — that re-sync is a backend concern
  this frontend issue deliberately does not smuggle in. It belongs with the ranking path
  (`src/lib/db/whitepages.ts`) and should be checked against the `CC-014` pre-flip checklist.

Tests: `isNewWorker` cases added to `src/lib/__tests__/reputation-compute.test.ts`, including the
boundary where a genuine 0 score must not read as "new".
