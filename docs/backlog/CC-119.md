# CC-119 — A lapsed task has no refund path

Raised by Aaron 2026-10-13 after a Sepolia test task, funded 2026-09-01, passed its delivery
deadline with no work submitted. The deadline did its job — the worker was locked out — but the
agent's 1 USDC was never refunded and no part of the product could have refunded it.

## What happened

`CarbonEscrow.expireTask(taskId)` (`contracts/CarbonEscrow.sol`, ~l.625) is `Funded`-only,
agent-only (`NotAgent`), and reverts `NotExpired` before the deadline. When it succeeds it
**pays out in the same transaction**: `Funded → Expired`, `totalLocked -= amount`, USDC to
`task.agent`. So the refund is a push the agent must trigger, not a balance it can claim later
(CLAUDE.md and `ADR-0001` A1.2 call it a pull-payment; the effect is the same but the mechanism is
one call, not two).

Consequences, each observed or read from code, not inferred:

- **The agent has no way to reclaim.** No MCP tool, no dashboard action, no API route calls
  `expireTask`. The platform signer can't either (`NotAgent`), which is correct (`CC-080`,
  `ADR-0001` A1.2). `expireTaskOnChain` in `src/lib/contracts/signer.ts` is dead code that can
  never succeed.
- **The DB never learns the task lapsed.** The row stayed `active` while the chain sat `Funded`
  past its deadline. `settlement-sync` only advances a row from a chain state change, and none
  happened.
- **The worker sees a live task they can't act on.** The dashboard's Submit gate checks
  `on_chain.state === "Funded"` only (`src/app/dashboard/page.tsx` ~l.2375), never the deadline,
  so after lapse it should still offer Submit, which then reverts. No explanation is shown.
- **The monitor reports it as INFO and moves on.** `verify-unclaimed.mjs` lists "Funded past the
  delivery deadline" but does not assert on it (`CC-085` specifies the worker case only).
- **Nothing alerts the agent.** An autonomous hiring agent whose worker went silent has USDC locked
  and no signal that it can act. This is the `NOR-333` question — *does this make an agent trust the
  pool less?* — answered badly.

## Things to decide (design first — `ADR`, not a guess)

1. **Surface for the agent.** Keep it agent-signed (the platform must never push funds; `CC-037`,
   `CC-051`). Options: an MCP tool that returns ready-to-sign `expireTask` calldata plus the
   preconditions; an agent-facing dashboard view; or both. An agent running without a UI needs the
   MCP form.
2. **Contract change?** `expireTask` pays `task.agent` whoever calls it, and the original reason it
   was restricted (a delivered task refunded out from under the worker) is now prevented by the
   `Funded`-only guard. Letting *anyone* trigger it would let the platform or a keeper do it
   without custody, at the cost of a redeploy: a one-way door (`docs/runbooks/ESCROW-REDEPLOY.md`),
   an ADR amendment and a new `ESCROW_DEPLOY_BLOCK`. Needs a view on whether that is worth it
   before mainnet, where redeploying is not free.
3. **Notification.** When a task passes its deadline `Funded`, who is told, and over what channel?
   The agent has no notification address on file; `ADR-0004`/`ADR-0002` limit what can be stored.
4. **DB state.** What does the row say between "deadline passed" and "agent called `expireTask`"?
   An `expired`-pending status derived from chain time, or leave `active` and fix the UI? Check
   `src/lib/db/tasks.ts` and `CC-080`'s chain-derived status rule before adding a state.
5. **Worker UX.** Hide Submit and say why once the deadline passes; make `accept`/`submit` failures
   at the deadline readable (`reverts.ts`).
6. **Monitor.** Promote "Funded past deadline" from INFO to an assertion once there is a baseline
   for what normal agent latency is — and decide whether the agent-side threshold differs from the
   worker's 3 days (`ADR-0003`).
7. **Dead code.** Remove `expireTaskOnChain` and its tests along with `CC-081` Defect 1, per
   `CLAUDE.md`.

## Immediate unblocker

`scripts/admin/expire-task.ts` (added with this ticket): dry run by default, `CONFIRM=true` sends
`expireTask` from `DEPLOYER_PRIVATE_KEY`, which is the test agent. Running it on the lapsed task is
what closes the `CC-077` line "`expireTask` refunds the agent". It is a test aid, not a product
surface, and does not address any decision above.

## Update 2026-10-13 — worker-side items fixed, awaiting a browser check

Aaron's screenshot from the worker view confirmed the gap: task `Funded` with deadline 2026-09-02,
Submit offered, and `submitWork` failing with a bare "The contract function reverted". Two causes:

- The Submit gate checked `state === "Funded"` and never the deadline. It now also requires
  `nowSec < deadline`, and a lapsed `Funded` task shows a note instead.
- The dashboard's write calls used hand-written ABI fragments with no `error` entries, so viem
  could not decode a custom revert. Every dashboard write failure read as a generic "reverted",
  not just this one. All five (`submitWork`, `releaseAfterReview`, `releaseAfterArbitration`,
  `claimWithVerdict`, `disputeTask`) now use the generated `CARBON_ESCROW_ABI`, so
  `reverts.ts`'s existing `DeadlinePassed` / `InvalidState` text can apply.

Typecheck, lint and `npm test` (1051) pass. The "worker dashboard does not offer Submit past the
deadline" box stays unticked until it is seen in a browser. Items 1–4 and 6 are still open.

## Update 2026-10-13 — agent-side Reclaim button on the dashboard

Aaron confirmed the worker lapse notice is live, and that the agent wallet still had nothing to
click. The dashboard now shows the funding agent a **"Reclaim funds (deadline passed)"** button on
a `Funded` task past its deadline, which sends `expireTask` from the agent's own wallet. "Agent"
is read from the contract (`on_chain.agent`), falling back to the DB column only if the chain read
failed (`CC-037`). The platform still has no path to it, by design.

This is the minimum surface for the dashboard only. Still open: an MCP form for agents that have
no UI (item 1), the contract-trigger question (item 2), notification (item 3), the DB status
(item 4) and the monitor (item 6). Typecheck, lint and `npm test` (1051) pass; the two acceptance
boxes it affects stay unticked until the button has been used in a browser. The Sepolia task can be
refunded either through it or with `scripts/admin/expire-task.ts`.

## Update 2026-10-13 — refund confirmed; the DB row did not follow

Aaron reclaimed the 1 USDC from the buyer wallet through the dashboard button, which closes the
`CC-077` expiry line in practice. Afterwards the task's `tasks` row (`payment_request_id`
`70b425f5…`) was still `status: active` with `updated_at` 2026-09-01 — nothing moved it. So the
"DB status matches the chain" box is not just untested, it is observed failing: after a successful
`expireTask` the app still lists a refunded task as active. `CC-080`'s chain-derived status rule
should cover `Expired`; check why `settlement-sync` did not.

Ticked: the refund and the worker lapse notice. Left open on purpose: solvency after the refund
(not run — this session cannot reach the chain), the design decisions, an agent with no UI, DB
status, and the monitor.

## Update 2026-10-19 — the DB row did follow; MCP reclaim hint; ADR-0015

- **The "DB row did not follow" finding was lag, not a defect.** Read live from Supabase: task
  `70b425f5…` is `expired`, `updated_at` 2026-10-13 09:23:25 UTC. That is exactly the
  `settlement-sync` cron slot (`23 * * * *`, `vercel.json`) after the refund. The row was checked
  before the cron's next run. The worst case is about an hour of lag, accepted in `ADR-0015` D4.
- **Item 1, the MCP form.** `get_task_status` returns a `reclaim` object when the chain reads
  `Funded` and `now >= deadline`. It carries the escrow address, `expireTask(bytes32)`, the bytes32
  task id and `callable_by` (the on-chain agent). It is omitted before the deadline, once the task
  is Delivered, and when the chain read fails. Tests are in `mcp-error-semantics.test.ts`.
- **Item 7, dead code.** `expireTaskOnChain` was removed from `signer.ts`. Its tests were retargeted
  at `resolveDisputeOnChain`, and a test pins the removal.
- **Items 2–4 are proposed in `ADR-0015`:**
  - no contract change;
  - no stored agent notification;
  - no new DB status.

  Aaron to accept or veto.

Still open: item 6, the `verify-unclaimed` assertion, which needs an agent-latency baseline. Also
