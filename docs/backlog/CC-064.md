# CC-064 — Every Hardhat script is currently broken — Hardhat 3 requires ESM, this repo is CJS

## Problem

Discovered while dry-running a new script for `CC-059`. Any Hardhat invocation fails immediately:

```
npx hardhat run scripts/deploy/escrow.ts --network baseSepolia
```
```
Hardhat only supports ESM projects.

Please make sure you have "type": "module" in your package.json.
```

Reproduced with an *existing* script (`scripts/deploy/escrow.ts`), not just the new one — this is
not something introduced today. `package.json` resolves `hardhat` via `^3.2.0`, which is currently
sitting at `3.12.0` (`npm ls hardhat`). Hardhat 3 dropped CommonJS project support entirely; this
repo has no `"type": "module"` in `package.json` (defaults to CJS), and `tsconfig.hardhat.json`
explicitly targets `"module": "commonjs"`.

So right now: `npm run compile`, `npm run deploy:sepolia`, `npm run deploy:reputation`, the new
`npm run transfer:ownership` (`CC-059`), and any Hardhat test all fail identically. Nobody has run
a Hardhat script recently enough to have noticed — same pattern as `Lessons-Learned.md`'s repeated
theme of "it works because it was never re-run."

## Why the obvious fix isn't simple

Downgrading `hardhat` to a 2.x CJS-compatible version is not a clean option:
`hardhat-deploy@2.0.3`'s own `package.json` declares `"peerDependencies": { "hardhat": "^3.1.8" }` —
this repo's *other* Hardhat dependency was chosen assuming Hardhat 3. So the fix is the ESM
migration Hardhat's own error message points to, not a downgrade.

## Fix

1. Add `"type": "module"` to `package.json`.
2. Update `tsconfig.hardhat.json` to an ESM-compatible module setting (`"module": "esnext"` or
   `"nodenext"`, matching what Hardhat 3's own ESM-first tooling expects) and verify `hardhat.config.ts`
   still loads under it.
3. Re-check every other toolchain piece that reads `package.json`'s `type` field or assumes CJS:
   `vitest`, `tsx` (`npm run seed`, `npm run verify:kms`), `cross-env`. Next.js's own bundler is
   independent of this field and should be unaffected, but confirm with a full `npm run build`
   after the change, not just typecheck.
4. Re-run `npm run compile`, `npm run deploy:sepolia` (dry — or at least far enough to confirm the
   ESM error is gone before it needs a signer), and the new `npm run transfer:ownership` (dry run,
   no `--confirm`) to confirm all three actually execute now.

## Acceptance

`npx hardhat run scripts/deploy/escrow.ts --network baseSepolia` gets past the ESM check (fails
later for an unrelated, expected reason like a missing env var — not this error). `npm run build`
and `npx vitest run` still pass after the `"type": "module"` change.

Blocks the practical execution of `CC-059`'s ownership-transfer script (which was written and its
address-derivation logic independently verified, but could not be dry-run through the actual
Hardhat CLI because of this). Related: `CC-059`.

---

## Resolution

The fix was bigger than "flip `type: module`" — Hardhat 3 also changed the plugin architecture and
the ethers access pattern, and the toolbox package this repo depended on was itself a deprecated
stub. In order:

**1. `"type": "module"` added to `package.json`.** Checked first for anything that would break:
no plain `.js`/`.cjs` config files anywhere in the repo (`eslint.config.mjs`, `vitest.config.ts`,
`next.config.ts` all have explicit extensions or their own loaders, unaffected either way).

**2. `@nomicfoundation/hardhat-toolbox` (`^7.0.0`) was a dead stub, not a real Hardhat 3 package.**
Its own `package.json` `homepage` pointed at a `deprecated-versions` branch, and installing it
printed "does not work with Hardhat 2 nor 3." Confirmed via the official migration guide
(`hardhat.org/migrate-from-hardhat2`) and the real `packages/hardhat/templates/02-mocha-ethers`
template in `NomicFoundation/hardhat` (fetched directly — the docs site's own examples were
incomplete) that the ethers-based replacement is `@nomicfoundation/hardhat-toolbox-mocha-ethers`,
config now goes through `defineConfig()`, and secrets are wrapped in `configVariable("ENV_VAR")`
(still reads from `process.env` under the hood — verified against the SDK's own test fixtures —
so the existing `.env.local` + `dotenv.config()` setup needed no changes).

**3. `hardhat.config.ts` rewritten**: `defineConfig({ plugins: [...] })` instead of a side-effect
import; `solidity.profiles.default` instead of a flat `solidity` block; each network needs an
explicit `type` (`"http"` for real RPC, `"edr-simulated"` for local) and `chainType` — Base is an
OP-stack chain, so `"op"` (confirmed against Hardhat's own `ChainType` union in
`packages/hardhat/src/types/network.ts`).

**4. All three scripts using `import { ethers } from "hardhat"` no longer worked** — Hardhat 3 has
no such export. Rewrote `scripts/admin/transfer-escrow-ownership.ts`, `scripts/deploy/escrow.ts`,
and `scripts/deploy/reputation-stake.ts` to use `const { ethers } = await network.create();`
(connects using whatever `--network` flag was already passed on the CLI — verified this against
the network-manager's own source, not assumed) inside `main()`, and switched the deploy scripts
from `getContractFactory().deploy()` to the simpler `ethers.deployContract(name, args)`. Also had
to swap `__dirname` for `dirname(fileURLToPath(import.meta.url))` in the new script — no
`__dirname` global under ESM.

**5. Found `@nomicfoundation/hardhat-toolbox-mocha-ethers` itself pulled in an unfixable
vulnerability** — `elliptic` (GHSA-848j-6mx2-7j84), already at its latest release with no patched
version available, via the toolbox's bundled `hardhat-verify` → legacy ethers-v5
`@ethersproject/*` chain. Neither `hardhat-verify` (contract-explorer verification) nor
`hardhat-ignition`/`hardhat-ignition-ethers` (declarative deployments) are used anywhere in this
repo, and they're separable peer dependencies of the toolbox, not baked in — replaced the toolbox
meta-package with the six individual plugins actually needed
(`hardhat-ethers`, `hardhat-ethers-chai-matchers`, `hardhat-mocha`, `hardhat-network-helpers`,
`hardhat-typechain`, `hardhat-keystore`), which drops the vulnerable subtree entirely. Two
remaining findings (`diff`, `serialize-javascript`, both via `mocha`) had real fixed versions
available and went into `overrides`, same pattern as `CC-061`. **Net: 14 → 0 vulnerabilities**, not
just "no new ones."

**6. `tsconfig.hardhat.json` and the `cross-env TS_NODE_PROJECT=...` wrapper on every Hardhat npm
script were vestigial** — Hardhat 3 bundles its own `tsx@^4.23.1` internally rather than using
`ts-node`, and empirically ignores that env var entirely (confirmed: removing the wrapper from a
script changed nothing). Deleted `tsconfig.hardhat.json`, removed the `cross-env` wrapper from all
four Hardhat npm scripts, and removed the now-unused `cross-env` dependency.

**7. Side effect caught by a full lint pass, not just typecheck**: `hardhat-typechain`'s default
output moved from the old `typechain-types/` to `types/ethers-contracts/`, and Hardhat 3's new
`artifacts/**/*.d.ts` build output tripped `@typescript-eslint/no-empty-object-type` (4 real lint
errors, not warnings) because neither new generated path was in `eslint.config.mjs`'s
`globalIgnores`. Added `artifacts/**`, `cache/**`, `types/ethers-contracts/**` alongside the
existing `typechain-types/**`, and the matching `.gitignore` entry.

**Verified, not assumed working:**
- `npm run compile` — succeeds
- Both deploy scripts, run for real against Hardhat's local `edr-simulated` network (not
  `baseSepolia` — a real deploy would create throwaway duplicate contracts nobody asked for) —
  deploy, verify state, and print correctly
- `npm run transfer:ownership` (`CC-059`'s script), dry run against the **real** `baseSepolia` —
  reads both contracts' actual `owner()`, correctly reports the same FAIL state `CC-059` already
  documented, sends zero transactions
- `npm run typecheck`, `npm run lint` (0 errors — down from 4, and the ~30 stale
  `typechain-types` warnings are gone too), `npx vitest run` (96/96), `npm run build` — all clean
- `npm run verify:kms` — still loads and reaches its expected `GCP_KMS_KEY_PATH` guard correctly
  under `"type": "module"`, no module-system error

Not done, deliberately: did not attempt a live `--confirm` run of the transfer-ownership script
against real infrastructure — `CC-059`'s own gating (confirm KMS signing works first, then Aaron's
explicit go-ahead) still applies untouched.
