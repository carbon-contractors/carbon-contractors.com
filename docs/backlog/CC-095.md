# CC-095 — Notification delivery

## Problem

**Nothing in `src/` sends a notification.** `grep -rn "notify\|sendNotification" src/` returns
nothing. Workers can register email, webhook, Telegram or Discord channels via
`register_notification_channel`; the rows are written to `notification_channels` and are never read
for the purpose of delivering anything. `getChannelsForContractor` is used only to display a
worker's own channels back to them (`src/lib/mcp/server.ts:584`).

So a worker learns they have been hired by loading the dashboard and noticing a new row.

**Two published claims already assert this works:**

- `src/lib/payments/x402.ts:106` — the instructions returned to every hiring agent state, as step 3,
  *"On success, task moves to `active` and the worker is notified."*
- `/learn` module 5 — *"you're notified and decide yourself."*

Neither is an `ADR-0004` forward-looking-copy case in the ordinary sense. The first is a runtime API
response telling an agent that something happened; the second describes a control the worker is told
they hold. Both go on `CC-014`'s pre-flip checklist until this ships.

## Why P0

`ADR-0005` D7 makes this a dependency rather than a feature: it **blocks `CC-094`**. An offer nobody
is told about is an expiry with extra steps — and worse than the status quo, because the worker is
then being timed against a clock they cannot see.

It also makes `CC-032`/`CC-077`'s lifecycle step *"notification fires to the worker"* currently
untestable.

## Scope

- **Delivery for the four registered channel types** — email, webhook, Telegram, Discord.
  `feedback: no phone/SMS channel.`
- **The events worth sending**, at minimum: offer received (`CC-094`), offer about to expire,
  task funded, verdict signed, payment claimable. The claimable one matters more than it looks —
  settlement is pull-payment (`ADR-0001` A1.2), so a worker who is not told has money sitting
  unclaimed, which is what `CC-085`'s `verify-unclaimed` monitors and what looks like theft from the
  worker's side.
- **Retry and failure semantics.** A webhook that 500s must not silently drop the only signal a
  worker gets. Failure to deliver needs to be visible — note `ADR-0003`'s "alert on absence"
  reasoning applies here too.
- **No PII in logs.** `maskMeta` masks wallet addresses, not emails (`CC-009`), and a notification
  path handles email addresses by definition. This is the single most likely way to leak them.
- **Retention.** A notification payload containing task content is task content — `ADR-0002` D4 and
  `ADR-0001` Amendment 2 A2.1. Do not build a durable outbox that outlives the task row, or the
  retention claim becomes false via the queue.

## Acceptance

- A worker with a registered channel receives a message on each in-scope event.
- Delivery failure is retried, and a permanent failure is visible rather than silent.
- No email address or task payload appears in any log line.
- No durable store of notification content survives the task's own retention window.
- `CC-032`/`CC-077`'s "notification fires to the worker" step becomes executable.

## Open

- Transport for email. There is no mail provider in the stack today, and adding one is the first
  third-party data processor in the architecture — it needs an `ADR-0002` read before it is chosen.
  → **Partially resolved 2026-08-22:** shipped behind a pluggable `EmailTransport` whose default is a
  signed JSON POST to `NOTIFICATION_EMAIL_WEBHOOK_URL` (an operator-configured gateway). Choosing a
  real provider remains open and still needs the `ADR-0002` read.
- Whether notification delivery runs inline or on a queue, given Vercel's execution model.
  → **Resolved for v1 2026-08-22:** inline, in-request, no durable outbox — so nothing containing task
  content outlives the task row (retention scope above). Bounded retries (3 attempts, exponential
  backoff) keep a dead webhook from spending the function's whole wall-clock budget.
- Whether an undeliverable channel should eventually disable auto-booking (`CC-075` territory).

## Progress

2026-08-22 — delivery engine shipped (`src/lib/notifications/`, this branch): adapters for all four
channel types, all five in-scope events, `notifyContractor()` resolving a worker by wallet or UUID
and dispatching to their registered channels in parallel; bounded-backoff retry over 5xx/429/timeout/
network faults with outcomes logged (exhausted retries at error level, per `ADR-0003` reasoning);
channel addresses appear in logs only as sha256 handles and payloads/task content never appear at
all. 19 unit tests in `src/lib/__tests__/notifications-delivery.test.ts`.

**Still open on this ticket before it can be `done`:** nothing calls `notifyContractor` yet — wiring
it into the lifecycle events (`CC-094`'s offer path, the funding path, verdict/claim settlement) is
the remaining acceptance work, and until then the two published claims stay on `CC-014`'s pre-flip
checklist.
