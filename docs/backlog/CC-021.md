# CC-021 — Workers cannot edit their profile or mark themselves unavailable

`availability` is hard-coded to `"available"` at `src/app/api/register/route.ts:138`, and the
only way to change categories or rate is to re-sign the entire registration at `/connect`.

A worker who is busy, on leave, or has changed their rate has no recourse — and agents will
keep matching them. Expect complaints within the first week of real signups.

Fix: add an availability toggle and profile edit on the dashboard, signature-authenticated
against the profile's own wallet.

---

## Update 2026-07-30 — hidden prerequisite

The obvious implementation is client-side: let the worker update their own row under the
`humans_update_self` RLS policy from migration 005. **That will not work.**

Those policies key off `current_setting('request.jwt.claims')::json->>'wallet_address'`, and
nothing in the codebase mints a Supabase JWT carrying that claim — the app authenticates by
wallet signature, not Supabase Auth. Migration 005 says so explicitly in its own header:
*"these policies are dormant — no authenticated sessions exist yet."* Confirmed against the live
database: the policies exist and match nothing.

So the real RLS posture is: anon cannot write, and every server-side write uses `service_role`,
which bypasses RLS entirely. That fails closed, which is correct — but it means RLS is doing
less work than the migration names imply, and there is no client-side write path at all.

### Two options
**(a) Server-side, signature-authenticated — recommended.** A `PATCH /api/profile` that verifies
a wallet signature exactly as `/api/register` does, then writes with the service role. Reuses a
proven pattern, needs no new auth infrastructure, and keeps the JWT question deferred.

**(b) Wire wallet-based Supabase Auth.** Mint a JWT with a `wallet_address` claim after
signature verification, which activates the dormant policies from 005 and enables direct
client-side writes. Architecturally cleaner and it makes RLS mean something. Materially more
work, and it introduces session management that does not currently exist.

Take (a) for this issue. Log (b) separately if the RLS layer should ever carry real weight —
worth noting that the audit narrative in `AUDIT-2026-03-25.md` reads as though it already does.

## Update 2026-08-11 — backlog triage pass

Raised P2 → **P1**. Verified `availability: "available"` is still hardcoded at
`src/app/api/register/route.ts:181`.

Reason for the raise: this gets materially worse alongside `CC-074`. Once auto-booking is a real,
reachable toggle, a worker on legitimate leave who cannot mark themselves unavailable keeps getting
committed to jobs by agents. The two issues compound, so this should not sit behind the auto-booking
work.

Take option (a) from the 2026-07-30 update — server-side signature-authenticated `PATCH
/api/profile`. Option (b) is not available without new auth infrastructure, because migration 005's
policies are dormant (nothing mints a Supabase JWT carrying a `wallet_address` claim).

## Done 2026-08-21 — option (a) implemented

`PATCH /api/profile` (`src/app/api/profile/route.ts`, alongside the existing GET) verifies a
wallet signature with the same ERC-6492/1271-aware `verifyWalletSignature` helper as
`/api/register`, then writes with the service role. The signed message is JSON with
`action: "profile-update"`, the wallet, a timestamp (5-minute window), and the fields being
changed — the `action` binding stops a registration signature being replayed here, and the
embedded wallet must match the request wallet. Only the three editable fields are accepted:
`availability` (available/busy/offline), `rate_usdc` (positive, ≤ 10,000, ≤ 2 decimals), and
`categories` (same min-1/max-2 validation as registration). Unknown wallet → 404.

Dashboard (`src/app/dashboard/page.tsx`): availability segmented toggle (one click signs and
PATCHes), and an "Edit profile" form for rate + categories that signs via wagmi
`useSignMessage` and PATCHes on save. Client-side validation mirrors the server's.

Tests: `src/lib/__tests__/profile-route.test.ts` (24 cases — auth, signature, replay,
validation, success, 404). Full suite, typecheck, lint and build pass.

No migration needed — the fields already exist on `humans`; nothing new is world-readable
beyond what the whitepages already exposes.
