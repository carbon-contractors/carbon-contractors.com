# CC-005 — No contact capture at signup — workers cannot be told they have been hired

## Problem
`src/app/connect/page.tsx:37-73` captures wallet, categories and hourly rate only.
There is no notification-channel UI anywhere in the app.

The only way to register a contact method is the MCP tool `register_notification_channel`,
which requires a `contractor_id` UUID the worker has no way to obtain.

Net result: a registry of wallets that cannot be contacted, and workers who will never find
out an agent hired them. That breaks the core loop and makes promotion pointless — signups
will churn immediately.

## Fix
Add an optional email (and/or Telegram/webhook) field to `/connect`. Write it server-side
with the service role into `notification_channels`, keyed off the newly created human row.
Treat it as PII: never echo it back in any API or MCP response (see AUD-004/AUD-007).

## Acceptance
A worker can register a contact method during signup, and it lands in `notification_channels`.

## Resolution

Added an optional "Contact Email" field to `/connect`'s registration form
(`src/app/connect/page.tsx`), included in the same signed JSON payload as categories/rate
(`contact_email`) — so the whole registration intent, contact info included, is what the worker's
wallet actually signed, not an unsigned field riding alongside.

`src/app/api/register/route.ts` validates it server-side (reusing a new shared
`isValidEmail`/`MAX_EMAIL_LEN` in `src/lib/validation.ts`, extracted from the near-identical inline
regex that already lived in `/api/waitlist` — one ReDoS-safe pattern now, not two copies to keep in
sync). After the `humans` upsert succeeds, if a contact email was supplied, the route calls
`registerNotificationChannel({ contractor_id: <new human's id>, type: "email", address, accepts_auto_booking: false })`
using the service role — `notification_channels` currently has zero anon policies (migrations 003 +
010 dropped them all), so service-role was already the only way in, matching the fix's instruction.

Treated as PII throughout: the address is never included in `/api/register`'s response (which only
ever returned `{ok, wallet}`), and every log line touching this path logs `type: "email"` or a
success/failure boolean, never the address itself — verified with a test that spies on
`console.log` and asserts the raw email never appears in any logged line. The notification-channel
write is best-effort: if it fails, registration still succeeds (a worker with an unreachable
contact method is still a registered worker; the categories/rate/wallet writes are what matter).

Added `src/lib/__tests__/validation.test.ts` and 5 new cases in `register-route.test.ts` (channel
registered with trimmed/lowercased address; skipped when omitted; invalid format rejected 400;
registration still succeeds if the channel write fails; raw email never logged).
`npm run typecheck`, `npm run lint`, `npx vitest run` (96/96) all clean. Verified `/connect` still
loads with zero console/server errors — the connected-state form (where the new field renders)
can't be exercised end-to-end without a real wallet, same limitation already documented for CC-055.

Not in scope, deliberately: Telegram/webhook/Discord channels (the issue says "optional email
and/or..." — email alone satisfies the acceptance criteria; adding the other three now would be
scope creep the issue didn't ask for) and an `accepts_auto_booking` toggle in the UI (defaults to
`false`; asking a brand-new worker to opt into unattended auto-hiring during signup is a separate,
bigger UX decision than this issue's).
