# CC-008 — No privacy policy or terms while collecting personal data from Australian users

## Problem
There is no `/privacy` or `/terms` route in `src/app`, and no link in
`src/components/Footer.tsx:33-44`. Meanwhile `/api/waitlist` collects email addresses and
`/api/register` collects wallet, categories and rate.

Under the Australian Privacy Act you need a privacy policy covering what is collected, why,
where it is stored (Supabase region), and how to request deletion. Under the Spam Act, any
marketing email off the back of that waitlist needs consent plus a functional unsubscribe.

## Fix
Add `/privacy` and `/terms` pages and link them in the footer. Cover:
- what is collected (email, wallet, categories, rate) and the lawful basis
- data residency of the Supabase project
- deletion / access requests and a contact address
- explicit consent wording at the waitlist and signup forms
- unsubscribe mechanism for the waitlist

Note: this is a compliance flag from a code review, not legal advice — worth a lawyer's eye
before you promote at any scale.

## Acceptance
Both pages live and linked before the gate comes off.

## Update 2026-08-08 — both pages live, linked, and consent wording added

Added `/privacy` (`src/app/privacy/page.tsx`) and `/terms` (`src/app/terms/page.tsx`), content in
`src/legal/privacy.md` / `src/legal/terms.md`, rendered through the existing `MarkdownContent`
component (same pattern as `/learn/[slug]`). Both statically prerender (confirmed in `npm run
build` output).

Traced every current collection point in the code before writing anything, rather than guessing:
`waitlist` (email only, `src/app/api/waitlist/route.ts`), `humans` (wallet, categories, rate —
deliberately public per the whitepages design, see `CLAUDE.md`'s own landmine about this table),
`notification_channels` (optional contact channel, **not** public since migration 010/`CC-062`),
and `tasks` (wallets + amount public via `tasks_public`, `task_description` never public). No
analytics, no cookies, no trackers exist in the codebase to disclose.

Two facts needed from Aaron rather than guessed, since getting either wrong in a live legal
document is worse than asking: the contact address (**privacy@carbon-contractors.com**) and the
Supabase project's region (**ap-south-1, Mumbai**) — the policy discloses this as an overseas
transfer under Australian Privacy Principle 8, since Mumbai is outside Australia.

**Linked in two places, not one** — the shared `Footer.tsx` (used across the real site) and,
separately, `ComingSoon.tsx`'s own inline footer, because that component does not use the shared
`Footer` and is currently the *only* thing public visitors see (`NEXT_PUBLIC_COMING_SOON`).
Missing the second one would have meant the policy existed but nothing currently live pointed to
it.

**Consent wording added at both collection points**, per the issue's own "Fix" list: a line under
the waitlist email field linking to `/privacy` (`ComingSoon.tsx`), and a line on the worker
registration form (`src/app/connect/page.tsx`) stating plainly that registering publishes wallet,
categories, rate and reputation to the whitepages — the single most important disclosure on that
form, previously only mentioned *after* registering, not before.

**Unsubscribe mechanism: documented honestly rather than over-built.** There is currently no
email-sending code anywhere in this codebase — the waitlist is a list, not a mailing pipeline. The
policy states this directly and gives `privacy@carbon-contractors.com` as an immediate manual
removal path, which satisfies the *Privacy Act*'s deletion-request right today. It does **not**
satisfy the *Spam Act*'s functional-unsubscribe-link requirement, because that requirement only
bites once a commercial electronic message is actually sent — which none are yet. Flagging this
now rather than waiting to discover it later: **the day this project sends its first waitlist
email, it needs a real unsubscribe link, not just this policy's wording.** Worth its own backlog
issue at that time rather than building unused unsubscribe infrastructure now.

Verified: `npm test` (103/103), `npm run typecheck`, `npm run lint`, `npm run build` all clean.
Checked both pages and the consent lines render correctly in-browser, including toggling
`NEXT_PUBLIC_COMING_SOON` locally to confirm the live gate's own footer (not just the shared one)
links to both pages.

Not legal advice, as the issue itself already notes — worth a lawyer's eye before promoting at
scale, same caveat as when this issue was filed.

**Closed.**
