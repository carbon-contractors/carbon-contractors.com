# CC-001 — Registration is impossible on mobile — wallet button is hidden

## Problem
`src/components/NavBar.module.css:126-128` sets `.wallet { display: none }` inside the
`@media (max-width: 768px)` block. The `<ConnectWallet>` in `src/components/NavBar.tsx:55-69`
is the **only** wallet connect entry point in the entire application.

On a phone there is therefore no way to connect a wallet, and no way to register.
Most traffic from promotion will be mobile, so this alone makes the launch pointless.

## Fix
- Show the wallet button on mobile (move it into the hamburger menu if the header is tight), **and**
- Add a `<ConnectWallet>` directly in the `/connect` hero (`src/app/connect/page.tsx:80-91`)
  so the signup page is self-contained regardless of nav state.

## Acceptance
Registration completes end to end on a 375px viewport.

## Update 2026-07-25 — why this is the most severe of the P0s

Mobile has no Coinbase Wallet browser extension. So a phone user's **only** route is the passkey
Smart Wallet flow, which per CC-055 has never once been completed successfully, behind a CSP that
per CC-003 blocks it.

Hiding the connect button is therefore not "mobile users have a worse experience." It is: the
entire mobile audience reaches a dead end on a path that would not have worked anyway. Fix all
three together (CC-001, CC-003, CC-055) or none of them buys anything.

## Resolution

Did both fixes from the "Fix" section, on top of the `NavBar.tsx` CC-043 already rewrote.

Extracted the wallet connect button out of `NavBar.tsx` into a shared
`src/components/WalletConnectButton.tsx` (+ its own CSS module) so it's one implementation used in
two places, not copy-pasted. `NavBar.tsx` now renders it twice: a `.walletDesktop`-wrapped instance
in the top bar (hidden under 768px), and a `.walletMobile`-wrapped instance appended inside the
hamburger dropdown's `.links` container (hidden at desktop widths, shown — with a border-top
separator — only when the mobile menu is open). Picking a connector or disconnecting from the
mobile instance also closes the menu, via an `onAction` callback prop.

The dropdown itself defaults to hanging from the button's right edge, which works for the
desktop/NavBar and the centered `/connect` hero button, but overflows off the left edge of a
375px viewport for the mobile-menu instance (a button near the left edge, dropdown `min-width:
180px` extending further left). Added a `dropdownAlign="left"` prop, applied only for the
mobile-menu instance, which flips the dropdown to hang from the left edge instead. Verified in the
browser at a 375px viewport via direct DOM measurement (`getBoundingClientRect`) rather than by eye
— both the hamburger-menu wallet button and its connector dropdown land fully inside `0–375px`.

Second fix: `src/app/connect/page.tsx`'s `!isConnected` hero now renders the same
`WalletConnectButton` (default right-aligned dropdown, centered in the hero — also verified
in-bounds at 375px), so the signup page has its own connect entry point independent of nav/menu
state, per the issue's second bullet.

**Not verified, because it can't be from this environment:** an actual end-to-end passkey
connection and signature. There's no real WebAuthn authenticator available to the automated
browser here, and clicking "Base Account" would need one. That gap is `CC-055`'s job, not this
issue's — what CC-001 asked for was a reachable connect entry point on mobile, which is now two,
both measured in-bounds at 375px. `npm run typecheck`, `npm run lint`, and `npx vitest run` (80/80)
all pass unaffected — none of them render a component tree, so this needed the same browser
verification CC-043 (`Lessons-Learned.md` §14) already flagged as non-optional for frontend work.
