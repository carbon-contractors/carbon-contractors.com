# CC-093 — `/api/tasks` serves task content unauthenticated

## Problem

Migration `011` deliberately removed `task_description` from public read access. Its own header says
why: it is *"free-text that may contain sensitive off-chain content (locations, personal details,
specific instructions)"*. The migration dropped the blanket anon `SELECT` on `tasks` and created
`tasks_public` **without** the description column.

`src/app/api/tasks/route.ts` gives it straight back.

```
GET /api/tasks?wallet=0x…   →  { ok: true, tasks: [ { task_description, … } ] }
```

- **No authentication.** The route validates the wallet is well-formed (`:18`) and nothing else.
  There is no signature check, unlike `src/app/api/dispute/route.ts:41`, which verifies a
  challenge signature before acting on a wallet.
- **RLS is bypassed, not consulted.** `getTasksByWallet` (`src/lib/db/tasks.ts:129`) uses
  `getSupabaseAdmin()`, the service role. Migration `011`'s protection is an RLS-layer control, and
  the app's own endpoint reaches around it.
- **Only rate limiting stands in front of it.** `middleware.ts:74-107`, 60 req/min per IP by
  default. That bounds the rate of enumeration, not the fact of it.
- **`/api/*` bypasses the coming-soon gate** (`middleware.ts:19`), so this is reachable on the
  deployed site right now.

Wallet addresses are not secret — `humans` is deliberately world-readable (`CC-030`), and
`search_whitepages` hands them out. So "knows a wallet address" is not a barrier: the whitepages
*is* the list of wallets to try.

**Live impact today is nil** — no real tasks exist. The defect is that the control migration `011`
established does not hold, and the first real task makes it live.

## Why it is filed now

Found while planning `CC-084`. The acceptance spec is strictly more sensitive than the prose
description — it carries GPS coordinates, radii, site references and an evidence bucket target
(`ADR-0001` D3, `ADR-0002` D3). Serving that through this endpoint would make a latent defect a
material one, so it gates `CC-084`'s worker-facing half.

## Fix

Authenticate the caller and return only their own tasks.

- Reuse the existing challenge-response pattern rather than inventing one: `verifyChallengeSignature`
  (`src/lib/auth/wallet-challenge.ts`), as used by `/api/dispute:41` and the MCP transport
  (`src/app/api/basedhuman.mcp/route.ts:153`).
- The authenticated wallet **is** the query — drop `?wallet=` as an input rather than checking it
  matches, so there is no path where the two can disagree.
- Both parties have a legitimate read: the worker (`to_human_wallet`) and the hiring agent
  (`from_agent_wallet`). Authorise on either, matching the on-chain `NotParty` posture in
  `CarbonEscrow.disputeTask`.
- The dashboard fetch needs the challenge round trip added — it already does this for disputes
  (`src/app/dashboard/page.tsx`), so the client-side pattern exists.

Consider whether an unauthenticated caller should get the `tasks_public` projection (no description)
rather than a `401`, so the public task feed keeps working. That is a product call, not a security
one — the security requirement is only that `task_description` stops being anonymous.

## Acceptance

- `GET /api/tasks` without a valid signature does not return `task_description`.
- A signed request returns only tasks where the caller is the worker or the hiring agent.
- The dashboard still lists a worker's tasks.
- A test asserts an unsigned request cannot reach another wallet's description.

## Resolution (2026-08-21)

1. **`src/lib/db/tasks.ts`**:
   - Implemented `getTasksForParty(wallet)` which checks either `to_human_wallet` or `from_agent_wallet`.
   - Implemented `getPublicTasks()` which selects exclusively from `tasks_public` (excluding `task_description` and `acceptance_spec`).
2. **`src/app/api/tasks/route.ts`**:
   - Validates challenge signature (`x-caller-wallet`, `x-caller-signature`, `x-caller-nonce`) via `verifyChallengeSignature`.
   - Returns 401 when a specific wallet is targeted unauthenticated.
   - Returns public projection only when accessed unauthenticated without wallet query.
3. **`src/app/dashboard/page.tsx`**:
   - Added challenge signature authentication flow on the worker dashboard with interactive "Sign to View Tasks" state.
4. **`src/lib/__tests__/tasks-route.test.ts`**:
   - Comprehensive test suite covering unauthenticated rejections, public projections, and authenticated multi-party retrieval.

Related: `CC-084` (the fix lands in its PR 2 — the spec must not ship onto this endpoint first),
migration `011`, `CC-030` (wallets are public by design), `CC-062`, `CC-009`, `ADR-0002` D2.
