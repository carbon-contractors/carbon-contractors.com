# CC-096 — Footer link row overflows the viewport and clips on narrow phones

## Problem

`src/components/Footer.module.css:51-54` declares `.links` as a bare `display: flex` with
`gap: 24px`, and the file contained **no `flex-wrap` and no media queries at all**. Default
`flex-wrap: nowrap` makes the row's min-content width equal its max-content width, so the six
links (`LEARN`, `MCP DOCS`, `GITHUB`, `PRIVACY`, `TERMS`, `UNSUBSCRIBE`,
`src/components/Footer.tsx:33-47`) cannot shrink and simply run past the viewport.

Measured 2026-08-16 on `/mcp-info` at 375px: `document.body.scrollWidth` 384 vs `clientWidth`
375. The row's max-content width is **393.1px** against a 327px content box (375 minus the
footer's `clamp(24px, 6vw, 64px)` side padding, which resolves to 24px a side) — so it overruns
its container by 33px a side, of which the padding absorbs 24px, leaving the 9px a side that
shows up in `scrollWidth`.

Two details make this worse than the raw numbers suggest, and both were confirmed by measurement
rather than assumed:

**It clips, it does not scroll.** `src/app/globals.css:41-45` sets `overflow-x: hidden` on both
`html` and `body`, so there is no horizontal scrollbar and no way to reach the cut-off content —
the same masking mechanism `CC-025` documents for the `/services` tables. The `scrollWidth`
discrepancy is the only signal that anything is wrong.

**It clips at both ends.** `.inner` is a column flex with `align-items: center`
(`Footer.module.css:9-16`), so an over-wide child overflows symmetrically. Measured before the
fix, the row sat at `left: -9.1px, right: 384.1px` against a 375px viewport — `LEARN` losing its
left edge and `UNSUBSCRIBE` its right. Only the right-hand 9.1px is scrollable overflow, which is
why `scrollWidth` under-reports the damage by half.

`Footer` is rendered by `PageShell` (`src/components/PageShell.tsx:12`), so this affected all ten
sub-routes, not one page. The coming-soon gate's own footer
(`src/components/ComingSoon.module.css:266-275`) is a separate implementation that stacks
vertically and was never affected.

## Fix

Two changes to `.links`, no JSX change:

- `flex-wrap: wrap` and `justify-content: center`, with the gap split to `12px 24px`. The wrap is
  what actually fixes it — it drops the row's min-content width to the widest single link, so the
  `align-items: center` fit-content sizing caps the row at the container instead of overflowing.
  This holds at any width, with no breakpoint to maintain. Column-gap stays 24px, so desktop is
  unchanged.
- A `@media (max-width: 480px)` block reducing `column-gap` to `14px`. 480px is the repo's
  existing narrow-phone breakpoint (`ComingSoon.module.css:301`, `learn/learn.module.css:103`,
  `learn/[slug]/module.module.css:93`).

**The gap reduction does not keep the links on one row, and the original plan for this fix was
wrong to say it would.** Measured: the six links are **299.8px of text alone**, against 327px of
content box at 375px. Fitting them on one line needs a column-gap of ≤5px, which is not a usable
value. Probing 24 / 14 / 10 / 8px produced an identical 5 + 1 break every time. So the row wraps
at 375px whatever the gap, and that is the correct behaviour rather than a compromise.

What the tighter gap actually buys, and the honest reason it stays in:

- **Edge clearance.** At 24px the wrapped first line spans 28.5 → 346.5 inside a 24 → 351 content
  box — 4.5px of slack, which reads as if it is about to clip again. At 14px it spans 48.5 → 326.5,
  a calm 24.5px each side.
- **A stable break.** At 24px the first line needs 318px, so it re-flows to 4 + 2 as soon as the
  viewport hits 360px — a very common Android width. At 14px it needs 278px and holds 5 + 1 down
  to ~350px.

`font-size` and `letter-spacing` were deliberately left alone. The links are already 9px; shrinking
them would trade this problem for a worse accessibility one, and the measurement above shows it
would not have bought a single row anyway.

## Acceptance

- At 375×812, `document.body.scrollWidth === clientWidth` and the same holds on
  `document.documentElement` — checked on the root too, since `overflow-x: hidden` on `body` can
  hide a discrepancy that still exists above it.
- The links row's own bounding box sits fully inside the viewport (`left >= 0`, `right <= innerWidth`),
  so nothing is clipped on the left either.
- All six links are visible and legible at 375px, wrapping to centred lines rather than
  overflowing. A wrap is a pass, not a failure — see the measurement in the fix above.
- Same holds at 320px, the realistic worst case.
- Desktop layout is visually unchanged: one row, 24px gaps.

Related: `CC-025` (the `/services` tables, same `overflow-x: hidden` masking, different
component), `CC-019` (unrelated NavBar hamburger defect, noted only so this is not mistaken for a
duplicate).

**A note on priority, for the PM call.** Filed P2 to sit alongside `CC-025`. The argument for P1
is that `UNSUBSCRIBE` is the rightmost link and so the one most degraded — that is the opt-out
path for the notification emails, which gives it a compliance edge the other five do not have.
Nothing is live yet, so it is not blocking; worth revisiting before notification emails start
going out.

## Update 2026-08-16 — fixed and verified in the browser

Implemented as described in `src/components/Footer.module.css`. Verified in the browser preview
rather than assumed, since only the renderer settles a layout defect.

The before-state was **re-measured rather than quoted** — the pre-fix declarations were reapplied
inline in the live page, measured, then removed — so the two rows below are the same page under
the same conditions:

| `/mcp-info` at 375px | `body` sw/cw | `documentElement` sw/cw | Links row box |
| :-- | :-- | :-- | :-- |
| before (`nowrap`, gap 24) | **384 / 375** | 375 / 375 | `left -9.1`, `right 384.1`, width 393.1 — clipped both ends |
| after | 375 / 375 | 375 / 375 | `left 24`, `right 351`, width 327 — inside |

The before row reproduces the originally reported 384 vs 375 exactly.

Wrap behaviour after the fix, and the full sweep:

- **375px** — `LEARN | MCP DOCS | GITHUB | PRIVACY | TERMS` on line 1 (spanning 48.5 → 326.5,
  centred symmetrically in the 24 → 351 content box), `UNSUBSCRIBE` centred beneath at
  148.6 → 226.4.
- **320px** — 320 / 320 on both, row at 24 → 296. Breaks 4 + 2, which is better balanced than
  375's 5 + 1.
- **`/learn` at 375px** — 375 / 375, and a sweep of every element on the page for
  `right > innerWidth` or `left < 0` returns **zero**. Confirms the fix is shell-wide, since
  `PageShell` is the only consumer.
- **1280px desktop** — one row, and the five inter-link gaps measure exactly 24px each. Visually
  unchanged, as intended.

`npm run lint` (0 errors; 1 pre-existing unrelated warning in `basedhuman.mcp/route.ts`),
`npm run typecheck` and `npm test` (131/131, 21 files) all clean. `npm run build` succeeds.

One trap worth recording, because it cost a false negative here: **`npm run build` in a fresh git
worktree fails with `Invalid environment configuration: SUPABASE_URL … NEXT_PUBLIC_USDC_ADDRESS`
while collecting page data for `/api/fund-task`.** That is not a code fault — `.env.local` is
gitignored and therefore does not exist in a worktree, and `src/lib/config.ts` validation is lazy,
so it surfaces at page-data collection rather than at boot. `npm run dev`, `lint`, `typecheck` and
`test` all pass without it, so the build is the only step that trips. Supply the env from the main
checkout for the duration of the command (`set -a; . ../../../.env.local; set +a; npm run build`)
rather than copying the file into the worktree. Node's `--env-file` does **not** work here: Next
propagates it into `NODE_OPTIONS` for its workers, which rejects it with
`ERR_WORKER_INVALID_EXEC_ARGV`.

No screenshot: the Browser pane was not being displayed in this session, so the page was not
compositing frames and `screenshot` timed out. The geometry above is the stronger evidence for
this particular defect anyway — a screenshot cannot show a 9px clip at the viewport edge, which is
precisely why this went unnoticed.

**`/services` was measured in the same pass and is clean at both 375px and 360px** — 375 / 375 and
360 / 360, zero overflowing elements, with the widest example table at 278.6px inside a 312px
parent. That does **not** close `CC-025`: its stated failure mode is `.exampleTask`'s
`white-space: nowrap` clipping at ~360px *and below*, and the widest table is already at 89% of
its container, so a longer example string would still push it over. Recorded into `CC-025` rather
than acted on here.
