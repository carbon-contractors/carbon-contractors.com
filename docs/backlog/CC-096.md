# CC-096 — Set-but-empty env vars bypass every default

## Problem

An environment variable that is **present but empty** arrives in the process as `""`, not
`undefined`. A blank field in the Vercel dashboard, a bare `VAR=` line in a `.env` file,
`docker run -e VAR` and an unset GitHub Actions secret all produce it.

`??` only catches `null` and `undefined`, so it does not select the default. That much was
already recorded — `docs/Lessons-Learned.md` §24 wrote it up on 2026-08-15, and §26 swept for
it on 2026-08-16 and found ten sites. This issue is the fix for what that sweep found.

### The one that matters

`src/lib/ratelimit.ts:141-142`, before this change:

```ts
parseInt(process.env.RATE_LIMIT_MAX_REQUESTS ?? "60", 10)
```

`parseInt("", 10)` is `NaN` — not `0`, not `60`. `maxRequests` becomes `NaN`, and
`entry.count > NaN` is **false for every value of count**. Both the in-memory path
(`src/lib/ratelimit.ts:46`) and the Upstash path (`src/lib/ratelimit.ts:100`) go dead. The
general `/api/*` limiter does not fall back to 60; it stops limiting anything at all.

`src/lib/ratelimit.ts:163` had the same shape for `TASK_CREATE_LIMIT_PER_HOUR`, which is the
bound on how fast one authenticated agent can grow the `tasks` table (`CC-081` Defect 4).

`middleware.ts:36-37` had it twice, and broke in **two opposite directions at once**:

- `WINDOW_MS = NaN` → `now - entry.windowStart > NaN` is false → the window never rolls over,
  so counters climb forever.
- `MAX_REQUESTS = NaN` → `entry.count > NaN` is false → the general `/api/*` limit never trips.

But `ENDPOINT_LIMITS` holds *literal* limits (10 for the MCP challenge endpoint, 30 for the MCP
route). Those are not `NaN`, so they still compare — against a window that never resets. A blank
`RATE_LIMIT_WINDOW_MS` would therefore have locked the MCP endpoints out **permanently** on
request 31 per IP, while the rest of the API stopped being rate limited at all. The `Retry-After`
header would have read the literal string `NaN`.

This is reachable today: `CLAUDE.md` records that every `/api/*` route bypasses the coming-soon
gate.

### Measured, not assumed

- **Vercel Production checked 2026-08-16** via `vercel env ls production`. Neither
  `RATE_LIMIT_MAX_REQUESTS` nor `RATE_LIMIT_WINDOW_MS` nor `TASK_CREATE_LIMIT_PER_HOUR` exists in
  any environment. **The defect was never triggered.** §26 recorded that this check had not been
  done from that session; it has now been done, and the answer is clean.
- `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` *are* set in Production, so production
  runs the Upstash path — line 100 is the one that would have gone dead, not line 46.
- Neither variable is set in `.env.local` either.

So this was a loaded trap, not an open hole, which is why it could be described in public before
being fixed (`CC-056`).

### The part that changes the prescribed fix

§26 concluded that the mechanism is to route these through `src/lib/config.ts`, "`z.coerce.number()
.positive()` rejects both the empty string and the `NaN` at the boundary". **Measured against
zod 4.3.6, routing them through `config.ts` as it stood would not have fixed this.** Two traps:

| expression | input `""` | result |
| :-- | :-- | :-- |
| `z.coerce.number().default(60)` | `""` | **`0`** — `Number("") === 0`, and `.default()` only fires on `undefined` |
| `z.coerce.number().int().nonnegative().optional()` | `""` | **`0`** |
| `z.coerce.number().int().positive().default(10_000)` | `""` | throws |
| `z.string().optional()` | `""` | `""` — present-and-empty |

So `config.ts` had the same defect class in four of its own fields, and it is the file whose whole
job is to stop it:

- `RATE_LIMIT_MAX_REQUESTS` / `RATE_LIMIT_WINDOW_MS` / `SESSION_TIMEOUT_MS` / `MAX_SESSIONS` —
  blank yields `0`, not the documented default. A limit of zero denies every request; a session
  timeout of zero purges every session immediately; `MAX_SESSIONS=0` refuses every new session.
  Routing the rate limiter through the schema unchanged would have swapped "limits nothing" for
  "limits everything" — still silent, still wrong.
- `ESCROW_DEPLOY_BLOCK` — blank yields `0`, which is a *valid block number*, so it passes the
  `configured === undefined` guard at `src/lib/contracts/escrow.ts:58`. Event queries scan from
  genesis **and the warning that exists to catch exactly that never fires**. This is the `CC-070`
  hazard, arriving silently, through the file that was supposed to prevent it.
- The optional string fields — a blank `GCP_KMS_KEY_PATH` reads as a configured key path of `""`,
  and that value selects the signer implementation. `vitest.setup.ts:36` had already noticed this
  shape and worked around it by deleting rather than blanking; the schema never learned it.

`RPC_MAX_BLOCK_RANGE` was already correct by accident of carrying `.positive()`.

### Assessment of the remaining sweep sites

Harmless, but converted anyway so the grep stays meaningful:

- `NEXT_PUBLIC_BASE_NETWORK ?? "testnet"` (× 7, in `scripts/audit/`) — an empty string fails the
  `=== "mainnet"` test and lands on testnet, which is what the default says. Safe in every
  direction: blank can never select mainnet. Converted to `||` to match the convention
  `verify-getlogs-recovery.mjs` and `verify-concurrent-escrow.mjs` already follow.
- `hardhat.config.ts:17,19` — `dotenv` turns `BASE_SEPOLIA_RPC_URL=` into `""`, which `??` passes
  through as an empty RPC URL. Cannot use `config.ts`: excluded from the Next tsconfig, and the
  Hardhat world has no Supabase environment for the full schema to validate. Fixed with `||`.
- `src/app/mcp-info/page.tsx:90,91` — display only; blank would render an empty contract address
  instead of "Not deployed". Cannot use `config.ts` either: Next inlines only literal
  `process.env.NEXT_PUBLIC_*` references at build time, so a value routed through a runtime helper
  is not substituted at all. Fixed with `||`.
- `scripts/audit/verify-unclaimed.mjs:140` — **already correct.** `Number("")` is `0`, and the
  next line rejects `<= 0` explicitly. Left alone; it is the pattern the others should copy.
- `docs/Key-Compromise-Recovery.md:183` — a snippet in a runbook someone will copy under pressure.

## Fix

Do it at the boundary, once, rather than at each call site:

1. `src/lib/config.ts` gains two helpers — `blankAsUnset`, and `envInt(fallback)` /
   `envOptional(schema)` built on it. Blank and whitespace-only read as unset, so the documented
   default is reachable. Anything else non-numeric (`"abc"`, `"0"`, `"-5"`, `"12.5"`) throws at the
   boundary rather than becoming a `NaN` that every downstream comparison answers `false` to.
2. Every numeric field moves to `envInt`; every optional string moves to `envOptional`.
   `TASK_CREATE_LIMIT_PER_HOUR` is added to the schema — it was read from `process.env` directly.
3. A new `getRateLimitConfig()` parses **only** the three rate-limit vars, sharing one field
   definition with the main schema. `middleware.ts` and `ratelimit.ts` read these at module scope,
   and the same middleware hosts the coming-soon gate — routing them through the full `getConfig()`
   would make the gate and every `/api/*` route depend on `SUPABASE_SERVICE_ROLE_KEY` being present.

### Why blank means "unset" rather than "reject"

Rejecting a blank would throw from `getRateLimitConfig()` at module scope, which for middleware is
a total site outage — caused by an operator clearing a field in a dashboard. Treating blank as
unset is what clearing a field means, and there is no case where falling back to the documented 60
is dangerous. A *malformed* value still throws, and at module scope that means the route fails to
initialise loudly. That is the right polarity for a security control: a rate limiter that cannot
read its own configuration must not come up silently permissive.

## Acceptance

- [x] Vercel Production checked for set-but-empty rate-limit vars — absent in all environments.
- [x] `RATE_LIMIT_MAX_REQUESTS=""` yields the documented 60, not `NaN` and not `0`.
- [x] `ESCROW_DEPLOY_BLOCK=""` reads as unset, so `escrow.ts` logs `escrow_deploy_block_unset`
      instead of silently scanning from genesis.
- [x] A malformed value (`"abc"`, `"0"`, `"-5"`) throws from the boundary naming the variable.
- [x] Tests cover blank, whitespace-only, valid, zero, negative, fractional and non-numeric input,
      for both `getConfig()` and `getRateLimitConfig()`, plus a middleware test asserting the
      limiter still trips with a blank window. Hermetic — no network (`CC-060`).
- [x] `grep -nE 'process\.env\.[A-Z_0-9]+\s*\?\?'` returns only prose and the deliberate
      `verify-unclaimed.mjs` site.
- [x] `.env.example` states that blank is not the same as unset.
- [x] `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` pass.

## Done

Fixed on `claude/cc-096-empty-env-vars`. `src/lib/config.ts` gained `blankAsUnset` / `envInt` /
`envOptional` and `getRateLimitConfig()`; `ratelimit.ts` and `middleware.ts` now read through it;
the remaining sweep sites converted to `||` with the reasoning recorded above.
`docs/Lessons-Learned.md` §26 amended — its prescribed fix was measured and did not hold, which is
the third time in this repo a recorded lesson's own remedy needed correcting (§22, §24, now §26).
