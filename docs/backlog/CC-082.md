# CC-082 — CarbonEscrow v2 and Sepolia redeploy

Specified by `ADR-0001` (D1, D2, D4, Amendment 1). This is step 1 of that ADR's handover and
**everything else in the money path sequences behind it.**

## Why this exists

`CarbonEscrow` has exactly one clock: deadline → `expireTask` → refund agent. Silence therefore
always resolves in the agent's favour, which produces the loss case neither `CC-081` nor `CC-075`
named: **the worker delivers, the agent never calls `completeTask`, the deadline passes, and the
agent is refunded automatically.** No bad actor required. The worker has no path to payment that
does not depend on the agent's continued goodwill.

## Scope

**Contract additions**

- `submitWork(taskId, evidenceHash, specVersionAck)` — `task.worker` only, state `Funded` →
  `Delivered`, records `submittedAt`, opens the review window.
- `releaseAfterReview(taskId)` — **pull-payment, claimed by the worker** (Amendment 1 A1.2). Pays
  the worker when the review window closes with no valid failing verdict presented.
- **EIP-712 signed verdicts, not a `postVerdict` transaction** (Amendment 1 A1.1). The verdict is
  signed off-chain; whoever claims presents the signature; the contract recovers the signer and
  checks it against an accepted-signer set. `expiry` and `nonce` are mandatory — an unbounded
  signed verdict is a replayable authorisation.
- Struct fields: `specHash`, `evidenceHash`, `submittedAt`, `verdictHash`, `verdictPassed`.
- New states `Delivered` and `Arbitrating`.
- **Optional `bytes32 attestationUid` on `submitWork`** — the `CC-036` slot, unused until EAS
  lands. Taking it now avoids a second redeploy.
- `expireTask` becomes a claim the agent makes for themselves, same pull-payment principle.

**Deploy**

Redeploy to Base Sepolia, then call `transferOwnership()` to the HSM key
`0xa8931097540e69B474013D294d0bA6A2cC853e4b` (`CC-059` — a fresh deploy is owned by the deployer).
Re-point `NEXT_PUBLIC_ESCROW_CONTRACT`, and re-derive `ESCROW_DEPLOY_BLOCK` with
`scripts/audit/find-deploy-block.mjs` (`CC-070`).

## Do it now, not later

`verify-escrow-solvency.mjs` measured `USDC.balanceOf(escrow) == totalLocked == 0` on 2026-08-11.
The escrow is empty, so a redeploy costs nothing today and will not be free once real tasks exist.

**Sequencing is load-bearing.** This lands *before* `CC-081` Defect 1's fix so the app layer is
rewritten once against the final ABI rather than twice.

## Acceptance

- `submitWork` → review window → worker claims via `releaseAfterReview` works end to end on Sepolia.
- An agent that does nothing after delivery cannot prevent the worker being paid.
- A signed verdict verifies on-chain; a replayed or expired one is rejected.
- `verify-escrow-solvency.mjs` reports CLEAN against the new deployment.
- `owner()` is the HSM address.

Related: `ADR-0001`, `CC-080`, `CC-081`, `CC-036`, `CC-059`, `CC-070`, `CC-083`, `CC-084`.

### Two decisions this needed, both taken with Aaron 2026-08-15

`ADR-0001` left both open and both change the bytecode, so they were settled before writing
rather than after deploying. Recorded here and in `ADR-0001`'s open items.

1. **Review window is agent-set within contract bounds**, `MIN_REVIEW_WINDOW` 12h,
   `MAX_REVIEW_WINDOW` 14d, chosen per task at `createTask`. Both bounds are load-bearing:
   the lower stops a worker claiming before the agent can look, the upper stops an agent
   stalling a delivered worker indefinitely.
2. **A valid failing verdict moves the task to `Disputed`**, it does not refund the agent.
   Refunding would hand the verdict signer unilateral power to take money off a worker who
   has already delivered — the authority `ADR-0001` D9 exists to bound.

### One thing the ADR under-specified, resolved in the contract

`disputeTask` **requires a signed failing verdict**. There is no bare-assertion dispute.
`ADR-0001` D2 says either party may dispute, and A1.3 says a valid failing verdict blocks the
worker's claim — but if a bare call also blocked it, the agent would still hold both outcomes
(release via `completeTask`, refusal via disputing) and the escrow would protect nobody. The
signature requirement is what makes a refusal re-runnable, and therefore falsifiable.

Consequence worth stating plainly: **if the platform will not sign a failing verdict, the
agent has no on-chain recourse and the worker gets paid.** That is D6's liveness default
operating as designed, but it is a sharper edge than the ADR spells out. It also means a task
with no machine-checkable spec (`specHash == 0`) always resolves to the worker — the category
applicability problem `ADR-0001` already flags, now with a concrete mechanism behind it.

The verdict signer is the HSM key `0xa893…3e4b` — the same key that owns the contract. That
is deliberate and grants no authority the platform did not already hold: Vercel can already
act as owner via WIF, and `resolveDispute` is `onlyOwner`, so anyone able to forge a verdict

that is a `setVerdictSigner` call, **no redeploy**, which is why the accepted-signer set is
owner-managed rather than constructor-baked.

### What the first real deploy exposed

The deploy script's own post-deploy verification threw
`could not decode result data (value="0x")` on `owner()` — **against a deployment that had
succeeded**. The public `sepolia.base.org` gateway load-balances across backends with no
read-your-writes guarantee, so the node answering the call had not yet seen the block
carrying the contract's code. The repo already knew this (`CC-059`, 2026-08-08) and already
had a `withRpcLagRetry` helper for it; the deploy script simply did not use one.

Two fixes, because a verification that can fail for reasons unrelated to what it verifies is
worse than no verification — the next reader cannot tell the two apart:

- `scripts/deploy/escrow.ts` retries its verification reads.
- `scripts/audit/verify-escrow-deployment.mjs` is new, re-runnable, and takes an optional
  address argument so a fresh deployment can be checked *before* `NEXT_PUBLIC_ESCROW_CONTRACT`
  is re-pointed — which is the order the checklist above actually happens in. It also binary
  searches for the deploy block, so `ESCROW_DEPLOY_BLOCK` never has to be guessed.

**The lifecycle proof takes 12 hours of wall clock**, because `MIN_REVIEW_WINDOW` is 12h and
`releaseAfterReview` cannot be reached sooner. The script is therefore resumable: phase 1
funds and submits, phase 2 claims. The verdict paths need no waiting and prove in one run.

`scripts/admin/test-dispute-lifecycle.ts` was replaced by that script — its v1 flow
(`createTask` → `disputeTask` → `resolveDispute`) no longer compiles against the v2 ABI, and
its `CC-059` purpose (proving `resolveDisputeOnChain` via the KMS signer) is carried forward.
