# CC-074 — Dashboard needs an accepts_auto_booking toggle, off by default

## Problem

`accepts_auto_booking` is a real, working field on `notification_channels`
(`register_notification_channel` MCP tool, `src/lib/mcp/server.ts`) — when true, an orchestrator
agent can hire a worker directly with no human approval step. It's the mechanism `/learn/module-5`
describes as the actual payoff of setting up automation.

There is no dashboard control for it at all. The only way it's ever set is a direct MCP tool call
— today, every worker who registered through the website has it hardcoded `false`
(`src/app/api/register/route.ts`'s `registerNotificationChannel` call never passes it as true).

## Fix

Add a toggle on `/dashboard`, next to whatever channel management `CC-073` builds:
- **Off by default** — this is a trust/safety default, not just a technical one. A worker should
  have to deliberately opt in to being auto-booked, never default into it.
- Clear, plain-English copy on what turning it on actually means: agents can commit you to jobs
  matching your stated categories and rate with no confirmation step. This is not a minor setting
  — say so.
- Should probably require at least one non-email channel to be set first (email auto-booking with
  no human reading it defeats the point — see `CC-073`), though worth deciding deliberately rather
  than assuming.

## Acceptance

A worker can turn auto-booking on and off from the dashboard, it defaults to off for every new
registration, and the copy makes the consequence of turning it on unambiguous.

Related: `CC-073`, `CC-075` (auto-disabling this if a worker goes AWOL — a safety mechanism this
toggle's existence makes newly relevant, since now a human can actually turn it on for real).

## Update 2026-08-13 — `ADR-0001` adds a category dimension to the toggle

`ADR-0001` lists this issue under `blocks:`, and adds a consideration the ticket does not have.

**Deterministic checkability varies sharply by service category.** Photo tasks check well; address
verification checks moderately; "review this PR" barely checks at all. The categories with no
meaningful automated check are the ones that will generate the adjudication load — and per
`ADR-0002` D7 they are largely the same categories with the highest PII risk.

So auto-booking is not a single boolean in practice. Those categories are candidates for **value
caps or exclusion from auto-booking entirely**, encoded in `/services` (`CC-088`).

This also affects the open question in this ticket about requiring a non-email channel first: an
agent-to-agent auto-booking path is exactly where an unbounded, uncheckable category does the most
damage.

`CC-075` remains downstream of this issue, and now also of `ADR-0001`.

Related: `ADR-0001`, `ADR-0002` D7, `CC-088`, `CC-073`, `CC-075`.

## Update 2026-08-16 — the field this toggles is never read, so the toggle is decoration

This ticket's opening line — *"`accepts_auto_booking` is a real, working field"* — is **wrong**, and
was wrong when written. It is a real *stored* field. Nothing enforces it.

Verified 2026-08-16: `getAutoBookableContractors()` (`src/lib/db/notifications.ts:79`) is a directory
listing for agents to find opted-in workers. **`request_human_work` never reads the flag.** A worker
with it `false` is booked exactly the same as one with it `true` — the agent names them and funds the
escrow, and the first they know of it is a dashboard row.

So shipping this toggle as specified would give a worker a control that visibly does nothing, which
is worse than not having it: it converts an invisible gap into an explicit false promise.

**`ADR-0005` D3 makes the flag load-bearing** — true auto-accepts the offer, false makes it wait for
the worker. `CC-094` builds that enforcement.

**This ticket is now downstream of `CC-094`, not just `CC-073`.** The UI half is unchanged and still
correct — off by default, unambiguous copy, the category dimension from the 2026-08-13 update. Only
the sequencing moves.

Related: `ADR-0005` D3, `CC-094`, `CC-095`, `CC-073`, `CC-014` (the `/learn` module 5 claim).

## Update 2026-08-22 — in progress: the UI half, on the CC-073 channel panel

Built on `feat/cc-074-dashboard-autobooking-toggle`:

- **Per-channel toggle** on `/dashboard`, next to each channel row from `CC-073` — a switch labelled
  by state ("Auto-book off"/"Auto-book on"), wired to a new **PATCH `/api/channels`** that requires
  the same challenge-response wallet signature as GET/POST/DELETE and checks channel ownership
  (403 otherwise). New `setChannelAutoBooking()` in `src/lib/db/notifications.ts`.
- **The boolean is required, not defaulted, on PATCH** — opting in must be an explicit act, so a
  malformed request is a 400 rather than a silent flip. Defaults stay `false` everywhere else: POST
  without the flag preserves an existing value or lands on `false`, and website registration never
  sets it (unchanged from before this ticket).
- **Enabling asks for a `window.confirm` first**, spelling out the consequence before the wallet
  signature prompt; the panel carries permanent explanatory copy ("off by default… agents can commit
  you directly… no manual confirmation step… not a minor setting").
- Route tests in `src/lib/__tests__/channels-route.test.ts` cover auth, the explicit-boolean
  requirement, 404/403, on and off, and no address leakage. No component-test harness exists in the
  repo (vitest runs in a node environment, no jsdom/testing-library), so the UI is covered via the
  API contract it drives.

**Deliberately not built:** the "require a non-email channel first" idea from the ticket body is
left out — the 2026-08-13 update says to decide it deliberately, and it belongs with `CC-094`'s
enforcement work where the auto-accept actually runs, not bolted onto the toggle UI.

**Still decoration until `CC-094` ships** — the 2026-08-16 update stands: nothing reads the flag
yet. The toggle copy describes the `ADR-0005` D3 target state, which is the `ADR-0004` posture, and
the pre-flip control is the new `CC-014` checklist entry added in the same commit.
