# CC-074 — Dashboard needs an accepts_auto_booking toggle, off by default

## Problem

`accepts_auto_booking` is a real, working field on `notification_channels`
(`register_notification_channel` MCP tool, `src/lib/mcp/server.ts`) — when true, an orchestrator
agent can hire a worker directly with no human approval step. It's the mechanism `/learn/module-5`
describes as the actual payoff of setting up automation.

There is no dashboard control for it at all. The only way it's ever set is a direct MCP tool call
— today, every worker who registered through the website has it hardcoded `false`
(`src/app/api/register/route.ts`'s `registerNotificationChannel` call never passes it as true).

## Fix

Add a toggle on `/dashboard`, next to whatever channel management `CC-073` builds:
- **Off by default** — this is a trust/safety default, not just a technical one. A worker should
  have to deliberately opt in to being auto-booked, never default into it.
- Clear, plain-English copy on what turning it on actually means: agents can commit you to jobs
  matching your stated categories and rate with no confirmation step. This is not a minor setting
  — say so.
- Should probably require at least one non-email channel to be set first (email auto-booking with
  no human reading it defeats the point — see `CC-073`), though worth deciding deliberately rather
  than assuming.

## Acceptance

A worker can turn auto-booking on and off from the dashboard, it defaults to off for every new
registration, and the copy makes the consequence of turning it on unambiguous.

Related: `CC-073`, `CC-075` (auto-disabling this if a worker goes AWOL — a safety mechanism this
toggle's existence makes newly relevant, since now a human can actually turn it on for real).

## Update 2026-08-11 — backlog triage pass

Reviewed in the triage pass — **stays P1**, strictly downstream of `CC-073`.

Related change: `CC-075` (auto-disable when a worker goes AWOL) was lowered to P2, on the basis
that funds are never at risk — `expireTask` refunds the agent either way — so it is a credibility
problem rather than a safety one. That does not weaken the case for the "off by default" requirement
here, which is the actual safety property.

`CC-021` was raised to P1 partly because of this issue: a worker who can be auto-booked but cannot
mark themselves unavailable is a worse position than either problem alone.

## Update 2026-08-13 — `ADR-0001` adds a category dimension to the toggle

`ADR-0001` lists this issue under `blocks:`, and adds a consideration the ticket does not have.

**Deterministic checkability varies sharply by service category.** Photo tasks check well; address
verification checks moderately; "review this PR" barely checks at all. The categories with no
meaningful automated check are the ones that will generate the adjudication load — and per
`ADR-0002` D7 they are largely the same categories with the highest PII risk.

So auto-booking is not a single boolean in practice. Those categories are candidates for **value
caps or exclusion from auto-booking entirely**, encoded in `/services` (`CC-088`).

This also affects the open question in this ticket about requiring a non-email channel first: an
agent-to-agent auto-booking path is exactly where an unbounded, uncheckable category does the most
damage.

`CC-075` remains downstream of this issue, and now also of `ADR-0001`.

Related: `ADR-0001`, `ADR-0002` D7, `CC-088`, `CC-073`, `CC-075`.
