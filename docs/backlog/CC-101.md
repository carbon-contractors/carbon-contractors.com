# CC-101 — Worker-facing UX uplift (hub)

## Why this exists

Found by manually walking the transactional workflow end to end on 2026-09-01/02 — not a code
review, an actual attempt to act as a worker. The session stalled repeatedly on gaps that only
show up when a human, not a script, tries to use the dashboard: no way to accept an offer, no way
to read a job's acceptance criteria before committing to it, evidence submission that only accepts
hand-typed JSON, and a wallet-signature prompt on almost every click regardless of whether
anything was actually being written on-chain.

Some of this is one already-open ticket (`CC-094`, offer/accept) plus one already-documented dead
end (`format.ts`'s spec formatter). The rest — the evidence form, the signing pattern, the
agent/poster-side gap — is new. This hub exists so all of it is visible as one worker-experience
problem instead of scattered defects, the same way `CC-076` groups the launch-gate items. **This
hub is not itself actionable** — each line should become its own ticket (or fold into `CC-094`
where one already exists) before anyone picks it up; see `docs/backlog/README.md`'s numbering
rule before filing.

## Signing hygiene — the new finding that prompted this hub

`src/app/dashboard/page.tsx`'s `signedApiHeaders()` (line ~559) mints a **fresh
challenge-response signature for every off-chain API call** — task list fetch, notification
channel load/add/remove, profile update all call it independently
(`fetchTasks` line 369, `signedChannelHeaders` line 871, profile PATCH line 1026). Each is a
separate `POST /api/basedhuman.mcp/challenge` + `signMessageAsync`, so opening the notifications
panel prompts a wallet signature indistinguishable, from the user's seat, from an on-chain
transaction confirmation — for an action that touches no contract at all.

This is the CC-093/CC-004 wallet-ownership proof pattern (correct in principle: an unsigned fetch
must only get the public projection) applied **per request** instead of **per session**. There is
no session token issued after the first successful sign, so every navigation that touches a
protected read re-runs the whole challenge round trip.

**Target behaviour:** sign only (1) once, to establish a session, and (2) whenever an actual
smart-contract write is about to happen (`writeContract` already prompts its own wallet
confirmation for those — that path is fine and should stay separate from this). Everything else —
viewing tasks, opening notification settings, editing a profile — should ride on the
already-established session and prompt nothing.

**Likely shape of the fix**, to be confirmed at design time: issue a short-lived session
(SIWE-style — sign once, get a signed session token/cookie back from `/api/basedhuman.mcp/challenge`
or a new endpoint) and have `signedApiHeaders()` reuse it until it expires, falling back to a new
challenge only on expiry or 401. Needs a decision on session lifetime and storage
(httpOnly cookie vs. in-memory) before implementation — flag as a design question, not a guess,
per `CLAUDE.md`'s "a design question gets an ADR" rule if it touches the auth boundary materially.

## Worker-experience gaps found in the same walkthrough

**Job discovery / acceptance**
- ~~Accept/decline UI for a pending offer — already tracked, `CC-094`.~~ **SHIPPED under `NOR-324`.**
  This pointer was stale: `CC-094` shipped the decision *endpoints* and explicitly deferred "what a
  worker sees" — nothing ever picked the UI up, so a pending offer rendered with no action on it
  anywhere in the app until `NOR-324` built it.
- ~~Job detail view distinguishing a pending offer from an active/completed task~~ **SHIPPED under
  `NOR-324`** — pending offers sort first with an amber "awaiting your decision" treatment.
- ~~Acceptance-criteria / "definition of done" preview before accepting~~ **SHIPPED under
  `NOR-323`** — `formatSpecForDisplay` wired in via `parseSpecForDisplay`, which validates against
  the checker's own schema minus the hash (CC-084).
- ~~Offer expiry countdown (`offer_expiry_unix`)~~ **SHIPPED under `NOR-325`** — lapse time plus a
  relative countdown on the offer card.
- Concurrency-cap feedback (`WORKER_CONCURRENCY_CAP`) — enforced server-side (409) with no prior
  warning in the UI.

**Work submission**
- Structured evidence form — `submitWork`'s evidence bundle is entered as raw JSON in a
  `<textarea>` (placeholder shows literal JSON syntax). The schema
  (`EvidenceBundleSchema`, `src/lib/checker/evidence-hash.ts`) supports `uri`, `mimeType`, EXIF
  fields, C2PA, `phash` — none have form inputs.
- File/photo upload path — missing; a worker must already have a hosted URL for each artifact.
- Live validation against the specific task's spec while composing evidence — blocked on the same
  dead-code gap as the acceptance-criteria item above.
- `claimWithVerdict` re-asks for the same evidence bundle as raw JSON a second time — same barrier,
  doubled.

**Review / release**
- No human-facing UI at all for the agent/poster side (fund a task, review delivered evidence,
  `completeTask`) — today that side only exists over MCP. Flag as a scope question: is a
  human-as-poster UI in scope for this platform, or is "poster" always an AI agent by design? Needs
  an explicit answer, not an assumption, before filing further tickets against it.
- No human-readable translation of contract revert reasons (`InvalidState`,
  `VerdictCommitmentMismatch`, etc.) — every failed write collapses into the same generic message
  as a plain wallet-cancel, so a worker can't tell "you rejected the signature" from "the contract
  rejected the call and here's why."

**Reputation**
- Slash notification shows a total but no link to which dispute caused it.

**Already tracked elsewhere — listed here only so this hub doesn't re-file them**
- `CC-094` — offer/accept lifecycle.
- `CC-092`/`CC-081` Defect 2 — dispute app-layer wiring.
- `CC-095` — notification channel delivery.
- Arbitration having no app/MCP surface — intentional, `ADR-0001` D2, not a gap.
