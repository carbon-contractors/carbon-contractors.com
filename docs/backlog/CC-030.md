# CC-030 — Confirm that anon SELECT on the whole humans table is intended

`supabase/migrations/001_init.sql:44-45` creates policy `humans_read_all` granting anon
SELECT across the worker table, and `/api/profile` plus MCP search rely on the anon key
(`src/lib/db/whitepages.ts:25,45,66,85,107`).

So anyone can enumerate every worker's wallet, categories and hourly rate. For a public
whitepages that is arguably the point — but it should be a decision on the record, not an
accident, especially since it is what makes CC-002's normalisation fix load-bearing.

Fix: confirm the intent, document it in the privacy policy (CC-008), and make sure no column
beyond the intended public set is readable.

---

## Closed 2026-07-30 — verified and intended

Live inspection confirms `humans` has RLS enabled with 2 policies: `humans_read_all`
(anon SELECT, `qual: true`) and the dormant `humans_update_self`. So anon can read every
worker's wallet, categories, rate, availability and reputation score.

This is the public whitepages and it is the point — the MCP discovery tools and `/api/profile`
both read with the anon key. Confirmed as a deliberate product decision rather than an accident,
which is what this issue asked for.

Two follow-ons, both already tracked:
- It must be disclosed in the privacy policy (**CC-008**) — workers should know their rate is
  public before they publish it.
- `human_whitepages` has an explicit field allowlist (AUD-008 / NOR-193), so adding a column to
  `humans` will not leak through the MCP resource. But it **will** be exposed by the
  `humans_read_all` policy to anyone querying the table directly with the anon key. Any new
  column on `humans` is public by default — noted in CLAUDE.md.
