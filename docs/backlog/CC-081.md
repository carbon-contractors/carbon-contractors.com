# CC-081 — Escrow trust boundary defects found by CC-037

`CC-037` verified the six fund-safety invariants against the current tree on 2026-08-11. One passed,
one split, four failed. This issue holds the failures; `CC-037` holds the verification record and the
evidence for each finding.

Filed as one issue rather than five because they are all consequences of the same thing — the money
path has never been executed, so nothing ever pushed back on it — and they will almost certainly be
fixed as one piece of work. `CC-080` (settlement) is the fifth consequence and was filed separately
because it was found first.

**Nothing here is exploitable against real funds today.** The site is behind the coming-soon gate, the
escrow holds 0 USDC on Sepolia with `totalLocked` 0, and the funding path has never been run. Published
as found, per `CLAUDE.md`'s disclosure policy — it exposes no third-party data and is not trivially
exploitable against real funds.

Taken with `CC-080`, the position is: **no part of the money path currently works end to end.**

---

## Defect 1 — `/api/fund-task` strands USDC in the escrow contract (fund loss on first real use)

`src/app/api/fund-task/route.ts:174-178` exports
`withX402(fundTaskHandler, getPlatformWallet(), dynamicRouteConfig)`, and `getPlatformWallet()`
(`:26-31`) returns `NEXT_PUBLIC_ESCROW_CONTRACT ?? PLATFORM_WALLET_ADDRESS ?? ""`.

An x402 settlement is a **plain ERC-20 transfer** to that address. So the documented funding path
deposits USDC straight into `CarbonEscrow` and **never calls `createTask`**. The consequences compound:

- No task struct is written, so `tasks[taskId].state` stays `None`.
- `totalLocked` is not incremented, so the contract's own accounting never sees the money.
- `CarbonEscrow` has **no `receive`, no `fallback`, no sweep, no rescue, and no owner-withdraw**
  (`contracts/CarbonEscrow.sol` — the only transfers out are in `completeTask`, `resolveDispute` and
  `expireTask`, and all three require a task in a specific state). The USDC is therefore
  **permanently unrecoverable by anyone, including the owner.**
- The handler then sets DB status to `active` (`:99-101`), so the platform reports the task as funded
  while on-chain there is no task at all.

Note the fallback chain is its own problem: if `NEXT_PUBLIC_ESCROW_CONTRACT` were ever unset, payment
would go to `PLATFORM_WALLET_ADDRESS` — the platform taking direct receipt of agent funds, which is
custody and would collapse the `CC-051` position outright. And `?? ""` as a final fallback means a
misconfiguration silently produces an empty recipient rather than failing loudly.

**`src/lib/payments/x402.ts` contradicts itself about which mechanism is intended.** Its header
(`:5-7`) and the JSDoc on `initiateX402Payment` (`:45`) both say the agent funds "via USDC approve +
`createTask` on-chain" — the correct design. But the `instructions` string it actually returns to the
agent (`:101-107`) says to POST to `/api/fund-task` and let an x402 client auto-pay. Two different
funding designs, documented in the same file, and the one that ships is the one that loses money.

**Measured state, 2026-08-11:** `scripts/audit/verify-escrow-solvency.mjs` reports
`USDC.balanceOf(escrow) == totalLocked == 0`. Nothing is stranded, because no agent has ever funded a
task. The defect is latent, not historic — which is the only reason this is publishable rather than an
incident.

### Fix

Make the agent call `escrow.createTask(taskId, worker, amount, deadline)` from its own wallet, which
is what the contract requires (`agent: msg.sender`, `:107`), what `x402.ts`'s own header describes, and
what Aaron's `CC-080` ruling established as the intended design. `request_human_work` already returns
everything needed for this — `task_id_bytes32`, `escrow_contract`, `amount_wei`, `chain_id`.

Then decide what `/api/fund-task` is *for*. Options: delete it; or keep it as a non-payment endpoint
that verifies the on-chain task exists and is `Funded` before flipping the DB to `active` (which is
also Defect 3's fix). It must stop being an x402 payment recipient either way.

Add the solvency check to CI or a pre-launch step so a regression is caught by measurement rather than
by reading.

## Defect 2 — the agent both raises and resolves its own disputes; the worker cannot do either

**The contract is fine.** `resolveDispute` is `onlyOwner` and the recipient is
`releaseToWorker ? task.worker : task.agent` (`contracts/CarbonEscrow.sol:159-175`) — both addresses
fixed on-chain at funding time. **No arbitrary destination is reachable by anyone, owner included.**
That is the strongest form of the `CC-051` non-custodial argument and it holds. `disputeTask`
(`:141-153`) correctly permits either party and reverts `NotParty` for anyone else.

**The app layer inverts the authorisation on both.**

- `resolve_dispute` (`src/lib/mcp/server.ts:808`, check at `:873`) authorises
  `task.from_agent_wallet === context.callerWallet`. Its own comment reads *"Authorization: only the
  originating agent may resolve a dispute."* `CC-037` item 4 asked whether it authorises the platform
  owner **rather than** the disputing agent. It authorises the agent.
- `dispute_task` (`:683`, check at `:731`) is *also* agent-only — *"only the originating agent may
  dispute a task."* The contract grants the worker this right; the product removes it.

So the reachable sequence is: agent funds → worker delivers → agent disputes → agent resolves with
`release_to_worker: false` → agent is refunded. **The worker cannot dispute, cannot resolve, and has no
adjudicator.** The platform's owner key executes the agent's decision, so `onlyOwner` is doing nothing
but rubber-stamping one interested party.

This is currently unreachable end to end, because Defect 1 means no on-chain task exists to dispute —
but that is sequencing luck, not a control.

### Fix — deliberately not specified

The intended design needs deciding, not guessing. Aaron's call on 2026-08-11 was to file it with the
options rather than settle it now, the same treatment as `CC-075`.

- **Platform adjudicates.** `resolve_dispute` authorises the platform owner, matching `onlyOwner`.
  Simplest match to the contract's intent, but it is discretionary authority over someone else's
  funds, which is the framing `CC-051` most wants to avoid.
- **Either party disputes, platform resolves.** Restores the worker's contract-granted right and keeps
  adjudication neutral. Closest to what `CarbonEscrow` was designed for.
- **Agent resolves, by design.** Consistent with the `CC-080` ruling that the paying agent controls
  release. If this is the intent, then a worker with no dispute right and no recourse needs to be
  stated plainly in `/learn` and the terms, because it materially changes what a worker is agreeing
  to — and it should not be described as an escrow with dispute resolution.

Whichever is chosen, the worker-facing copy must match it. Note `CC-036`'s attestation work and
`CC-051`'s regulatory position both depend on the answer.

## Defect 3 — the DB is not a projection of chain state

`CLAUDE.md` states the on-chain escrow is the authority on money. Two places break that:

- **`active` is not gated on the on-chain task being funded.** `/api/fund-task:99-101` flips to
  `active` once the x402 facilitator reports payment, with no read of `getTask(taskId)`. Given Defect
  1, there is never an on-chain task to read.
- **Nothing waits for confirmation.** `src/lib/contracts/signer.ts` has three write functions
  (`:120`, `:152`, `:179`) and every one returns the hash straight from `writeContract`. There is no
  `waitForTransactionReceipt` anywhere in the file. So a DB status change is gated on transaction
  *submission*, not on a confirmed `TaskCompleted`/`TaskResolved` event — a reorg or a dropped
  transaction leaves the DB claiming an outcome that never settled.

### Fix

Gate `active` on reading `Funded` from `getTask()`. Gate terminal statuses on a confirmed receipt or
on the corresponding event, not on a submitted hash. `getTaskResolvedOutcome` already exists for the
event-reading half — but see `CC-070`, which currently breaks it.

## Defect 4 — `request_human_work` is unauthenticated, and neither wallet argument is validated

`request_human_work` (`src/lib/mcp/server.ts:112`) **never touches `context.callerWallet`** — unlike
`confirm_task_completion`, `dispute_task` and `resolve_dispute`, which all authenticate. Combined with
`/api/*` bypassing the coming-soon gate, that makes task creation an open endpoint on the live site
right now.

- **`from_agent_wallet` is accepted as an argument** (`:116-119`), not bound to the authenticated
  caller. Anyone can attribute a task to any wallet. It cannot be turned directly into theft — the
  three privileged tools all compare the caller against `from_agent_wallet`, so a false attribution
  locks the attacker *out* — but it means task provenance is unauthenticated, and it is the field
  every downstream authorisation check trusts.
- **`to_human_wallet` is only format-checked**, by a Zod regex (`:120-123`) and
  `isValidWalletAddress` (`src/lib/payments/x402.ts:56`). It is **never checked against the `humans`
  table**, despite the parameter description claiming it comes "from `search_whitepages`". So a task
  can be created paying an address that belongs to no registered worker — and because Defect 1's fix
  makes the agent pass `worker` to `createTask`, this value becomes the on-chain payout destination.

This is also why `CC-037` item 2 passes only conditionally: the contract does pay `task.worker` from
on-chain state, but the value in that slot originates from unvalidated caller input.

Live effect today: unlimited unauthenticated `pending` task rows with arbitrary addresses and
arbitrary 1000-character descriptions. Database pollution, not fund loss.

### Fix

Require `context.callerWallet` and bind `from_agent_wallet` to it rather than accepting it as an
argument. Validate `to_human_wallet` against `humans` (lowercased on both sides — see the casing
landmine) and reject unregistered addresses. Consider a per-caller rate limit on task creation, noting
`CC-020`: the current limiter is per-instance in-memory.

## Defect 5 — `ReputationStake.slash()` is never called from anywhere

`slash(address worker, uint256 amount)` exists, is `onlyOwner`, and is documented in the contract
itself as *"owner-only, triggered on dispute resolution"* (`contracts/ReputationStake.sol:18,123`).
Nothing triggers it. `grep -rn "slash" src/ contracts/ scripts/` finds the contract, the ABI entry
(`src/lib/contracts/reputation-abi.ts:33`), and read-only display of `slashedTotal`
(`src/lib/reputation/index.ts:88`, `src/app/dashboard/page.tsx:366`) — no call site.

So a stake can be posted and can be displayed, but can never be lost. Meanwhile `README.md:11` sells
staking as the trust layer: *"workers put skin in the game."* A stake with no slashing condition is a
deposit, not skin in the game, and the claim is quotable from a public repo.

### Fix — one of

- Wire `slash()` into dispute resolution, once Defect 2 settles who resolves disputes and on what
  basis. Slashing on an agent-self-resolved dispute would be indefensible, so this genuinely depends
  on that decision.
- Or remove the "skin in the game" framing from `README.md` and `/learn`, and correct
  `ReputationStake.sol`'s own comment, until it is real.

Related: `CC-072` (the staking flow has never been executed), `CC-011` (the panel's UX).

## Acceptance

- The agent calls `createTask` from its own wallet; `/api/fund-task` is no longer an x402 payment
  recipient; `verify-escrow-solvency.mjs` still reports clean after a full funded lifecycle.
- The dispute design is decided, implemented, and reflected in worker-facing copy.
- DB status transitions are gated on on-chain reads and confirmed events.
- `request_human_work` authenticates, binds `from_agent_wallet` to the caller, and rejects
  `to_human_wallet` values absent from `humans`.
- `slash()` is either wired in or the staking claims are corrected.
