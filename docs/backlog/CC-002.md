# CC-002 — Wallet case mismatch — every registered worker 404s on profile lookup

## Problem
`src/app/api/register/route.ts:135` inserts `wallet: wallet` — the raw EIP-55 checksummed,
mixed-case address supplied by wagmi. But `src/lib/db/whitepages.ts:50` looks it up with
`.eq("wallet", wallet.toLowerCase())`.

`humans.wallet` is `TEXT NOT NULL UNIQUE` (`supabase/migrations/001_init.sql:6`) — case
sensitive, with no normalising constraint.

Consequences:
- `/api/profile` returns 404 for every worker who has ever registered
- the dashboard profile card never renders (`src/app/dashboard/page.tsx:426`)
- the MCP `get_contractor` tool cannot find anybody
- the same person can register twice under different casing

## Fix
1. Normalise on write: `wallet.toLowerCase()` in the register route.
2. Normalise on every read path in `whitepages.ts` (audit all of them).
3. Migration: backfill `UPDATE humans SET wallet = lower(wallet)`, then add
   `CHECK (wallet = lower(wallet))` so it cannot regress.
4. Check `tasks.to_human_wallet` / `from_agent_wallet` for the same class of bug.

## Acceptance
Register a fresh wallet, land on the dashboard, and see the profile card populated.

## Resolution

Fixed all four items, plus the same bug class in `tasks`:

1. **`src/app/api/register/route.ts`** — signature verification still uses the original,
   client-signed casing (`verifyMessage({ address: wallet, ... })`), but everything written or
   logged afterward (`used_nonces.wallet`, `humans.wallet`, the JSON response) uses a single
   `normalizedWallet = wallet.toLowerCase()` computed right after verification succeeds.
2. **`src/lib/db/whitepages.ts`** — `getHumanByWallet` already lowercased its query; added a test
   (`whitepages.test.ts`) asserting `.eq("wallet", ...)` receives the lowercased value even when
   called with mixed case, so this can't silently regress. The other reads (`searchByCategory`,
   `getAllHumans`, `getDistinctCategories`) don't filter by wallet, so they weren't at risk.
3. **Migration `014_normalize_wallet_casing.sql`** — backfills `humans.wallet` to lowercase and
   adds `CHECK (wallet = lower(wallet))`. **Not yet applied to production** — this session has no
   live Supabase credentials and migrations are run by hand in the SQL editor per `CLAUDE.md`.
4. **Same bug in `tasks`** — `src/lib/db/tasks.ts`'s `createTask` wrote `from_agent_wallet`/
   `to_human_wallet` verbatim (whatever casing the MCP caller or `search_whitepages` result
   happened to have), and `getTasksByWallet` queried without lowercasing either. Both agent-facing
   entry points (`/api/tasks`, `/api/reputation`, dashboard) use wagmi's checksummed `address`, so
   this was a live version of the same bug on a second table. Fixed the same way: lowercase on
   write in `createTask`, lowercase on read in `getTasksByWallet`. The MCP tool authorization
   checks (`dispute_task`, `resolve_dispute`, `confirm_task_completion` in `server.ts`, and
   `/api/dispute`) already compared `.toLowerCase()` on both sides, so they were never affected by
   storage casing — no change needed there.

**The trap in the migration:** `009_task_immutability_trigger.sql`'s trigger raises an exception
if `to_human_wallet`/`from_agent_wallet` change on a non-`pending` task — and a same-value,
different-case `UPDATE` still counts as a change under Postgres's case-sensitive `TEXT` equality.
The backfill for `tasks` disables that trigger for the one UPDATE statement and re-enables it
immediately after; once the CHECK constraint lands, no future write can reintroduce mixed case, so
the trigger's exact-match comparison stays correct going forward without needing to change the
trigger function itself.

Added `src/lib/__tests__/register-route.test.ts` (2 cases: normalizes on write while verifying
with original casing; rejects bad signatures regardless of casing) and extended
`tasks.test.ts`/`whitepages.test.ts` with explicit lowercase-query assertions.
`npm run typecheck`, `npm run lint`, `npx vitest run` (85/85) all clean. The migration SQL was
reviewed by hand, not executed against any database — no local Postgres was available in this
session to dry-run it, and production access requires Aaron.
