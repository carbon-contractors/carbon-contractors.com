# CC-094 — Offer/accept lifecycle

Specified by `ADR-0005`. **Blocked on `CC-095`** (notification delivery) per `ADR-0005` D7 — an
offer nobody is told about is an expiry with extra steps.

## Problem

**The worker is named on a funded task without ever agreeing to it.** An agent picks them out of
`search_whitepages`, calls `request_human_work`, funds the escrow naming their address, and they
find out afterwards — if at all, since nothing sends notifications (`CC-095`).

`accepts_auto_booking` was supposed to be the consent mechanism. It is stored and never enforced:
`getAutoBookableContractors()` (`src/lib/db/notifications.ts:79`) is a directory listing for agents,
and `request_human_work` never reads the flag. A worker with it **false** — the default — is booked
exactly the same as one with it true.

`/learn` module 5 tells workers otherwise: *"When it's `false` (the default…), you're notified and
decide yourself."* Add to `CC-014`'s pre-flip checklist until this ships.

## Fix

`ADR-0005` D1–D5. The offer is entirely off-chain and sits in the gap that already exists between
`request_human_work` (creates a `pending` row) and `createTask` (locks USDC). **No contract change.**

```
request_human_work → pending (offer, with expiry)
   ├─ worker accepts / auto-accepts  → accepted
   ├─ worker declines                → agent re-targets
   └─ offer expires                  → agent re-targets
accepted → agent calls createTask   → active (funds locked)
```

- **New task states** `accepted`, `declined`, `lapsed`. `VALID_TRANSITIONS`
  (`src/lib/db/tasks.ts:78`) gains them; migration `009`'s `prevent_task_mutation` trigger needs to
  know which of them still permit mutation (`declined` and `lapsed` are terminal for an offer that
  never became a task, and no money was ever involved).
- **`accepts_auto_booking` becomes a gate** in the hire path — D3. True auto-accepts; false waits.
- **Offer expiry, agent-set, bounded 15 minutes to 7 days** — D4. Lower bound stops an unanswerable
  offer being used to claim unresponsiveness; upper bound stops an agent holding a free option on
  someone's availability.
- **One live offer per task** — D1. An agent may not fan out to several workers simultaneously;
  that reinvents the wasted-effort race the directed model exists to prevent.
- **Concurrency cap** on `accepted` + `active` per worker — D5. Prevents a worker self-inflicting a
  cascade of missed deadlines, each of which is an `ADR-0001` D1 expiry.
- **Expiry needs a sweeper.** Lapsing is the absence of an event, so something has to notice. Prefer
  evaluating it inline on read (the `CC-075` precedent — a cron maintaining a flag only read at
  booking time is pure overhead) unless the notification side needs a push.

## Acceptance

- A worker with `accepts_auto_booking: false` is not committed to a task until they accept.
- An unanswered offer lapses at its expiry and the agent can re-target.
- A declined offer frees the agent immediately; the worker is not penalised (`ADR-0005` D6).
- An agent cannot hold two live offers for the same task.
- A worker at the concurrency cap cannot accept another.
- `request_human_work` rejects an expiry outside the bounds.
- No task reaches `active` without having passed through `accepted`.

## Open

From `ADR-0005`: ~~offer expiry default~~ (resolved 2026-08-22: 24h, `DEFAULT_OFFER_EXPIRY_SECONDS`);
concurrency cap starting value and whether it varies by category (resolved for v1 at 3,
`WORKER_CONCURRENCY_CAP` — variation still open); whether an agent may re-offer to a worker who
declined; what a worker sees for a declined offer; whether `humans.availability` should gate offers
at all (`CC-021`).

## Progress

2026-08-22 (in progress, branch `feat/cc-094-offer-accept-lifecycle`):

- States `accepted` / `declined` / `lapsed` in `TaskStatus` + `VALID_TRANSITIONS` — `active` now
  reachable only from `accepted`; `declined`/`lapsed` terminal. Migration `018` adds
  `tasks.offer_expiry_unix`, widens the status CHECK, partial index for the sweep.
- `accepts_auto_booking` is now a gate (D3): `request_human_work` reads the worker's channels via
  `getChannelsForContractor`; any channel with the flag true → row born `accepted` (after the D5 cap
  check), otherwise `pending` with an agent-set expiry (`offer_expiry_minutes`, bounded 15m–7d at
  both the schema and `x402` layers, default 24h).
- Worker decision endpoints `POST /api/offers/accept` and `POST /api/offers/decline` (CC-093
  wallet-signature auth, only `to_human_wallet`), shared logic in `src/lib/offers.ts`; accept
  enforces the D5 cap (409).
- Lapse is inline on inspection (D4): `lapseExpiredOffers()` runs in `getTaskByPaymentId` and
  `/api/tasks`, and `respondToOffer` re-checks the clock before accepting so a raced offer can
  never be accepted out of time.
- `/api/fund-task` refuses anything not `accepted` (D2).
- Notifications fire through `notifyContractor` (`src/lib/notifications/dispatch.ts`) — the D7 seam.
  **CC-095 remains open**: the seam records structured events per channel (never an address,
  ADR-0002 D9) and does not deliver. This issue stays `in-progress` until CC-095 makes delivery
  real, per D7.
- "One live offer per task" (D1) is **not yet enforced** — with one task row per
  `payment_request_id` there is no cross-row task identity to key it on; needs a decision on what
  "same task" means before it can be coded.
