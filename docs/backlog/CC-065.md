# CC-065 — resolve_dispute MCP tool never calls resolveDisputeOnChain — dispute resolution is DB-only

## Problem

Found while verifying CC-059 step 3 (proving `resolveDisputeOnChain` works now that escrow
ownership sits with the KMS key). While tracing the call path, `resolveDisputeOnChain`
(`src/lib/contracts/signer.ts:129`) turned out to have **zero call sites** anywhere in the app.
Confirmed with:

```
grep -rn "resolveDisputeOnChain(" src
```

only the function's own definition and `signer.test.ts` (which doesn't even test it) match. It is
not imported into `src/lib/mcp/server.ts` at all — check the import list at
`src/lib/mcp/server.ts:8-34`; `completeTaskOnChain` is imported (line 32), `resolveDisputeOnChain`
is not.

The `resolve_dispute` MCP tool (`src/lib/mcp/server.ts:806-935`) only:
1. Flips the Supabase `tasks.status` to `completed` or `expired` (line 894), and
2. Returns a text note telling the caller to call `escrow.resolveDispute(taskId, ...)` themselves
   (line 917: `"Database updated. Call escrow.resolveDispute(taskId, ...) on-chain..."`).

So today, resolving a dispute through the product never moves any USDC. The database and the
escrow contract silently disagree the moment a dispute is "resolved" — the DB says `completed`
(worker paid) while the on-chain task is still stuck in `Disputed`, with funds still locked,
unless a human separately and manually calls the contract. This is the same class of bug as
CC-037 (`completeTaskOnChain` unreachable due to `onlyAgent` gating) but worse: CC-037's function
is at least *called* and fails loudly on-chain; this one is never called at all, so nothing fails
loudly — the DB just reports a false completion.

Confirmed the underlying signer function itself is correct and does work once called — see the
CC-059 step 3 verification note in `CC-059.md` (2026-08-08): a direct call to
`resolveDisputeOnChain` via the KMS signer released escrowed USDC to a worker address exactly as
expected (tx `0x08cd2e374b5f7399370ffd767bcdf2b1fe063078fd8269e13b172d2984b918eb`). The bug is
purely that the MCP tool never invokes it.

## Fix

In the `resolve_dispute` tool handler, after `updateTaskStatus` succeeds, call
`resolveDisputeOnChain(taskIdBytes32, release_to_worker)` (already imported style matches
`completeTaskOnChain`'s usage in `confirm_task_completion`, `src/lib/mcp/server.ts:390`) and
include the resulting tx hash in the response. Decide and handle the failure mode explicitly: if
the DB update succeeds but the on-chain call reverts or throws, the tool must not report `ok:
true` with a stale "note to self-serve on-chain" — that's the exact inconsistency this issue
exists to remove. Consider whether the on-chain call should happen first (so a revert prevents
the DB write) — `completeTaskOnChain`'s call ordering in `confirm_task_completion` may already
answer this; check it before choosing.

## Acceptance

- `resolve_dispute` calls `resolveDisputeOnChain` and the on-chain state and DB state cannot
  diverge after a successful response (either both moved or neither did).
- A test exercises this (unit test with a mocked signer is fine — no need for another live
  Sepolia round-trip per CI run).

## Update 2026-08-08 — fixed, matching confirm_task_completion's existing on-chain-first ordering

`resolve_dispute` (`src/lib/mcp/server.ts`) now:

1. Reads on-chain state first via `getOnChainTask`. If it's already `Resolved` (partial-failure
   recovery — a prior call succeeded on-chain but the DB write afterward failed), it recovers the
   **true** outcome from the `TaskResolved` event via a new `getTaskResolvedOutcome` helper
   (`src/lib/contracts/escrow.ts`) rather than trusting a possibly-mismatched retry argument, skips
   calling the contract again, and updates the DB to match reality.
2. If on-chain state is anything other than `Disputed` or `Resolved` (a genuine DB/chain
   inconsistency — e.g. the on-chain `disputeTask()` was never actually called by the agent's own
   wallet), returns an explicit error instead of guessing.
3. Otherwise calls the real `resolveDisputeOnChain` (unchanged from CC-059's fix) **before**
   touching the database — same ordering `confirm_task_completion` already used for
   `completeTaskOnChain`, chosen for the same reason: a chain failure must never leave the DB
   claiming something that didn't happen. If the on-chain call throws, the DB is left untouched
   and the error is returned as-is.
4. Only updates `tasks.status` after the on-chain step is confirmed done (or already was).

**Confirmed `dispute_task` does NOT have the same bug and does not need the same fix.**
`disputeTask()` on the contract requires `msg.sender` to be the task's agent or worker
(`NotParty` otherwise) — the platform signer is neither, so it structurally *cannot* call it on
anyone's behalf. Checked `src/app/dashboard/page.tsx`: the real human-facing flow already calls
`escrow.disputeTask()` client-side via the connected wallet (wagmi `writeContract`) before hitting
the DB-update API. `dispute_task`'s MCP-tool docstring correctly tells an AI-agent caller to do the
on-chain call itself, for the same reason `createTask` is agent-wallet-signed rather than
platform-signed. This is an intentional asymmetry, not a second instance of CC-065.

Added `src/lib/__tests__/mcp-resolve-dispute.test.ts` (6 cases, mocked signer/DB/escrow — no live
Sepolia round-trip needed): successful release-to-worker and refund-to-agent paths call the
contract then update the DB in that order; an on-chain revert leaves the DB untouched; the
partial-failure recovery path recovers the true outcome instead of trusting a mismatched retry
argument; a genuine DB/chain mismatch is surfaced rather than guessed at; a non-disputed task is
still rejected before touching the chain. `npm test` (102/102), `npm run typecheck`, `npm run
lint`, and `npm run build` all clean.

**Closed.**
