# CC-067 — No self-serve unsubscribe for the waitlist

## Problem

`CC-008` shipped `/privacy` and `/terms` and documented, honestly, that there is no unsubscribe
mechanism because there is no email-sending code anywhere in this codebase — the waitlist
(`waitlist` table, `src/app/api/waitlist/route.ts`) is currently a list, not a mailing pipeline.
The policy points people at emailing `privacy@carbon-contractors.com` to be removed.

Aaron flagged this directly: an easy, working, self-serve unsubscribe is something he cares about
personally, not just a compliance checkbox to defer. "Email us and wait" is a bad experience even
before the *Spam Act*'s functional-unsubscribe-link requirement formally kicks in (it only applies
once a commercial electronic message is actually sent, which none are yet).

## Fix

Build a real, immediate self-serve removal path, not a mailto: link dressed up as one:

1. `DELETE /api/waitlist` with `{ email }` in the body — removes the matching row from `waitlist`.
2. Always return a generic success response regardless of whether the email was found, to avoid
   turning the endpoint into an email-existence oracle.
3. Rate-limit it (`apiRateLimiter` from `src/lib/ratelimit.ts` — already built, currently unused by
   any REST route including the existing `POST /api/waitlist`, which is a separate, pre-existing
   gap worth its own issue if it matters).
4. A minimal public `/unsubscribe` page: an email field and a button, no auth, no token. This is a
   low-stakes marketing list, not sensitive financial data — the threat model is the same as
   joining it in the first place (you already know the email you're typing in).
5. Update `src/legal/privacy.md` to point at the real link instead of "email us" as the primary
   path, keeping email as the fallback for full data-access/deletion requests beyond just the
   waitlist.

## Acceptance

- Visiting `/unsubscribe`, entering an email that's on the waitlist, and submitting actually
  removes it — verified against the real `waitlist` table structure, not just a mocked test.
- The endpoint does not leak whether a given email was ever on the list.
- `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` all pass.

Related: `CC-008`.

## Update 2026-08-08 — built and shipped

Added `DELETE /api/waitlist` (`src/app/api/waitlist/route.ts`) — deletes the matching row,
always returns the same generic success message regardless of whether the email existed,
rate-limited via the existing (previously unused-by-any-route) `apiRateLimiter`. Added
`/unsubscribe` (`src/app/unsubscribe/page.tsx` + `UnsubscribeForm.tsx`), linked from the shared
footer, the coming-soon gate's own separate footer, and its waitlist-signup consent line.
`src/legal/privacy.md` now points at the real link as the primary removal path, keeping
`privacy@carbon-contractors.com` as the fallback for full data-access/deletion requests.

**One acceptance criterion downgraded honestly, not silently dropped.** "Verified against the
real `waitlist` table" turned out not to be fully achievable in this session:
`SUPABASE_SERVICE_ROLE_KEY` in `.env.local` is the documented placeholder (`CLAUDE.md`'s own
landmine list), so any local write against the real project fails with an auth error before ever
reaching the `waitlist` table. Verified instead via: (1) 5 unit tests against the exact
`.from("waitlist").delete().eq("email", ...)` call shape — structurally identical to every other
working admin write in this codebase; (2) a live browser submission against the real Supabase
project, which correctly reached the real auth boundary and failed for the *expected*,
pre-existing, documented reason (bad local credentials), not a bug in this code. A quick manual
check once deployed to a preview with real credentials would close the gap fully, but isn't
something this session could do.

**That live verification attempt paid for itself anyway** — it surfaced `CC-068`, a real,
previously-live bug in `safeErrorResponse` (`src/lib/errors.ts`) affecting five other existing
routes, not just this new one. Fixed in the same commit; see that issue for detail.

`npm test` (111/111), `npm run typecheck`, `npm run lint`, `npm run build` all clean.

**Closed.**
