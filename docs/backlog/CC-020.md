# CC-020 — Rate limiter claims Upstash Redis but is per-instance in-memory

The header comment at `middleware.ts:5-8` describes distributed rate limiting via Upstash
Redis. The implementation at `middleware.ts:30-108` is an in-memory `Map`. There is no
Upstash code in the repo, despite `UPSTASH_REDIS_REST_URL`/`_TOKEN` sitting in `.env.local`
and a commit titled "added upstash_redis".

Across Vercel serverless instances a per-instance map is close to useless — the effective
limit is 60/min multiplied by however many instances are warm.

Fix: either implement the Upstash-backed limiter the comment describes, or correct the
comment and accept the weaker guarantee explicitly. Do not leave the docs lying.

## Update 2026-08-11 — backlog triage pass

Reviewed in the triage pass — **stays P2**, and both remedies stay deliberately open.

Re-verified the discrepancy is real and unchanged: `middleware.ts:6` states "Rate limiting now
supports Upstash Redis for distributed" while the implementation at `middleware.ts:34` is
`const rateLimitMap = new Map<string, WindowEntry>()`. Grepping the repo finds no Upstash or Redis
code at all, despite the env vars in `.env.local` and a commit titled "added upstash_redis".

The choice between implementing the Upstash-backed limiter and correcting the comment is left to
whoever picks this up. Worth knowing when deciding: `CC-015` (waitlist has no honeypot or captcha)
currently depends on this bucket as its only throttle, and across warm Vercel instances a
per-instance map makes the effective limit 60/min multiplied by the instance count. So the two issues
should be decided together — if the comment is corrected rather than the limiter built, `CC-015`
needs its own dedicated limit rather than relying on this one.
