# CC-020 — Rate limiter claims Upstash Redis but is per-instance in-memory

The header comment at `middleware.ts:5-8` describes distributed rate limiting via Upstash
Redis. The implementation at `middleware.ts:30-108` is an in-memory `Map`. There is no
Upstash code in the repo, despite `UPSTASH_REDIS_REST_URL`/`_TOKEN` sitting in `.env.local`
and a commit titled "added upstash_redis".

Across Vercel serverless instances a per-instance map is close to useless — the effective
limit is 60/min multiplied by however many instances are warm.

Fix: either implement the Upstash-backed limiter the comment describes, or correct the
comment and accept the weaker guarantee explicitly. Do not leave the docs lying.

## Update 2026-09-16 — remedy chosen: implement the Upstash-backed limiter

The 2026-08-11 coupling note is moot: `CC-015` closed `wontfix` on 2026-08-21 when `CC-089`
removed the waitlist form and `/api/waitlist` entirely. There is no form left to protect.

The investigation also found the "implement" remedy was half-built already. `src/lib/ratelimit.ts`
(since the NOR-174–178 security sweep, extended by CC-096/CC-097) is a genuine zero-dependency
Upstash REST limiter — pipeline `INCR`+`EXPIRE`, Bearer auth, fail-open on transport error, in-memory
fallback when the env vars are absent — and the MCP route and `mcp/server.ts` consumed it. But
`middleware.ts`, the layer that throttles **all** `/api/*`, still ran its own private inline
in-memory `Map` while its header comment claimed "Rate limiting now supports Upstash Redis for
distributed limiting" (NOR-179). That private counter is the documented lie.

**Changes (PR pending — this branch: `fix/cc-020-upstash-rate-limiter-wt`):**

- `middleware.ts` no longer keeps a private counter. It delegates to `apiRateLimiter`,
  `mcpRateLimiter` and `challengeRateLimiter` from `@/lib/ratelimit`, so the same bucket is
  Upstash-backed when `UPSTASH_REDIS_REST_URL`/`_TOKEN` are set and per-instance in-memory when
  they are not. Endpoint routing preserved: `/api/basedhuman.mcp/challenge` → 10/min,
  `/api/basedhuman.mcp` → 30/min, everything else under `/api/*` → `RATE_LIMIT_MAX_REQUESTS`/min.
  `/api/health` stays exempt. The middleware function is now `async` (the limiter's `limit()` is a
  Promise on both paths); Next.js supports async middleware.
- `src/app/api/basedhuman.mcp/route.ts` drops its route-level `mcpRateLimiter` call. With
  middleware delegating to the *same shared limiter object*, the route's call was a second increment
  of the same bucket — it would have halved the effective 30/min to 15/min. It was already dead
  code in practice: middleware's bucket always tripped first, so the route's 429 branch never ran
  in production. The 429 for MCP now comes from middleware as
  `{"ok":false,"error":"Too many requests"}` with `Retry-After`.
- `src/lib/__tests__/ratelimit.test.ts` gains a CC-020 suite covering the Upstash REST path with a
  stubbed `fetch`: wire protocol (pipeline `INCR`+`EXPIRE` on the prefixed key, `Bearer` auth,
  `/pipeline` endpoint), blocking past the limit with `retryAfterS` = the window, per-limiter key
  prefixes (no bucket collisions), and fail-open on both transport errors and non-2xx responses.
- `src/lib/__tests__/middleware.test.ts` updated for the async middleware signature.

**Verification:** full suite 803/803, `eslint` and `tsc --noEmit` clean, `next build` green with
middleware compiled as the edge Proxy importing `@/lib/ratelimit`. All run in an isolated worktree
off latest `origin/master` (8944f65).

**Operational note:** distributed limiting only takes effect once
`UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` are set in the Vercel environment. Until then
the code honestly falls back to per-instance in-memory — the comment no longer lies about which one
is active. `.env.example` already documents both variables; setting them on Vercel is an ops action,
not a code change.
