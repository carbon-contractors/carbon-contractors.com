# CC-084 — Acceptance spec schema

Specified by `ADR-0001` D3. Step 3 of that ADR's handover.

## The problem it solves

Today the agent writes prose, the worker submits, and the agent decides *after the fact* whether it
counted. `ADR-0001` calls that grading against a rubric written after the answers arrived — and
identifies it as the root cause behind `CC-081` Defect 2, in a more sympathetic costume.

## Scope

`request_human_work` carries a machine-checkable acceptance spec alongside the prose description,
committed as `specHash` at `createTask`, and **shown to the worker before they accept.**

Illustrative, from `ADR-0001` D3:

```json
{
  "min_artefacts": 8,
  "exif_gps_within_m": { "lat": -37.8136, "lon": 144.9631, "radius_m": 100 },
  "captured_after": "task_funding_block_timestamp",
  "provenance": { "require_camera_model": true, "reject_c2pa_ai_generated": true },
  "phash_max_similarity_to": {
    "source": ["ff00ff00ff00ff00", "0f0f0f0f0f0f0f0f"],
    "threshold": 0.85
  }
}
```

Authoring this is work a hiring agent is well suited to, and is core to the platform being
agent-native rather than a form with an API.

**The `source` array is a 2026-08-26 correction** — it read `"listing_images"` until then, a
label an offline checker cannot resolve. See the update at the end of this file and
`ADR-0001` Amendment 3.

Also carries the bucket target for `CC-083`'s evidence path, and the `ADR-0002` D7 agent-facing
notice attaches here.

## Why it has to be committed before acceptance

The worker can verify pre-acceptance that `specHash` matches what they were shown, so the goalposts
cannot move. In the worked fraud case from `ADR-0001`, the fake submission fails on capture
timestamp alone — before any state transition and before anyone exercises judgement. The task never
leaves `Funded`.

**"Before acceptance" had no referent until `ADR-0005`.** There was no acceptance step at all — an
agent named a worker and funded the task, and the worker found out afterwards. `ADR-0005` D2 puts an
offer/accept handshake in the gap between `request_human_work` and `createTask`, and **that is the
moment this section is talking about**: the spec displays at the offer, and accepting it is what
binds the worker to it. Built by `CC-094`; the display half is this issue's PR 2.

## Acceptance

- A spec is committed at `createTask` and its hash matches what the worker was shown.
- A worker can reject a task on spec content before accepting.
- Schema is versioned, and the version is inside the `specHash` preimage.
- The criteria are rendered human-readably to the worker, not dumped as JSON beside the prose.
- Prose edits are append-only and the accepted version is pinned to the worker's acceptance.
- An old-version task still resolves correctly after a new version ships.

## Update 2026-08-16 — scope settled by `ADR-0001` Amendment 2

Both of this issue's open questions are answered. The amendment is the reasoning; this is what it
means for the build.

### `specHash` binds the criteria and the schema version — not the prose

Aaron's call (A2.1): the machine-checkable criteria are the definition of done and must not move.
The prose is context for a human, and clarifying it mid-task is legitimate.

Safe because payment cannot follow the prose — the checker reads only the criteria. But **mutable is
not silent**: prose edits are append-only, and the version the worker accepted is pinned to their
acceptance. That closes scope creep, not a fund-safety hole.

Two traps called out in the amendment:

- **The prose history is task content, not audit log.** It is deleted at terminal state with
  everything else — `ADR-0002` D4, `CC-087`. Do not exempt it.
- **The worker must see the criteria rendered human-readably.** Under this split the prose is the
  half that does not bind, so a worker who reads only the prose has not seen the definition of done.
  This is acceptance criteria for this issue, not polish.

`verify-commitments` (`CC-085`) narrows to hashing the criteria and the schema version.

### There is no migration path — that is the design

A2.2: the preimage carries `schema_version`, and **a task resolves under the schema it was created
with, permanently.** No in-flight migration, no invalidation mechanism. Deprecation is at intake —
stop accepting new tasks on the old version and let the in-flight ones drain, bounded by the
delivery deadline plus at most `MAX_REVIEW_WINDOW` (14d).

The apparent cost — the checker supporting several versions at once — **is already paid by `CC-083`**,
because D5 re-runnability requires a six-month-old verdict to be reproducible from its pinned
`checkerHash`. Noted on `CC-083` as an explicit scope item so it is not discovered late.

### A broken version is an incident, not a migration

A2.4, and the reason this issue now relates to `CC-086`. A schema version found to be *wrong* is
handled by pausing intake (kill switch; never pause claims) and signing **corrected failing
verdicts** for tasks in flight — which moves them to `Disputed` rather than refunding, so the worker
keeps recourse.

**Consequence for anyone sizing the review window:** it is a security parameter, not just worker UX.
`MIN_REVIEW_WINDOW` of 12h is the floor on incident-response time, because after the window closes
the worker can claim and the platform has no lever.

### Rejected: scheduled-downtime migration with refunds

Recorded because it will be proposed again. The platform **cannot refund an in-flight task** — v2 has
three `onlyOwner` functions and none of them reaches money from `Funded` or `Delivered`. Doing it
would require adding an owner-callable refund, reversing the custody property `CC-082` established.
Full reasoning at `ADR-0001` A2.3.

## Update 2026-08-16 — PR 1: schema, hashing and storage

Built against the answers above. Worker-facing display is PR 2, together with `CC-093`.

### The agent sends a JSON *string*, and we hash those exact bytes

`specHash` has to be computed identically by three parties — the platform stores it, the agent
passes it to `createTask`, the worker echoes it as `specVersionAck` at `submitWork` (which reverts
`SpecAckMismatch()` on any difference). Three implementations agreeing byte-for-byte forever is
where a design like this fails.

**So there is no canonicalisation step. The preimage is the bytes the agent sent.** Zod validates
shape; the stored and hashed value is the original string, untouched. `keccak256(toHex(…))`, the
same idiom as `toTaskId` (`src/lib/contracts/escrow.ts:193`).

Two semantically identical specs with different key order hash differently. That is correct — they
are different tasks — and in exchange nobody ever has to reproduce our serialiser. There is a test
asserting the hashes differ, so a future canonicaliser fails loudly rather than silently breaking
worker verification.

*Rejected: accept an object and canonicalise server-side (RFC 8785 / JCS).* Float serialisation —
`lat`, `lon`, `threshold` — is the classic divergence source, and a worker verifying the hash would
have to reimplement our canonicaliser exactly. That bug class only ever surfaces as a task nobody
can claim.

### `.strict()` everywhere is load-bearing

An unrecognised criteria key would be displayed to the worker as a requirement and then silently
ignored by the checker — the goalpost problem this issue exists to prevent, arriving through the
back door. **If it is in the spec, it must be checkable.** Unknown keys are rejected.

### `acceptance_spec` is optional in this PR, and says so loudly when absent

Nothing consumes it yet: `CC-083`'s checker does not exist and `CC-081` Defect 1 does not yet call
`createTask`. Requiring it now would break the tool before anything could use it.

Absent *or* empty criteria → `spec_hash: null` and an explicit `spec_warning` in the response,
because `ADR-0001` records that a task with nothing checkable **always resolves to the worker** — a
dispute needs a signed failing verdict and there is nothing to fail against. Legitimate for an
uncheckable category; never something to discover afterwards.

**Flipping it to required belongs with `CC-081` Defect 1**, noted on that ticket.

### Migration 016

- Three columns on `tasks`, `CHECK`-constrained to lowercase hex and all-three-or-none
- **`prevent_task_mutation` replaced.** Migration `009` named five columns explicitly, so the new
  ones would have been freely mutable on a funded task. They are now immutable **unconditionally**,
  not merely past `pending` — the agent gets the hash while the row is still `pending` and passes it
  to `createTask`, so a change in that window strands them against a stale hash with no error
  anywhere.
- **`task_description_history`** with `ON DELETE CASCADE` — Amendment 2 A2.1. The cascade is
  load-bearing: this is task content and dies with the task under `ADR-0002` D4 / `CC-087`, not an
  audit log to be exempted from retention.
- RLS enabled and anon/authenticated grants revoked in the same migration.
- **`tasks_public` deliberately unchanged** — explicit column list, so the spec does not leak into
  the public feed. Recorded rather than left implicit, per `CLAUDE.md`.

### Verified, and what was not

24 tests pass (13 new in `spec-schema.test.ts`, 4 added to `mcp-request-human-work.test.ts`),
including a pinned hash vector so a preimage change fails in CI rather than on chain.

**Not verified locally, and not claimed to be:** `SUPABASE_SERVICE_ROLE_KEY` is the placeholder in
local `.env.local`, so nothing that writes a task row runs here. At the time of this PR **migration
`016` had not been applied**, so its constraints and both triggers were unproven — there is no
runner (`CC-057`). Closed out below.

## Update 2026-08-17 — migration 016 applied and verified against the live database

Aaron applied `016`. Every property it was written to establish is now measured rather than
inferred from the file.

### The trigger, exercised rather than inspected

A rollback'd probe inserted a task with a spec, edited its description, then attempted to change
`spec_hash`:

```
ERROR: P0001: Cannot modify the acceptance spec once a task row exists (CC-084)
CONTEXT: PL/pgSQL function prevent_task_mutation() line 8 at RAISE
```

**Line 8 is the block `016` added.** That distinguishes the two failure modes that look identical
from outside: migration `009` created `prevent_task_mutation`, and `016` does a `CREATE OR REPLACE`
on it. Had the replacement not taken, the trigger would still exist and still fire — just without
guarding the spec columns, leaving `specHash` silently mutable while every catalogue check passed.

The `RAISE` aborted the transaction, so nothing persisted.

### Catalogue state

```
spec_columns_expect_3           3
spec_constraints_expect_2       2
task_triggers_expect_2          2
trigger_guards_spec_expect_1    1
history_table_expect_1          1
spec_leaked_to_public_expect_0  0
```

The last line is the one worth keeping. `tasks_public` runs as its owner and bypasses RLS by design
(`CC-030`, migration `011`) — Supabase's advisor flags it CRITICAL and it is deliberate. Its entire
safety rests on the explicit column list, and this confirms the three spec columns did **not** leak
into it. That matters more here than for the other columns: the spec carries GPS coordinates, site
references and an evidence bucket target (`ADR-0002` D3). Asserted in `016`'s comment, now measured.

### What remains unproven

The `task_description_history` trigger fires on a description edit, which the probe performed — but
the `RAISE` aborted before the count could be read, so only the table's existence is confirmed, not
its behaviour. Low stakes: it is `ADR-0001` Amendment 2 A2.1's prose-edit trail, not a fund-safety
control, and the first real edit will demonstrate it.

## Update 2026-08-26 — `phash_max_similarity_to` corrected: hashes inline, and a cap

Found by a code review of the merged `CC-083` checker. Decided by `ADR-0001` Amendment 3; this is
what it means for this issue.

### The example in this file specified something the checker could not do

`"source": "listing_images"` names a *set of images held somewhere*. `ADR-0001` D5 requires the
checker to be pure and offline, so it cannot resolve a name into anything. The criterion as written
was unimplementable, and the spec schema accepted it anyway — a bare string passed validation, and
the checker then failed every artefact against a reference it could not parse.

`source` is now an array of perceptual hashes the agent supplies at task creation. That keeps the
checker offline, and it puts the reference set **inside the hashed preimage**, so `specHash` freezes
the references along with the criteria — a reference set that could move after funding is a goalpost
that can move. It also means the platform holds fingerprints of the agent's own material and never
the material, which extends `ADR-0002` D3 from the evidence to the criteria.

### The check was implemented backwards, and this issue's own PR 2 was the half that was right

Between 2026-08-21 and 2026-08-26 `evaluator.ts` required similarity **≥** threshold — a floor. A
re-upload of the reference passed at similarity 1.0; an honest new photograph failed. This issue's
worker-facing renderer, built a day later, implemented the cap correctly, so the product showed the
worker *"No more than 0.85 similarity — i.e. a re-upload of existing material — fails the verdict"*
and enforced the exact opposite.

That is the failure mode `.strict()` was adopted to prevent, arriving from the other side: not a
criterion shown and unenforced, but a criterion shown and enforced **backwards**. Worth recording
against this issue specifically, because the display half being correct is what made the
contradiction visible at all.

### Why nothing caught it

It was the only criterion with **no failing canary case**. `CC-083`'s fixture set had `pass-all`
plus five single-check failures covering everything else, so both the suite and the `verify-checker`
monitor were silent on the one check that was wrong.

`src/lib/checker/__tests__/canary.test.ts` now asserts the fixture set's completeness in both
directions: every criterion the schema accepts must produce a check, and every check the evaluator
emits must be failed by at least one canary case. Adding a criterion without a failing case now
fails the suite. `CANARY_FAIL_PHASH_REUPLOAD` closes the gap for this one, and `verify-checker`
reports 7 cases.

### No schema version bump

`schema_version` stays `1`. Amendment 2 A2.2 protects tasks that already committed a `specHash`, and
none exist — the escrow holds 0 USDC and the funding path has never run. **After the first funded
task the same change would cost a new version plus indefinite multi-version checker support**, so any
remaining correction to v1's shape belongs now.

### Changed

- `src/lib/spec/schema.ts` — `source: z.array(...).min(1).max(64)`; a bare string is refused at intake.
- `src/lib/checker/evaluator.ts` — cap semantics, inclusive threshold, max-similarity across all
  references, fails closed on a hash that cannot be compared.
- `src/lib/spec/format.ts` — renders the reference count; the cap wording was already correct.
- `src/lib/checker/canary/fixtures.ts` — `CANARY_FAIL_PHASH_REUPLOAD`; the good artefact's phash is
  now dissimilar to the reference, since under a cap that is what passing looks like.
- Tests updated to the cap direction; 635 passing, typecheck and lint clean.

**Still open on this issue** — unchanged by this update. This is a correction to work already merged
under PR 1 and PR 2, not a step toward closing it.

Related: `ADR-0001` Amendment 3, `CC-083`, `CC-092`.

## Update 2026-09-16 — the last acceptance item: the accepted prose version is pinned

A full audit of all six acceptance criteria against the codebase found five shipped and one half
shipped. Criterion 5 read: *"Prose edits are append-only and the accepted version is pinned to the
worker's acceptance."* Migration `016` built the append-only half (`task_description_history`), and
its own comment promised "a worker who re-reads the brief mid-job must be able to see that it
changed since they accepted" — but nothing recorded **which** prose version the worker accepted,
and no worker surface ever compared current against it. This update supplies the missing half.

### Where each criterion stands after the audit

1. **Spec committed at `createTask`, hash matches what the worker was shown** — PR 1: verbatim
   preimage, `keccak256(toHex(…))`, `SpecAckMismatch` at `submitWork`, immutability trigger,
   migration 016 verified live 2026-08-17.
2. **Worker can reject on spec content before accepting** — CC-094's `/api/offers/decline`, free,
   terminal, agent free to re-target.
3. **Schema versioned, version inside the `specHash` preimage** — `schema_version` in the hashed
   string (Amendment 2 A2.2), pinned hash vector in `spec-schema.test.ts`.
4. **Criteria rendered human-readably** — `src/lib/spec/format.ts` exhaustive switch + the offer
   card rows (NOR-323); the display half is what exposed the phash inversion of 2026-08-26.
5. **Append-only prose + pinned accepted version** — append-only since migration 016; the pin is
   **this update** (below).
6. **Old-version task still resolves after a new version ships** — `EVALUATORS` dispatch on
   `schema_version` in the checker; the canary set keeps one case per supported version.

### The pin

`tasks.accepted_description_hash` — `keccak256` of the `task_description` bytes at the moment of
acceptance. A commitment, not content, so it follows `spec_hash`'s retention posture: it survives
the CC-087 prune (migration 024 rewrites `prune_task_content` to keep it) and leaks nothing about
the prose (ADR-0002 D2). Same idiom as the spec preimage — no canonicalisation, the platform's own
string is hashed. Pinned hash vector in `tasks.test.ts`.

- **`acceptTask`** (`src/lib/db/tasks.ts`): one guarded statement writes the status flip
  `pending → accepted` AND the pin, gated on the exact `task_description` the worker read. An agent
  edit that raced the decision makes the guard miss and returns `brief_changed` — the route maps it
  to 409 with "the brief changed while you were accepting it. Re-read the new version and accept
  again." Never pin text the worker never saw.
- **Auto-booked tasks** (born `accepted`, ADR-0005 D3) pin at creation in `createTask` —
  pre-authorisation is consent. Pending rows insert with pin NULL; only acceptance sets it.
- **Dashboard drift notice**: on a live task (`accepted`/`active`) where the worker's pin no longer
  hashes to the current `task_description`, the card says the brief changed since acceptance, that
  the criteria still bind payment, and to re-read before submitting. This is the surface
  migration 016's comment promised.
- **Immutability**: migration 024's trigger replaces `prevent_task_mutation` carrying every prior
  branch forward, plus pin-once semantics — NULL → hash is the acceptance moment; any later change
  raises.

### No backfill

Zero tasks have ever been funded — escrow holds 0 USDC and the funding path has never run — the
same state that justified no `schema_version` bump on 2026-08-26. Pre-024 accepted/active rows keep
pin NULL; the drift comparison simply never fires on them.

### What remains unproven

Migration 024 has not been applied to the live database — the repo has no migration runner
(`CC-057`); Aaron applies migrations by hand, as with 016. Its trigger and RPC changes are
unproven against live Postgres until then, exactly as 016's were before 2026-08-17.

Related: `ADR-0001` Amendment 2 A2.1, `ADR-0005` D2/D3, `CC-087`, `CC-094`, `CC-057`.
