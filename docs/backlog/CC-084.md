# CC-084 — Acceptance spec schema

Specified by `ADR-0001` D3. Step 3 of that ADR's handover.

## The problem it solves

Today the agent writes prose, the worker submits, and the agent decides *after the fact* whether it
counted. `ADR-0001` calls that grading against a rubric written after the answers arrived — and
identifies it as the root cause behind `CC-081` Defect 2, in a more sympathetic costume.

## Scope

`request_human_work` carries a machine-checkable acceptance spec alongside the prose description,
committed as `specHash` at `createTask`, and **shown to the worker before they accept.**

Illustrative, from `ADR-0001` D3:

```json
{
  "min_artefacts": 8,
  "exif_gps_within_m": { "lat": -37.8136, "lon": 144.9631, "radius_m": 100 },
  "captured_after": "task_funding_block_timestamp",
  "provenance": { "require_camera_model": true, "reject_c2pa_ai_generated": true },
  "phash_max_similarity_to": { "source": "listing_images", "threshold": 0.85 }
}
```

Authoring this is work a hiring agent is well suited to, and is core to the platform being
agent-native rather than a form with an API.

Also carries the bucket target for `CC-083`'s evidence path, and the `ADR-0002` D7 agent-facing
notice attaches here.

## Why it has to be committed before acceptance

The worker can verify pre-acceptance that `specHash` matches what they were shown, so the goalposts
cannot move. In the worked fraud case from `ADR-0001`, the fake submission fails on capture
timestamp alone — before any state transition and before anyone exercises judgement. The task never
leaves `Funded`.

## Acceptance

- A spec is committed at `createTask` and its hash matches what the worker was shown.
- A worker can reject a task on spec content before accepting.
- Schema is versioned, and the version is inside the `specHash` preimage.
- The criteria are rendered human-readably to the worker, not dumped as JSON beside the prose.
- Prose edits are append-only and the accepted version is pinned to the worker's acceptance.
- An old-version task still resolves correctly after a new version ships.

## Update 2026-08-16 — scope settled by `ADR-0001` Amendment 2

Both of this issue's open questions are answered. The amendment is the reasoning; this is what it
means for the build.

### `specHash` binds the criteria and the schema version — not the prose

Aaron's call (A2.1): the machine-checkable criteria are the definition of done and must not move.
The prose is context for a human, and clarifying it mid-task is legitimate.

Safe because payment cannot follow the prose — the checker reads only the criteria. But **mutable is
not silent**: prose edits are append-only, and the version the worker accepted is pinned to their
acceptance. That closes scope creep, not a fund-safety hole.

Two traps called out in the amendment:

- **The prose history is task content, not audit log.** It is deleted at terminal state with
  everything else — `ADR-0002` D4, `CC-087`. Do not exempt it.
- **The worker must see the criteria rendered human-readably.** Under this split the prose is the
  half that does not bind, so a worker who reads only the prose has not seen the definition of done.
  This is acceptance criteria for this issue, not polish.

`verify-commitments` (`CC-085`) narrows to hashing the criteria and the schema version.

### There is no migration path — that is the design

A2.2: the preimage carries `schema_version`, and **a task resolves under the schema it was created
with, permanently.** No in-flight migration, no invalidation mechanism. Deprecation is at intake —
stop accepting new tasks on the old version and let the in-flight ones drain, bounded by the
delivery deadline plus at most `MAX_REVIEW_WINDOW` (14d).

The apparent cost — the checker supporting several versions at once — **is already paid by `CC-083`**,
because D5 re-runnability requires a six-month-old verdict to be reproducible from its pinned
`checkerHash`. Noted on `CC-083` as an explicit scope item so it is not discovered late.

### A broken version is an incident, not a migration

A2.4, and the reason this issue now relates to `CC-086`. A schema version found to be *wrong* is
handled by pausing intake (kill switch; never pause claims) and signing **corrected failing
verdicts** for tasks in flight — which moves them to `Disputed` rather than refunding, so the worker
keeps recourse.

**Consequence for anyone sizing the review window:** it is a security parameter, not just worker UX.
`MIN_REVIEW_WINDOW` of 12h is the floor on incident-response time, because after the window closes
the worker can claim and the platform has no lever.

### Rejected: scheduled-downtime migration with refunds

Recorded because it will be proposed again. The platform **cannot refund an in-flight task** — v2 has
three `onlyOwner` functions and none of them reaches money from `Funded` or `Delivered`. Doing it
would require adding an owner-callable refund, reversing the custody property `CC-082` established.
Full reasoning at `ADR-0001` A2.3.
