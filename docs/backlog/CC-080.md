# CC-080 — `confirm_task_completion` calls `completeTask` as the platform signer and always reverts

## Problem

**The core hire→pay loop has never worked and cannot work as written.** Two incompatible designs
coexist in the codebase: agent-signed client-side escrow writes, and platform-signed server-side
escrow writes. The payout path is built out of both halves.

Verified in the current tree during the 2026-08-11 triage pass:

1. `CarbonEscrow.createTask` records the funder as the task's agent —
   `agent: msg.sender` (`contracts/CarbonEscrow.sol:107`).
2. **Nothing server-side calls the contract's `createTask`.** `src/lib/db/tasks.ts:34`'s
   `createTask` is an unrelated *database* function with a colliding name.
   `src/lib/payments/x402.ts:45` states the agent funds the escrow "via `USDC.approve()` +
   `escrow.createTask()`", and `src/lib/contracts/escrow.ts:6` says outright that write operations
   "happen client-side". So `task.agent` is **the AI agent's own wallet address**.
3. `CarbonEscrow.completeTask` requires that exact address:
   `require(msg.sender == task.agent, "only agent")` (`contracts/CarbonEscrow.sol:128`), and
   `CLAUDE.md` records this as confirmed present in the deployed bytecode.
4. But `confirm_task_completion` calls it **server-side as the platform signer** —
   `src/lib/mcp/server.ts:391` → `completeTaskOnChain` (`src/lib/contracts/signer.ts:102`), which
   builds the call with `account = await getPlatformAccount()`.

The platform signer is not `task.agent`, so `simulateContract` fails and the call reverts with
`"only agent"`. Unconditionally, for every task, since the contract was deployed. No key, signer
or config change fixes this — the platform signer is the wrong sender by design.

### What this does *not* mean

The failure is **safe and loud**, which is why it has gone unnoticed rather than causing damage.
`src/lib/mcp/server.ts:389-409` catches the revert, logs `signer_complete_task_failed`, returns
`isError: true` with the chain error text, and **returns before `updateTaskStatus`**. So the
database is never flipped to `completed` on a failed payout. No worker has ever been told they were
paid when they weren't, and no USDC has been stranded by this. AUD-005 (atomic state transitions)
and AUD-006 (idempotent on-chain checks) are doing exactly their job.

It also means the on-chain-state pre-check immediately above (`getOnChainTask` →
`alreadyCompletedOnChain`) is currently unreachable in its intended role: it exists to recover from
"completed on-chain but the DB write failed", a state this code path can never produce.

## Fix

**Aaron's ruling (2026-08-11): the contract is correct; the defect is entirely app-side.**

The intended design is agent-signed: the agent that created and funded the job calls `completeTask`
itself, from its own wallet, once it has received evidence the work is done. That is what
`CarbonEscrow` enforces, what `x402.ts` and `escrow.ts` already describe, and it is the stronger
position for the non-custodial argument in `CC-051` — the platform genuinely cannot release funds.

So:

- `confirm_task_completion` must stop calling `completeTaskOnChain`. It should record the
  completion evidence and return whatever the agent needs in order to call `completeTask(taskId)`
  itself — the task id, escrow address, and a clear statement that the agent's own wallet must send
  the transaction.
- Decide deliberately what the DB status becomes at that point. It must not be `completed`, since
  no payout has occurred. A distinct state ("awaiting agent settlement", or similar) is honest;
  reusing an existing one to avoid a migration is not.
- The DB should flip to `completed` on observing the `TaskCompleted` event, not on the tool call.
  That is the same on-chain-state-is-the-authority principle `CLAUDE.md` states, and it is what the
  existing `getOnChainTask` pre-check was reaching for.
- `completeTaskOnChain` in `src/lib/contracts/signer.ts` should be removed rather than left in
  place unused — it cannot succeed, and leaving a callable function that always reverts is how this
  survived in the first place. Note `src/lib/__tests__/signer.test.ts` exercises it in four places
  and `mcp-resolve-dispute.test.ts` mocks it, so those need updating with it (and see `CC-060`:
  that test file is also the one broadcasting real transactions).

**No contract change and no redeploy are implied by this fix.** Redeploy timing was formally
deferred until `CC-037` confirms the funding flow end to end. Note `CC-034`/`CC-049` separately
contemplate adding `completeTaskByOwner(taskId)` at the mainnet deploy as an *emergency* function
for tasks stuck by signer rotation — that remains a real operational question, but it is not the
fix for this issue and should not be conflated with it. Such a function would still pay
`task.worker`, which is fixed on-chain at funding time, so it would not create an
arbitrary-destination payout.

## Acceptance

- A full task lifecycle completes: an agent funds a task, the worker delivers,
  `confirm_task_completion` records it, the agent calls `completeTask` from its own wallet, USDC
  lands in the worker's wallet, and the DB reflects `completed` only after the `TaskCompleted`
  event is observed.
- No code path calls `completeTask` with the platform signer.
- The MCP tool's response gives an agent everything it needs to settle, and says plainly that
  settlement is the agent's action.

## Why this was not caught earlier

Recorded because it is the transferable part. The revert is handled correctly and returns a clear
error, so from the outside it looks like a working error path rather than a dead code path — and
nothing had ever driven the flow far enough to hit it, because all testing to date has been
worker-side (wallet connection, registration, site functionality — `CC-069`, `CC-071`, `CC-055`).
`CC-032` was supposed to cover this, but it was one large ticket that was never started, so its
happy path was never attempted. This is the third defect in this area found by tracing a call path
rather than by running it (`CC-059` found `CC-065` the same way).

Related: `CC-037` (verifies the invariants by reading; item 1 is what pre-empted this),
`CC-078` (the Settlement stage test, blocked on this), `CC-032`, `CC-065`, `CC-051`.
