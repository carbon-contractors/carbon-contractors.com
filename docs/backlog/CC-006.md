# CC-006 — Supabase keep-alive cron targets a table that does not exist

## Problem
`.github/workflows/keep_alive.yml:14` pings `/rest/v1/keepalive`. There is no `keepalive`
table in any of migrations 001-011, so the workflow has been erroring rather than keeping
the project warm.

On the Supabase free tier a paused project takes the entire site down — including the
waitlist form, which is the one thing currently earning value.

Note: `/api/health` currently reports `database: ok` with ~820ms latency, so the project is
awake right now. That is luck, not the cron.

## Fix
Point the ping at an existing table (`humans` with `?select=id&limit=1`), confirm the
workflow run goes green, and confirm the cron cadence (currently every 3 days) is inside
the free-tier pause window.

## Acceptance
A green workflow run, and a deliberate check that the ping returns 200 rather than 404.

## Closed 2026-07-30 — wontfix. **The original finding was wrong.**

`pg_policies` output from the live database shows a `keepalive` table with a `public read`
policy granting `SELECT` to `anon` (`qual: true`). The workflow pings it with the anon key
(`.github/workflows/keep_alive.yml:16-18`). So the cron **works**, and has been keeping the
project warm as intended. That is also consistent with `/api/health` reporting
`database: ok` after four months of dormancy.

### Why the original finding was wrong
The claim was: "there is no `keepalive` table in any of migrations 001-011, so the workflow has
been erroring." The premise was true; the conclusion did not follow. Absence from the migration
files is not absence from the database.

This is precisely the error class described in `docs/Lessons-Learned.md` §6 — reasoning from an
incomplete source and presenting the result as fact. Recorded rather than quietly deleted,
because the failure is the useful part.

### What it actually revealed
`keepalive` is a **second confirmed out-of-band object**, alongside `exec_sql`. Two known
objects exist in production that appear in no migration. That moves the schema-drift problem
from suspicion to established fact and makes **CC-057** materially more important — the
`supabase db pull` diff is now guaranteed to return findings.

### Residual, minor
- Confirm the `keepalive` table holds nothing meaningful. It is anon-readable, so anything in it
  is public.
- Fold both objects into the CC-057 reconciliation so they end up in a migration.

## Closed 2026-07-30 (3) — done. And the explanation was wrong a **third** time.

Migration 013 confirmed applied. `keepalive` returns `404 PGRST205` to the anon key
("Could not find the table 'public.keepalive' in the schema cache") while all seven other public
objects — `humans`, `tasks`, `tasks_public`, `waitlist`, `notification_channels`, `used_nonces`,
`mcp_challenges` — resolve in that same cache. Since `DROP TABLE` triggers a PostgREST schema
reload, the cache is demonstrably current and `keepalive` alone is absent from it.

### The actual reason the keepalive failed

Every previous explanation, including the one written above, was inference. The GitHub Actions run
history settles it. The workflow ran **30 times: 8 succeeded, 22 failed.** Exit codes pulled from
six failures spanning April to July are **all exit code 6** — curl `CURLE_COULDNT_RESOLVE_HOST`.

That single fact disposes of the original finding's mechanism. The workflow used `curl -f`, which
exits **22** on an HTTP error such as a 404 for a missing table. It never exited 22. **The absent
`keepalive` table never caused a single failure.**

Exit 6 means DNS did not resolve, which is what a *paused* Supabase project looks like — paused
projects lose their DNS record. So the ping was not failing and thereby allowing a pause; it was
failing *because the project was already paused*. A keepalive cron is a one-way trapdoor: it can
only prevent pausing, never recover from it, because once paused the ping can no longer land.

The repository secrets were last updated 2026-04-13 and were unchanged across both the successes
and the failures, so a malformed secret is ruled out.

Timeline: last success 2026-06-01, then 15 consecutive failures through 2026-07-13, after which
GitHub set the workflow to `disabled_inactivity`.

And the detail that matters most for `CC-058`: **2026-05-04 succeeded, 2026-05-07 already failed.**
The project paused within three days of a *successful* ping. So a REST read against a small table
evidently does not reset Supabase's inactivity timer at all. The conclusion in the previous section —
"a ping every three days does not reliably prevent free-tier pausing" — is correct, but not for the
stated reason, and the stronger version is that **no ping cadence would have worked.** That makes
`CC-058` the only real fix, on firmer ground than before.

### Score-keeping, because it is the useful part

1. Original finding: "no `keepalive` table exists, so the workflow has been erroring." Premise
   wrong, **conclusion right** — it had been erroring, continuously, for months.
2. First correction: "the table exists, so the cron works." Wrong.
3. Second correction: "it ran but a 3-day ping is too infrequent." Wrong reason, right decision.
4. Now, from run logs: it ran, failed 22 of 30 times on DNS, and the cadence was never the variable.

A correct conclusion was talked out of twice by better-informed-looking reasoning. Recorded in
`docs/Lessons-Learned.md` §11.
