# CC-041 — Enforce YubiKey-only 2FA on GCP

Migrated from NOR-301. The whole zero-secret escrow story rests on GCP being unbreachable —
the HSM key cannot be extracted, but anyone who can reach the GCP console can re-point IAM.

## Scope
- YubiKey-only 2FA enforced at GCP org/project level, no TOTP or SMS fallback
- Verify `gcloud` CLI requires FIDO2
- Verify the KMS service account has no interactive login path
- Document the final 2FA posture in `docs/Security-Trust-Disclosure.md`

## Hardware-swap note
See CC-053. A motherboard swap destroys TPM-backed platform credentials. If any GCP factor
was a Windows Hello passkey rather than the YubiKey, that factor is gone — which is exactly
the fragility this issue exists to remove.

Related: CC-039, CC-053.

## Update 2026-08-10 — reclassified: public-launch, not mainnet

The GCP account this protects already controls the HSM/KMS key that already arbitrates disputes
today, per `CC-059`. Anyone who can re-point IAM on that project can already cause real damage —
that risk exists the moment the site is public, not just once real money is moving through it.

## Update 2026-08-11 — backlog triage pass

Lowered P1 → **P2** by Aaron's call during the triage pass. The KMS key remains
non-exportable regardless of the 2FA posture, and the GCP project has a single account holder.

Worth keeping visible rather than forgetting: `CC-059` did raise the stakes here. Ownership of both
contracts now sits with the HSM address `0xa8931097540e69B474013D294d0bA6A2cC853e4b`, and that key
arbitrates live disputes — so console access to that project is equivalent to control over dispute
outcomes. Also unresolved from `CC-053`: if any enrolled factor was a Windows Hello passkey rather
than the YubiKey, the motherboard swap destroyed it. Checking which factors are actually enrolled is
the cheap first step whenever this is picked up.
