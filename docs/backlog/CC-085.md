# CC-085 — Invariant monitoring

Specified by `ADR-0003`, which splits `CC-040` in two. This is the correctness half. `CC-040` keeps
the operational, day-of half.

## Why this is not a day-of task

`CC-040`'s "set it up right before launch, or you are just watching an empty coming-soon page"
reasoning is correct for availability monitoring and **wrong for this**, because `ADR-0001` and
`ADR-0002` introduced failure modes that are **silent** — the system keeps working and produces
wrong outcomes without erroring:

- **Checker unavailability auto-releases funds.** `ADR-0001` D6: no valid failing verdict before
  the window closes → the worker can claim. If the checker is down, every task in flight becomes
  claimable regardless of evidence quality. Fraudulent submissions get paid and **nothing errors**
  — the system does exactly what it was designed to do. Highest-consequence gap in the design.
- **Verdict signing failure looks identical to a passing task.** Post-Amendment 1 the platform makes
  no transaction, so there is no failed transaction to alert on. The absence of a signature is the
  failure, and absence is not an event.
- **Unclaimed settlements look like theft.** Pull-payment means funds sit until the worker claims.
- **Retention job failure publishes a false claim** rather than degrading a feature.
- **Commitment drift is undetectable by reading.**

The next work item after the contract lands is running the full funded lifecycle
(`CC-077`/`078`/`079`). **These monitors are how you know it actually worked.** Building them after
means verifying the same properties twice.

## The monitors

Each is a script exiting non-zero on violation — same pattern as the existing
`verify-contract-owner.mjs` and `verify-escrow-solvency.mjs`, not a new framework.

| Monitor | Invariant | Violation means |
| :-- | :-- | :-- |
| `verify-escrow-solvency` (exists) | `balanceOf(escrow) == totalLocked` | funds stranded |
| `verify-commitments` | every DB row hashes to its on-chain commitment | DB corrupt or tampered |
| `verify-retention` | no task content past terminal state + window | published privacy claim false |
| `verify-signer` | the verdict signer can produce a valid signature | settlement degrades to auto-release |
| `verify-checker` | canary set yields expected verdicts | the checker is wrong, not merely down |
| `verify-unclaimed` | no claimable task older than N days | pull-payment UX broken |
| `verify-verdict-rate` | verdicts ÷ submissions over a window | pipeline failing silently |
| `verify-concurrent-escrow` | peak concurrent USDC escrowed per funding agent | `CC-051` threshold instrumentation |

## Alert on absence, not error

The dominant post-Amendment-1 failure is *nothing happened*, which conventional error alerting
cannot see. Every invariant is a **positive assertion checked on a schedule**. The monitors must
report success, so that **silence from the monitor is itself an alert** — a cron that stops running
has to be detectable.

## Near-zero cost, per ADR-0003 D5

Scheduled GitHub Actions running the scripts · webhook to Discord or Telegram · Sentry free tier for
application errors · a free external uptime monitor against `/api/health` · on-chain event
monitoring via scheduled `getLogs`. **Explicitly reject a paid indexer** at current volume.

**Two alerting paths are required, not one.** Scheduled Actions are best-effort, can be delayed, and
are auto-disabled after repository inactivity. Fine for hourly invariant checks; not acceptable as
the only path. The external uptime monitor must be independent of GitHub so one path survives
GitHub being the thing that failed.

## Acceptance

All monitors run on a schedule, report success as well as failure, alert on two independent paths,
and are wired into CI. `verify-checker` and `verify-escrow-solvency` route somewhere that wakes
someone up.
