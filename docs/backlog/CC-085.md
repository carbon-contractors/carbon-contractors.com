# CC-085 — Invariant monitoring

Specified by `ADR-0003`, which splits `CC-040` in two. This is the correctness half. `CC-040` keeps
the operational, day-of half.

## Why this is not a day-of task

`CC-040`'s "set it up right before launch, or you are just watching an empty coming-soon page"
reasoning is correct for availability monitoring and **wrong for this**, because `ADR-0001` and
`ADR-0002` introduced failure modes that are **silent** — the system keeps working and produces
wrong outcomes without erroring:

- **Checker unavailability auto-releases funds.** `ADR-0001` D6: no valid failing verdict before
  the window closes → the worker can claim. If the checker is down, every task in flight becomes
  claimable regardless of evidence quality. Fraudulent submissions get paid and **nothing errors**
  — the system does exactly what it was designed to do. Highest-consequence gap in the design.
- **Verdict signing failure looks identical to a passing task.** Post-Amendment 1 the platform makes
  no transaction, so there is no failed transaction to alert on. The absence of a signature is the
  failure, and absence is not an event.
- **Unclaimed settlements look like theft.** Pull-payment means funds sit until the worker claims.
- **Retention job failure publishes a false claim** rather than degrading a feature.
- **Commitment drift is undetectable by reading.**

The next work item after the contract lands is running the full funded lifecycle
(`CC-077`/`078`/`079`). **These monitors are how you know it actually worked.** Building them after
means verifying the same properties twice.

## The monitors

Each is a script exiting non-zero on violation — same pattern as the existing
`verify-contract-owner.mjs` and `verify-escrow-solvency.mjs`, not a new framework.

| Monitor | Invariant | Violation means | Status |
| :-- | :-- | :-- | :-- |
| `verify-escrow-solvency` (exists) | `balanceOf(escrow) == totalLocked` | funds stranded | scheduled |
| `verify-contract-owner` (exists) | the HSM key owns the escrow | ownership lost or never transferred | scheduled |
| `verify-commitments` | every DB row hashes to its on-chain commitment | DB corrupt or tampered | deferred → `CC-084` |
| `verify-retention` | no task content past terminal state + window | published privacy claim false | deferred → `ADR-0002` D4 job |
| `verify-signer` | the verdict signer can produce a valid signature | settlement degrades to auto-release | built |
| `verify-checker` | canary set yields expected verdicts | the checker is wrong, not merely down | deferred → `CC-083` |
| `verify-unclaimed` | no claimable task older than N days | pull-payment UX broken | built |
| `verify-verdict-rate` | verdicts ÷ submissions over a window | pipeline failing silently | deferred → `CC-083`/`CC-084` |
| `verify-concurrent-escrow` | peak concurrent USDC escrowed per funding agent | `CC-051` threshold instrumentation | built |

`verify-contract-owner` was not in the original table. It already existed, it is an
invariant, and `ADR-0003`'s handover step 3 says to schedule "the two that already exist" —
so it is scheduled alongside the others.

## Alert on absence, not error

The dominant post-Amendment-1 failure is *nothing happened*, which conventional error alerting
cannot see. Every invariant is a **positive assertion checked on a schedule**. The monitors must
report success, so that **silence from the monitor is itself an alert** — a cron that stops running
has to be detectable.

## Near-zero cost, per ADR-0003 D5

Scheduled GitHub Actions running the scripts · webhook to Discord or Telegram · Sentry free tier for
application errors · a free external uptime monitor against `/api/health` · on-chain event
monitoring via scheduled `getLogs`. **Explicitly reject a paid indexer** at current volume.

**Two alerting paths are required, not one.** Scheduled Actions are best-effort, can be delayed, and
are auto-disabled after repository inactivity. Fine for hourly invariant checks; not acceptable as
the only path. The external uptime monitor must be independent of GitHub so one path survives
GitHub being the thing that failed.

## Acceptance

All monitors run on a schedule, report success as well as failure, alert on two independent paths,
and are wired into CI. `verify-checker` and `verify-escrow-solvency` route somewhere that wakes
someone up.

## Open

From `ADR-0003`: `verify-unclaimed` age threshold, `verify-verdict-rate` floor and window, alert
routing tiers.

Related: `ADR-0003`, `CC-040`, `CC-083` (canary), `CC-086` (kill switch, the runbooks' first step),
`CC-051`, `CC-077`, `CC-078`, `CC-079`.

## Update 2026-08-15 — three monitors and the alerting layer built and run live

Branch `claude/cc-085-invariant-monitors`. Everything below was **run against the live Base
Sepolia deployment** (`0xe80d03688E8fa6270668AD73191d353e522CB1b1`, the `CC-082` v2
contract), not merely written. `Lessons-Learned.md` §23 is the reason that sentence is here.

### Built

| File | What it does |
| :-- | :-- |
| `scripts/audit/verify-signer.mjs` | four checks, three of which need no credentials |
| `scripts/audit/verify-unclaimed.mjs` | `Delivered` tasks claimable for more than N days |
| `scripts/audit/verify-concurrent-escrow.mjs` | `CC-051`'s two exemption limbs, from an event replay |
| `scripts/audit/run-monitors.mjs` | the runner: registry, statuses, webhook, dead-man's switch |
| `.github/workflows/monitors.yml` | hourly schedule + `workflow_dispatch` |
| `npm run monitors` / `npm run monitors:list` | local run · offline registry validation |

`npm run monitors:list` is wired into `ci.yml`. It is offline and takes no secrets — it
asserts every script named in the registry exists, so a renamed or deleted monitor fails a
PR instead of silently dropping out of the schedule while it keeps reporting green. The
monitors themselves are **not** run in CI: they read the live chain, and a `pull_request`
trigger holding secrets is exactly what should not exist.

### `verify-signer` — the gap `npm run verify:kms` left

`verify:kms` proves the KMS key can sign and that the signature recovers to the derived
address. It proves nothing about whether the *contract* will accept that signature, and
every one of those failures is silent:

1. **`acceptedSigners[signer]`** — the check the ticket asked for. A signer the contract
   does not accept reverts `VerdictSignerNotAccepted()` on every claim and dispute.
2. **`domainSeparator()`** vs one computed for this escrow. EIP-712 binds the signature to
   `verifyingContract`, so **a redeploy invalidates every signature shaped for the old
   address** — which is precisely the situation that existed this morning. It looks like a
   bad key and it is a stale address.
3. **`VERDICT_TYPEHASH()`** vs the struct this repo signs.
4. the live KMS round trip, delegated to `npm run verify:kms` as a child process so the
   DER → r/s/v conversion exists in exactly one place.

Checks 1–3 need no credentials, so they run everywhere including the scheduled workflow.
`--signer=0x…` checks a different address, for confirming `setVerdictSigner()` landed
before rotating to a new key.

### Thresholds chosen (`ADR-0003` open items — narrowed, not closed)

- **`verify-unclaimed`: 3 days** past the review deadline. `MIN_REVIEW_WINDOW` is 12h and a
  worker who is owed money and knows it claims within hours; 3 days absorbs a weekend
  without paging and still surfaces before a worker concludes they have been robbed and
  says so publicly. `MONITOR_UNCLAIMED_MAX_AGE_DAYS` overrides. **Revisit once there is real
  claim latency to measure** — this number is reasoned, not observed.
- **`verify-concurrent-escrow`: $5,000 per client concurrent, $10m trailing-365-day
  volume**, warn at 80%. Both come straight from `CC-051`; neither is a judgement call.
- **Alert routing:** `tier: wake` on solvency, owner and signer; `normal` on the other two.
  Currently one channel — the tier is carried in the payload so a second route is a change
  to the webhook target, not to the monitors.

### Alerting — two paths, and why success is not announced

- **Path 1, webhook** (Discord / Slack / Telegram): fires on failure. Tells you *what*
  broke. It cannot report its own absence, because it needs the run to have happened.
- **Path 2, dead-man's switch**: the runner pings `MONITOR_HEARTBEAT_URL` **only on a fully
  green run**, and `…/fail` otherwise. A free external cron monitor alerts when the ping
  does not arrive. That is the path that survives Actions being delayed, Actions being
  auto-disabled after 60 days of repository inactivity — **this repo was dormant
  May–July 2026, so that is a lived failure mode, not a hypothetical** — and GitHub itself
  being what failed.

Success is deliberately not posted to the webhook by default (`MONITOR_HEARTBEAT_ON_SUCCESS=1`
opts in). An hourly "all clear" is read for a week and ignored forever after, and an alert
channel nobody reads is not an alert channel. Silence is the success signal; path 2 is what
turns silence into noise when it should not be silent.

**Alert delivery is itself monitored.** A failed webhook POST exits non-zero and skips the
heartbeat, so the run goes red *and* path 2 fires. An alerting system that fails quietly is
worse than none, because it is trusted.

No paid indexer (`ADR-0003` D5 — every monitor reads the chain directly with chunked,
`ESCROW_DEPLOY_BLOCK`-bounded `getLogs`), no paid alerting vendor, no database, no state
carried between runs.

### Deliberately not built, and on what

- **`verify-checker`** — blocked on `CC-083`. There is no checker and no canary fixture, so
  there is nothing to assert against. This is the highest-consequence monitor in the ADR and
  it stays unbuilt until the thing it checks exists.
- **`verify-commitments`** — blocked on `CC-084`. `specHash` is committed on-chain today but
  no spec schema exists, so there is no DB preimage to hash and compare.
- **`verify-retention`** — blocked on the `ADR-0002` D4 retention job. Nothing deletes
  anything yet, so the monitor would assert against a policy with no implementation.
- **`verify-verdict-rate`** — needs both a checker (`CC-083`) and submissions at a volume
  where a ratio means something. Zero verdicts over zero submissions is not a signal.

A stub that always passes would be worse than the absence, because it reads as coverage.

### Verified live, both branches

```
node --env-file=.env.local scripts/audit/run-monitors.mjs --no-alert
  PASS  verify-escrow-solvency      CLEAN — balance equals totalLocked.
  PASS  verify-contract-owner       PASS — owned by the HSM-derived address.
  PASS  verify-signer               CLEAN — configured for this deployment.
  PASS  verify-unclaimed            CLEAN — nothing claimable past the threshold.
  PASS  verify-concurrent-escrow    CLEAN — both limbs have headroom, replay reconciles.
  5 pass · 0 fail · 0 skip                                          (~10s total)
```

Detection paths were exercised against **real chain state**, not fixtures:

- `verify-signer --signer=<not-accepted>` → exit 1, correct diagnosis.
- `verify-unclaimed --as-of=2026-08-20T00:00:00Z` → exit 1 on the live `Delivered` task,
  `4.43 d` claimable. `--as-of` exists for exactly this: evaluating the invariant at a
  different wall-clock time against real state, so the detection path can be proven while
  no violation exists yet.
- `verify-concurrent-escrow --per-client-limit=1 --annual-limit=2` → exit 1 on both limbs;
  at `--annual-limit=3` the 80% warn fires and the exit stays 0.
- Runner: webhook delivery (Discord and Telegram payload shapes) and heartbeat ping/`/fail`
  proven against a local receiver; unreachable webhook → exit 1; missing env → `SKIP`;
  `--strict` turns `SKIP` fatal; unknown `--only=` → exit 2.

**`verify-concurrent-escrow` reconciles its event replay against `totalLocked()`** and
refuses to be trusted when they disagree. Live: replay says 1 USDC open, contract says
1 USDC. A threshold breach is a fact about the business; a replay mismatch means the
instrument is lying, and that is the louder failure.

## Update 2026-08-16 — the alerting drill

`MONITOR_WEBHOOK_URL` and `MONITOR_HEARTBEAT_URL` are set as repository secrets, and the heartbeat
proved itself on the first real scheduled run (`heartbeat ping delivered (HTTP 200)`). **The webhook
leg had still never been watched to fire outside a local receiver** — and an alerting path nobody
has seen work is not one you can rely on. A live incident is the wrong moment to learn it does not.

`run-monitors.mjs` now takes `--args=`, appended to every selected monitor, exposed as the
`monitor_args` input on `workflow_dispatch`.

**Deliberately generic, not a `--threshold-days` flag.** Which monitor can be driven into failure
depends on what is on chain at the time:

- With a task in flight, `--max-age-days=0.001` breaches `verify-unclaimed`.
- **Against a settled escrow it cannot, at any threshold** — there are no `Delivered` tasks to find.
  Measured 2026-08-16 after `CC-082`'s task was claimed: `--max-age-days=0.001` exits `0`.
- `--annual-limit=1` still bites, because `verify-concurrent-escrow` replays historical volume that
  survives settlement.

Hard-coding either would have shipped a drill that silently stopped working the moment the chain
state changed.

Two properties that matter more than the flag itself:

- **A drill is labelled as one.** The payload leads with `🧪 DRILL — NOT A REAL FAILURE` and echoes
  the overrides. If a test alert were indistinguishable from a real one, the next genuine alert is
  one someone has already been trained to ignore — worse than no alert at all.
- **A drill does not touch the heartbeat.** The dead-man's switch exists to record whether the
  monitors are really running and really passing. Marking it down because someone tested the webhook
  makes its own history lie, and that history is the only thing separating "the schedule stopped"
  from "everything is fine". Drills exercise path 1; path 2 proves itself on every real green run.

Safe on the schedule by construction: a scheduled run supplies no workflow inputs, so `--args` is
always empty there and cannot arm itself. The input is passed to the shell via `env:` rather than
`${{ }}` interpolation, since this job holds secrets and interpolation happens before the shell
sees the string.

Verified end to end against a local receiver, not assumed:

```
runner exit=1
alerting  webhook delivered (HTTP 204)
alerting  heartbeat skipped — drill runs must not mark the dead-man's switch down
payload:  🧪 **DRILL — NOT A REAL FAILURE.** … overrides: --annual-limit=1
```

Normal run regression-checked: 5 pass, exit 0, unchanged behaviour.

**To run the drill:** Actions → Invariant monitors → Run workflow → `monitor_args` = `--annual-limit=1`.

## Update 2026-08-16 — the drill commit broke the schedule for seven hours

Same-day regression from the update above, found while chasing an unrelated CI question. Recorded
here rather than as a new issue because it is a defect in this ticket's own work.

**`monitors.yml` was an invalid workflow file from 02:29 to 09:0x.** The comment added inside the
`Run monitors` step's `run:` block — the one explaining why inputs go through `env:` rather than
being interpolated — contained a literal empty expression pair. GitHub scans the whole `run:` scalar
for expressions before any shell sees it and does not care that the line is a shell comment, so the
file failed to parse.

**An invalid workflow on the default branch stops its schedule.** Not "runs and fails" — does not
run. Last successful scheduled run 01:59; seven hourly runs missed.

```
gh run list --workflow monitors.yml
  31936982066  failure  push      master   2026-08-16T08:38:57Z   .github/workflows/monitors.yml
  31920840990  success  schedule  master   2026-08-16T01:59:57Z   Invariant monitors
```

The name rendering as the file path rather than `Invariant monitors` is the tell for a startup
failure. Nothing else in the API surfaces it: no job is created, so there is no check run, no log,
and `--log-failed` returns `log not found`. **The error text exists only as an annotation in the
Actions web UI** — `(Line: 112, Col: 14): An expression was expected`.

Fixed by rephrasing the comment, plus a note in the file telling the next person not to write the
delimiters there at all.

### What this says about the design

**Path 2 is the only thing that could have caught this, which is exactly why `ADR-0003` D5 insisted
on it.** The webhook cannot fire when no run happens. The dead-man's switch is not hosted by the
thing that stopped, so it is the only mechanism in the design capable of reporting "the monitors are
not running". This is its first test against a real outage rather than a drill.

**Nothing was at risk** — the escrow is settled, no funds are in flight, and the site is gated. The
cost was the gap itself, not a missed violation.

### The gate that was missing — now added

**Nothing gated workflow files.** CI did not lint them, so the class of change most able to break
scheduled monitoring — a change to the monitoring workflow — was the class with no check on it.

`actionlint` now runs as the **first** step of the CI job: it needs nothing installed, so a broken
workflow file fails in seconds rather than after `npm ci` and a contract compile. It would have
caught this exact defect in the PR.

Pinned by version **and** sha256 (`1.7.12`), and deliberately **not** a marketplace action. This
step downloads a binary and executes it inside a job that checks out the repository; a mutable tag
in that slot is a silent code change. The checksum is taken from the release's own `checksums.txt`
and both values are bumped together.

→ `Lessons-Learned.md` §25.

## Update 2026-08-17 — both alerting paths proved themselves, and the reporting failed

**The open question from 2026-08-15 is closed. Both paths have now fired on real events**, not
drills:

- **Path 2** caught a genuine 51-minute gap and reported the recovery.
- **Path 1** delivered a real monitor failure to Discord.

That is the design working. What did not work is what the alert *said*.

### The alert's entire content was a version string

```
misconfig · verify-concurrent-escrow · Version: viem@2.55.10
```

Three defects behind one line, none of them an invariant violation. Four monitors passed; the fifth
crashed rather than finding a problem, and re-running it locally against the live chain returns
`CLEAN` with the replay reconciling.

**1. The alert is guaranteed uninformative on any crash.** `verdictLine()` looked for a line
starting with a known verdict marker and, finding none, returned `lines.at(-1)`. The last line of
every uncaught viem error is its version footer, so *every* RPC failure in *any* monitor reported
identically and told the reader nothing. The comment directly above that function reads *"an alert
that makes you go and open the log to learn anything at all is a worse alert."*

**2. A transient network failure was reported as `misconfig`.** `verify-concurrent-escrow` returned
exit `2` on any RPC error, and `2` means "set up wrong" — sending the reader after a configuration
problem that does not exist.

**3. No retry, though the pattern already existed in this directory.**
`verify-escrow-deployment.mjs` has had a `withRetry` helper since `CC-085` shipped. The monitors
run hourly against a rate-limited public endpoint (`CC-048`), and one blip cost a Discord alert, an
hour of heartbeat downtime and a recovery email.

Taken together that is **alert fatigue**, arriving exactly where this ticket's own reasoning said it
would: *an alert channel nobody reads is not an alert channel.* The channel was training its reader
to ignore it, and the one thing it could not do was say why.

### Fixed

- **`scripts/audit/rpc-retry.mjs`** — retry with exponential backoff, transient failures only. A
  revert or bad address throws immediately, because retrying a genuine finding just delays the
  alert. Safe because every monitor here is read-only.
- **Exit `3` = `TRANSIENT`**, distinct from `2` = `MISCONFIG`. Still counts as a failed run — an
  unchecked invariant is not a passing one (`ADR-0003` D3) — but labelled so the response differs.
- **`scripts/audit/verdict-line.mjs`** — extracted so it can be tested, which it could not be while
  inline in a self-executing script. On a crash it now reports `CRASHED before reporting a verdict`
  plus the error class and viem's `Status:`/`URL:` detail, skipping version footers and stack frames.
- **`verify-concurrent-escrow` fetches sequentially**, not four concurrent chunked sweeps. It is the
  heaviest monitor by request count and the concurrency was provoking the rate limit the retry then
  had to absorb. Costs ~16s instead of ~6s on an hourly job.

### Tests, and the one that earned its place

`scripts/` had **no test coverage at all** — `vitest.config.ts` included only `src/`. That is how an
untested fallback in the alerting path reached production. The include now covers
`scripts/**/__tests__/**/*.test.mjs`, with 10 tests built from the real 2026-08-17 output.

One of them failed on first run and caught a bug in the fix itself: the error-class matcher was
anchored to line start, and the real output is `block timestamp read failed: HttpRequestError: …`,
where the class sits mid-line. The repair would have shipped still dropping the most useful token.

### Pattern across all three CC-085 regressions this week

`§25` (a comment disabled the schedule), the seven-hour outage, and now this. **The monitoring logic
has been correct every time; the reporting around it has failed three times.** Worth weighting
future work here toward the delivery path rather than more invariants.

## Update 2026-08-21 — retrofit RPC retry and transient handling across all monitors

While `verify-concurrent-escrow` was hardened in the previous update, `verify-unclaimed` remained un-retrofitted. Over Aug 19–20, scheduled runs repeatedly failed when `verify-unclaimed` hit public RPC rate limits (`https://sepolia.base.org` returning `Details: over rate limit`), returning exit `2` (`MISCONFIGURED`) and causing alert floods.

### Fixed

1. **`verify-unclaimed.mjs`**:
   - Integrated `withRpcRetry`, `isTransient`, and `shortError` from `./rpc-retry.mjs`.
   - Changed concurrent `Promise.all([ getLogsChunked(...) ])` to sequential sweeps wrapped in retry.
   - Wrapped `getBlockNumber()` and `getTask` calls in `withRpcRetry`.
   - Returns exit code `3` (`TRANSIENT`) for network/rate-limit blips, distinguishing them from exit `2` (`MISCONFIGURED`).
2. **`verify-escrow-solvency.mjs`**, **`verify-signer.mjs`**, **`verify-contract-owner.mjs`**:
   - Integrated `withRpcRetry` and exit code `3` (`TRANSIENT`) across all on-chain queries.
3. **`rpc-retry.mjs` & tests**:
   - Added regex support for `RPC Request failed` / `over rate limit` variants.
   - Verified 189 unit tests pass and all 5 invariant monitors pass cleanly against live Base Sepolia state.
