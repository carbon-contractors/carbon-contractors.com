# CC-037 — Re-verify the escrow trust boundary against current code

## Why
A review pass was run against the pre-hiatus tree (73 commits stale) and raised serious
concerns. Master has since landed "Server-side platform signer for escrow write operations",
AUD-005 atomic state transitions, and AUD-006 idempotent on-chain checks — so most or all of
it is likely already fixed. But it was never confirmed on the current code, and these are the
findings that would lose other people's money.

## Verify specifically
1. `/api/fund-task` causes `escrow.createTask(...)` to execute, rather than sending a bare
   USDC transfer to the contract address. `CarbonEscrow.sol` has no sweep or rescue function,
   so USDC arriving without a task is unrecoverable. Check whether anything is already
   stranded at the Sepolia escrow address.
2. `completeTask()` pays the address held in on-chain escrow state, never a DB value.
3. DB status is a projection of chain state: `active` gated on the on-chain task being
   funded, `completed` gated on a confirmed `TaskCompleted` event.
4. `resolve_dispute` authorises the platform owner, matching `onlyOwner` on the contract —
   not the disputing agent.
5. `to_human_wallet` is validated against the `humans` table, and `from_agent_wallet` is
   bound to the authenticated caller rather than accepted as an argument.
6. `ReputationStake.slash()` is wired into dispute resolution, or the "skin in the game"
   claim is removed from the README.

Treat each as unproven until read in the current tree.

## Update 2026-07-25 — this now has a second purpose

Beyond fund safety, this issue is the evidence base for the regulatory position in **CC-051**.

The strongest argument that the platform is not a Digital Asset Platform is not "the operator
cannot extract the signing key" — it is "the contract permits no destination other than the
on-chain worker or a refund to the funding agent." That is a claim about code, and items 2, 3, 4
and 5 below are what verify it.

Priority consequence: item 4 (does `resolve_dispute` authorise the platform owner, and can the
owner direct funds to an arbitrary address?) matters more than its position in the list suggests.
An owner-directed arbitrary payout would be both a security finding and the collapse of the
non-custodial argument.

## Update 2026-08-11 — backlog triage pass

Reviewed in the triage pass — **stays P0, and is the next piece of work.** Aaron's call.
It is the only P0 that is both actionable immediately and load-bearing twice over: fund-safety
invariants on already-deployed contracts, and the evidence base for `CC-051`'s non-custodial

**Correction to this issue's own 2026-08-10 update.** It states `CC-059` "transferred escrow
ownership to the KMS/HSM key" — that is correct, and `CLAUDE.md`'s landmine claiming
`transferOwnership()` was never called is the stale one. Fixed in `CLAUDE.md` as part of this
triage pass. Ownership of both contracts sits with `0xa8931097540e69B474013D294d0bA6A2cC853e4b`,
independently confirmed on Basescan.

**Item 1 is partly pre-answered, and the answer is surprising.** Nothing server-side calls the
contract's `createTask` at all. `src/lib/db/tasks.ts:createTask` is an unrelated database
function; `src/lib/payments/x402.ts:45` and `src/lib/contracts/escrow.ts:6` both state the agent
funds the escrow client-side from its own wallet. So `task.agent` is the agent's wallet, set by
`agent: msg.sender` at `contracts/CarbonEscrow.sol:107`. Confirming that end of the flow properly
is what closes the redeploy question deferred during triage, and it is why `CC-080` exists.

Item 4 remains the highest-value item, per the 2026-07-25 update: whether the owner can direct funds
to an arbitrary address is both a security finding and the hinge of the `CC-051` position.
