# CC-037 — Re-verify the escrow trust boundary against current code

## Why
A review pass was run against the pre-hiatus tree (73 commits stale) and raised serious
concerns. Master has since landed "Server-side platform signer for escrow write operations",
AUD-005 atomic state transitions, and AUD-006 idempotent on-chain checks — so most or all of
it is likely already fixed. But it was never confirmed on the current code, and these are the
findings that would lose other people's money.

## Verify specifically
1. `/api/fund-task` causes `escrow.createTask(...)` to execute, rather than sending a bare
   USDC transfer to the contract address. `CarbonEscrow.sol` has no sweep or rescue function,
   so USDC arriving without a task is unrecoverable. Check whether anything is already
   stranded at the Sepolia escrow address.
2. `completeTask()` pays the address held in on-chain escrow state, never a DB value.
3. DB status is a projection of chain state: `active` gated on the on-chain task being
   funded, `completed` gated on a confirmed `TaskCompleted` event.
4. `resolve_dispute` authorises the platform owner, matching `onlyOwner` on the contract —
   not the disputing agent.
5. `to_human_wallet` is validated against the `humans` table, and `from_agent_wallet` is
   bound to the authenticated caller rather than accepted as an argument.
6. `ReputationStake.slash()` is wired into dispute resolution, or the "skin in the game"
   claim is removed from the README.

Treat each as unproven until read in the current tree.

## Update 2026-07-25 — this now has a second purpose

Beyond fund safety, this issue is the evidence base for the regulatory position in **CC-051**.

The strongest argument that the platform is not a Digital Asset Platform is not "the operator
cannot extract the signing key" — it is "the contract permits no destination other than the
on-chain worker or a refund to the funding agent." That is a claim about code, and items 2, 3, 4
and 5 below are what verify it.

Priority consequence: item 4 (does `resolve_dispute` authorise the platform owner, and can the
owner direct funds to an arbitrary address?) matters more than its position in the list suggests.
An owner-directed arbitrary payout would be both a security finding and the collapse of the
non-custodial argument.

| :-- | :-- | :-- |
| 1 | `/api/fund-task` causes `escrow.createTask(...)` to execute, not a bare transfer | **FAIL** (code) · clean (state) |
| 2 | `completeTask()` pays the on-chain address, never a DB value | **PASS**, conditionally |

| 4 | `resolve_dispute` authorises the platform owner, not the disputing agent | **SPLIT** — contract passes, app fails |

### Item 1 — FAIL on code, clean on state

`src/app/api/fund-task/route.ts:174-178` exports `withX402(handler, getPlatformWallet(), ...)`, and
`getPlatformWallet()` (`:26-31`) returns `NEXT_PUBLIC_ESCROW_CONTRACT`. An x402 settlement is a plain
ERC-20 transfer, so the documented funding path pays USDC *directly to the escrow contract* and never
calls `createTask`. `CarbonEscrow` has no `receive`, `fallback`, sweep, rescue or owner-withdraw, so
such funds are unrecoverable by anyone.

**Measured, and this is the reassuring half:** `scripts/audit/verify-escrow-solvency.mjs` (added by
this issue — read-only, re-runnable) reports on Base Sepolia:

```
USDC balanceOf(escrow)   0 USDC      escrow.totalLocked()   0 USDC      -> CLEAN
escrow.owner()           0xa8931097540e69B474013D294d0bA6A2cC853e4b
```

Nothing is stranded, because no agent has ever funded a task. The defect is **latent, not historic** —
which is the only reason this is publishable as found rather than an incident. First real use loses
money.

`src/lib/payments/x402.ts` documents *both* designs and ships the wrong one: its header (`:5-7`) and
JSDoc (`:45`) describe agent-side `approve` + `createTask` (correct), while the `instructions` it
returns to agents (`:101-107`) tell them to let an x402 client auto-pay `/api/fund-task`.

Incidentally re-confirms `owner()` is the HSM address, independently of `CC-059`'s own measurement.

### Item 2 — PASS, conditionally

`contracts/CarbonEscrow.sol:133` is `usdc.safeTransfer(task.worker, task.amount)`, reading on-chain
state written at `createTask` (`:106-112`). No payout path in the contract reads a DB value —
`resolveDispute` (`:171`) and `expireTask` (`:191`) likewise use `task.worker` / `task.agent`.

The condition: the *value* in `task.worker` originates from the agent's `to_human_wallet` argument,
which item 5 shows is never validated against the `humans` table. So "pays the on-chain address" is
true, and the on-chain address is only as trustworthy as item 5.

### Item 3 — FAIL, both limbs

- `active` is not gated on the on-chain task being funded. `/api/fund-task:99-101` flips status once
  the x402 facilitator reports payment, with no `getTask()` read — and per item 1 there is no on-chain
  task to read.
- **No code path waits for confirmation.** `src/lib/contracts/signer.ts` has three write functions and
  all three (`:120`, `:152`, `:179`) return the hash straight from `writeContract`. There is no
  `waitForTransactionReceipt` in the file. DB transitions are gated on *submission*, not on a confirmed
  `TaskCompleted` / `TaskResolved` event.

### Item 4 — SPLIT. The contract holds; the app inverts it.

**The contract passes, and this is the finding `CC-051` needs.** `resolveDispute`
(`contracts/CarbonEscrow.sol:159-175`) is `onlyOwner`, and the recipient is
`releaseToWorker ? task.worker : task.agent` — both fixed on-chain at funding time. **No arbitrary
destination is reachable by anyone, owner included.** The strongest form of the non-custodial argument
— "I cannot reach the money, because the contract will not let me" — is verified true. `disputeTask`
(`:141-153`) correctly permits either party.

**The app layer fails.** `resolve_dispute` (`src/lib/mcp/server.ts:808`, check at `:873`) authorises
`task.from_agent_wallet === context.callerWallet`; its own comment says *"only the originating agent
may resolve a dispute."* This item asked whether it authorises the platform owner **rather than** the
disputing agent. It authorises the agent.

**A finding outside the original six:** `dispute_task` (`:683`, check at `:731`) is *also* agent-only.
The contract grants the worker a dispute right; the product removes it. So the reachable sequence is
agent funds -> worker delivers -> agent disputes -> agent self-resolves as a refund -> **worker unpaid,
with no dispute right and no adjudicator.** The owner key rubber-stamps one interested party.

Unreachable today only because item 1 means no on-chain task exists to dispute. Sequencing luck, not a
control.

Design intentionally left open — Aaron's call, filed with options in `CC-081`.

### Item 5 — FAIL, both limbs

`request_human_work` (`src/lib/mcp/server.ts:112`) **never reads `context.callerWallet`**, unlike
`confirm_task_completion`, `dispute_task` and `resolve_dispute`, which all authenticate. With `/api/*`
bypassing the coming-soon gate, task creation is an open endpoint on the live site.

- `from_agent_wallet` is an argument (`:116-119`), not bound to the caller. Task provenance is
  unauthenticated — and it is the field all three privileged tools trust for authorisation. Not
  directly a theft vector, since a false attribution locks the attacker out of those tools, but it is
  the root of trust for the whole authorisation model.
- `to_human_wallet` is format-checked only — Zod regex (`:120-123`) and `isValidWalletAddress`
  (`src/lib/payments/x402.ts:56`) — and **never checked against `humans`**, despite the parameter
  description claiming it comes "from `search_whitepages`".

Live effect today: unlimited unauthenticated `pending` rows with arbitrary addresses and
1000-character descriptions.

### Item 6 — FAIL

`slash(address, uint256)` is `onlyOwner` and documented in the contract as *"triggered on dispute
resolution"* (`contracts/ReputationStake.sol:18,123`). **Nothing calls it.** Grepping `slash` across
`src/`, `contracts/` and `scripts/` finds only the contract, the ABI entry
(`src/lib/contracts/reputation-abi.ts:33`) and read-only display of `slashedTotal`
(`src/lib/reputation/index.ts:88`, `src/app/dashboard/page.tsx:366`).

A stake that cannot be lost is a deposit. `README.md:11` sells staking as the trust layer — *"workers
put skin in the game"* — which is not currently true, and is quotable from a public repo. The
contract's own comment is wrong too.

### What this settles for CC-051

The regulatory position rests on "the contract permits no destination other than the on-chain worker or
a refund to the funding agent." **Item 4 verifies that claim as true at the contract level**, which is
the evidence this issue was also filed to produce. It is a genuinely strong card.

But item 4's app-layer half changes the argument's shape: the platform is not exercising discretion
over someone else's funds — it is executing one party's instruction with its owner key. That is
arguably *better* for the custody question and clearly *worse* for fund safety, and a lawyer should be
shown both halves rather than the contract half alone. Whichever dispute design `CC-081` settles on
will change this answer, so brief the lawyer after that decision, not before.

### What this settles for CC-080

Item 1 pre-empted and confirmed `CC-080`'s premise from the other end: nothing server-side calls the
contract's `createTask`, so `task.agent` is the agent's own wallet, so a platform-signed `completeTask`
can never satisfy `msg.sender == task.agent`. **No redeploy is needed** — the contract is correct on
both counts. That closes the redeploy question deferred during the triage pass.

Closed. Verification only; defects filed as `CC-081` and `CC-080`. Commit: see
`git log --grep=CC-037`.
