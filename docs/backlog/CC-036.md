# CC-036 — Task completion attestations (EAS)

Listed as unchecked in the README project status, marked "roadmap, post-monetisation".
On-chain attestation per completed task, surfaced on the worker's reputation.

Currently reputation is computed from escrow event logs plus a DB fallback
(`src/lib/reputation/index.ts`), which works but is not independently verifiable by a third
party. Attestations are what make the reputation claim in the README actually true.

## Update 2026-08-10 — reclassified: public-launch, P0, not mainnet/P2

Found while sweeping the `/learn` docs for staleness: the homepage's own "How it works" copy and
`/learn/how-x402-pays-you` both describe a formal on-chain attestation as something that already
happens on every completed task. It doesn't — this issue was filed against the real gap, but
scoped as `epic: mainnet` / `P2`, i.e. "later, after real money." Aaron corrected that directly:
this is core to the pitch and needs to exist **before** the coming-soon gate comes off, not after.

Reclassified to `public-launch` / `P0` accordingly. Left the Learn docs and homepage copy with an
honest inline note that the formal attestation isn't live yet, rather than either overclaiming it
exists or stripping the concept out entirely — the copy describes what's true today (on-chain
event logs, independently recomputable, just not a formal EAS attestation object) and should have
that caveat sentence removed as part of closing this issue, once it's actually shipped.

Related: `docs/backlog/CC-070` (why the reputation event queries need fixing before this is even
usable at scale — chunked `eth_getLogs`, currently broken on any long-lived contract).

## Update 2026-08-31 — `ADR-0008` proposed; schema and verification shipped, not live

The design question this ticket had never answered — *how* a completion becomes an
independently verifiable attestation — is answered in **`ADR-0008` (proposed)**. Read that before
implementing further; the schema UID is permanent once registered, so the shape is not a commit-level
decision.

**Answered first: what EAS buys over what already works.** This ticket's own 2026-08-11 note recorded
that its justification had partly expired — the homepage no longer overclaims, and event logs really
are "a permanent onchain record". So the argument had to be remade, and only one of the three
candidates carries weight:

- **Portability across redeploys.** Escrow events live at a contract *address*. `CC-082` was one
  redeploy and `CC-034` is another, so a worker's history fragments across addresses and
  reconstructing it needs every address we have ever used. That is a real defect in "the reputation is
  yours" and better event queries cannot fix it. This is why the schema carries `escrow` and `chainId`.
- **A schema readable without our ABI.** Real, but would not justify the work alone.
- **Composability with other EAS consumers.** Speculative. Listed for honesty, not weight.

### Decided (`ADR-0008`)

- **D1 — the attestation is a signature, not a transaction.** The platform signs off-chain and hands
  it over; it sends nothing. Same move `ADR-0001` A1.1 made for verdicts. An on-chain `attest()` per
  completion would put platform liveness back one function after A1.1 removed it, fail silently when
  it did not land, and cost gas per task forever.
- **D2 — the worker registers it if they want, paying their own gas.** Off-chain is verifiable but not
  *discoverable*, and D1 does not pretend otherwise. The durable copy belongs with the person whose
  reputation it is (`ADR-0006` D7), not with us.
- **D3 — the attester is the existing verdict signer.** No new key, no new trust root.
- **D4 — hashes and public facts only.** No task content, so an attestation survives the `ADR-0002`
  D4 retention deletion without contradicting it.
- **D5 — `route` is included**, and it is deliberately unflattering: "review elapsed" means nobody
  checked. A score that cannot tell that from a passing verdict rewards silence.

### Shipped in this pass

- `src/lib/attestation/schema.ts` — the schema string, the three UID inputs, offline UID derivation,
  and ABI encoding whose field list is *derived from the schema string* rather than restated.
- 9 tests. Most are tripwires on values that must not move by accident, plus a positional round-trip,
  a no-task-content assertion, and a check that `escrow`/`chainId` are still present — because
  dropping them removes the only argument for the feature.
- `scripts/audit/verify-eas-schema.mjs` — confirms the registered schema is byte-identical to the one
  this build encodes against.
