## Update 2026-08-26 — two `ADR-0006` decisions are now bytecode-or-never for this deploy

`ADR-0006` was accepted 2026-08-26 with execution parameters. Two of them are scoped **into this
milestone** rather than after it, because both are one-way doors that a redeploy is the only way to
reopen.

### 1. Arbitration deadline, in the bytecode (D3)

A disputed task currently has **no clock**. `resolve_dispute` was removed from MCP on 2026-08-26
(`ADR-0001` D2, PR #146), so arbitration is owner-only via `scripts/admin/`, and if the owner never
acts the task sits `Disputed` indefinitely with the escrow held.

D3, as corrected by **Amendment 1** (2026-08-26) — read that before implementing, because the
mechanism in D3's original text does not work:

- **`ARBITRATION_WINDOW = 7 days`, a contract constant.** Not a settable window: the arbitrator must
  not choose its own deadline, which is the structure `ADR-0001` D2 removed.
- **The clock runs from `disputeTask`, not `beginArbitration`.** `beginArbitration` is `onlyOwner`
  and the contract documents `Disputed → Arbitrating` as "a marker, not a gate" — so an owner who
  never calls it would never start a clock, and the task would sit `Disputed` forever. That is the
  stranding case this decision exists to close. `disputeTask` is callable by either party, so the
  clock cannot be withheld.
- Window passes with no `resolveDispute` → the task becomes claimable **by the worker**, on the same
  pull-payment mechanism as `releaseAfterReview`.
- **Worker-default, not refund-default.** `ADR-0001` D6's reasoning carries over: a refund-default
  hands the platform a griefing lever it exercises by doing nothing, and would mean the operator's
  death pays the agent.

**Bytecode scope:**

- `uint64 disputedAt` on `Task`. Slot 1 is 30 of 32 bytes used so this takes a new slot; only
  `disputeTask` writes it, so `createTask` never pays for it.
- A worker-claim path for the timeout, reusing `_payOut` with a new `CompletionRoute` member
  **appended** (safe — the enum is only read from events).
- Tests on the boundary in both directions, and specifically **a dispute where `beginArbitration` is
  never called must still time out**. That test is the one that proves A1.1 rather than restating it.

**Worst-case post-delivery wait becomes `MAX_REVIEW_WINDOW` + 7 days = 21 days**, and only when an
agent chose the maximum review window, disputed, and let arbitration run full length.

**In bytecode, not in a scheduled job.** A clock enforced by a cron is a clock that stops when the
operator does — which is the exact scenario `ADR-0006` exists for. `ADR-0001` A1.1 removed platform
liveness from settlement; a runbook-enforced deadline would put it straight back.

**Blocked on one thing:** the bound values. They are an `ADR-0006` open item and must be chosen
before this bytecode is frozen. Everything else about D3 is decided.

### 2. Owner is a 2-of-4 Safe, and is not the verdict signer (D2, `CC-090`)

Today one HSM key owns `CarbonEscrow` **and** is its only accepted verdict signer. Both change before
this deploy:

- **Owner → a 2-of-4 Safe** over four hardware-isolated keys: each Tangem card initialised **on its
  own**, link step not run (`ADR-0006` A2). Custody is decided — Aaron holds two in two separate
  buildings, two family members hold one each, and **the two family keys reach threshold alone**,
  which is what makes succession work without an estate locating anything.
- **Verdict signer stays a single HSM key.** It must sign automatically and holds no custody; losing
  it fails safe, because no verdicts means everything resolves to workers after the review window.

**Four cards are only four keys if each is initialised on its own.** Cards linked to one key are one
key wearing several plastic coats, and it looks exactly like a real multisig on Basescan.

*Corrected 2026-08-31 (`ADR-0006` A2). This said the trap was silent and that Tangem cards share one
seed by default. Neither is true: cards arrive uninitialised and linking one to another's key is an
explicit setup step, so a shared seed is a visible choice during setup.* **The acceptance test is
on-chain and not procedural** — four Safe owners at four addresses with no shared derivation, verified
before any value moves — plus reading the four addresses off the cards before they are distributed,
which costs nothing. Both are `CC-090` closing conditions.

**Hardware ordered 2026-08-31, ~A$130, expected ~2026-09-17.** Procurement is no longer the blocker on
this half; the family-only rehearsed signature and the on-chain owner check are (`CC-090`).

**And a sequencing hazard already recorded on `CC-082`:** a redeploy resets ownership to the deployer.
So the Safe must be made owner *after* deployment and *before* anything is funded, and
`verify-contract-owner.mjs` must be re-run against mainnet — not assumed from the Sepolia result.

### Consequence for this ticket

**Neither item can be retrofitted.** The arbitration deadline is bytecode; the ownership transfer is
cheap but its verification is the gate. If this deploy happens without D3, v1 ships with disputes that
can strand — and the fix is a second mainnet deploy with a migration, which is the thing this project
has spent the whole of `ADR-0001` avoiding.

Custody of the three Safe keys is an **open `ADR-0006` item and a blocker on D2's actual purpose** —
three cards held by one person is loss resistance, not succession.
