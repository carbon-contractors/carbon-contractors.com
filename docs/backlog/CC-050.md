# CC-050 — Confirm Supabase connection pooling was actually addressed

NOR-180 (Supabase connection exhaustion under agent load) was **cancelled with no stated
reason.** The export flags this as worth checking rather than trusting.

The original concern stands on its face: no pooling configured, and Vercel serverless spawns
a fresh connection per invocation. Under agent load that exhausts the Postgres connection
limit, and on the free tier that limit is low.

## Do
Check whether the Supabase connection string in use is the pooler (pgbouncer, port 6543)
or a direct connection (5432), and confirm the intent. If it was genuinely deferred rather
than solved, reopen with a real decision. This is cheap to check and expensive to discover
during a launch spike.

---

## Update 2026-08-11 — backlog triage pass

Closed as **`done`** — verified during the triage pass, and the premise does not hold.
No code change was required.

**What was checked.** The application talks to Postgres exclusively through
`@supabase/supabase-js` (`src/lib/db/client.ts:9,21,30`), which is a PostgREST client over HTTPS.
`package.json` declares `@supabase/supabase-js` as its only database dependency — there is no
`pg`, no Prisma, no Drizzle, and no `DATABASE_URL` or Postgres connection string anywhere in the
codebase or the env schema.

**Why that settles it.** NOR-180's concern was that Vercel serverless spawns a fresh Postgres
connection per invocation and exhausts the connection limit under agent load. That mechanism
requires a direct Postgres connection, and there isn't one. `supabase-js` issues stateless HTTP
requests; PostgREST owns the connection pool server-side. So the question this issue asks — is the
connection string the pooler on 6543 or a direct connection on 5432 — has no answer, because there
is no connection string to inspect. This is very likely why NOR-180 was cancelled without a stated
reason.

**The residual risk is real but different, and is already covered.** Load pressure would show up as
PostgREST/API rate limiting and plan limits, not connection exhaustion. `CC-058` (Supabase Pro,
done) addresses that, and `CC-040` covers watching for it.

Verified by reading dependencies and client construction, not under load — recorded plainly so a
future session knows which kind of evidence this is.
