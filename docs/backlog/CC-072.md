# CC-072 — The on-chain reputation staking flow has never been executed

## Problem

Spotted while reviewing the dashboard after `CC-069`/`CC-071`'s live testing: the staking panel
(`src/app/dashboard/page.tsx`, `handleStake`/`handleUnstake`, lines ~206-246) is fully wired up —
approve USDC, then call `ReputationStake.stake(amount)`; `unstake(amount)` after a 7-day cooldown
(`ReputationStake.sol`'s `COOLDOWN = 7 days`) — but as far as this project's history shows, nobody
has ever actually clicked **Stake**, confirmed both transactions, and watched a real stake land
on-chain and reflect back into the reputation score.

This is a different, narrower gap than `CC-011` (which is about the UX/content problem — the
panel demanding 20 USDC from a worker with no reason to trust the platform yet, and no explainer
of what staking buys them). `CC-011` is about *whether the panel should ask for this at all, and
how it's framed*. This issue is about *whether the mechanism underneath actually works* — the two
are related but distinct, and `CC-011`'s content fix doesn't require the flow to be proven
functional first, so they're tracked separately rather than folding one into the other.

Unlike `CC-069`, this doesn't go through this app's own signature-verification code — it's a
direct client-side contract write via the connected wallet (`useWriteContract`), so the
EOA-vs-Smart-Wallet distinction that broke registration doesn't obviously apply here. But
"doesn't obviously apply" is exactly the kind of assumption that turned out to be wrong once
already tonight, so it's worth being honest that this is unverified, not assumed-fine.

## Fix

Run the actual flow end to end, on a real wallet (both a Base Account and an EOA, since they're
architecturally different enough that one working doesn't guarantee the other does):

1. Stake a small amount — confirm both the `approve` and `stake` transactions land, and the
   dashboard's stake balance updates afterward (`fetchData()` re-fetch on `txConfirmed`).
2. Confirm the reputation score computation actually reflects a non-zero stake (`compute.ts`,
   also flagged as inconsistent with the DB in `CC-010`).
3. Attempt `unstake` before the 7-day cooldown — confirm it's rejected with a clear reason, not a
   silent failure or a confusing raw revert message in the UI.
4. After the cooldown, confirm `unstake` actually returns funds.

## Acceptance

A real stake and a real (post-cooldown) unstake have both been completed on Base Sepolia, through
the actual UI, on a real wallet, with the dashboard correctly reflecting the result at each step.

Related: `CC-011` (UX/content), `CC-010` (reputation score display), `CC-069` (why "untested"
gets taken seriously as a real risk category in this project, not just a formality).

## Update 2026-08-13 — behind `ADR-0001` / `CC-082`

`ADR-0001` lists this issue under `blocks:`. Two reasons it should not be run yet:

- `ADR-0001` D8 changes what a stake *means*. Slashing becomes progressive with decaying strikes and
  requires established fault, so the stake's behaviour under `slash()` is not yet what it will be.
- `CC-082` redeploys the escrow. `ReputationStake` is a separate contract and is not itself
  redeployed, but testing the staking flow while the surrounding money path is mid-rewrite risks
  proving something that then changes.

The 7-day cooldown tail noted above is unchanged, so this still wants starting early once unblocked.

Related: `ADR-0001` D8, `CC-082`, `CC-081` Defect 5, `CC-011`.

## Update 2026-09-16 — unblocked, verified, and the on-chain half is now a runnable protocol

### The gates have dissolved

- `CC-082` closed **done 2026-08-16**; the v2 escrow has been live at `0xc6aa…E4d3` since
  2026-09-01 with the D3 arbitration clock confirmed on-chain. The money path is no longer
  mid-rewrite.
- `ADR-0001` **D8 is explicitly "v2, deferred, and never a dependency of the happy path"** —
  and this ticket's acceptance is the happy path: stake, cooldown refusal, unstake. `slash()`
  semantics changing later does not invalidate a proof of the mechanics, exactly as sibling
  `CC-074` (also on ADR-0001's `blocks:` list) already executed and closed.
- The `CC-076` hub reconciliation merged 2026-09-16 states it outright: *"CC-072 — unblocked
  since CC-082 landed but never started; the 7-day unstake cooldown makes it the longest-tail
  item here. Start it alongside the earliest lifecycle stage."*

### What was verified live against Base Sepolia (2026-09-16)

The deployment record itself was the first defect found: `chain-constants.json` had
`reputationStake.address: null` — "deployed, address not recorded here — it lives only in the
Vercel environment." Recovered and cross-verified from three concordant repo sources
(`.github/workflows/monitors.yml:79`, `docs/Security-Trust-Disclosure.md:177`,
`docs/backlog/CC-059.md:24`) and then verified against the chain itself, not assumed from the
record:

- **`ReputationStake` at `0x4cdeF542F9361201f9543512eeCd1eE834793203`** — `eth_getCode` returns
  the runtime bytecode; `owner()` is the HSM key `0xa893…3e4b`; `usdc()` is the canonical
  `0x036CbD…CF7e`; `minStake()` is 20 USDC (6dp); `COOLDOWN()` is 604800s; **`totalStaked()`
  reads exactly 0** — the ticket's core premise, confirmed on-chain: no stake has ever landed.
- **The production data path is correct**: `GET /api/reputation?wallet=…` on
  `www.carbon-contractors.com` returns `source: "on-chain"` and
  `stake.contract = 0x4cdeF…3203` — the Vercel env points at the right contract, so once a
  stake lands, the dashboard panel renders real data through the exact route it uses in
  production.
- **Gas is not a blocker**: Base Sepolia gas is ~0.006 gwei; the CC-090 testnet deployer EOA's
  remaining ~0.0009 ETH funds thousands of transactions.

### What was built — `scripts/staking/`

The CC-076 hub called this "the longest-tail item". A one-shot manual test with a 7-day tail
is a protocol you cannot re-run; the fix is the same shape CC-082 used for its 12-hour
lifecycle proof — a resumable harness, in the house style of `scripts/lifecycle/`:

- `scripts/staking/stake-lifecycle.mjs` — four phases, dry-run by default, state in
  `.stake-lifecycle-state.json` (git-ignored):
  **`status`** (read-only) → **`stake`** (approve + stake, then chain AND `/api/reputation`
  readback, asserting the exact `compute.ts` math) → **`cooldown-refusal`** (eth_call
  `unstake(1)` mid-cooldown; must revert `CooldownNotElapsed(readyAt)`) → **`unstake`**
  (post-cooldown; verifies exact USDC returned and the API view).
- `scripts/staking/config.mjs` — pure config/constants/validation module, unit-tested; reads
  the stake address from `chain-constants.json` (never env, never hard-coded); refuses
  `FORBIDDEN_STAKERS` (the three known platform addresses) so the worker role can't be
  conflated with the platform role in the record this ticket exists to produce (CC-081
  Defect 1 rule).
- `scripts/staking/__tests__/staking-harness.test.mjs` — hermetic tests, including a
  cross-check that the harness's expected-reputation math mirrors `computeReputation()` for
  the whole stake range.
- `scripts/staking/README.md` — operator runbook, including the human UI steps and why they
  are human steps.
- `chain-constants.json` — `reputationStake.address` filled with the verified address (and
  `deployBlock` 34411824 from the creation tx), per that file's own "recovered, then fill
  this in" instruction.
- `.env.example` — documents the new `WORKER_WALLET_PRIVATE_KEY` var.

### What remains, and why it is Aaron's

The harness executes the on-chain half end to end the moment a worker wallet exists. What no
agent can produce autonomously:

1. **A funded throwaway worker wallet** (≥ 20 test USDC + gas ETH). The canonical USDC on Base
   Sepolia mints only via Circle's masterMinter (verified: `mint` reverts
   "caller is not a minter" for outsiders), and no funded wallet's key material exists on
   frankenfarm — the original deployer EOA (`0x7863…B91b`, 41 USDC) lives in `.env.local` on
   Aaron's Windows box, and the HSM key is GCP-sealed. Quickest path: ~5 min at
   **faucet.circle.com** (select Base Sepolia, send to a fresh throwaway address), then the
   wallet key into `.env.local` as `WORKER_WALLET_PRIVATE_KEY`.
2. **The UI walkthrough on a real wallet**, both architectures, per the acceptance: EOA leg
   (browser, click Stake, confirm both txs) and the Base Account passkey leg (the `CC-069`
   path). `scripts/staking/README.md` documents the exact steps, including that the dev
   server bypasses the coming-soon gate via `.env.local` while the production flip stays
   sequenced behind `CC-014`/`CC-039`.
3. **The 7-day tail**: stake on day 0, cooldown-refusal immediately after (any time in the
   window), unstake on day 7+. The harness is resumable across the gap; the state file holds
   the `readyAt` timestamp.

Until the first real stake lands on-chain, this ticket stays open — the harness is the
instrument, not the proof.
