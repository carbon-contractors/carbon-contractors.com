# CC-072 — The on-chain reputation staking flow has never been executed

## Problem

Spotted while reviewing the dashboard after `CC-069`/`CC-071`'s live testing: the staking panel
(`src/app/dashboard/page.tsx`, `handleStake`/`handleUnstake`, lines ~206-246) is fully wired up —
approve USDC, then call `ReputationStake.stake(amount)`; `unstake(amount)` after a 7-day cooldown
(`ReputationStake.sol`'s `COOLDOWN = 7 days`) — but as far as this project's history shows, nobody
has ever actually clicked **Stake**, confirmed both transactions, and watched a real stake land
on-chain and reflect back into the reputation score.

This is a different, narrower gap than `CC-011` (which is about the UX/content problem — the
panel demanding 20 USDC from a worker with no reason to trust the platform yet, and no explainer
of what staking buys them). `CC-011` is about *whether the panel should ask for this at all, and
how it's framed*. This issue is about *whether the mechanism underneath actually works* — the two
are related but distinct, and `CC-011`'s content fix doesn't require the flow to be proven
functional first, so they're tracked separately rather than folding one into the other.

Unlike `CC-069`, this doesn't go through this app's own signature-verification code — it's a
direct client-side contract write via the connected wallet (`useWriteContract`), so the
EOA-vs-Smart-Wallet distinction that broke registration doesn't obviously apply here. But
"doesn't obviously apply" is exactly the kind of assumption that turned out to be wrong once
already tonight, so it's worth being honest that this is unverified, not assumed-fine.

## Fix

Run the actual flow end to end, on a real wallet (both a Base Account and an EOA, since they're
architecturally different enough that one working doesn't guarantee the other does):

1. Stake a small amount — confirm both the `approve` and `stake` transactions land, and the
   dashboard's stake balance updates afterward (`fetchData()` re-fetch on `txConfirmed`).
2. Confirm the reputation score computation actually reflects a non-zero stake (`compute.ts`,
   also flagged as inconsistent with the DB in `CC-010`).
3. Attempt `unstake` before the 7-day cooldown — confirm it's rejected with a clear reason, not a
   silent failure or a confusing raw revert message in the UI.
4. After the cooldown, confirm `unstake` actually returns funds.

## Acceptance

A real stake and a real (post-cooldown) unstake have both been completed on Base Sepolia, through
the actual UI, on a real wallet, with the dashboard correctly reflecting the result at each step.

Related: `CC-011` (UX/content), `CC-010` (reputation score display), `CC-069` (why "untested"
gets taken seriously as a real risk category in this project, not just a formality).

## Update 2026-08-13 — behind `ADR-0001` / `CC-082`

`ADR-0001` lists this issue under `blocks:`. Two reasons it should not be run yet:

- `ADR-0001` D8 changes what a stake *means*. Slashing becomes progressive with decaying strikes and
  requires established fault, so the stake's behaviour under `slash()` is not yet what it will be.
- `CC-082` redeploys the escrow. `ReputationStake` is a separate contract and is not itself
  redeployed, but testing the staking flow while the surrounding money path is mid-rewrite risks
  proving something that then changes.

The 7-day cooldown tail noted above is unchanged, so this still wants starting early once unblocked.

Related: `ADR-0001` D8, `CC-082`, `CC-081` Defect 5, `CC-011`.
