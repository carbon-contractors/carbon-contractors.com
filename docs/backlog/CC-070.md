# CC-070 — Every eth_getLogs query in escrow.ts exceeds the public RPC's 2000-block range limit

## Problem

Found live while verifying `CC-069`'s Smart Wallet fix on a real registration: a fresh worker's
`/api/reputation` call logged

```
{"level":"warn","event":"reputation_onchain_fallback","error":"Invalid parameters were provided
to the RPC method... Details: query exceeds max block range 2000 ... URL: https://sepolia.base.org"}
```

Every `getLogs` call in `src/lib/contracts/escrow.ts` defaults `fromBlock` to `BigInt(0)` —
genesis — querying the entire chain history in one `eth_getLogs` call. The public
`sepolia.base.org` RPC (already documented as rate-limited, `CC-048`) caps a single `eth_getLogs`
call at a 2000-block window. At Base's ~2 second block time, that's about 66 minutes of chain
history per call. `CarbonEscrow` has been deployed far longer than that, so **every one of these
queries fails, unconditionally, the moment the contract is more than about an hour old** — which
has been true for essentially this entire project's life. It has been silently broken, or silently
falling back, this whole time.

Affected call sites (`src/lib/contracts/escrow.ts`):
- `getTaskResolvedOutcome` (line ~129) — added in `CC-065` as the partial-failure recovery path
  for `resolve_dispute`: if a prior on-chain resolution succeeded but the DB write failed, this
  is what recovers the true outcome. **This one is a correctness bug, not just a display gap** —
  if that recovery path is ever actually exercised, it currently throws instead of recovering.
- `getTaskIdsForWorker` (line ~160) and the three `getLogs` calls inside
  `getOnChainReputationSummary` (lines ~212-233) — feed on-chain reputation data into
  `/api/reputation`. Currently always fails and falls back (gracefully, per the log event name,
  though what that fallback actually shows to a fresh worker was not checked in this session).

## Fix

Chunk `eth_getLogs` queries into windows no wider than the RPC's cap (2000 blocks — consider
pulling this from config since it's a property of the RPC provider, not the protocol) and
aggregate results across chunks, from `fromBlock` (or contract deployment block, if known and
smaller than "genesis") to `latest`. This is the standard workaround for RPC providers that cap
`eth_getLogs` ranges; several small library-free implementations exist (loop `fromBlock` to
`toBlock` in `2000`-block strides, `Promise.all` or sequential per provider rate limits).

Alternatively/additionally: consider whether a paid RPC provider or an indexer removes the need
for client-side chunking entirely — worth a cost/complexity comparison rather than assuming
chunking is the only answer, especially since `CC-048` already flags the public endpoint as a
recurring pain point.

## Acceptance

- `getTaskResolvedOutcome`, `getTaskIdsForWorker`, and `getOnChainReputationSummary` all return
  correct results against the real deployed contracts, not just "fails without crashing."
- A regression test or manual check confirms `getTaskResolvedOutcome` actually recovers a real
  past `TaskResolved` event rather than silently returning `null` because the query range was
  too narrow, or throwing because it was too wide.

Related: `CC-048` (public RPC pain points), `CC-065` (the correctness-sensitive call site).

## Update 2026-08-11 — backlog triage pass

Raised P1 → **P0**, matching the project's pattern of P0 for fund-adjacent correctness
defects. Re-verified in the current tree: five `getLogs` call sites in
`src/lib/contracts/escrow.ts` (lines ~133, 162, 212, 220, 228), every one defaulting `fromBlock`
to `BigInt(0)`, with no chunking anywhere. Unchanged since filing.

The deciding factor for P0 is `getTaskResolvedOutcome` — `CC-065`'s partial-failure recovery path
for `resolve_dispute`. That is a correctness bug on a money path, not a display gap: if the
recovery path is ever exercised it throws instead of recovering the true outcome.

**Shared root cause worth recording here.** Nothing sets `BASE_SEPOLIA_RPC_URL`, so
`getChainConfig()` falls back to the free public `sepolia.base.org`, whose 2000-block cap is what
this issue is about. The same fallback also makes the test suite non-deterministic (`CC-060`) and is
the motivation for `CC-048`. Setting that one variable to a paid provider endpoint partially
mitigates all three, and paid providers typically allow far larger `getLogs` ranges — so try that
before assuming chunking is the only answer. Aaron's call is that the chunking work still stands.
