# CC-070 — Every eth_getLogs query in escrow.ts exceeds the public RPC's 2000-block range limit

## Problem

Found live while verifying `CC-069`'s Smart Wallet fix on a real registration: a fresh worker's
`/api/reputation` call logged

```
{"level":"warn","event":"reputation_onchain_fallback","error":"Invalid parameters were provided
to the RPC method... Details: query exceeds max block range 2000 ... URL: https://sepolia.base.org"}
```

Every `getLogs` call in `src/lib/contracts/escrow.ts` defaults `fromBlock` to `BigInt(0)` —
genesis — querying the entire chain history in one `eth_getLogs` call. The public
`sepolia.base.org` RPC (already documented as rate-limited, `CC-048`) caps a single `eth_getLogs`
call at a 2000-block window. At Base's ~2 second block time, that's about 66 minutes of chain
history per call. `CarbonEscrow` has been deployed far longer than that, so **every one of these
queries fails, unconditionally, the moment the contract is more than about an hour old** — which
has been true for essentially this entire project's life. It has been silently broken, or silently
falling back, this whole time.

Affected call sites (`src/lib/contracts/escrow.ts`):
- `getTaskResolvedOutcome` (line ~129) — added in `CC-065` as the partial-failure recovery path
  for `resolve_dispute`: if a prior on-chain resolution succeeded but the DB write failed, this
  is what recovers the true outcome. **This one is a correctness bug, not just a display gap** —
  if that recovery path is ever actually exercised, it currently throws instead of recovering.
- `getTaskIdsForWorker` (line ~160) and the three `getLogs` calls inside
  `getOnChainReputationSummary` (lines ~212-233) — feed on-chain reputation data into
  `/api/reputation`. Currently always fails and falls back (gracefully, per the log event name,
  though what that fallback actually shows to a fresh worker was not checked in this session).

## Fix

Chunk `eth_getLogs` queries into windows no wider than the RPC's cap (2000 blocks — consider
pulling this from config since it's a property of the RPC provider, not the protocol) and
aggregate results across chunks, from `fromBlock` (or contract deployment block, if known and
smaller than "genesis") to `latest`. This is the standard workaround for RPC providers that cap
`eth_getLogs` ranges; several small library-free implementations exist (loop `fromBlock` to
`toBlock` in `2000`-block strides, `Promise.all` or sequential per provider rate limits).

Alternatively/additionally: consider whether a paid RPC provider or an indexer removes the need
for client-side chunking entirely — worth a cost/complexity comparison rather than assuming
chunking is the only answer, especially since `CC-048` already flags the public endpoint as a
recurring pain point.

## Acceptance

- `getTaskResolvedOutcome`, `getTaskIdsForWorker`, and `getOnChainReputationSummary` all return
  correct results against the real deployed contracts, not just "fails without crashing."
- A regression test or manual check confirms `getTaskResolvedOutcome` actually recovers a real
  past `TaskResolved` event rather than silently returning `null` because the query range was
  too narrow, or throwing because it was too wide.

Related: `CC-048` (public RPC pain points), `CC-065` (the correctness-sensitive call site).

## Closed 2026-08-11 — fixed, with the diagnosis corrected twice on the way

Two things in this issue's own problem statement turned out to be wrong, and both changed the
fix. Measuring before implementing is the only reason this landed as something that works rather
than something that merely compiles.

### Correction 1 — the limit is 10,000, not 2,000

Probed the live endpoint against the real escrow address on 2026-08-11:

| span requested | result |
| :-- | :-- |
| 2,000 blocks | OK |
| 10,000 blocks | OK |
| 50,000 blocks | FAIL |
| genesis → latest | FAIL — `eth_getLogs is limited to a 10,000 range` |

This issue was filed quoting a live error that said `max block range 2000`. Whatever the cause —
a raised limit, or different limits behind the load balancer — a hardcoded constant would have
been wrong within days. The cap now comes from **`RPC_MAX_BLOCK_RANGE`** (default `10000`), because
it is a property of the provider, not of the protocol.

### Correction 2 — chunking was necessary but nowhere near sufficient

The proposed fix was "chunk into 2000-block windows and aggregate." Measured, that does not work:

| approach | requests per query |
| :-- | :-- |
| genesis → head, 2k windows | 22,691 |
| deploy block → head, 2k windows | 3,174 |
| deploy block → head, 10k windows | **635** |

`getOnChainReputationSummary` made **four** log queries, so a single dashboard load would have
been ~2,540 requests — roughly 13 minutes, and rate-limited long before finishing. Chunking alone
would have converted a fast failure into a slow one.

Finding the contract's deployment block was the prerequisite nobody had measured.
`scripts/audit/find-deploy-block.mjs` (new) binary-searches `eth_getCode` and found
**39,032,720** in 26 calls. Now carried as **`ESCROW_DEPLOY_BLOCK`**.

## What was actually done

**1. The request-time path no longer queries events at all.** Aaron's call: discovery from the DB,
authority from the chain. `getOnChainReputationSummary(wallet, paymentRequestIds)` now takes
candidate ids from the caller and reads each task's real state with `getTask()`, batched into a
single multicall (`batch: { multicall: true }` on the public client). Every fact that matters for
money still comes from the chain — state, amount, and the worker address, which is **re-checked
against the requested wallet**, so a DB row cannot attribute someone else's task. The DB only
proposes which ids to look at, which is why `CLAUDE.md`'s "the DB is not the authority on money"
rule survives intact.

The caller (`src/lib/reputation/index.ts`) supplies the ids, so `escrow.ts` stays DB-free — the
layering improved rather than degraded.

**2. `getTaskResolvedOutcome` is chunked, newest-first, with an early exit.** It is a recovery path
for a resolution that just failed to persist, so the event is nearly always recent. Measured
against the real event: **18 requests out of 635 available windows.**

**3. `getTaskIdsForWorkerFromEvents` is now exported and documented as offline-only.** The old
private event scan still has value — it is the only way to find a task that exists on-chain but not
in the `tasks` table, which is the one blind spot of DB-based discovery. It carries an explicit
"do not call this on a request path" warning and costs ~635 requests.

**Two deliberate gaps, recorded rather than hidden:**

- **Recency uses DB timestamps.** `getTask()` returns no block or time, and fetching a block per
  completion would undo the single-round-trip win. The caller buckets 30/90-day recency from
  `created_at`, but only over completions the chain confirmed. Soft ordering from the DB, hard facts
  from the chain.
- **`Resolved` tasks are excluded from earnings.** The state alone does not reveal which way the
  owner arbitrated — only the `TaskResolved` event does. They are counted separately rather than
  guessed at. Currently affects exactly one task in existence (`CC-059`'s).

## Acceptance evidence

**Unit tests** — `src/lib/__tests__/escrow-chunked.test.ts`, 12 tests, fully hermetic (viem's
`createPublicClient` is mocked, so nothing touches the network — deliberately, given `CC-060`).
They cover: no window ever exceeds the cap; the lower bound is `ESCROW_DEPLOY_BLOCK` rather than
genesis; windows are contiguous and non-overlapping across the whole range; newest-first stops at
the first hit; a full scan returns `null` rather than throwing; an empty range issues no query at
all; the reputation path issues **zero** `getLogs` calls; each on-chain state is counted correctly;
earnings exclude `Resolved`; a worker-address mismatch and a non-existent task are both rejected as
`unverified`; and address matching is case-insensitive (the casing landmine).

Suite is **128/128**, up from 116.

**Live-chain proof** — `scripts/audit/verify-getlogs-recovery.mjs` (new) against the only real
`TaskResolved` event in existence, `CC-059`'s 1 USDC resolution:

```
1. Ground truth from the receipt (tx 0x08cd2e37…)
   block 45204414   taskId 0xfaaa6fa2…   releasedToWorker true   amount 1000000
2. OLD behaviour — single unbounded getLogs from block 0
   fails as expected: eth_getLogs is limited to a 10,000 range
3. NEW behaviour — newest-first windows, bounded below, early exit
   windows available 635   requests made 18   recovered at block 45204414
PASS — every field matches the receipt
```

That is this issue's acceptance criterion directly: the recovery path neither throws on an
over-wide range nor silently returns null on an over-narrow one, proven against a real historical
event rather than a fixture.

## Update 2026-08-16 — the acceptance script was broken by the CC-082 redeploy; pinned, not retired

`scripts/audit/verify-getlogs-recovery.mjs` exited `1` at step 1 with "no TaskResolved log found
in that transaction — wrong tx or wrong escrow?". Nothing about this issue's fix regressed. The
script read `NEXT_PUBLIC_ESCROW_CONTRACT` and `ESCROW_DEPLOY_BLOCK` from the environment while
asserting against a hardcoded **v1** transaction, and `CC-082` moved both env vars to the v2
deployment. Two failures, not one:

| input | was | became | effect |
| :-- | :-- | :-- | :-- |
| `NEXT_PUBLIC_ESCROW_CONTRACT` | `0xb9bF8dAC…` (v1) | `0xe80d0368…` (v2) | receipt's log address never matched → died at step 1 |
| `ESCROW_DEPLOY_BLOCK` | `39032720` (v1) | `45494043` (v2) | lower bound now **above** the event at `45204414` → step 3 would have scanned a range starting after the event and found nothing |

Fixing only the address would have moved the failure from step 1 to step 3, not fixed it.

**Kept and pinned, rather than retired.** Both were live options. Pinning won because the thing
the script proves is still shipping code: `getTaskResolvedOutcome`
(`src/lib/contracts/escrow.ts:261`) is still on `resolve_dispute`'s partial-failure recovery path
(`src/lib/mcp/server.ts:909`), and v2 still declares `TaskResolved`
(`contracts/CarbonEscrow.sol:172`). Only the address it was proved against moved — the query shape
did not. And `CC-059`'s resolution remains the **only** `TaskResolved` event that has ever been
emitted; v2 has produced none, so retiring the script would have deleted the sole live-chain proof
at exactly the moment there is no replacement for it.

`V1_ESCROW` and `V1_DEPLOY_BLOCK` are now constants alongside `CC059_TX`, with the header stating
plainly that this is historical evidence with every input pinned — which is the same reason
`CC-085` deliberately left it out of the monitor registry. It asserts a fact about the past, and a
fact about the past cannot regress. Reading live config implied it tracked the current deployment;
it never did. When the deployment moved, the script was simply lying about what it was.

It also now prints a note when `NEXT_PUBLIC_ESCROW_CONTRACT` differs from the pinned address, so a
reader cannot mistake a pinned pass for a statement about the live contract.

**A second, unrelated defect fixed in passing.** `BigInt(process.env.RPC_MAX_BLOCK_RANGE ?? "10000")`
— `??` only catches `null`/`undefined`, so an env var that is *present but empty* gave
`BigInt("") === 0n`, and `for (let start = from; start <= head; start += maxRange)` never advanced:
an unbounded loop pushing windows until it exhausted memory. Empty/whitespace is now treated as
unset, and a non-integer or non-positive cap exits `2` with a message. Never triggered in practice
— nothing sets the variable — but it was a live trap for the first person who set it to `""`.
