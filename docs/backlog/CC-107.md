# CC-107 — Off-vendor export pipeline for Tier 1 reference tables

Implements the export half of `ADR-0006` D8 ("Registration and reference data is backed
up, exported off-vendor on a schedule, and restore-tested"), which `BCP-DR.md` recorded
as *"Nothing implements this yet. D8 is a requirement."* Kanban `t_1b1b03ff` / ADR-0006
handover item 3.

## What ships

- **`src/lib/db/backup-export.ts`** — the engine. Exports `humans`,
  `notification_channels`, task *metadata* (hashes, wallets, amounts, timestamps — never
  `task_description`/`acceptance_spec`), the CC-087 deletion log, and `stake_slashes`
  (absent until migration 023 is applied; recorded as `absent`, not skipped) as NDJSON
  with a per-run manifest carrying per-table sha256s.
- **`src/lib/r2.ts`** — Cloudflare R2 push/read-back over its S3 API with hand-rolled
  SigV4 (`node:crypto` only; dependency freeze honored). Endpoint host derived from the
  account id, never accepted from env. Error paths scrubbed of credentials.
- **`src/app/api/cron/backup-export/route.ts`** — daily 04:17 UTC Vercel cron (one hour
  after the 03:17 retention prune, so the export reflects post-prune state). Same
  fail-closed shape as the retention route: unset `CRON_SECRET` → 503, unconfigured R2
  target → 503 with a CC-109 pointer. Runs where the service-role key already lives
  (PR #147 argument — no credential copied to a second location).
- **`scripts/audit/verify-backup-export.ts`** — independent manual deep-verify: fetch a
  prefix's manifest, GET every object, hash-compare, count rows.
- **Tests** — 31 new: the D8 boundary (forbidden column/table specs throw at startup),
  read-back verification poisoning `ok`, absent-vs-empty distinction, fail-closed route
  behaviour, SigV4 header shape, credential scrubbing.

## The D8 boundary is structural, not procedural

Every table exports through an explicit column allowlist; `select *` is never used. A
future migration adding a content column to `tasks` is *unable* to leak — the column is
simply absent from the export until deliberately added. `assertSpecCompliance()` throws
at startup if the spec ever intersects `FORBIDDEN_COLUMNS`
(`task_description`, `acceptance_spec`) or names an excluded table
(`task_description_history`, `sessions`, `used_nonces`, `mcp_challenges` — reasons
recorded in the manifest's `excludes` map so nobody re-derives them from the ADR).

## Verification on every run

Each object is PUT then GET back and sha256-compared before the run reports `ok: true`.
`BACKUP_HEARTBEAT_URL` (optional dead-man's switch) is pinged only on a fully verified
run — run-monitors.mjs Path-2 polarity: silence is the success signal.

## Acceptance

- [x] Export engine with allowlist-only column access; forbidden columns/tables throw
- [x] Manifest with per-table sha256, row counts, and the exclusion record
- [x] Cron route, fail-closed on both `CRON_SECRET` and the R2 target
- [x] Read-back hash verification on every run; failures poison `ok`
- [x] `npm test` / `tsc --noEmit` / `eslint` green (75 files, 829+ tests)
- [ ] First live run against a provisioned bucket (blocked on CC-109) — route 503s
      daily until then, which is the correct loud posture, not a defect
- [ ] One-time full restore test before mainnet (ADR-0006 D8: "restore-tested at least
      once before mainnet") — restore the NDJSON into a scratch Postgres and compare
      row counts + hashes against the manifest
