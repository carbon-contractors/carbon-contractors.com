# CC-083 — Deterministic checker and evidence path

Specified by `ADR-0001` D5, `ADR-0002` D3, and `ADR-0003` D2. Step 2 of `ADR-0001`'s handover.

## Implementation (2026-08-21)

- **Pure Deterministic Checker Engine (`src/lib/checker/evaluator.ts`)**: Evaluates evidence against pinned `AcceptanceSpecV1` criteria (artefact count, EXIF GPS within radius via haversine, UTC capture timestamp vs funding block, C2PA AI generation rejection, camera make/model presence, perceptual hash similarity). Fails closed on missing required criteria. Zero network or wall-clock dependencies.
- **Pinned Rule Digest & Versioning (`src/lib/checker/hash.ts`)**: Generates byte-identical `checkerHash` via keccak256 over pinned rule schema metadata.
- **Canary Fixtures (`src/lib/checker/canary/fixtures.ts`)**: 6 versioned canary cases with known outcomes (1 pass-all, 5 independent single-check failures: min artefacts, GPS radius, capture before funding, camera model, and C2PA generative AI). Answers open question: each check is independently tested.
- **Canary Test Suite & Offline Monitor (`scripts/audit/verify-checker.mjs`)**: Verified via Vitest (`src/lib/checker/__tests__/`) and wired into `scripts/audit/run-monitors.mjs` running under `tsx`. All 242 tests passing.

## Why deterministic, and why no LLM

**Re-runnability is the security property the whole design rests on.** A verdict that anyone can
re-run is falsifiable; a verdict nobody can reproduce is discretionary authority wearing a
technical costume. LLM inference is not reproducible across sampling seeds or model versions, so a
verdict containing one cannot be re-run and the property is lost. `ADR-0001` D5 rejects it
explicitly.

## In the checker

Artefact counts · EXIF GPS radius · capture timestamp vs funding block · C2PA / provenance
assertions · camera-model presence · perceptual-hash comparison against supplied reference images.

All thresholds pinned in `checkerHash`. Dependencies pinned. **No network calls** — a checker that
fetches something mutable is not deterministic. The bundle is content-addressed and `checkerHash`
doubles as `ruleVersion`.

**Not in the checker:** "do these eight photos genuinely show the vehicle's condition, or are they
eight angles of one bumper." Irreducibly subjective, routes to the `ADR-0001` D8 jury tier in v2,
and never blocks a task from resolving.

## Evidence path — the platform is not in the data path

Per `ADR-0002` D3:

- Evidence is written to a bucket the **hiring agent** nominates. They commissioned it, they
  receive it, they determine the purpose — so they are the controller in fact as well as in
  substance. The spec schema (`CC-084`) gains a bucket target field.
- The checker receives a **time-limited URL**, reads, evaluates, and retains nothing.
- The platform persists `evidenceHash` and `verdictHash` only.
- If a local copy is unavoidable for reliability it is scratch: held for the check, deleted on
  completion, never written to durable storage, never backed up.

## Canary fixture — one artefact, two purposes

A committed, versioned set of evidence with known-correct verdicts. It is both the `ADR-0001` D5
re-runnability fixture and the input to `verify-checker` (`CC-085`).

**This is the monitor that does not exist in any conventional stack and matters most.** "The
checker is running" is not the property worth holding; "the checker still returns the right
answers" is. A checker that is up and wrong is worse than one that is down, because down eventually
fails loudly and wrong never does.

## The checker supports several spec schema versions at once

Added 2026-08-16 from `ADR-0001` Amendment 2 (A2.2), because it is scope that is cheap to plan for
and expensive to retrofit.

Spec schemas are **never migrated in flight** — a task resolves under the schema it was created
with, permanently. So a live checker must evaluate every schema version that still has tasks
outstanding, and an archived one must evaluate any version it ever supported.

**This is not a new cost.** D5 already requires a verdict to be reproducible indefinitely from its
pinned `checkerHash`, and a checker that cannot read a six-month-old spec cannot re-run a
six-month-old verdict. Multi-version support falls out of re-runnability; the amendment only makes
it explicit.

Practical consequences: dispatch on the `schema_version` in the spec preimage rather than assuming
the current shape, and keep at least one canary case per supported version so a dropped version
fails the fixture instead of failing a real task.

## Acceptance

- The same evidence and `checkerHash` produce a byte-identical verdict on re-run, on a different
  machine, offline.
- The canary set yields its expected passes and failures through the real pipeline.
- **A spec written against an older schema version still evaluates correctly**, with a canary case
  covering each supported version.
- No durable artefact of evidence exists anywhere in platform storage after a check.
- `checkerHash` is published.
