# CC-022 — rate_usdc accepts absurd values and silently rounds

`src/app/api/register/route.ts:60-66` only checks `rate_usdc > 0`. The column is
`NUMERIC(10,2)` (`supabase/migrations/001_init.sql:8`), so anything above 99,999,999.99
throws a 500, and more than two decimal places is silently rounded.

Fix: add a sane upper bound and 2-decimal validation server-side, mirrored in the client at
`src/app/connect/page.tsx:128-136`.

---

## Update 2026-08-11 — backlog triage pass

Raised P2 → **P1**. It sits on the registration path — the one flow every worker must
complete — and the failure mode is a 500, which loses the signup outright rather than degrading.

Consider doing this in one pass with `CC-023` and `CC-024`: all three are `/connect`
registration-form problems living in the same two files
(`src/app/api/register/route.ts`, `src/app/connect/page.tsx`).

## Resolution

Done 2026-08-21 on `feat/cc-022-023-024-connect-registration-polish`.

Added a shared `rateUsdcError`/`MAX_RATE_USDC` (10,000) validator in `src/lib/validation.ts`,
used identically on both sides:

- **Server** (`src/app/api/register/route.ts`): rejects non-positive, non-finite, >10,000 and
  >2-decimal rates with a specific 400 message before any DB write. The decimal check scales by
  100 with a 1e-6 tolerance so IEEE-754 noise (`10.10 * 100 === 1010.0000000000001`) passes
  while a genuine third decimal is rejected — nothing is silently rounded any more.
- **Client** (`src/app/connect/page.tsx`): validates `Number(rateUsdc)` via the same helper
  *before* signing, so a bad rate costs a form fix rather than a wasted wallet signature.
  Input now carries `max`/`step="0.01"`.

Covered by new `register-route.test.ts` cases: negative/zero, 1e9 (the old 500 path),
50.123, and acceptance of 50.5 / 50.55 / the 10,000 bound.
