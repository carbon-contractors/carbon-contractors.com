# CC-099 — Sanctions/PEP wallet screening — block flagged wallets before they can participate

Named as Track E in `docs/funds_control_aml_gating.md`'s 2026-08-17 synthesis: "cheap, scoped, no
ticket yet. Should gate `CC-034` (mainnet)." This is that ticket.

## Why this does not wait on `CC-098`'s classification question

Two independent legal bases apply regardless of whether Carbon Contractors turns out to be an
AUSTRAC-registrable VASP (`CC-098`):

- **Australia's targeted financial sanctions regime binds everyone, not just AUSTRAC reporting
  entities.** The *Autonomous Sanctions Act 2011* and the *Charter of the United Nations Act
  1945* make it a criminal offence for **any person** to make an asset available to, or for the
  benefit of, a person or entity on DFAT's consolidated sanctions list. This does not turn on
  registration status. If `CarbonEscrow` ever locks USDC for a sanctioned wallet, that exposure
  exists whether or not `CC-098` concludes Carbon Contractors needs to register.
- **USDC itself carries US-nexus exposure.** Circle (the issuer) and Coinbase (Base's operator)
  are both US-regulated entities subject to OFAC. Either can freeze addresses independently of
  anything this platform does, and facilitating a transaction that benefits an OFAC-listed
  address carries exposure under US law for US-nexus activity regardless of where Carbon
  Contractors is domiciled.

So this ticket is worth doing at MVP scale, before `CC-098` resolves, not after. It also
strengthens whichever way `CC-098` lands — an AML/CTF program requires sanctions/PEP screening as
a baseline element, so this is not throwaway work if VASP registration turns out to be required.

## Compatible with `ADR-0002` D1 — worth stating explicitly

`ADR-0002` D1 commits to no identity verification, ever. Sanctions screening does not conflict
with this: it is **address-based, not identity-based** — checking whether a wallet address
appears on a published list, never asking who controls it. This ships without touching the
pseudonymity model. (`CC-098` explores whether *full customer due diligence* is separately
required — that is a different, harder question this ticket does not need to wait for.)

## Design considerations — decide before building, this is the part that needs a call

### Mechanism: on-chain oracle vs off-chain API screening

Chainalysis publishes a free on-chain "sanctions oracle" contract
(`0x40C57923924B5c5c5455c48D93317139ADDaC8fb`, same address across the chains it supports) that a
contract can call directly — `isSanctioned(address)`. **Checked 2026-08-18: Base is not confirmed
among Chainalysis's documented supported chains** (Ethereum, Polygon, BSC, Avalanche, Optimism,
Arbitrum, Fantom, Celo are). Confirm directly with Chainalysis before designing around on-chain
availability — if Base genuinely isn't covered, the on-chain oracle route is closed for now and
the only viable path is off-chain screening via Chainalysis's Address Screening API (or an
equivalent provider — TRM Labs and Elliptic offer comparable address-risk APIs) called from the
backend.

**Recommendation: screen at the app layer first, regardless of oracle availability.** Reasons:

- AUSTRAC's own framing ("screen your customers... before you act for them and keep screening
  during the relationship") is a *process* obligation, not a smart-contract obligation. An
  on-chain oracle call only protects the `createTask` path; it does nothing for the AML/CTF
  program requirement to screen at registration and on an ongoing basis, which is inherently an
  app-layer control.
- `createTask` is deliberately permissionless (`ADR-0001` A1.1's "no platform liveness in the
  funding path" ethos, `A2.4`'s residual note that the contract has no version gate). An on-chain
  check would be the first gate the contract enforces on anyone, which is a bigger design change
  than the app-layer equivalent and would need its own redeploy.
- This mirrors `CC-086`'s already-open kill-switch question almost exactly ("contract-level
  vs app-level... probably both, at different tiers"). Same answer likely applies here: app-layer
  now, on-chain as defense-in-depth later if Chainalysis (or another oracle) supports Base.

### Where to screen

- **`request_human_work`** (`src/lib/mcp/server.ts`) — screen `context.callerWallet` (the agent,
  now bound not argued per `CC-081` Defect 4) and the resolved `worker.wallet` from
  `getHumanByWallet(to_human_wallet)`, before returning task parameters. Reject with a clear error
  before any on-chain call is even possible from this path.
- **Worker registration** (wherever `humans` rows are written) — screen at registration so a
  flagged wallet never enters the whitepages at all, rather than only being caught at hire time.
- **Ongoing re-screening** — sanctions lists change; a wallet clean at registration can be listed
  later. Add a monitor in the `CC-085` style (`verify-sanctions` or similar): periodically
  re-screen active registered wallets and open tasks' `agent`/`worker` addresses, alert on a new
  hit, and feed `CC-086`'s kill switch for the affected wallet's ability to create/accept new
  tasks. Do not attempt to unwind funds already locked for a wallet later listed — that is a
  legal question (asset-freezing obligations differ from prevention obligations), not an
  engineering one; flag it to `CC-098`'s legal review rather than building a reversal mechanism
  speculatively.

### Blocking vs monitoring-only

Recommend **blocking** at `request_human_work` and registration (fail the call outright, log the
attempt without PII beyond the wallet, per `CLAUDE.md`'s masking rules), and **alerting** (not
silent auto-action) for the ongoing re-screening case, since freezing an in-flight task
automatically is a fund-custody question that belongs with `CC-098`'s legal review, not a
monitor's discretion.

## Fix

1. Confirm Chainalysis (or equivalent) Base coverage and pricing at MVP volume — the free
   sanctions-oracle tier historically covers exactly this use case.
2. Add a screening call (API-based, given the Base gap) in `request_human_work` and the
   registration path, both wallets, before any state is written.
3. Add the re-screening monitor, wired into `CC-085`'s alerting paths.
4. Add a sanctions/prohibited-persons clause to `/terms` (`src/legal/terms.md`) once the
   mechanism ships — it currently has none.
5. Document the screening mechanism in `docs/Security-Trust-Disclosure.md`, same treatment as
   every other trust-relevant control in that doc.
6. Add this as an explicit gate in `CC-039`.

## Acceptance

- A wallet on the DFAT consolidated list (or OFAC SDN, whichever the chosen provider covers)
  cannot register, cannot be named as `to_human_wallet`, and cannot call `request_human_work` as
  the caller.
- Re-screening runs on a schedule and alerts on a new match against an already-registered or
  already-active wallet.
- `/terms` and `docs/Security-Trust-Disclosure.md` reflect the control.
- `CC-034`/`CC-039` do not proceed to mainnet without this shipped.

Related: `docs/funds_control_aml_gating.md` (Track E), `CC-098` (AUSTRAC VASP classification),
`ADR-0002` D1 (pseudonymity, compatibility), `CC-086` (kill switch, same design shape), `CC-085`
(monitor pattern and alerting paths), `CC-081` Defect 4 (authenticated `request_human_work`,
prerequisite), `CC-034`, `CC-039`.

## Update 2026-08-23 — shipped on `feat/cc-099-sanctions-screening`

Implemented as recommended in the ticket: app-layer blocking at both doors, plus alerting
(not auto-action) for re-screening. All acceptance items except the two explicitly deferred
below are met.

**Module** — `src/lib/sanctions/` (`index.ts` + `data.ts`): `isWalletSanctioned(wallet)` with
address normalisation (lowercased `0x`+40 hex, validated), an always-on bundled dataset
(`data.ts`, one cited OFAC SDN entry as the seed — every entry requires a citation because the
SDN list moves in both directions), an optional Chainalysis provider layer when
`CHAINALYSIS_API_KEY` is set (own Zod-validated config via `getSanctionsConfig()`, CC-097
blank-as-unset semantics), and a 6h TTL in-memory cache. The provider layer **fails open with a
loud log** (`sanctions_provider_api_error`) — the dataset is the control that ships, and a
sanctions vendor outage must not take down intake.

**Enforcement** — `/api/register` rejects with `403 { error, code: "SANCTIONED_WALLET" }` after
signature verification and before the nonce is consumed or any row written
(`register_sanctioned_wallet_rejected`, wallet masked by `maskMeta`). `request_human_work`
screens both wallets with a new `SANCTIONED_WALLET` tool error code (`retryable: false`): the
caller **before** the idempotency replay and rate limiter (a listed agent gets nothing back, not
even its own prior task details), the resolved worker after the whitepages lookup
(`request_human_work_sanctioned_wallet_rejected`, `role` distinguishes the two).

**Re-screening** — `scripts/audit/verify-sanctions.ts` (tsx, read-only, ANON key only since
`humans` and `tasks_public` are world-readable by design): a canary asserts the screening
pipeline actually screens, then re-screens every registered worker and every task party, alerts
(via the `CC-085` webhook/heartbeat paths) on a match, and deliberately takes no fund action —
printed in the failure output as belonging to `CC-098`'s legal review. Registered in
`run-monitors.mjs` (`requires: SUPABASE_URL, SUPABASE_ANON_KEY`) and wired into
`.github/workflows/monitors.yml`; until those repo secrets are set it SKIPs visibly, which is
the designed behaviour, not an oversight.

**Tests** — `sanctions.test.ts` (normalisation, dataset hits/misses, cache, provider
match/negative-cache/fail-open/indeterminate-not-cached), `mcp-sanctions.test.ts` (both-wallet
screening, ordering, error shape, no idempotent replay to a listed caller, masked logging),
register-route CC-099 cases. `CHAINALYSIS_API_KEY` added to `vitest.setup.ts`'s `FORBIDDEN_ENV`
— a credential must never leak into a hermetic test run. Full suite 618 vitest + 58 hardhat
passing; `typecheck`, `lint`, `build`, `monitors:list` green.

**Legal** — the pre-drafted `/terms` sanctions clause's drafting note removed (clause and
mechanism now publish together, as the note demanded); clause extended to state re-screening.
`docs/Security-Trust-Disclosure.md` gains a "Sanctions screening" section stating the three
honest limits: not identity verification, does not gate the permissionless `createTask`, and
the provider layer is optional/unverified.

**Deliberately not done, and why:**

- **Fix item 1 (confirm Chainalysis Base coverage and the REST contract) remains open.** Their
  API documentation sits behind an access form and the on-chain oracle does not support Base
  (checked 2026-08-18). The provider integration is written against a tolerant response parse
  (`src/lib/sanctions/index.ts` names itself as the one place to correct when the contract is
  confirmed) and treats any unrecognised shape as indeterminate-and-logged, never as a match.
  Until a key is configured the platform runs dataset-only — which is exactly what the ticket
  recommended shipping.
- **Fix item 6 (add this as a gate in `CC-034`/`CC-039`) not done here** — editing other
  backlog files is out of scope for this PR per the repo's tracked-work-item rule; the gate
  addition is a one-line follow-up for Aaron to approve.
- **No on-chain oracle** — per the ticket's own recommendation; revisit if Chainalysis (or
  another oracle) ships Base support, as defence-in-depth on top of the app layer.
