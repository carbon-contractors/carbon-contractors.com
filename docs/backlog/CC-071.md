# CC-071 — Wallet reconnect on page load fires a popup and gets blocked, every refresh

## Problem

Aaron reported: on mobile (and possibly desktop), there is no visible "connected" indicator after
connecting a wallet, and refreshing the page re-triggers the connection request every time —
asked whether session persistence (even just an hour) is something we can fix.

Traced to a real, specific mechanism, not a missing feature — wagmi already persists connection
state to `localStorage` by default, and a visible "connected" indicator already exists
(`WalletConnectButton.tsx` shows the truncated address once `isConnected`). The actual bug:

`<WagmiProvider>`'s default `reconnectOnMount` behaviour calls `@wagmi/core`'s `reconnect()`
action on every mount. That action calls `connector.isAuthorized()` first (a silent, read-only
check — for `baseAccount`, `eth_accounts`), but **then calls `connector.connect({ isReconnecting:
true })` regardless of the result**. Read `@wagmi/connectors`'s `baseAccount()` implementation
directly (`node_modules/@wagmi/connectors/dist/esm/baseAccount.js`): `connect()` unconditionally
sends `wallet_connect` to the Coinbase SDK, which is the same RPC call that opens a popup window
— there is no `isReconnecting`-aware fast path that skips it.

An automatic reconnect fired on page load is not a user gesture. Mobile browsers block popups
that aren't the direct result of a click, so the popup attempt fails (or re-surfaces the same
"this action requires your permission to open a new window" prompt seen live in `CC-069`'s
testing) on every single page load — which is exactly "re-triggers the connection request every
time." The session state persisted in `localStorage` was never actually the problem.

## Fix

- `src/lib/wallet/providers.tsx`: pass `reconnectOnMount={false}` to `<WagmiProvider>`, so wagmi's
  default (popup-triggering) reconnect never runs automatically.
- `src/lib/wallet/useResumableConnector.ts` (new): on mount, if not connected, checks
  `connector.isAuthorized()` directly for each configured connector (most-recently-used first,
  via the same `recentConnectorId` storage key wagmi itself writes on connect) — a plain
  read-only check, no popup — and returns the connector to resume, if any.
- `src/components/WalletConnectButton.tsx`: if a resumable connector is found and the user isn't
  connected, shows a **"Resume Session"** button instead of "Connect Wallet". Clicking it is a
  real user gesture, so if the connector's `connect()` does need to open a popup, the browser
  allows it — and since the session is already authorized, it should complete with no further
  passkey prompt. A "Use a different wallet" link falls through to the normal connector picker.

## Acceptance

- Refreshing the page after a successful connection shows "Resume Session," not a silently
  failed/blocked popup attempt, and no connection popup fires without a click.
- Tapping "Resume Session" restores the connection in one tap, with no passkey re-prompt, on a
  real phone.
- A first-time visitor (no prior connection) still sees the normal "Connect Wallet" → picker flow
  unchanged.

## Update 2026-08-09 — implemented, local verification only so far

Implemented as described. Verified locally in a clean browser profile: with no prior connection,
`/connect` correctly falls through to the normal "Connect Wallet" → picker flow (no regression),
console clean. `npm test` (116/116), `npm run typecheck`, `npm run lint`, `npm run build` all
clean.

**Not yet verified on a real device** — the actual "Resume Session" path (a real prior connection,
refresh, one-tap resume with no popup) needs the same real-phone test as `CC-069`, since this is
exactly the kind of browser-popup behaviour that only shows its true colours on a real device.
Status stays `in-progress` until that's confirmed.

## Update 2026-08-09 — real-device test: partial fix, one real gap remains, deliberately parked

Aaron tested on a real phone (mobile Brave). Results:

- **In-app navigation (clicking between pages) never re-triggers a connection request** — the
  connected wallet address correctly persists and shows in the dropdown throughout. This was
  already true before this fix (client-side React/wagmi state survives client-side navigation
  regardless), but confirms no regression.
- **A true hard reload (pull-to-refresh) still re-triggers the wallet connect flow.** The
  `reconnectOnMount={false}` change stops wagmi's own automatic popup-triggering reconnect, but
  `useResumableConnector`'s `isAuthorized()` check apparently still isn't finding a resumable
  session to offer after a full reload — meaning either the underlying Base Account SDK doesn't
  keep a silently-restorable session across a full page teardown (likely: `getProvider()`
  re-instantiates the SDK from scratch on every fresh mount, and `eth_accounts` may only reflect
  an in-memory session that reload just destroyed, not something backed by persistent storage on
  the SDK's own side), or something more subtle. Not fully root-caused.

Per Aaron's direction, **not chasing this further right now** — pull-to-refresh is a deliberate,
uncommon mobile gesture, not the default way users experience the app (normal navigation, which
does work correctly, covers the vast majority of real usage). Downgraded to `P2`/`todo`, recorded
honestly rather than left silently unresolved. Revisit if it turns out to actually bother users in
practice, at which point the next step is confirming whether `@base-org/account`'s SDK exposes any
session-restoration hook beyond `eth_accounts`, or whether `isAuthorized()` itself needs a retry
loop to allow for the SDK's own async initialization after a fresh page load.

Related: `CC-069`, `CC-055`.
