# CC-004 — /api/dispute is unauthenticated and live right now

## Problem
`src/app/api/dispute/route.ts:14-41` takes a `payment_request_id` and flips the task to
`disputed` with **no authentication of any kind** — no signature, no wallet header, no session.

This is reachable on the live site today: `middleware.ts:63-69` bypasses `/api/*` for the
coming-soon gate, so the endpoint is public while the rest of the site is dark.

Any anonymous caller who can guess or obtain a `payment_request_id` can freeze payment on
any task.

## Fix
Require a wallet signature matching `task.to_human_wallet`. The MCP path already does this
correctly — mirror the challenge-response pattern from `src/lib/mcp/server.ts:311,730` and
`src/app/api/basedhuman.mcp/route.ts:89-141`.

## Acceptance
Unsigned POST returns 401. Signed POST from a wallet other than the assigned worker returns 403.

## Resolution

Extracted `verifyChallengeSignature` out of `src/app/api/basedhuman.mcp/route.ts` into a shared
`src/lib/auth/wallet-challenge.ts` so the same nonce-based challenge-response check backs both the
MCP transport and this REST endpoint, rather than reimplementing it.

`/api/dispute` now requires `x-caller-wallet` / `x-caller-signature` / `x-caller-nonce` headers,
verified against a nonce minted by `POST /api/basedhuman.mcp/challenge`. Unauthenticated or
invalid-signature requests get 401; a validly-signed request from any wallet other than the task's
`to_human_wallet` (the assigned worker — this endpoint is worker-initiated, unlike `dispute_task` in
the MCP server which authorizes the requesting agent) gets 403. The existing task-status guard
(only `active`/`pending` tasks can be disputed) is unchanged.

The dashboard's `handleDispute` (`src/app/dashboard/page.tsx`) fetches a challenge, signs it with
`useSignMessage`, and sends the signature alongside the existing on-chain `disputeTask` call.

Added `src/lib/__tests__/dispute-route.test.ts` (6 cases: missing auth, malformed wallet header,
failed signature verification, wrong-wallet 403, happy path, status-guard still enforced).
`npm run typecheck` and `npm run lint` clean; full suite 77/80 passing — the 3 failures are the
pre-existing `escrow.test.ts`/`signer.test.ts` flakiness from real Sepolia broadcasts (CC-060),
unrelated to this change.

Landed on branch `claude/cc-004-dispute-auth`, not yet merged.
