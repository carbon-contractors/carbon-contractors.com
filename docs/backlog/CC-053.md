# CC-053 — Recover the local dev environment after the CPU and motherboard swap

Storage devices were kept, CPU and motherboard were replaced. That combination leaves data
intact but breaks anything bound to the old hardware. Work through this before trusting a
local test result.

## 1. TPM-bound credentials — check this first
A new motherboard means a new TPM (or a reset firmware TPM in the new CPU). **Everything
sealed to the old TPM is unrecoverable**, not merely re-authenticated:

- **Coinbase Smart Wallet passkeys.** This is the one that bites hardest. Smart Wallets are
  passkey-based, and a Windows Hello passkey is a TPM-resident platform credential. If any
  test worker or agent wallet was enrolled only via Windows Hello on that machine, that
  wallet is gone — and the signup flow you are trying to launch is exactly the flow that
  needs it. Check whether those wallets had a second owner or a phone/YubiKey passkey enrolled.
- **Windows Hello factors on GitHub, Vercel, Supabase, GCP, npm.** YubiKeys are external and
  unaffected, so if the YubiKey enrolment held, platform access is fine. Any account where
  Windows Hello was the *only* second factor now needs recovery codes. Directly relevant to
  CC-041.
- **BitLocker.** TPM-only protectors trigger a recovery-key prompt after a board swap. The
  machine boots, so the OS drive was handled — but confirm the data drives, including the one
  holding this repo. `manage-bde -status` lists every volume.
- **Bitwarden unlock with Windows Hello** will fall back to the master password.

## 2. Virtualisation is probably off in the new UEFI
Fresh firmware defaults usually disable AMD-V/SVM or Intel VT-x. WSL2 and Docker Desktop then
fail with errors that do not mention virtualisation at all. Re-enable it in UEFI before
debugging anything else. NOR-302 notes a separate WSL git config, so WSL is in the loop.

## 3. Windows activation
The digital licence is keyed to a hardware hash dominated by the motherboard, so expect
deactivation. Settings → System → Activation → Troubleshoot → "I changed hardware on this
device recently", then sign in with the linked Microsoft account. An OEM licence tied to the
old board may not transfer.

## 4. Drive letters may have moved
A new chipset can enumerate NVMe and SATA devices in a different order. This repo is expected
at `F:\Project_Meat-Sacks-Need-Work-2`, and `.claude/settings.local.json` has that path
hardcoded. Confirm the letter, or fix the paths.

## 5. Node toolchain — mostly fine, but reinstall
Same x86_64 architecture, so native bindings do not care about an Intel/AMD change, and the
user profile survived with npm cache and global installs intact. Two real issues though:

- `node_modules` was installed against the **March** `package.json`, before the 73-commit
  fast-forward. `next` alone went 16.2.1 → 16.2.6. Run a clean `npm ci`. Expect it to be slow
  if the repo lives on a mechanical or heavily-shared drive.
- `.claude/launch.json` hardcodes `C:/nvm4w/nodejs/node.exe`. If the nvm-for-Windows symlink
  target changed or the active version moved, the debug launch config silently breaks.

## 6. Sepolia test funds
Not hardware, but four months of decay: check the test wallets still hold Sepolia ETH for gas
and test USDC, and that the faucets you used still work.

Related: CC-041, CC-047, CC-052, CC-032.

## Update 2026-07-25 — mostly cleared by Aaron, downgraded P1 → P3

Two of the three headline risks above do not apply. Recorded here so this is not re-raised.

**TPM-bound credentials — not applicable.** Windows Hello was never used as a passkey provider,
nor to unlock Bitwarden. So there were no TPM-resident platform credentials to lose, and the
Smart Wallet passkey concern is void.

One residual thing worth 30 seconds, not more: confirm where the Coinbase Smart Wallet passkeys
used for testing actually live. If they are Chrome profile passkeys synced to a Google account
they are hardware-independent and fine. If any were created as browser-local credentials they
are not TPM-sealed but are still tied to that browser profile, so they survive a board swap and
die with a profile reset. Either way this is a "know where it is" item, not a recovery item.

**Virtualisation — confirmed enabled.** Task Manager reports Virtualization: Enabled on the new
AMD Ryzen 7 9700X (8 cores / 16 logical). The UEFI default concern does not apply.

**WSL still worth updating.** Four months of no updates; run `wsl --update` and
`wsl --status`. Kernel updates ship out of band from Windows Update, so a stale kernel is likely
even though virtualisation itself is fine.

**BitLocker — unaddressed, low priority.** Machine boots, so the OS volume is fine. If the data
drive holding this repo was ever encrypted with a TPM protector, auto-unlock would have broken.
`manage-bde -status` settles it in one command.

### What remains genuinely open on this issue

- Drive letters may have moved — `.claude/settings.local.json` hardcodes `F:\Project_Meat-Sacks-Need-Work-2`

On the hardware: a 9700X will chew through `npm ci` and `next build`. Any install slowness seen

## Update 2026-07-25 (2) — passkey question closed

Test wallets were **Coinbase Wallet browser extension** wallets — seed-phrase EOAs, keystore
encrypted at rest inside the Chrome profile on disk. Nothing TPM-sealed, nothing passkey-based.
Storage was retained through the swap, so they survived intact. This thread is closed.

Two residual notes, neither hardware-related:

- **Recovery phrase.** A browser-extension wallet is recoverable *only* from its 12-word phrase.
  It survives motherboard swaps but not a profile reset, a browser reinstall, or disk corruption.
  Worth confirming the phrase is in Bitwarden before doing anything else with those wallets.
- **Is one of them the deployer?** If `DEPLOYER_PRIVATE_KEY` in `.env.local` was ever exported
  from or imported into a browser extension, that key has had a materially weaker custody story
  than the KMS narrative implies. Not urgent — NOR-196 moved live authority to the HSM — but it
  affects what the old key should still be trusted with. See CC-052.

The more consequential finding from this is not about hardware at all: it means the passkey
onboarding path was never tested. Tracked as **CC-055**.
