# CC-056 — Decide repo visibility before pushing the backlog — it documents live vulnerabilities

## Problem
`github.com/carbon-contractors/carbon-contractors.com` is **Public** (confirmed 2026-07-25:
121 commits, 2 stars, 2 open PRs).

The backlog created on 2026-07-25 contains, in plain text with `file:line` precision:

- **CC-004** — `/api/dispute` accepts an unauthenticated POST and freezes payment on any task.
  Reachable **right now**, because `middleware.ts` bypasses `/api/*` for the coming-soon gate.
- **CC-054** — an out-of-band `exec_sql` RPC on Supabase whose grants are unverified.
- **CC-002** — the wallet-casing defect, which also implies duplicate-registration behaviour.
- **CC-003** — the exact CSP gaps.
- **CC-015 / CC-016** — the waitlist has no honeypot or captcha.

That is a working exploit list for a live deployment, indexed by GitHub and readable by anyone.

**Nothing is exposed yet.** All five commits from the 2026-07-25 session are local and unpushed.
This is a decision to make *before* `git push`, not damage to clean up after.

Note this is a sharper version of the pre-existing CC-028 (`AUDIT-2026-03-25.md` published in the
repo root). That one is lower risk because its findings are closed. CC-004 and CC-054 are not.

## Options

**(a) Make the repo private until launch — recommended.** Costs nothing, reversible in two clicks,
and there is no benefit to public source pre-launch. The transparency argument behind
`docs/Security-Trust-Disclosure.md` is about the HSM architecture being independently verifiable —
which it is, via the attestation bundle and on-chain owner address. It has never required
publishing an unfixed-defect list. Re-open the repo after CC-004 and CC-054 are closed, if you
still want to.

**(b) Keep the repo public, keep the backlog out of it.** Add `docs/backlog/` to `.gitignore`.
Loses version history on the tracker, which is most of why it lives in the repo. Weakest option.

**(c) Fix CC-004 and CC-054 first, then push.** Both are small. CC-004 is a signature check
mirroring the pattern already in `src/lib/mcp/server.ts`; CC-054 is a `REVOKE`. Defensible, but it
serialises the launch work behind two unrelated fixes.

## Recommended sequence
1. Set the repo private now.
2. Push the local commits.
3. Fix CC-004 and CC-054.
4. Revisit visibility as a deliberate choice rather than a default.

## Also worth checking
Two pull requests are open on the repo and have been since at least May. Dependabot PRs going
stale on a public repo advertise which known-vulnerable versions are in use.

## Acceptance
A conscious, recorded decision on visibility, made before the first push.

Related: CC-004, CC-054, CC-028, CC-015.

## Decided 2026-07-25 — stay public. Recommendation withdrawn.

Aaron's reasoning, which is better than the recommendation above:

Web3's characteristic failure mode is an anonymous developer who conceals everything until the rug
pull. An unknown solo builder asking people to trust an escrow service cannot close that trust gap
by assertion — verifiable self-scrutiny is the only currency available. A public tracker saying
"here is what is wrong with my own app and here is me fixing it" is a *stronger* signal than a
clean README, because a repository containing only successes is indistinguishable from one that was
never examined. The journey is the evidence.

And the exploitable surface is close to nil: no users, no real money, Sepolia only. `CC-004` lets
someone freeze payment on a task that is worth nothing.

`AUDIT-2026-03-25.md` sitting in the repo root was read as an oversight during the review. It was
a deliberate choice, consistent with this ethos. `CC-028` is closed on the same basis.

## One carve-out retained, and it is the reason this is P1 not P3

Publishing a pointer to an unfixed defect is fine when the downside lands on the operator. It is
not fine when it lands on someone else.

The `waitlist` table holds **real email addresses from real people** who signed up in good faith.
`CC-054` (unverified `exec_sql` grants) is the one open item where a reader of this backlog could
reach third-party data. So it is fixed before the backlog is pushed, not after.

Counter-argument acknowledged: the anon key ships to every browser, so `exec_sql` is discoverable
by anyone probing the API — publishing `CC-054` does not create the exposure, it just lowers the
cost of finding it from "probe systematically" to "read a file." That is still a meaningful
difference for a repo about to be actively promoted. And it makes for a better document: every
entry reading "found and fixed" is stronger than one reading "found, here it is."

## Disclosure policy — now recorded in docs/Lessons-Learned.md

Defects are published as found, with two exceptions, both fixed before publication:

1. anything exposing third-party data
2. anything trivially exploitable against real funds

Everything else publishes immediately, unfixed, with the reasoning intact.

## Sequence
1. Fix `CC-054` (a `REVOKE`, plus a migration so it stops being invisible).
2. Push.
3. Fix `CC-004` and add its entry to `docs/Lessons-Learned.md`.
4. Continue publishing as found.

## Still worth a look
Two pull requests have been open since at least May. Stale Dependabot PRs on a public repo
advertise which vulnerable versions are running — that one is a genuine argument for closing them
promptly rather than for hiding the repo.

Related: CC-054, CC-004, CC-028.
