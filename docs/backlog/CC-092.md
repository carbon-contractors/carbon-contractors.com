# CC-092 — The app layer has no v2 write path

## Problem

`CC-082` shipped CarbonEscrow v2 and proved the full lifecycle on Sepolia — but it proved it
through `scripts/admin/verify-escrow-lifecycle.ts`, driving the contract directly with viem. **None
of that path exists in `src/`.** The read side followed the redeploy; the write side did not.

Found while doing `CC-081` Defect 4. Filed separately because it is a gap in coverage, not a defect
in any one of the existing issues — each of them assumes this exists.

Verified in the current tree on 2026-08-16:

1. **A worker cannot deliver.** `submitWork` is the `Funded` → `Delivered` transition and the whole
   reason v2 exists (`ADR-0001` D1). `grep -rn "submitWork" src/` hits only
   `src/lib/contracts/escrow-abi.ts` and the event-reading helper
   `getSubmittedTaskIdsForWorkerFromEvents` (`src/lib/contracts/escrow.ts:330`). There is no MCP
   tool, no API route, and no dashboard control that submits work. The 10 MCP tools in
   `src/lib/mcp/server.ts` go straight from `request_human_work` to `confirm_task_completion`.
2. **Nothing signs a verdict.** The only EIP-712 verdict signer in the repo is `signVerdict` at
   `scripts/admin/verify-escrow-lifecycle.ts:181`. `src/lib/contracts/signer.ts` has three write
   functions and none of them is it; the file's only mention of a verdict is a comment at `:116`.
   Neither party can obtain the signature the contract requires.
3. **A worker cannot claim.** `releaseAfterReview` and `claimWithVerdict` are worker-called
   pull-payments (`ADR-0001` A1.2/A1.3). No route, tool or UI initiates either — the dashboard has
   no claim affordance at all.
4. **Neither party can dispute.** v2's `disputeTask` requires a **signed failing verdict**; there is
   no bare-assertion dispute. Both `/api/dispute` and the `dispute_task` MCP tool predate that and
   pass no verdict, so neither can produce a call the contract would accept.

## Why this is its own issue

The four issues that touch this each assume it exists and none of them owns it:

- **`CC-080`** covers settlement and was correctly resequenced behind `CC-082`, but its scope is
  *removing* the platform's `completeTask` call and deciding the resulting DB status. It does not
  add the worker's side.
- **`CC-083`** builds the deterministic checker that *decides* a verdict. Turning that decision into
  a signed EIP-712 struct and serving it to whichever party needs it is a separate concern, and
  `ADR-0001`'s handover does not name it as a step.
- **`CC-081`** Defects 1 and 3 are the funding and DB-projection halves.
- **`CC-085`**'s `verify-signer` proves the *contract will accept* a signature from the configured
  signer. It deliberately says nothing about whether any code path produces one.

**Consequence:** `CC-077`/`CC-078`/`CC-079` can only be run by hand with scripts. Passing them that
way would demonstrate the contract works and say nothing about whether the product does — which is
the `Lessons-Learned.md` §23 failure mode exactly.

## Fix

Sequencing note: this lands **after `CC-084`**, for the same reason `CC-081` Defect 1 does.
`submitWork` reverts `SpecAckMismatch()` unless the worker echoes `task.specHash`
(`contracts/CarbonEscrow.sol:295`), so there is nothing coherent for a worker to acknowledge until
the spec schema exists.

- **A worker-facing submit path** — evidence hash, `specVersionAck`, and the optional `CC-036`
  `attestationUid` slot. Worker-signed from their own wallet; the platform is not the sender.
- **A verdict service.** Take `scripts/admin/verify-escrow-lifecycle.ts:181` as the reference
  implementation and move it into `src/lib/contracts/`, so the domain separator, typehash and
  struct encoding exist in exactly one place. It must be reachable by **both** parties — a worker
  presenting a passing verdict to `claimWithVerdict`, and either party presenting a failing one to
  `disputeTask`. Note `CC-090`: the signing key should be the verdict signer, not the owner.
- **A claim path** for `releaseAfterReview` and `claimWithVerdict`, surfaced in the dashboard.
  Pull-payment means an unclaimed settlement is indistinguishable from theft to the worker
  (`CC-085`'s `verify-unclaimed` monitors exactly this), so the UI is load-bearing, not cosmetic.
- **Rewrite `dispute_task` and `/api/dispute`** to carry a verdict and signature, and correct the
  authority to either party per `ADR-0001` D2 — the app-layer half of `CC-081` Defect 2, which the
  contract already enforces.

## Acceptance

- A worker submits, waits out the review window, and claims — entirely through the product, with no
  script and no platform transaction in the path.
- A worker claims early against a passing signed verdict obtained from the platform.
- Either party opens a dispute by presenting a signed failing verdict; a bare assertion is refused
  before it reaches the chain.
- `CC-077`/`CC-078`/`CC-079` are executed through the app, not through
  `scripts/admin/verify-escrow-lifecycle.ts`.

## Open

- Whether the verdict service is an MCP tool, an API route, or both. The worker is a human on the
  dashboard and the agent is an MCP client, so it probably needs both surfaces.
- What the worker sees when the platform declines to sign. `CC-082` records the consequence
  plainly: if the platform will not sign a failing verdict, the worker is paid. That is the intended
  bias, but it needs saying in worker-facing copy.

Related: `CC-082` (the contract and the reference implementation), `CC-080`, `CC-081` (Defects 1–3),
`CC-083` (produces the verdict this service signs), `CC-084` (blocks this), `CC-090`, `CC-036`,
`CC-077`/`CC-078`/`CC-079`, `ADR-0001` D1/D2 + Amendment 1.

## Update 2026-08-21 — PR 1: verdict signing extracted into `src/`

First slice only. The other three gaps this issue identifies — the worker submit path, the
claim path, and the `dispute_task`/`/api/dispute` rewrite — are still not built.

- `src/lib/contracts/verdict.ts`: `signVerdict`, `VERDICT_TYPES`, `verdictTuple` and
  `randomVerdictNonce`, extracted from `scripts/admin/verify-escrow-lifecycle.ts:151-210` so
  the domain separator, typehash and struct encoding exist in exactly one place, reachable by
  `src/`. The script now imports from here instead of carrying its own copy.
- Domain `chainId` comes from `getEscrowConfig()` (`NEXT_PUBLIC_BASE_NETWORK`), not a hardcoded
  `baseSepolia.id` as the script had — this signs correctly against either deployment.
- Tests pin a real signature vector against the well-known Hardhat account #0 key and assert a
  testnet vs mainnet domain produces a different signature, so a chainId regression fails here
  rather than as a silent `VerdictSignerNotAccepted` on whichever chain was not tested by hand.

Deliberately not in this PR: nothing calls `signVerdict` yet. There is still no verdict
*computation* service — something that takes a `taskId`, loads its committed `specHash` and
`evidenceHash`, runs `CC-083`'s checker against a caller-supplied `EvidenceBundle`, and signs the
result — and no route or MCP tool exposing one. That composition, plus the worker submit path,
the claim UI, and the dispute rewrite, are separate follow-up PRs against this same issue.
