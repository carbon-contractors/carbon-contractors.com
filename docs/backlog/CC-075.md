# CC-075 — Auto-accept bookings should turn off if a worker goes AWOL — mechanism undecided

## Problem

Once `CC-074` ships a real, working `accepts_auto_booking` toggle, a new failure mode opens up: a
worker turns it on, then goes unresponsive — stops checking notifications, stops completing
work — while agents keep auto-booking them against a rate/category match that's technically still
"available." Every booking still resolves safely on the money side (escrow either completes or
expires and refunds the agent — see `CarbonEscrow.expireTask`), but it's a bad experience for
agents repeatedly hiring someone who never delivers, and bad for the platform's credibility if
auto-booking quietly keeps assigning work to someone who's gone dark.

Aaron flagged this directly, explicitly as unsolved: **the mechanism for detecting "AWOL" and
acting on it needs real design work, not just a flag to flip.**

## Open questions — not decided yet

- **What counts as AWOL?** Candidates, not mutually exclusive: N consecutive expired/disputed
  tasks in a row; no completed task within X days of being auto-booked; no wallet/dashboard
  activity for X days; some explicit "are you still active?" check the worker has to answer.
- **Who/what makes the call?** A scheduled job scanning recent task outcomes? A threshold check
  inline whenever a new auto-booking would occur? Both have different cost/latency tradeoffs.
- **What actually happens when triggered?** Just flip `accepts_auto_booking` back to `false`
  (silent, safe, but the worker might not notice)? Notify them first? Require manual re-enable, or
  let it self-heal once they're active again?
- **False positives matter.** A worker on legitimate leave (holiday, illness) shouldn't come back
  to find themselves silently opted out with no explanation — whatever the trigger is, the
  worker-facing communication matters as much as the detection logic.

## Fix

Not specified — this issue exists to hold the problem, not prescribe the answer. Whoever picks
this up should propose a mechanism (probably starting with the simplest detectable signal —
consecutive expirations/disputes is the cheapest to build on top of data the escrow contract
already emits) and get it reviewed before building, given the false-positive risk above.

## Acceptance

A documented, agreed mechanism exists and is implemented — not just a database column that
nothing ever sets.

Related: `CC-074` (this only matters once auto-booking is a real, reachable toggle).

## Update 2026-08-11 — backlog triage pass

Lowered P1 → **P2**. It is a consequence of a feature that does not exist yet — there is
nothing to detect until `CC-074` makes auto-booking a real, reachable toggle — and, as this issue

That makes this a credibility and experience problem rather than a fund-safety one, which is the
right shape for P2. The design questions above stay open and unprescribed; nothing about the
downgrade settles them.

## Update 2026-08-13 — mechanism decided by `ADR-0001`

This issue was filed explicitly as unsolved: *"the mechanism for detecting AWOL and acting on it
needs real design work, not just a flag to flip."* That design work is done. `ADR-0001` resolves it,
and the title no longer says "undecided".

**The reason it was unsolvable before is now visible.** `CarbonEscrow` had one clock and no delivery
signal, so "the worker did not deliver" and "the agent did not accept" produced the identical
on-chain outcome — an expiry. There was nothing to detect. `ADR-0001` D1 adds `submitWork`, which
separates the two cases, and the signal this issue was missing appears as a side effect.

**Decided mechanism:**

- **Trigger:** N consecutive `TaskExpired` events with zero `WorkSubmitted`. Start at **N = 3**.
- **Where:** checked **inline at auto-booking time**, not on a cron. A scheduled job maintaining a
  flag that is only ever read at booking is pure overhead.
- **Action:** set `accepts_auto_booking` false, notify the worker, and let them self-re-enable from
  the dashboard.
- **Explicitly not** a slash and **not** a reputation penalty. An expiry refunded the agent —
  nobody lost anything — and the legitimate-leave false positive costs the worker one toggle. That
  answers the false-positive concern in the open questions above without needing a leave mechanism.

**Answering this issue's own open questions:** "what counts as AWOL" is consecutive expiries with no
submission, because that is the only signal that distinguishes worker inaction from agent inaction.
"Who makes the call" is the booking path itself. "What happens" is the toggle, reversibly. "False
positives matter" is handled by making the consequence trivially reversible rather than by trying to
detect leave.

**Now depends on `CC-082`** (the contract work that adds `submitWork`) as well as `CC-074`. Until
`submitWork` exists there is still no signal to count.

Priority stays **P2** — funds are never at risk either way, since `expireTask` refunds the agent.

Related: `ADR-0001` D1 and its "CC-075 resolves as a consequence" section, `CC-082`, `CC-074`.
