# CC-075 — Auto-accept bookings should turn off if a worker goes AWOL — mechanism undecided

## Problem

Once `CC-074` ships a real, working `accepts_auto_booking` toggle, a new failure mode opens up: a
worker turns it on, then goes unresponsive — stops checking notifications, stops completing
work — while agents keep auto-booking them against a rate/category match that's technically still
"available." Every booking still resolves safely on the money side (escrow either completes or
expires and refunds the agent — see `CarbonEscrow.expireTask`), but it's a bad experience for
agents repeatedly hiring someone who never delivers, and bad for the platform's credibility if
auto-booking quietly keeps assigning work to someone who's gone dark.

Aaron flagged this directly, explicitly as unsolved: **the mechanism for detecting "AWOL" and
acting on it needs real design work, not just a flag to flip.**

## Open questions — not decided yet

- **What counts as AWOL?** Candidates, not mutually exclusive: N consecutive expired/disputed
  tasks in a row; no completed task within X days of being auto-booked; no wallet/dashboard
  activity for X days; some explicit "are you still active?" check the worker has to answer.
- **Who/what makes the call?** A scheduled job scanning recent task outcomes? A threshold check
  inline whenever a new auto-booking would occur? Both have different cost/latency tradeoffs.
- **What actually happens when triggered?** Just flip `accepts_auto_booking` back to `false`
  (silent, safe, but the worker might not notice)? Notify them first? Require manual re-enable, or
  let it self-heal once they're active again?
- **False positives matter.** A worker on legitimate leave (holiday, illness) shouldn't come back
  to find themselves silently opted out with no explanation — whatever the trigger is, the
  worker-facing communication matters as much as the detection logic.

## Fix

Not specified — this issue exists to hold the problem, not prescribe the answer. Whoever picks
this up should propose a mechanism (probably starting with the simplest detectable signal —
consecutive expirations/disputes is the cheapest to build on top of data the escrow contract
already emits) and get it reviewed before building, given the false-positive risk above.

## Acceptance

A documented, agreed mechanism exists and is implemented — not just a database column that
nothing ever sets.
