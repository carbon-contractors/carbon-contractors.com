# CC-059 — Escrow ownership was never transferred to the HSM key

## Problem

`docs/Security-Trust-Disclosure.md` asserted, in a public repository, that the KMS/HSM-derived
address is the owner of the deployed escrow contract, and invited readers to confirm it on
Basescan. Measured against Base Sepolia on 2026-07-30, it is not:

| | Address | Balance |
| :-- | :-- | :-- |
| HSM key, derived from `docs/carbon-contractors-escrow-signer-1.pub` | `0xa8931097540e69B474013D294d0bA6A2cC853e4b` | 0.101 ETH |
| `CarbonEscrow.owner()` — `0xb9bF8dAC51f62cA237F2C439c63c9D8f16FD2ef7` | `0x7863A5c4396E7aaac2e99Cb649a7Aa4F6A36B91b` | 0.1866 ETH |
| `ReputationStake.owner()` — `0x4cdeF542F9361201f9543512eeCd1eE834793203` | `0x7863A5c4396E7aaac2e99Cb649a7Aa4F6A36B91b` | |

`0x7863A5c4…` is the address of `DEPLOYER_PRIVATE_KEY` in the local `.env.local` — a conventional
private key on a developer machine. The HSM key was created and funded, but
`HSM-Deployer-Checklist.md:47` ("Authorize this address on the escrow contract via
`transferOwnership()` or equivalent") was never performed.

The checklist recorded this honestly as unticked boxes at lines 262 and 264. The disclosure
document asserted it as verified fact regardless. See `docs/Lessons-Learned.md` §10.

**No user funds were ever exposed.** These are Base Sepolia contracts holding test USDC, and
`totalLocked()` was `0` when measured. This is a correctness-and-trust defect, not a live theft
risk — which is why it is published as found rather than fixed first under the `CC-056` carve-out.

  contract owner… Local escrow writes will revert"). Local writes work; it is production that has

## Update 2026-07-30 — resolved: Vercel has `GCP_KMS_KEY_PATH` set. This is live, not hypothetical.

Aaron checked the Vercel dashboard. `GCP_KMS_KEY_PATH` is present, marked Sensitive, added
2026-04-17, scoped to **Production and Preview**.

So `getPlatformAccount()` (`src/lib/contracts/signer.ts:49`) takes the KMS branch in both deployed
environments. Production and every preview deploy sign as `0xa8931097540e69B474013D294d0bA6A2cC853e4b`
— the HSM address. The escrow's actual owner is `0x7863A5c4396E7aaac2e99Cb649a7Aa4F6A36B91b`, the raw
local key. Those are different addresses.

`CarbonEscrow.resolveDispute` is `onlyOwner` (`CarbonEscrow.sol:162`). **Right now, in production, any
call to `resolveDisputeOnChain` reverts with `OwnableUnauthorizedAccount`.** This is not a future risk
contingent on a Vercel setting — the setting is already what it would need to be for the break to be
live. Promoted from P1 to **P0** for that reason, though the blast radius stays bounded: Sepolia, test
USDC, `totalLocked() = 0` at last measurement, and disputes are presumably rare pre-launch. It should
still be fixed before any real dispute-resolution testing (`CC-032`) and definitely before mainnet
(`CC-039`).

`completeTaskOnChain` and `expireTaskOnChain` are unaffected by *this* issue: `completeTask` is
gated on `msg.sender == task.agent` regardless of who owns the contract (a separate, already-broken
path — `CC-037`), and `expireTask` has no access restriction at all.

## Fix

1. **Verify KMS signing actually works end-to-end before transferring anything** —
   `npm run verify:kms` locally (needs `gcloud auth application-default login` and
   `GCP_KMS_KEY_PATH` in `.env.local`), or trigger a Vercel preview and watch it sign. Ownership
   transfer is one-way: once `0xa8931097…` owns the contract, the raw key can no longer arbitrate
   disputes, so confirm the replacement actually works first.
2. `transferOwnership(0xa8931097540e69B474013D294d0bA6A2cC853e4b)`, called from the current owner
   (`DEPLOYER_PRIVATE_KEY`), on both `CarbonEscrow` and `ReputationStake`. **This is a production
   contract write — do not run it without Aaron's explicit go-ahead in chat, immediately before.**
3. Re-run `node --env-file=.env.local scripts/audit/verify-contract-owner.mjs` — it exits `0` once
   this is right.
4. Verify `resolveDisputeOnChain` succeeds end-to-end on a preview deployment.
5. Remove `DEPLOYER_PRIVATE_KEY` from every deployed environment (`HSM-Deployer-Checklist.md:264`).
6. Update `docs/Security-Trust-Disclosure.md` to state the match as verified now that it is, and
   tick the checklist boxes only once the script passes.

## Acceptance

`node --env-file=.env.local scripts/audit/verify-contract-owner.mjs` exits `0`, and a dispute
resolution succeeds on a preview deployment signed by the HSM key.

Gates `CC-039` (mainnet go-live). Related: `CC-052`, `CC-037`, `CC-041`.

## Update 2026-08-08 — steps 1 and 2 done, ownership transferred on-chain

**Step 1, done properly.** `kms-signer-svc` (the service account name in
`HSM-Deployer-Checklist.md` was stale — it's always actually been `kms-signer-svc`, corrected in
that doc now) only had the KMS signing role granted to itself, not to Aaron's own account, so
`gcloud auth application-default login` alone couldn't work — confirmed by checking the actual IAM
console rather than assuming. Granted Aaron's account `roles/iam.serviceAccountTokenCreator`
scoped to `kms-signer-svc` (a standing project-level grant was made once by mistake via the wrong
IAM page first — caught and left as a live example of the failure mode in
`Lessons-Learned.md` — then corrected to scope it to the account, not the service account).
`gcloud auth application-default login --impersonate-service-account=kms-signer-svc@carbon-contractors.iam.gserviceaccount.com`,
then `npm run verify:kms` — **✓ ALL CHECKS PASSED** against real GCP Cloud KMS: fetched the real
public key, derived the known HSM address, had KMS actually sign a message, recovered the signer
from that signature and it matched.

**Step 2, executed with explicit go-ahead given in chat immediately before, as this issue
requires.** Hit one more blocker first: Hardhat 3's `run` task validates CLI arguments strictly
against its own defined parameters and rejects anything else — the Hardhat 2-era `hardhat run
script.ts -- --confirm` passthrough `CC-064` didn't know had changed no longer works
(`HHE506: argument not consumed`). Switched `scripts/admin/transfer-escrow-ownership.ts`'s
confirmation flag from `process.argv.includes("--confirm")` to `process.env.CONFIRM === "true"`,
re-verified the dry run still worked, then ran it live: `CONFIRM=true npx hardhat run
scripts/admin/transfer-escrow-ownership.ts --network baseSepolia`.

**The script's own output said both transfers FAILED. They had not.** Both `transferOwnership()`
calls succeeded on-chain — confirmed independently via Basescan directly on both transaction
hashes, `OwnershipTransferred` emitted, no reverts:
[`0xcaf22c7…`](https://sepolia.basescan.org/tx/0xcaf22c758ec388adfb51354f33094c2d94f6a96f9b821adc963c45871c882035)
(CarbonEscrow),
[`0xe17a8f0…`](https://sepolia.basescan.org/tx/0xe17a8f0152b65030c99422f9d9099a73157d88c58490c12c7628139ee6f7280f)
(ReputationStake). The script's own `contract.owner()` re-read, immediately after `tx.wait()`
resolved, against the same public `sepolia.base.org` RPC endpoint used for the write, returned the
*old* owner — a stale read on a load-balanced public gateway with no read-your-writes guarantee
across its backend nodes, not a real failure. See `Lessons-Learned.md` for the full account of why
this is worth remembering rather than just noting in passing.
