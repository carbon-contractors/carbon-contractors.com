# CC-025 — /services tables can clip on narrow phones

`src/app/services/services.module.css` has no media queries, and `.exampleTask` uses
`white-space: nowrap` (line 158) inside a `<table>` (`src/app/services/page.tsx:57-72`).
Combined with `overflow-x: hidden` on `body` (`src/app/globals.css:41-45`), example tables
can clip at around 360px with no way to scroll to the cut-off content.

`connect.module.css` and `mcp-info.module.css` also lack media queries but are fluid, so
they are lower risk.

Fix: wrap the tables in a horizontally scrollable container, or restack them as cards below
~600px. Check on a real 360px device.

## Update 2026-08-16 — a second source of the same symptom, split out as `CC-096`

A viewport-overflow measurement on `/mcp-info` at 375px (`body.scrollWidth` 384 vs `clientWidth`
375) traced not to that page but to the **shared `Footer`** — `.links` was a `nowrap` flex row
with no media queries, overflowing on every page `PageShell` renders. Filed and fixed as
`CC-096`.

Two things this ticket got right and one it did not cover:

- **Right:** the assessment above that `mcp-info.module.css` is "fluid, so lower risk" holds. The
  overflow measured there was not its own.
- **Right:** the `overflow-x: hidden` masking described here (`globals.css:41-45`) is exactly what
  hid the Footer defect too — it clips silently instead of offering a scrollbar. That mechanism is
  now the recurring theme across both tickets, and is worth checking first for any future "content
  is cut off on mobile" report.
- **Not covered:** this ticket is scoped to `/services` tables, so the shared Footer was never in
  its remit. Splitting rather than folding, per `docs/backlog/README.md`.

**This ticket stays open and stays P2**, but with a measurement it did not have before. `/services`
was swept after the `CC-096` fix, at both widths, sweeping every element for
`right > innerWidth` or `left < 0`:

| Viewport | `body` sw/cw | Overflowing elements | Widest example table |
| :-- | :-- | :-- | :-- |
| 375px | 375 / 375 | 0 | 270px in a 312px parent |
| 360px | 360 / 360 | 0 | **278.6px in a 312px parent** |

So the tables are **not** clipping at 360px today — the overflow that was visible at that width
was the Footer, now fixed. This ticket is less acute than written.

It is not closed, for one measured reason: the widest table is at **89% of its container** with
`white-space: nowrap` still in force (`services.module.css:158`). There is 33px of headroom, so a
longer example-task string, a longer category name, or a 320px viewport still tips it over — and
when it does, `overflow-x: hidden` will hide it exactly as before. The fix in this ticket (scroll
container, or restack as cards) remains the right one; it is now a latent defect rather than a
live one. Closing it on the strength of "it looks fine at 360px" would be the same mistake the
Footer got away with for months.

Related: `CC-096`.

## Done 2026-08-21 — commit `ad1c930`

Went with the scroll container: each `<table>` in `src/app/services/page.tsx` is now wrapped
in a `.tableScroll` div (`overflow-x: auto`, `-webkit-overflow-scrolling: touch`), and the
table's own `margin-bottom` moved to the wrapper so spacing is unchanged. `white-space: nowrap`
on `.exampleTask` stays — a too-wide table now scrolls within the card instead of being clipped
by `body`'s `overflow-x: hidden`, which covers the 33px-headroom, longer-string and 320px-viewport
cases from the 2026-08-16 measurement. Not re-measured on a real 360px device — the mechanism
fix (a scrollbar exists where `overflow-x: hidden` previously clipped silently) does not depend
on width, but a device pass during the `CC-014` pre-flip checklist would still be prudent.
