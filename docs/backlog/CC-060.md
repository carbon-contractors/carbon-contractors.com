# CC-060 — The test suite broadcasts real Base Sepolia transactions

## Problem

`npm test` is not hermetic. It makes live calls to the public Base Sepolia RPC and **sends real
transactions**. Consequently its pass/fail depends on network latency and rate limiting, which was
measured on 2026-07-30 across five consecutive runs on an unchanged tree:

| run | result |
| :-- | :-- |
| 1 | 3 failed / 71 passed |
| 2 | 1 failed / 73 passed |
| 3–5 | 74 passed |

The failing runs were the ones executed while `scripts/audit/verify-contract-owner.mjs` was also
hitting `sepolia.base.org`. That is the whole explanation: the suite competes with anything else
using the same public endpoint.

### Mechanism

`src/lib/__tests__/signer.test.ts:20` stubs `NEXT_PUBLIC_ESCROW_CONTRACT` to
`0x1234567890123456789012345678901234567890`, and line 25 supplies Hardhat account #0's
well-known key. The test then calls `completeTaskOnChain`.

`completeTaskOnChain` (`src/lib/contracts/signer.ts:112`) calls `simulateContract` first, and the
assumption is that this fails. It does not: **an `eth_call` against an address with no code
succeeds**, returning empty data rather than reverting. So `writeContract` runs and broadcasts.

Confirmed on chain:

```
tx     0x1cc38f04139e49370470258905788b72827cc3052ebd120be583a53e7255647d
block  44801606
from   0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266   (Hardhat account #0)
to     0x1234567890123456789012345678901234567890   (the stub address, no code)
status success, 22440 gas
```

The comment at `signer.test.ts:94-95` says "It will fail at simulateContract since there's no RPC" —
but there *is* an RPC. `getChainConfig()` falls back to `chain.rpcUrls.default.http[0]` when
`BASE_SEPOLIA_RPC_URL` is unset, which is the public endpoint. The test's premise has been wrong
since it was written; it passed by luck.

### Second, related problem

Vitest loads `.env.local` into `process.env`, and `vitest.config.ts` sets no `env` block to prevent
it. So a local run can pick up the **real** `DEPLOYER_PRIVATE_KEY`, `NEXT_PUBLIC_ESCROW_CONTRACT`
and Supabase credentials, while CI runs with the stubs in `.github/workflows/ci.yml:39-45`. Local
and CI are therefore not running the same tests. Given `DEPLOYER_PRIVATE_KEY` is currently the
escrow *owner* (`CC-059`), a test that reaches `writeContract` with real config would sign as the
contract owner.

No harm occurred — the broadcast used the throwaway Hardhat key against a codeless address — but
the arrangement is one stubbed variable away from signing something real.

## Fix

1. Stub the transport. Either mock `viem`'s `http` transport in `signer.test.ts`, or point
   `BASE_SEPOLIA_RPC_URL` at a dead address in test config so any real call fails fast and loudly
   instead of succeeding quietly.
2. Assert the *intent*: that `simulateContract` was called with the expected arguments, rather than
   relying on it throwing.
3. Add an `env` block to `vitest.config.ts` mirroring CI's stubs so local and CI runs match, and
   explicitly clear `DEPLOYER_PRIVATE_KEY`/`GCP_KMS_KEY_PATH` unless a test sets them.
4. Fix the misleading comment at `signer.test.ts:94-95`.
5. Consider a guard: refuse to run the suite if `NEXT_PUBLIC_ESCROW_CONTRACT` points at an address
   that has code, so the test can never transact against a live contract.

## Acceptance

`npm test` passes 20 consecutive runs with the network unplugged, and produces no new transactions
from any test key.

Written up as `docs/Lessons-Learned.md` §12 — the transferable point being that the test's pass
condition ("a mock was reached", inside a `try/catch`) stayed true after the behaviour underneath it
changed shape entirely, so it went green for months while broadcasting transactions.

Related: `CC-048` (public RPC rate limits — this is the concrete evidence for it), `CC-032`,
`CC-059`.

## Update 2026-08-11 — backlog triage pass

Lowered P1 → **P2**.

**Clarification that drove the decision.** This issue is about the *automated* `npm test` suite —
not a live or manual test, not wallet connection, not the MCP lifecycle. That distinction mattered
because it was initially read as overlapping `CC-032`. It does not: the manual agent-side lifecycle
testing is `CC-032`/`CC-077`/`CC-078`/`CC-079`, and this is a unit test that was written as a
mock and turned out not to be one.

Why P2 rather than P1 or P0: the measured flakiness is mild (worst run 3 failures of 74), and what it
actually broadcasts is a throwaway Hardhat key against a codeless address, so nothing of value is at
risk today. The latent "one stubbed variable from signing something real" concern is also weaker
than when this was filed — `CC-059` moved contract ownership to the HSM key, which is **not** in
`.env.local`, so the real key reachable from a local test run is no longer the contract owner.

It stays genuinely important for one reason, and that should drive its sequencing rather than its
priority: **it must be fixed before `npm test` is used as evidence that anything works.** Until
then "the tests pass" is not a claim worth making during launch validation.

Note also the shared root cause recorded on `CC-070`: nothing sets `BASE_SEPOLIA_RPC_URL`, so
everything falls back to the free public endpoint. Setting it to a dedicated provider is part of the
fix here, alongside stubbing the transport.

**New measurement, 2026-08-11 — the flakiness is worse than recorded above.** Two consecutive runs on
an unchanged tree, during the triage pass, on a docs-only working tree:

| run | result |
| :-- | :-- |
| 1 | **10 failed** / 106 passed (5 of 20 test files failed) |
| 2 | 116 passed (20/20 files) |

The worst run measured on 2026-07-30 was 3 failures. This is more than triple that, and it took only
two runs to see it. The failing run included `wallet-verify.test.ts`, which is mock-based — so the
blast radius is not confined to the signer tests that broadcast.

Two things this changes. First, the suite grew from 74 to 116 tests over the same period, so there is
more surface competing for the same rate-limited endpoint — expect this to keep degrading as tests are
added. Second, it undermines the P2 justification somewhat: a suite that fails 10 tests on one run and
0 on the next cannot be used to distinguish a real regression from noise, which is exactly the
situation during launch validation. The priority stays P2 per Aaron's call, but the sequencing note
above ("fix before `npm test` is used as evidence") is now the operative part of this issue, not a
footnote.

## Closed 2026-08-13 — the suite is hermetic, and the mechanism was still live

Fixed, verified by measurement rather than by absence of failure. Two corrections to this issue's own
text fell out of doing it.

### Correction 1 — the mechanism was still active, not historical

The broadcast recorded above is from 2026-07-30 and the line numbers had since shifted, so the first
thing checked was whether the suite still did it. **It did.** A `console.error` in the new fetch guard
showed **4 blocked network requests to `sepolia.base.org` on every single run — while the suite
reported 128/128 passed.**

Four, because that is viem's default retry count: one attempt plus three retries. Every run, from
`signer.test.ts > uses KMS signer when GCP_KMS_KEY_PATH is set` — the test with the bare
`try {} catch {}`. Pre-guard, all four went to the public endpoint.

Worth recording how close this came to being missed: with the guard installed but *not* logging, the
suite went 128/128 three runs in a row, which looked like proof. It was not. Only counting the
attempts revealed that the code was still reaching for the network and the failure was being
swallowed downstream of the assertion.

### Correction 2 — `.env.local` does not leak into `process.env`

The "Second, related problem" section above is **wrong**, or no longer true. Measured 2026-08-13
under Vitest: `DEPLOYER_PRIVATE_KEY` absent, `NEXT_PUBLIC_ESCROW_CONTRACT` unset,
`ESCROW_DEPLOY_BLOCK` unset. Vitest does not populate `process.env` from `.env.local`.

So the "one stubbed variable away from signing something real" gap was narrower than filed. The
environment is stripped anyway, because the reason it was safe was accidental — nobody had added
dotenv loading, changed the runner, or exported the variable in their shell.

### What was done

**`vitest.setup.ts`** (new, wired via `setupFiles`):

- Deletes every signing key (`DEPLOYER_PRIVATE_KEY`, all `GCP_*`), both real RPC URLs, both live
  contract addresses, and `ESCROW_DEPLOY_BLOCK`. Deleted rather than blanked — `z.string().optional()`
  accepts `""` as present, so blanking would leave config validation seeing a set-but-empty value.
- Replaces global `fetch` with a thrower that names the URL and points at how to mock properly. Every
  client here goes through `fetch`, so this makes a real request impossible rather than unlikely.
- **Logs each blocked attempt to stderr as well as throwing**, so a test with a bare `try/catch`
  cannot swallow it and stay quietly green. This is what found Correction 1 and is the single most
  useful line in the file.
- `ALLOW_TEST_NETWORK=1` bypasses the guard for a deliberate integration run. Never set in CI.

**`signer.test.ts`** — mocks `createPublicClient`/`createWalletClient`, drops the `try/catch`, and now
asserts the intent this issue asked for (fix item 2):

- `simulateContract` is called once with the expected address, function name and args
- `writeContract` receives **exactly** the request `simulateContract` prepared — the simulate→write
  handoff is the step that turns a dry run into a real transaction
- a `simulateContract` rejection means **no write happens**; the property the original test assumed
  and never checked, and the live behaviour of `completeTask` today (`CC-080`, `ADR-0001` D2)
- the KMS test now calls `completeTaskOnChain` and asserts its return value rather than catching

The misleading comment (fix item 4) is replaced by a note explaining why the transport is mocked.

**Fix item 5 deliberately not implemented.** Refusing to run when `NEXT_PUBLIC_ESCROW_CONTRACT` points
at an address with code would itself require a network call — `eth_getCode` — which contradicts
hermeticity. It is also redundant: with `fetch` blocked, a test cannot transact against anything,
deployed or not. Recorded so it is not re-added as an oversight.

### Verification — measured, not assumed

| Check | Result |
| :-- | :-- |
| 20 consecutive runs | **131/131 each, 0 failures** (was 3, then 10, then 13 on unchanged trees) |
| Blocked network attempts across all 20 | **0** — the code no longer even tries |
| Hardhat #0 on-chain tx count, before and after | **unchanged at 23842** |
| `npm run typecheck` | clean |
| `npm run lint` | clean bar the one pre-existing warning |

Test count 128 → **131**; three new assertions, no deletions.

The nonce check is the strongest of these. Hardhat account #0 is a publicly known shared key, so
"unchanged across 20 runs" means **nobody** broadcast anything in that window — a stronger statement
than "we did not".

### What this unblocks

`npm test` can now be used as evidence during launch validation, which the 2026-08-11 triage note
identified as the operative reason this issue mattered. It also removes the shared-resource
contention that made concurrent sessions interfere with each other — two sessions running the suite
no longer cause each other's failures.

`Lessons-Learned.md` §12 updated: status closed, both corrections recorded, plus the transferable
point that **a passing suite is not evidence of hermeticity — count the attempts, do not infer from
the result.**
