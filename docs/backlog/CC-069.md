# CC-069 — Every wallet-signature check rejects Smart Wallet / Base Account signatures

## Problem

Found live, on a real phone, finishing `CC-055`'s own outstanding test: Aaron created a genuine
Base Account (Coinbase Smart Wallet) via passkey — real login-code email from Coinbase, real
signing prompt at `keys.coinbase.com/sign/...` for the registration message, tapped **Sign**. The
app came back with **"Signature verification failed."**

Root cause: `src/app/api/register/route.ts` verified the signature with viem's **standalone**
`verifyMessage({ address, message, signature })` (no client). That function's own docstring says
exactly what happened:

> Note: Only supports Externally Owned Accounts. Does not support Contract Accounts. It is highly
> recommended to use `publicClient.verifyMessage` instead to ensure wallet interoperability.

Base Account is an ERC-4337 smart contract account, not an EOA — the entire product pitch
("no seed phrases, no extensions, just a passkey") is built on the one wallet type this check
structurally cannot verify. Standalone `verifyMessage` does pure offline `ecrecover`; a smart
wallet's signature is ERC-6492/ERC-1271 and is really validated by calling `isValidSignature` on
(or counterfactually for) the wallet's own contract, which requires a public client, not offline
math.

**This is not limited to registration.** `grep -rn "verifyMessage\|recoverAddress" src` found the
identical class of bug in `src/lib/auth/wallet-challenge.ts` (`verifyChallengeSignature`), which
gates `/api/dispute` (`CC-004`) and is designed to gate any MCP tool call requiring
`callerWallet` authentication. Same root cause: raw `recoverAddress`/`hashMessage`, EOA-only.

**Net effect before this fix:** a Base Account / Smart Wallet user — every phone user, since
there's no extension fallback on mobile (`CC-055`) — could connect a wallet and receive a login
code, but could never complete registration, and could never authenticate a dispute or any
signature-gated MCP action. The passkey onboarding path was not just untested (`CC-055`'s original
framing); it was provably broken for its own target account type, the moment it was actually
tried.

## Fix

Added `src/lib/wallet/verify.ts` — `verifyWalletSignature({ address, message, signature })`,
backed by a `viem` public client (`chain.verifyMessage`-equivalent), which is documented as
"Compatible with Smart Contract Accounts & Externally Owned Accounts via ERC-6492." This makes a
real RPC call (an `eth_call` against a deployless signature-validator) rather than a pure offline
check — an unavoidable trade-off of supporting contract accounts correctly, and one the app
already depends on elsewhere (escrow reads).

Replaced both broken call sites:
- `src/app/api/register/route.ts` — was standalone `verifyMessage` from `viem`.
- `src/lib/auth/wallet-challenge.ts` — was `recoverAddress`/`hashMessage` from `viem`.

Both now verify EOA and Smart Wallet signatures identically, through one shared, testable helper.

## Acceptance

- A signature from a genuine Base Account / Smart Wallet passes registration and challenge-based
  auth; a signature from a genuine EOA continues to pass (this fix must not regress the path that
  already worked).
- Unit tests cover the new helper directly (mocked public client — no live RPC dependency in CI).
- Re-verified live: the same real phone, same real Base Account, completes registration
  end-to-end.

## Update 2026-08-08 — fixed, unit-tested; live re-verification pending Aaron's retry

Implemented as described. `src/lib/__tests__/wallet-verify.test.ts` (4 cases: delegates to the
public client, returns false on an invalid signature, caches the client across calls, resets on
demand). Updated `register-route.test.ts`'s mock from `viem`'s `verifyMessage` to
`@/lib/wallet/verify`'s `verifyWalletSignature` — no behavioural change to those tests, same
mocked boundary, different (correct) module. `dispute-route.test.ts` and `challenge.test.ts`
needed no changes — they mock at the `wallet-challenge.ts` function boundary, which kept its
exported signature.

`npm test` (115/115), `npm run typecheck`, `npm run lint`, `npm run build` all clean.

Not yet independently re-verified against a live signature from a real Base Account on a real
phone — that's the one thing a unit test can't stand in for, and it's exactly the failure this
issue exists because of. Asked Aaron to retry the same registration flow once this deploys to a
preview. Status stays `in-progress` — the code fix and its test coverage are complete and correct
as far as this session can verify, but the acceptance criterion this issue is actually about (a
real Smart Wallet signature succeeding) isn't confirmed yet. Will update this issue and `CC-055`
once it is.

## Update 2026-08-08 — confirmed live, on a real phone, with a brand new Smart Wallet

The road here was not a straight line, and it's worth recording honestly:

1. First retry after the fix (same real phone, same Base Account) still failed. Root cause of
   *that*: the register route's own error handling swallowed the real reason entirely (fixed
   separately, see the `register_signature_verification_error` / `register_invalid_signature`
   logging added same day) — debugging was blind until that was fixed too.
2. Second and third retries surfaced two unrelated failures: Brave's Shields blocking
   `window.opener` for the Coinbase popup ("This app doesn't support smart wallets" — a
   documented Brave/Coinbase-SDK friction point, not a bug in this app: confirmed no
   `Cross-Origin-Opener-Policy` header is set anywhere in this stack), and a Chrome attempt that
   failed before ever reaching the server at all (client-side, pre-request — not this issue).
3. A brand new Base Account, created fresh in Brave, finally completed the full flow. Caught
   live via `vercel logs --follow`:
   `{"event":"wallet_signature_verified","address":"0x37DD...EE00","chain":"Base Sepolia","result":true}`
   — a genuinely new address, neither the dev EOA nor the original test account. Independently
   confirmed the row landed via the public whitepages MCP tool (`get_contractor`), not just the
   UI's word for it: `wallet: 0x37ddfd6c67b7abe5a08a5dda9064988a71b4ee00, categories:
   [home-maintenance, garden-outdoors], rate_usdc: 20`.

**The original bug (EOA-only signature verification) is fixed and confirmed.** The Brave/Chrome
friction encountered along the way turned out to be separate, real, but not blocking — a Smart
Wallet does complete registration successfully given a browser that doesn't interfere with the
Coinbase popup.

Also surfaced along the way, filed separately as `CC-070`: `reputation_onchain_fallback` fired
during this same test — the on-chain reputation query hits the public RPC's 2000-block
`eth_getLogs` range limit and always fails once the contract is more than ~66 minutes old at
Base's block time. Degrades gracefully today, but it also affects `getTaskResolvedOutcome`
(`CC-065`'s partial-failure recovery path), which is a correctness bug, not just a display gap.

**Closed.**

## Update 2026-08-09 — second, independent success on Brave; resolves the earlier doubt about it

Aaron registered again via Base Account on mobile Brave, unprompted and outside any monitored
debugging session ("on the way home from work") — no live log tail, no coordinated retry, just
ordinary use. This matters specifically because the *previous* session's Brave attempt was the
one that hit "This app doesn't support smart wallets" (the `window.opener`/popup friction, not
this issue). A second, organic, independent success narrows that down: Brave is not structurally
incompatible with this flow — the earlier failure was something transient or account/state-
specific (a stale popup-blocker setting, a first-run permission prompt, etc.), not a standing
Brave-vs-Coinbase-SDK wall. Nothing to fix here; recorded because "is Brave reliably usable" was
left as an open question and now has a real answer.
