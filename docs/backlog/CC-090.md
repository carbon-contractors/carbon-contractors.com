# CC-090 — Separate the verdict signer from the contract owner

`CarbonEscrow` v2 was deployed on 2026-08-15 with the HSM key
`0xa8931097540e69B474013D294d0bA6A2cC853e4b` as **both** the contract owner and the sole
accepted verdict signer. One key therefore signs verdicts, arbitrates disputes, and manages
the signer set.

## Why this is P2 and not P0

**It grants no authority the platform does not already hold.** Vercel can already act as the
owner via Workload Identity Federation, and `resolveDispute` is `onlyOwner`. Anyone who could
forge a verdict through that path could instead call `resolveDispute` directly, which is
strictly more powerful — a forged verdict only moves a task to `Disputed`, whereas
`resolveDispute` settles it. Separating the keys buys nothing against that threat model.

So this is not a live weakness. It is a constraint on a *future* posture.

## When it starts to matter

The moment the owner moves somewhere colder than a Vercel-reachable key — a multisig, a
hardware wallet, an offline signer. At that point verdict signing must stay hot (it happens on
every settlement) while ownership does not, and one key cannot be both.

`ADR-0001` D9's v2 step points the same way: verdicts become permissionless against a bond, at
which point the accepted-signer set has several members and the owner being one of them is
incidental rather than structural.

## Scope

- A second KMS key (or key version) for verdict signing, with its own IAM grant and its own
  WIF binding.
- `VERDICT_SIGNER_ADDRESS` points at the new key; `setVerdictSigner(new, true)` then
  `setVerdictSigner(old, false)`.
- `docs/Security-Trust-Disclosure.md` updated — it currently describes one key.
- `scripts/audit/verify-escrow-deployment.mjs` checks the signer against the *expected signer*
  rather than against the HSM owner constant, which is what it does today.

## No redeploy required

This is the reason the accepted-signer set is an owner-managed mapping rather than a
constructor-baked immutable. The whole change is two `setVerdictSigner` calls plus key
provisioning — deliberately designed to be a set change, not a migration.

## A second, stronger argument — added 2026-08-15

`CC-091` (succession and DR) needs **the same change** for a different reason. `resolveDispute` is
`onlyOwner` with no timeout and no fallback, so if the owner key becomes unreachable — not
compromised, just unreachable — every task in `Disputed` or `Arbitrating` is stranded permanently.
A multisig owner turns that from a legal problem into an operational one.

The P2 above was reasoned purely on the compromise threat model, where separation genuinely buys
nothing while both roles sit on one Vercel-reachable key. **That reasoning does not cover
unavailability, and unavailability is the stronger case.** Priority is Aaron's call; flagging that
it was set without this argument in view.

Related: `CC-082`, `CC-059`, `CC-091`, `ADR-0001` D9, `CC-039` (mainnet — worth deciding before the
one-way migration, since mainnet is where a colder owner key actually earns its cost).

## Update 2026-08-26 — re-rated P1, and the target architecture is now decided

**P2 → P1.** `ADR-0006` D2 re-rates this, and was accepted 2026-08-26. The original P2 reasoning
still holds on its own terms — separation buys little against a *compromise* while both roles sit on
one key — but succession is a second and stronger argument for the same change, and it is the one
that sets the priority.

### Accepted target architecture

| Role | Custody |
| :-- | :-- |
| **Contract owner** | **2-of-4 Safe**, four hardware-isolated keys: each Tangem card initialised **on its own**, link step not run (`ADR-0006` A2). Custody: Aaron two (separate buildings), two family members one each. Slots 3 and 4 are transitional (`ADR-0006` D11). |
| **Verdict signer** | a single GCP Cloud KMS / HSM key, unchanged — it signs automatically and holds no custody |

Losing the verdict signer **fails safe**: no verdicts means every delivered task resolves to the
worker after the review window (`ADR-0001` D6). That asymmetry is why the two roles want different
custody models rather than the same one twice.

### The acceptance test is on-chain

**Four cards are only four keys if each is initialised on its own.** Cards linked to one key have the
security of a 1-of-1 and are indistinguishable from a real multisig on a block explorer.

Corrected 2026-08-31 (`ADR-0006` **A2**): this paragraph said Tangem "sells cards as a set that shares
one seed by default" and that buying separately closed the risk by construction. Neither holds — cards
arrive uninitialised, and linking one to another's key is an explicit setup step with its own screen.
**Hardware ordered 2026-08-31 as two multi-card packs, expected ~2026-09-17.**

So the requirement is a setup procedure, and a procedure performed once is a claim. This ticket does
not close on it having been performed. It closes on:

- [ ] **Four distinct addresses read off the four cards, before they are distributed** (`ADR-0006`
      A2.2). Free, needs no Safe and no transaction. After distribution the cards are in different
      buildings and in non-technical hands, which is the expensive moment to discover a repeat.
- [ ] Four Safe owners at **four addresses with no shared derivation**, read from the chain.
- [ ] The Safe is the `CarbonEscrow` owner — `verify-contract-owner.mjs` passes against it.
- [ ] The accepted verdict signer is **not** any Safe owner — `verify-signer.mjs` passes, and the two
      scripts together assert the separation.
- [ ] `chain-constants.json` `verdictSignerSeparation.separated` flips to `true`, with the owner
      block updated.
- [ ] A 2-of-4 signature has executed one owner-only call on testnet.
- [ ] **The succession path specifically: a 2-of-4 signature by the two family keys alone.** Not one
      that merely includes them. If Aaron is gone, family-only is the only path there is, and both
      holders are non-technical — an untested succession path is a designed one, not a working one.

### Ordering

Before `CC-034`, and **after** the mainnet deployment transaction — a redeploy resets ownership to the
deployer (`CC-082`). Scoped into `CC-034`'s milestone 2026-08-26.

**Custody of the three keys is an open `ADR-0006` item, not an engineering task.** Three cards in one
person's hands delivers loss resistance; it does not deliver succession, which is D2's stated purpose.
This ticket can complete the *architecture* while that remains unanswered — and if it does, the
succession claim must not be recorded as satisfied.

Related: `ADR-0006` D2 + open items, `CC-034`, `CC-059`, `CC-082`, `docs/BCP-DR.md`
