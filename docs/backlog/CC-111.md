# CC-111 — Duplicate migration number 018 in supabase/migrations — renumber to match applied history

Discovered during CC-090 wrap-up (2026-09-16): `supabase/migrations/` on master carried two
files numbered 018 — `018_funded_at.sql` (CC-092 PR 2, commit 040f59f) and
`018_offer_lifecycle.sql` (CC-094 #126). Lexical order matched landed order only by luck.

## The decisive fact

Whoever hand-applied these migrations used the renumbered names. The live project's
`supabase_migrations.schema_migrations` (read directly, 2026-09-16) records:

```
018 funded_at · 019 offer_lifecycle · 020 task_content_retention
021 task_idempotency_key · 022 hide_live_offer_payment_ids
023 worker_sessions · 024 stake_slash_records
```

The repo filenames were **drifted from production**, not the other way round. The fix is
therefore a reconciliation rename, not a history rewrite: after this ticket the repo
filenames match the applied record 1:1, and no DB action is required on any environment.
(This also answers the original task's "check whether staging/production already applied
both under the duplicate names" — they did not; there is only the one project, and it
tracked the cascade names.)

Why the cascade (offer_lifecycle → 019, shift followers +1) and not the first-blush
`018_offer_lifecycle → 024`: offer_lifecycle merged 2026-08-22 17:46, *before* five of the
six followers, and 019-task_content_retention has a hard order dependency (its trigger
replaces the function from 018_funded_at). Moving offer_lifecycle to 024 would invert
chronology and break lexical == landed == applied order.

## What was done

PR #223 (branch `fix/migration-duplicate-018-renumber`, commit fbb91e4, signed):

- Renamed the six files: `018_offer_lifecycle → 019`, `019_task_content_retention → 020`,
  `020_task_idempotency_key → 021`, `021_hide_live_offer_payment_ids → 022`,
  `022_worker_sessions → 023`, `023_stake_slash_records → 024`. Migration headers updated.
- Shifted all 38 cross-references across `docs/`, `src/`, `scripts/`, each under an asserted
  expected-replacement count (a miss aborts rather than lands silently).
- Disambiguated the two `from 018` refs inside the retention migration to name
  `018_funded_at` explicitly — with the duplicate resolved, a bare `018` still names a
  file, but the retention migration's dependency is specifically on funded_at.
- `CLAUDE.md`: stale `001-022` range corrected to `001-024`, plus the standing rule that
  `supabase_migrations.schema_migrations` must match these filenames 1:1.
- `ADR-0010`'s future migration is now `025_task_upload_credentials` (024 is taken).

A near-identical renumber had been attempted in local commit 1c13c42 (2026-09-16) but was
twice swept into sibling branches by a shared-tree checkout race and stripped back out of
PRs #209/#213 to keep their diffs atomic. This ticket is the clean re-land of that work.

## Verification

- All 24 migrations apply cleanly in lexical order on a fresh Postgres 17 container with
  `ON_ERROR_STOP=1` (platform stubs only: roles, `auth` schema, `auth.uid()`).
- `npm test` 875/875 (78 files) · `typecheck` · `lint` · `compile` · `check-encoding.mjs` green.
- Repo-wide sweep: zero stale migration-number references remain.
- Live `supabase_migrations.schema_migrations` read directly (before the rename): it
  already records the new names, so `supabase db push`/manual apply is a no-op on every
  environment once this lands.
