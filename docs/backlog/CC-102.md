# CC-102 — MCP authorization spec conformance (RFC 9728 discovery vs documented deviation)

## Problem

The MCP authorization specification (2025-11-25, the current dated version) makes authorization
OPTIONAL overall, but **when an HTTP-transport MCP server supports auth, it SHOULD conform**, and
conformance has hard MUSTs:

> "MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata (RFC 9728)." The metadata
> document "**MUST** include the `authorization_servers` field containing at least one
> authorization server." Servers advertise it either via a `WWW-Authenticate` header on 401
> responses (`resource_metadata=` parameter) or a well-known URI
> (`.well-known/oauth-protected-resource`, root or endpoint-path-suffixed).

Carbon Contractors **supports auth** on its HTTP MCP transport (mutating tools reject
unauthenticated callers), so the SHOULD applies to us — and we do not conform. Verified in the
current tree, 2026-09-07:

1. `src/app/api/basedhuman.mcp/route.ts` (152–172): auth is a custom SIWE-style wallet challenge —
   `x-caller-wallet` / `x-caller-signature` / `x-caller-nonce` headers verified via
   `src/lib/auth/wallet-challenge.ts` at session init. Not OAuth; no bearer tokens; no audience.
2. The 401 path (`route.ts` ~167) returns a bare JSON-RPC error (`-32001`) with **no
   `WWW-Authenticate` header**, so a spec-conformant client cannot even discover that metadata
   should exist.
3. No `.well-known` endpoints anywhere: `find` over the repo (excluding `node_modules`) returns
   nothing; `public/` contains only `base-mark.svg` and `og.png`; `vercel.json` has no relevant
   rewrites. A client probing the well-known URIs gets the coming-soon/404 surface.
4. Tool-level errors (`src/lib/mcp/server.ts` 224–229, `UNAUTHENTICATED`) describe the
   wallet-challenge handshake in prose — discoverable by an LLM, invisible to an OAuth client.

**Practical effect today:** read-only tools (`search_whitepages` etc.) work unauthenticated, so a
spec-conformant MCP client can still use the read path. The gap bites exactly where auth matters:
`request_human_work`, `confirm_task_completion`, `dispute_task`, `get_signed_verdict` are
unreachable for any client that only implements the spec's OAuth discovery and has no idea a
wallet-challenge handshake exists.

## Prior art that constrains this

- **ADR-0009 D6** (accepted 2026-09-02): "MCP and hiring agents keep per-request
  challenge-response… Nothing in the agent path changes." That ruling was made on
  **worker-anxiety grounds** (NOR-321), not MCP-interoperability grounds — OAuth discovery was
  never weighed. This ticket does not overturn D6; it asks whether D6's scheme needs a
  spec-conformant front door in addition.
- **CC-044 / CC-045**: the standalone `basedhuman-mcp` package and its pre-publish hardening.
  Publishing to an external audience (MCP registry, agent frameworks) is when conformance stops
  being theoretical — registries and enterprise clients increasingly check it.
- **CC-020 / NOR-179**: existing rate-limit/infra constraints apply to any new public endpoint
  (a metadata JSON route is cheap, but it must respect the middleware's limits).

## Options

**A — Full conformance.** Serve RFC 9728 Protected Resource Metadata naming a real authorization
server, accept OAuth 2.1 bearer tokens with audience validation, keep wallet-challenge as a
parallel path or migrate off it. Cost: an authorization server (hosted IdP or self-hosted) is a
new external dependency → PO approval + 7-day quarantine rule apply; audience/`resource`
(RFC 8707) validation is real work; ADR-0009's agent path is untouched only if wallet-challenge
stays.

**B — Metadata without a server of our own.** Point `authorization_servers` at a third-party IdP
(e.g. the endpoint's existing Supabase auth) and treat OAuth as an alternative identity rail.
Cheaper than A but still a new auth surface and a PO architecture call.

**C — Documented deviation (recommended now).** Record an ADR: the agent-facing transport
deliberately uses wallet-challenge, not OAuth discovery, because (i) our clients are agents whose
operators read docs, not vanilla MCP clients doing OAuth handshakes; (ii) x402 already handles the
trust-critical exchange at the HTTP layer; (iii) identity here is a wallet, and OAuth would add a
token layer *around* the thing we actually authenticate. Disclose the handshake properly
(`mcp-info` page + tool error text already do most of this). Record **trigger conditions** for
revisiting: mainstream MCP clients gating server connectivity on OAuth metadata, registry listing
requirements, or the A2A expansion ADR-0009 D4 reserved.

## Recommendation

Option C now — the missing artifact is a **decision record, not code** — with B as the likely
shape if a trigger fires (and CC-044 the natural vehicle, since the standalone package is where a
second auth rail belongs). Do not let this silently drift: an undocumented deviation from a MUST
we never weighed is exactly the kind of gap the ADR series exists to prevent.

## Acceptance

- [ ] PO ruling recorded: either ADR-0011 (or an ADR-0009 addendum) choosing A, B, or C, with the
      chosen option's rationale.
- [ ] If A or B: `/.well-known/oauth-protected-resource` (root + path-suffixed) serves valid
      RFC 9728 metadata with `authorization_servers`; 401s from `/api/basedhuman.mcp` include
      `WWW-Authenticate: Bearer resource_metadata="…"`; tests cover both discovery mechanisms;
      one mainstream MCP client is manually verified end-to-end.
- [ ] If C: the ADR states the deviation explicitly, and the `mcp-info` page documents the
      wallet-challenge handshake (challenge → sign → headers) for agent developers.
- [ ] Either way: no new dependencies land without PO approval and the 7-day quarantine rule;
      x402 flow and ADR-0009 D6 worker-session work are untouched.
