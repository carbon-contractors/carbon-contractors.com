# CC-088 — Notices, and category-level PII control

Specified by `ADR-0002` D7. Steps 5 and 8 of that ADR's handover, combined because D7 pairs them
explicitly.

## Why notices, and why both directions

Neither party can be assumed to have thought about this. **The agent is a language model; the worker
is in a car yard with a phone.**

- **To the agent, at `request_human_work`:** the spec and description must not request personal
  information beyond what the task requires; you receive and control the resulting evidence; you are
  the controller of it. Note the spec itself can carry personal information — *"go to 42 Smith St,
  ask for Dave"* — and the description field is currently stored unauthenticated
  (`CC-081` Defect 4).
- **To the worker, before acceptance:** what you capture may contain third parties' personal
  information, and you are the one creating it. Shown alongside the acceptance spec (`CC-084`), not
  buried in terms.

## Category-level control is the cleaner lever

Some service categories should be prohibited from PII-bearing tasks outright, encoded in
`/services` and `src/lib/categories.ts`.

This pairs with the checkability tiering in `ADR-0001`: the categories with no meaningful automated
check are largely the same ones with the highest PII risk. Photo tasks check well; address
verification checks moderately; "review this PR" barely checks at all. Those are also the categories
that will generate the adjudication load, and are candidates for value caps or exclusion from
auto-booking (`CC-074`).

## Also

`ADR-0002` says the agent becoming the evidence controller needs stating in the **terms**, not only
in the notice.

## Acceptance

Both notices are shown at the right moment, PII-prohibited categories are encoded and enforced, and
the terms reflect the agent's controller status.

Related: `ADR-0002` D7, `ADR-0001` (category checkability), `CC-084`, `CC-074`, `CC-081` Defect 4,
`CC-008`.

## Update 2026-08-21 — done

Shipped on `feat/cc-027-088-adr0002-notices-and-readme-pii` (commit references this id).

**Agent notice, in the tool itself.** `request_human_work`'s description in
`src/lib/mcp/server.ts` now carries a `NOTICE — you are the controller of the evidence` block:
don't request personal information beyond what the task requires; the evidence may contain
third-party PII; you commission it, you receive it, you are its data controller; the platform
stores hashes only. It reaches the agent at the exact moment it authors the spec — and reaches
the `tools/list` surface that is already public (`CC-014`'s 2026-08-15 finding).

**Category-level PII guidance and checkability tiering encoded.** `src/lib/categories.ts` gains
`checkability` (`strong`/`moderate`/`limited`), `checkabilityNote` and `piiNote` on every
`CategoryDetail`, plus the exported `EVIDENCE_PRIVACY_RULE` standing statement. Tiering follows
`ADR-0001`'s category-applicability reasoning: photo-verification is the one `strong` category
(EXIF GPS, counts, timestamps, pHash); home-maintenance, cleaning, pet-services and
personal-assistant are `limited`, with their notes stating plainly that a task with no
machine-checkable criteria resolves to the worker — the value-caps argument `ADR-0001` leaves
open. `/services` renders a page-level evidence-and-privacy notice and a per-card metadata block,
so a worker browsing categories meets the "what you capture may contain third parties' personal
information" warning before registration, not just at acceptance.

**Not hard prohibition — deliberately.** `ADR-0001`'s open items explicitly leave undecided
whether weakly-checkable categories get caps, auto-booking exclusion or a different resolution
path; encoding an outright PII prohibition now would pre-empt a settled-as-open question. The
guidance and tiers are the lever this issue asked `/services` to carry; enforcement belongs with
`CC-074` (auto-booking) when that decision lands.

**Terms updated.** `src/legal/terms.md` gains an *"If you are a hiring agent"* subsection stating
controller status in substance: obligations for security, retention and deletion attach to the
agent from delivery, the platform holds hashes and cannot erase or restrict what sits in the
agent's storage, and a criterion demanding third parties' identities is a privacy problem, not a
specification.

**Not done here, deliberately:** the worker-facing notice *before acceptance, alongside the
acceptance spec* is `CC-084`'s surface — this issue's `/services` guidance is the pre-registration
touch, not the pre-acceptance one.

Verified: `npm test` (244/244), `npm run typecheck`, `npm run lint`, `npm run build` all clean;
`/services` renders in the build output.

**Closed.**
