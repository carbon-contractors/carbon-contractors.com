`CC-079` Dispute.

## Scope

The path from "an agent has found a worker" to "the worker knows they have been hired and the money
is locked":

`request_human_work` → x402 payment challenge → agent funds the escrow → `escrow.createTask` →
task row created → notification fires to the worker.

## Happy path

1. `request_human_work` returns a well-formed x402 payment requirement.
2. The agent funds the escrow. **Note the architecture:** nothing server-side calls the contract's
   `createTask` — the agent does it from its own wallet via `USDC.approve()` +
   `escrow.createTask()` (`src/lib/payments/x402.ts:45`, `src/lib/contracts/escrow.ts:6`). So this
   stage must be driven by an agent-held wallet, not by the platform signer. Confirming that is
   also `CC-037` item 1.
3. `task.agent` on-chain is the funding agent's address, `task.worker` is the worker's on-chain
   address, and `task.amount` matches what was quoted.
4. The DB task row is created and its status reflects `funded` only once the on-chain task exists.
5. A notification actually reaches the worker through their configured channel.

## Unhappy paths

- Funding an already-existing `taskId` reverts (`TaskAlreadyExists`).
- Zero amount reverts (`ZeroAmount`); `address(0)` worker reverts (`InvalidWorker`); a deadline in
  the past reverts (`DeadlinePassed`).
- Insufficient USDC allowance or balance fails cleanly, with the DB left untouched.
- Task expiry and refund via `CarbonEscrow.expireTask` returns the funds to the funding agent.
- A worker with no notification channel configured — the task should still fund, and the failure to
  notify must be visible rather than silent (`CC-073` is why most workers have only email, and
  three of the four channel types are unreachable from the website today).

## Edge cases

- **USDC sent directly to the escrow address without calling `createTask`.** `CarbonEscrow` has no
  sweep or rescue function, so such funds are unrecoverable. Check whether anything is already
  stranded at the Sepolia escrow address — this is `CC-037` item 1's other half.
- On-chain success followed by a DB write failure — the task exists and is funded on-chain but not
  in Supabase. What recovers it?
- Concurrent funding of several tasks for the same worker.

## Acceptance

A real agent-held wallet funds a task end to end on Base Sepolia, the on-chain task state matches
what was quoted, the DB is a faithful projection of it, and the worker is notified. Every unhappy
path above has been attempted and produces a clean, diagnosable outcome rather than a silent
failure.

## Before running this

- `CC-070` (P0) — every `eth_getLogs` query in `escrow.ts` exceeds the public RPC's 2000-block
  limit, so anything read back through those helpers is unreliable until it lands.
- `CC-060` — `npm test` is not yet trustworthy as corroborating evidence.
- Set `BASE_SEPOLIA_RPC_URL` to a dedicated provider endpoint rather than relying on the free
  public fallback (see `CC-048`).

## Blocked 2026-08-11 — behind `CC-081` Defect 1

`CC-037`'s verification found that funding via `/api/fund-task` sends a **bare ERC-20 transfer** to the
escrow contract without calling `createTask` — the route is wrapped in
`withX402(handler, getPlatformWallet(), ...)` and `getPlatformWallet()` returns
`NEXT_PUBLIC_ESCROW_CONTRACT`. `CarbonEscrow` has no sweep or rescue function, so running this stage as
it stands would **strand real USDC permanently**, even on testnet.

Do not attempt this stage until `CC-081` Defect 1 is fixed. The fix changes the shape of this test
substantially: the agent will call `escrow.createTask` from its own wallet, so the happy path above
needs rewriting around an agent-held wallet rather than a POST to `/api/fund-task`.

The scope notes above already anticipated this, which is why step 2 says the stage must be driven by an
agent-held wallet — that instinct was correct and is now confirmed.

### The flow, as it actually is

There is **no x402 payment challenge**. That mechanism was removed by `CC-081` Defect 1 and must
never come back — an x402 settlement is a bare ERC-20 transfer, so paying the escrow address deposits
USDC without calling `createTask`, and the contract has no sweep or rescue.

```
request_human_work            → row born 'pending' (an offer) or 'accepted' (auto-booking)
worker accepts                → POST /api/offers/accept  → 'accepted'      [CC-094, ADR-0005 D2]
agent funds from its own wallet → USDC.approve + escrow.createTask
agent confirms                → POST /api/fund-task      → 'active'
notification fires to the worker                                            [CC-095]
```

### Happy path

1. `request_human_work` returns **every argument `createTask` takes** — `task_id_bytes32`, `worker`,
   `amount_wei`, `deadline_unix`, `review_window_seconds`, `spec_hash` — plus `escrow_contract` and
   `chain_id`. `acceptance_spec` and `review_window_hours` are now **required** tool arguments.
2. **The offer stage exists and money must not move before it clears.** With auto-booking off the row
   is `pending`; the worker accepts through the dashboard. `/api/fund-task` refuses anything that is
   not `accepted` — a `pending` row is still an open offer.
3. The agent funds from **its own wallet**: `USDC.approve` then `escrow.createTask`. The platform
   transacts nowhere. `task.agent` on-chain is the funding agent, because `createTask` records
   `msg.sender`.
4. The agent POSTs `/api/fund-task`. That route **reads `getTask(taskId)` from the chain** and only
   moves the row to `active` when the on-chain task is `Funded` or later **and** matches the row on
   worker and amount. A mismatch or a failed read refuses (`409`/`502`).
5. A notification actually reaches the worker through their configured channel.

### Unhappy paths

- Funding an already-used `taskId` reverts `TaskAlreadyExists`.
- `ZeroAmount`, `InvalidWorker`, `DeadlinePassed` all revert.
- `reviewWindow` outside 12h–14d reverts `InvalidReviewWindow`.
- Insufficient allowance or balance fails cleanly with the DB untouched.
- **`/api/fund-task` before funding** → `409` with `on_chain_state: "None"`, row stays put.
- **Worker or amount mismatch** → `409`, refuses to activate. Worth provoking deliberately: fund with
  a different amount than quoted and confirm the row does *not* go active.
- Offer expiry: an unanswered offer lapses and the agent can re-target.
- A worker at the `ADR-0005` D5 concurrency cap cannot accept another.
- `expireTask` refunds the agent — and is **agent-only** now (`ADR-0001` A1.2), so the platform
  signer calling it reverts `NotAgent`. That is correct behaviour, not a bug.

### Edge cases

- **USDC sent directly to the escrow without `createTask`** — still unrecoverable, still no rescue
  function. Confirm nothing is stranded: `verify-escrow-solvency.mjs` asserts
  `balanceOf(escrow) == totalLocked()`.
- On-chain success followed by a DB write failure. The chain is the authority; `/api/fund-task` is
  idempotent and re-POSTing should recover.
- **`payment_request_id` is no longer public for unfunded tasks** (migration 021). A harness that
  scrapes `GET /api/tasks` will see `null` for `pending`/`accepted` rows — take the id from the
  `request_human_work` response instead. This is deliberate: `taskId` is `keccak256` of it and
  `createTask` is permissionless, so publishing it pre-funding let anyone burn the id for a fraction
  of a cent.
- Concurrent funding of several tasks for the same worker.

### Acceptance

- [ ] A real agent-held wallet funds a task end to end on Base Sepolia.
- [ ] The row reaches `active` **only** via `/api/fund-task` reading `Funded` from the chain.
- [ ] On-chain `task.agent`, `task.worker` and `task.amount` match what was quoted.
- [ ] The worker is notified through a real channel.
- [ ] Every unhappy path above produces a clean, diagnosable outcome rather than a silent failure.
- [ ] `verify-escrow-solvency.mjs` still reconciles afterwards.
