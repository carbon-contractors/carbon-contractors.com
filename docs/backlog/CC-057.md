# CC-057 — No migration tooling — which is why exec_sql exists

## The root cause behind CC-054
There is **no Supabase CLI configured** on this project: no `supabase/config.toml`, no CLI
dependency in `package.json`, no migration runner in `scripts/`. `supabase/migrations/` holds
twelve `.sql` files that are applied entirely by hand.

That is almost certainly *why* `exec_sql` was created — a convenience shim to apply migrations
over HTTP because there was no proper channel. So CC-054 is the symptom; this is the cause.
Revoking the grant without fixing this invites the next out-of-band helper.

## Consequences beyond CC-054
- **No record of what is actually applied.** Nothing tracks which of 001-012 have run against the
  live database. The only reason we believe 001-011 are applied is that the app works.
- **No repeatable environment.** A second environment (staging, or a fresh project after a key
  compromise per CC-049) cannot be stood up without manually replaying twelve files in order.
- **Schema drift is invisible.** `exec_sql` itself is the proof: an object exists in production
  that appears in no migration and was found only via a stray entry in a local settings file.
- **No rollback story.** Relevant before mainnet.

## Do
1. Install the Supabase CLI and `supabase link` the project.
2. `supabase db pull` to capture current live state, and **diff it against 001-012**. That diff is
   the interesting artefact — it will reveal every other out-of-band change, not just `exec_sql`.
   Expect surprises; write them up.
3. Commit `supabase/config.toml` and adopt `supabase db push` as the only way schema changes reach
   production.
4. Once that is in place, drop `exec_sql` rather than merely restricting it (the commented block in
   `012_restrict_exec_sql.sql`) — the reason it existed is gone.
5. Consider adding a CI check that migrations apply cleanly to a scratch database.

## Acceptance
Schema changes reach production only through version-controlled migrations, and the drift diff from
step 2 is resolved and documented.

## Lessons-learned angle
Worth an entry once done. The transferable point is not "use migration tooling" — it is that
**convenience shims created to work around missing tooling become the largest hole in the system,
and they are invisible precisely because they were never part of the design.** `exec_sql` grants
arbitrary SQL and exists in no file anyone would think to review.

Related: CC-054, CC-049, CC-017.

## Update 2026-07-30 — promoted to P1, drift now confirmed rather than suspected

Live `pg_policies` output confirms a **second** out-of-band object: a `keepalive` table with an
anon `SELECT` policy, present in the database and in no migration. Together with `exec_sql`
that is two confirmed objects existing in production outside version control.

This is no longer a tidiness issue. The schema in `supabase/migrations/` is **known incomplete**,
which means:

- it cannot be used to stand up a second environment
- it cannot be used to rebuild after a key compromise (CC-049)
- and nobody knows what else is in there

Both known objects were found by accident — `exec_sql` from a stray line in a gitignored
settings file, `keepalive` from an unrelated RLS query. That is not a detection method.

The `supabase db pull` diff in step 2 is now the highest-value action in this issue: it is
guaranteed to return findings, and it is the only way to enumerate the drift rather than
stumble across it.

## Update 2026-07-30 (2) — the drift count is back to one, and the enumeration is still blocked

`keepalive` is gone: migration 013 is confirmed applied against the live database (`CC-006`), so one
of the two known out-of-band objects has been removed. `exec_sql` remains unaccounted for — anon
provably cannot reach it (`CC-054`), but whether it still *exists* is unmeasured.

**Why the enumeration did not happen this session, and what it teaches.** The plan was to list every
public-schema function and its grants via the service role. That failed for a reason that belongs in
this issue: `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` is the placeholder string `placeholder…`, and
the OpenAPI spec endpoint that would return the full object inventory in one request is service-role
only. So the drift surface still cannot be enumerated from a developer machine — with the anon key
you can only probe *names you already guessed*, which is precisely the accidental-discovery method
this issue objects to.

Eleven candidate names were guessed and probed (`exec_sql`, `execute_sql`, `run_sql`, `exec`,
`execute`, `sql`, `query`, `eval_sql`, `raw_sql`, `admin_sql`, `apply_migration`) and all returned
404. That is not enumeration. It is a slightly wider stumble.

**Added:** `scripts/audit/inspect-live-schema.sql` — a single-statement, single-result-set catalog
query covering functions and their per-role `EXECUTE` grants, table/view RLS state, anon
`SELECT`/`INSERT`/`UPDATE`/`DELETE` privileges, every policy, the `tasks_public` column list, and
view `reloptions` (so a stray `security_invoker=true` is caught — see the `CLAUDE.md` landmine). Its
section `2_anon_exec_fn` is the drift baseline this issue needs. That is a stopgap for the SQL editor,
not a substitute for `supabase db pull`.

**One ordering consequence.** Step 4 above says to drop `exec_sql` once the CLI is in place. Aaron
has decided to drop it now. Since PostgREST is the *only* SQL channel on this project and `exec_sql`
is the only route from it to `pg_catalog`, dropping the function removes the last way to inspect the
schema without the dashboard. That is an argument for doing step 1 (install the CLI) close behind the
drop, not months later — otherwise every future schema question needs a human in a browser.

## Update 2026-07-30 (3) — drift count is now zero. The enumeration finally happened.

`scripts/audit/inspect-live-schema.sql`, run in the dashboard, answered what the anon key never
could. `pg_proc` shows **`exec_sql` does not exist** — zero rows, queried at a privilege level anon
cannot reach, so this is the authoritative negative the anon-key probes could only gesture at
(`CC-054`). Combined with `keepalive` confirmed gone (`CC-006`), **both known out-of-band objects are
now gone.**

The generalised query — every public function `anon`/`authenticated` can execute — returned exactly
**one** result: `prevent_task_mutation`, which is `supabase/migrations/009_task_immutability_trigger.sql`
(`AUD-002`), fully tracked. So the enumeration this issue has wanted since it was filed is done, and
it found nothing new. Drift count: **zero.**

This does not close the issue. The root cause — no CLI, no `supabase db pull`, migrations applied by
hand with no record of what's actually landed — is unchanged, and this session only confirmed there
happens to be no *current* drift, not that drift can't recur. The next out-of-band object will be
found by the same accident method unless steps 1–3 above actually happen. But the immediate pressure
is gone: nothing needs cleaning up before the CLI work, and there is no urgency forcing step 4 (drop
`exec_sql`) since there is nothing left to drop.

## Update 2026-08-11 — backlog triage pass

Lowered P1 → **P2**. The 2026-07-30 promotion to P1 was driven by confirmed schema drift.
That justification is gone: the third update on this issue records drift at **zero** — `pg_proc`
shows `exec_sql` does not exist, `keepalive` is confirmed dropped, and the generalised query for
every public function `anon`/`authenticated` can execute returned exactly one fully-tracked
result.

The root cause is untouched and the issue stays open for it: no Supabase CLI, no record of which
migrations have actually landed, no repeatable environment, no rollback story. But nothing needs
cleaning up right now, and there is no longer anything forcing urgency.

One thing to preserve when this is picked up: the ordering argument in the second update still
applies in reverse. `exec_sql` is already gone, so PostgREST has no route to `pg_catalog` at all
— every future schema question now needs either the dashboard or the CLI. That is an argument for
doing step 1 sooner rather than later, not for reopening step 4.
